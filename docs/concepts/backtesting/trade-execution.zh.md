# 基于逐笔成交的执行

当交易场所设置 `trade_execution=True` 时，成交 tick 默认会触发撮合。一笔成交可以
证明其价格处发生了流动性交易，因此能够使被动方的挂单成交。

设置 `trade_execution=False`，可以把成交用作策略数据，而不让它触发撮合：

```python
from vibe_trader.config import BacktestVenueConfig
from vibe_trader.model import AccountType
from vibe_trader.model import BookType
from vibe_trader.model import OmsType

venue = BacktestVenueConfig(
    name="SIM",
    oms_type=OmsType.NETTING,
    account_type=AccountType.CASH,
    book_type=BookType.L1_MBP,
    starting_balances=["100_000 USD"],
    trade_execution=False,
)
```

禁用成交执行后，成交 tick 不会运行订单撮合，也不会运行撮合引擎的维护工作，例如
GTD 到期、追踪止损激活和金融工具到期检查。后续报价或可执行 K 线可以触发这些维护。

## 成交驱动的撮合

引擎会暂时把撮合参考价移动到成交价格：

- `SELLER` 成交可以撮合买方挂着的 BUY 订单。
- `BUYER` 成交可以撮合卖方挂着的 SELL 订单。
- `NO_AGGRESSOR` 成交可能影响双方，因为无法确定被动方是哪一侧。

历史订单簿保持不变。只有撮合核心的瞬时买价、卖价和最新价会在本轮迭代中移动。

### 成交判定

成交触发限价单成交时：

1. 如果订单簿中存在交叉流动性，引擎会与这些订单簿档位成交。
1. 如果订单簿没有体现成交价格，引擎可以按订单的限价创建成交驱动的成交。
1. 成交驱动的成交量上限为 `min(order.leaves_qty, trade.size)`。

当 `liquidity_consumption=False` 时，同一笔成交的数量可以在一次迭代中支持多个订单。
当 `liquidity_consumption=True` 时，成交驱动的各笔成交共享一个消耗计数器，因此总量
不能超过尚未消耗的成交数量。

例如，一笔价格为 100.00 的 `SELLER` 成交可以使限价为 100.05 的 BUY LIMIT 成交。
如果订单簿中没有代表该成交的档位，引擎会使用 100.05，而不会给予更优的成交价格。

### 撮合状态恢复

本轮迭代结束后，引擎会从可用的市场基准恢复撮合参考值：

- 使用 L2 或 L3 数据时，深度订单簿仍是买卖价状态的独立来源。
- 使用 L1 报价基准时，从最新报价恢复非主动方一侧。
- 只有成交数据的 L1 场景没有可供恢复的报价基准，因此最新成交会继续定义可用的
  最优档位状态。

解释没有报价的成交数据流时，这一区别非常重要。连续成交可以移动模拟的 L1 状态，
但有报价基准的 L1 撮合不会逐步丢弃最新报价的非主动方一侧。

## 主动方方向

主动方是跨越价差完成交易的参与者：

- `SELLER`：卖方击穿买价。该成交可以使挂着的 BUY 订单成交。
- `BUYER`：买方吃掉卖价。该成交可以使挂着的 SELL 订单成交。
- `NO_AGGRESSOR`：数据未标识主动方。需要方向时，引擎会同时考虑双方。

BUYER 成交为被动 SELL 订单提供成交依据，而不是 BUY 订单。SELLER 成交为被动 BUY
订单提供成交依据，而不是 SELL 订单。

## 结合订单簿与成交数据

订单簿更新确定价差和可见深度，成交 tick 则在这些更新之间提供执行依据。当深度快照
受到限流，而某笔成交发生在最新快照中不存在的价格时，这种组合很有用。

使用这两种数据流时需要谨慎：

- 一笔成交必须具有与挂单相反的主动方方向，才能使该挂单成交。
- 订单簿更新可以独立于成交而穿过订单价格。
- 在订单簿缺少成交价格档位时，成交量受成交驱动数量上限约束。
- 启用消耗后，在触发订单消耗剩余深度之前，引擎会计入已经从 L2 或 L3 订单簿中
  移除的成交量。

## 队列位置跟踪

同时设置 `queue_position=True` 和 `trade_execution=True`，可以跟踪每个 LIMIT 订单
前方的可见数量：

```python
venue = BacktestVenueConfig(
    name="SIM",
    oms_type=OmsType.NETTING,
    account_type=AccountType.MARGIN,
    book_type=BookType.L2_MBP,
    starting_balances=["100_000 USD"],
    trade_execution=True,
    queue_position=True,
)
```

### 队列生命周期

1. LIMIT 订单被接受时，会记录其价格处同侧的可见数量。
1. 该价格上方向正确的成交会减少前方数量。
1. 前方数量降至零时，订单才具备成交资格。
1. 只有清空队列后剩余的成交量，才能在该 tick 上使订单成交。

例如：

1. 100.00 买价处有 100 单位。
1. 一笔 50 单位的 BUY LIMIT 加入队列，前方有 100 单位。
1. 一笔 80 单位的 `SELLER` 成交把前方队列减至 20。
1. 一笔 30 单位的 `SELLER` 成交清空队列，并留下 10 单位可用于成交。
1. 下一笔方向正确的成交可以完成剩余订单量的成交。

### 订单簿变更

对于 L2 订单簿和聚合的 L3 更新：

- DELETE 会清除该价格档位及其队列。
- UPDATE 会把前方数量限制为该档位新的可见数量。

对于 L3 MBO 订单簿：

- 针对单笔订单的 DELETE，会按该订单剩余的已跟踪数量推进队列。
- 数量减少时，按减少量推进队列。
- 数量增加时，增加后的更大订单仍排在前方。
- 价格变更会把订单簿中的该订单从跟踪队列移除。

修改模拟订单的价格，会在新档位重置其队列位置。仅修改数量则保留已经取得的队列进度。

### L1 队列跟踪

使用 `BookType.L1_MBP` 时，成交 tick 会减少前方数量，报价则提供价格移动和可见数量
方面的依据：

- 价格向远离盘口的方向越过订单价格时，清空队列。
- 价格向订单方向移动时，保留队列。
- 回到先前可见的档位时，把前方数量限制为新的可见数量。
- 位于 BBO 之后的订单保持挂单状态，直到报价到达其价格或成交越过该价格。

### 限制

- 队列跟踪只适用于 `LIMIT` 订单。
- 每个模拟订单都有独立的队列估算。
- 初始估算只包含订单被接受时可见的订单簿状态。
- `NO_AGGRESSOR` 成交会同时减少双方队列。这可能比现实更早地清空队列并使订单成交，
  因而从策略执行角度看偏乐观。
- 历史数据无法揭示隐藏订单，也无法呈现每个交易场所特有的全部优先级规则。
