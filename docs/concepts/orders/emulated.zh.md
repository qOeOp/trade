# 模拟订单

## 简介

即使交易场所不原生支持某种订单类型，模拟功能也允许使用该类型。

Vibe 在本地模拟这些订单类型（例如 `STOP_LIMIT` 或 `TRAILING_STOP` 订单）的行为，
但在交易场所实际执行时只使用 `MARKET` 和 `LIMIT` 订单。

创建模拟订单时，Vibe 会持续跟踪特定类型的市场价格（由 `emulation_trigger` 参数指定），
并根据订单类型和设定条件，在满足触发条件时自动提交适当的基本订单（`MARKET` / `LIMIT`）。

例如，创建模拟 `STOP_LIMIT` 订单后，Vibe 会监控市场价格，直到达到 `stop` 价格，
然后自动向交易场所提交 `LIMIT` 订单。

为了执行模拟，Vibe 需要知道应监控哪一种**市场价格类型**。默认使用买卖报价，
因此示例中经常会看到 `emulation_trigger=TriggerType.DEFAULT`
（这等同于使用 `TriggerType.BID_ASK`）。不过，Vibe 还支持多种其他价格类型，
可用于指导模拟过程。

## 提交订单进行模拟

模拟订单的唯一要求，是将 `TriggerType` 传给 `Order` 构造函数或 `OrderFactory`
创建方法的 `emulation_trigger` 参数。目前支持以下模拟触发类型：

- `NO_TRIGGER`：完全禁用本地模拟，将订单完整提交至交易场所。
- `DEFAULT`：与 `BID_ASK` 相同。
- `BID_ASK`：使用报价触发模拟。
- `LAST_PRICE`：使用成交触发模拟。

触发类型的选择决定订单模拟的行为：

- 对于 `STOP` 订单，将触发价格与指定触发类型比较。
- 对于 `TRAILING_STOP` 订单，根据指定触发类型更新追踪偏移。
- 对于被模拟的 `LIMIT` 订单，将限价与指定触发类型比较，以确定何时将订单以 `MARKET` 订单形式释放。

以下是可以设置到 `emulation_trigger` 参数中的所有可用值及其用途：

| 触发类型          | 说明                                                     | 常见使用场景                                                     |
| :---------------- | :------------------------------------------------------- | :--------------------------------------------------------------- |
| `NO_TRIGGER`      | 完全禁用模拟。订单不经任何本地处理，直接发送至交易场所。 | 希望使用交易场所原生订单处理，或使用无需模拟的简单订单类型时。   |
| `DEFAULT`         | 与 `BID_ASK` 相同。这是大多数模拟订单的标准选择。        | 希望使用"默认"市场价格类型时的通用模拟。                         |
| `BID_ASK`         | 使用最优买卖价格（报价）指导模拟。                       | 止损订单、追踪止损订单，以及应对当前市场点差作出反应的其他订单。 |
| `LAST_PRICE`      | 使用最近一笔成交的价格指导模拟。                         | 应根据实际执行成交而非报价触发的订单。                           |
| `DOUBLE_LAST`     | 使用连续两个最新成交价格确认触发条件。                   | 希望触发前对价格变化进行额外确认时。                             |
| `DOUBLE_BID_ASK`  | 使用连续两次买卖报价更新确认触发条件。                   | 希望触发前对报价变化进行额外确认时。                             |
| `LAST_OR_BID_ASK` | 使用最新成交价格或买卖报价中的任一种触发。               | 希望对任何类型的价格变化响应更快时。                             |
| `MID_POINT`       | 使用最优买卖价格之间的中点。                             | 应根据理论公允价格触发的订单。                                   |
| `MARK_PRICE`      | 使用标记价格（衍生品市场常见）触发。                     | 尤其适用于期货和永续合约。                                       |
| `INDEX_PRICE`     | 使用标的指数价格触发。                                   | 交易跟踪指数的衍生品时。                                         |

## 技术细节

无论交易场所是否支持某种订单类型，平台都可以在本地模拟大多数订单类型。
订单模拟在所有[环境上下文](../architecture.md#environment-contexts)中使用完全相同的逻辑和代码路径，
并使用共同的 `OrderEmulator` 组件。

:::note
每个运行实例可持有的模拟订单数量没有限制。
:::

## 生命周期

模拟订单会经历以下阶段：

1. 由 `Strategy` 通过 `submit_order` 方法提交。
2. 发送到 `RiskEngine` 执行交易前风险检查（此时可能被否决）。
3. 发送到 `OrderEmulator`，由其*持有*/模拟。
4. 触发后，模拟订单转换为 `MARKET` 或 `LIMIT` 订单并释放（提交到交易场所）。
5. 释放的订单在提交到交易场所前接受最终风险检查。

:::note
模拟订单与*常规*订单受相同的风险控制，可以由交易策略按正常方式修改和取消。
取消所有订单时也会包括模拟订单。
:::

:::info
模拟订单在整个生命周期中会保留原始客户端订单 ID，因此可以轻松通过缓存查询。
:::

### 持有中的模拟订单

当模拟订单由 `OrderEmulator` 组件*持有*时，会发生以下操作：

- 缓存原始 `SubmitOrder` 命令。
- 在本地 `MatchingCore` 组件内处理模拟订单。
- `OrderEmulator` 订阅更新撮合核心所需的市场数据（如果尚未订阅）。
- 在订单*释放*或取消之前，交易者可以修改模拟订单，市场也可以更新它。

### 已释放的模拟订单

当到达的数据在本地触发/撮合模拟订单后，会执行以下*释放*操作：

- 通过额外的 `OrderInitialized` 事件，将订单转换为 `MARKET` 或 `LIMIT` 订单（见下表）。
- 订单的 `emulation_trigger` 将被设为 `NONE`（任何组件都不再将其视为模拟订单）。
- 由于期间可能发生修改/更新，会将附在原始 `SubmitOrder` 命令上的订单重新发送到 `RiskEngine` 进行额外检查。
- 如果未被否决，命令会继续流向 `ExecutionEngine`，并照常通过 `ExecutionClient` 到达交易场所。

## 可模拟的订单类型

下表列出可以模拟的订单类型，以及它们在释放并提交到交易场所时转换成的订单类型。

| 用于模拟的订单类型     | 能否模拟 | 释放后的类型 |
| :--------------------- | :------- | :----------- |
| `MARKET`               |          | 不适用       |
| `MARKET_TO_LIMIT`      |          | 不适用       |
| `LIMIT`                | ✓        | `MARKET`     |
| `STOP_MARKET`          | ✓        | `MARKET`     |
| `STOP_LIMIT`           | ✓        | `LIMIT`      |
| `MARKET_IF_TOUCHED`    | ✓        | `MARKET`     |
| `LIMIT_IF_TOUCHED`     | ✓        | `LIMIT`      |
| `TRAILING_STOP_MARKET` | ✓        | `MARKET`     |
| `TRAILING_STOP_LIMIT`  | ✓        | `LIMIT`      |

## 查询

编写交易策略时，可能需要了解系统中模拟订单的状态。可以通过多种方式查询模拟状态：

### 通过 Cache

可以使用以下 `Cache` 方法：

- `self.cache.orders_emulated(...)`：返回当前所有模拟订单。
- `self.cache.is_order_emulated(...)`：检查特定订单是否被模拟。
- `self.cache.orders_emulated_count(...)`：返回模拟订单数量。

更多详情请参阅完整的 [API 参考](/docs/python-api-latest/cache.html)。

### 直接查询订单

可以直接通过以下属性查询订单对象：

- `order.is_emulated`

如果这些查询返回 `False`，则订单已从 `OrderEmulator` *释放*，
因此不再被视为模拟订单（或从未被模拟）。

:::warning
不要持有模拟订单的本地引用。模拟订单*释放*时，订单对象会发生转换。请改用 `Cache`。
:::

## 持久化与恢复

如果运行中的系统在存在活动模拟订单时崩溃或关闭，这些订单会从已配置的缓存数据库重新加载到
`OrderEmulator` 中。这样可以在系统重启和恢复后保留订单状态。

## 最佳实践

使用模拟订单时，请考虑以下最佳实践：

1. 始终使用 `Cache` 查询或跟踪模拟订单，不要存储本地引用
2. 注意模拟订单在释放时会转换为不同类型
3. 记住模拟订单在提交和释放时都会接受风险检查

:::note
订单模拟允许在并不原生支持高级订单类型的交易场所使用这些类型，
使交易策略可以更轻松地跨不同交易场所移植。
:::
