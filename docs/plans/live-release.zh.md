## 要补的问题

### 1. 账户槽卡死（20261107-122）

`preflight` 不判断准入，不合格的账户也退出 0（`engine/live.py:765`）。`start` 先占账户槽（`live/runs.py:372`），准入失败后：

- `reconcile` 报 `LIVE_RUN_MISSING`，因为没有 `armed.json`；
- 重跑报 `LIVE_RESTART_REQUIRES_RECONCILIATION`；
- 新运行报 `LIVE_ACCOUNT_OWNED`，并且没有释放命令。

修法：

- `preflight` 执行同一套准入和源码检查（`require_admission`、`source_for_run`），并报告结果。
- 只有同时满足这三条才释放账户槽：所有 `run` 启动的容器都已确认 `State.Status == "exited"`，或者从未发出过 `run`；没有 `armed.json`；没有 `connecting` 事件。
- 其他情况继续占槽，包括容器不见了或启动结果不明。`docker run` 超时后容器可能还活着，所以不能只看最新一次启动。
- 占槽后网络创建失败、一次都没启动的情况，也要能释放。
- `armed.json` 写入后补一次父目录 fsync，否则主机崩溃后文件可能丢失而订单已存在。
- 文档写明同一个 run-id 不能再启动，要换新的。释放后的运行再 `reconcile` 不能重新占槽。

这放宽了“未决就占槽”的规则，需要用户授权。

### 2. 成交后没有确认保护单（20261107-123）

`engine/live.py` 没有成交后检查保护单的逻辑（只搜到注释），也不读 `USES_STOP_LOSS`。保护完全靠策略源码自己下。

修法：

- 持仓期间每次观察都检查，不是只查一次：保护单之后被撤或到期也要发现。缺口从出现时起算，成交不重新计时，和研究审计一致。
- 归属、只减仓和类型以**原生缓存**为准。Hedge 模式下发给 Binance 的订单不带 `reduceOnly`，订单 ID 也被重新编码（`binance-live-hedge-phase-a.zh.md:52-54`），所以不能用交易所的行直接判断，否则每笔真实交易都会被误判并平仓。
- 只有挂着的止损单（`ACCEPTED`）算保护。已触发的不算：止损市价单会在时限内成交；市场越过后的止损限价单已不提供保护。这一点比研究审计严，审计没有发现这种情况。
- 时限 90 秒：研究审计容忍的 1 分钟，加原生开放订单检查的 5 秒阈值和 10 秒间隔，留出余量。写进问题 7 的指引。
- 没有保护就走现有 STOP 流程平仓，本轮记为失败。
- `USES_STOP_LOSS = False` 的策略在 `preflight` 就拒绝。

实现时去掉了原计划的交易所确认查询，只查原生缓存。阶段 A 的算法单样本是空的，无法离线核对字段；解析错了会把每笔真实交易平掉，而订单状态本来由 Nautilus 负责，并由它每 10 秒对一次开放订单。局限：原生认为还在、但交易所已丢失的止损单，要等原生对账才会发现。这一点放到第 10 步真实账户验收里看。这是新增检查，用户已授权（决定 4）。

### 3. 没有亏损限制（20261107-123）

固定版 `LiveRiskEngineConfig` 没有亏损字段，所以触发逻辑只能在产品里做。

现有账户查询不能直接用：它只在连接、入场和结束时跑，一次发十几个请求，只有一个观察槽，占用它可能让入场失败；代码也不读未实现盈亏。如果查询失败走 `tick` 的异常路径，结果是节点停止但不平仓，等于限额失效。

做法：

- 不查账户。Observer 在 `run` 模式订阅原生标记价（和 Paper 同一个调用、同一个公开行情连接），每秒用原生成交算本轮结果：所有仓位的 `total_pnl(标记价)`，加上仓位重开前已结束周期的快照 `realized_pnl`。
- 不做线程和 HTTP，也就没有解析错误把每笔真实交易平掉的风险。回调抛错只会让标记价变旧，走下一条。
- 结果达到 `-max_loss_usdt` 走 STOP 平仓，原因 `max_loss`。已空仓时也算：止损跳空后已实现亏损超限，还在挂的入场单要撤掉。这一轮不算失败：空仓就干净结束并释放账户槽。`status` 的 `stop_reason` 显示这一轮最初的停止原因，后面的 `reconcile` 不会覆盖它。
- 有仓位但 60 秒没有标记价（从仓位出现或上一个标记价起算），或检查本身跑不了，按触发处理：本轮记为失败，走 STOP 平仓。超过 60 秒的标记价不用来计价。
- `preflight` 必须声明 `--max-loss-usdt`，不超过预算。

**和原计划的不同。** 原计划是定时查 `positionRisk`，并把它和原生结果对比后再选。这个对比没有做，因为要动用凭据；独立评审还发现两个数据源的时间差可能误平健康仓位（读到的未实现是成交前的，已实现已是成交后的），而原生算法的数量和均价来自同一个对象，没有这个问题。代价：没有 REST 心跳，也没有交易所数量交叉核对，只靠原生每 10 秒和 30 秒的检查。标记价按到达时间判断新旧，如果行情一直重复推送旧数据不会被发现；用事件时间判断的话，一旦适配器的时间字段不如预期，每笔真实交易都会被平掉，所以没有加。

离线证明不了、第 10 步真实验收必须确认的三点：`Strategy` 的 `on_mark_price` 在 `LiveNode` 里能收到（回测里已证明；Paper 用的是 `DataActor`，只算部分证据），收不到的话每个仓位都会在 60 秒后被当成失败平掉；`position_snapshots` 在 Redis 缓存下的行为（只在回测的内存缓存里跑过）；结果和 `positionRisk` 对一次。

**字段评审（独立评审，11-07，结论：接受）。** 字段是私有 `manifest.json` 的 `config.max_loss_usdt`，不进账本、DoltHub 或 Git。使用者是 runner 的亏损检查。它记录的独立事实是操作者为这一轮接受的亏损。现有字段表达不了：`budget_usdt` 是准入和仓位上限，既不是亏损界限，也不能随意调低，因为要容得下交易所最小下单额；用止损距离推算等于让策略自己给自己打分；固定预算比例和决定 5 的必填参数相矛盾。放在 manifest 是因为它是 runner 唯一不可变的绑定。检查在 runner 的 `read_manifest`；主机也查一次，只为不让错误的值浪费一个 run-id。

**对旧设计的例外。** `binance-live-hedge-design.zh.md:122` 说不重写风险计算：固定版 `LiveRiskEngineConfig` 没有亏损字段，所以这里算一个结果并触发 STOP，订单和平仓仍归 Nautilus。`binance-live.zh.md:42` 说不把派生 PnL 写成权威：结果只在触发时写进私有事件，不作为账务依据。

文档写明：限额按每轮计算，不累计；不含资金费和用其他资产付的手续费；运行期间不要划转或手动交易；跳空、断线或平仓被拒时可能超过。触发只尝试一次平仓，平仓失败的处理放在问题 6。限额要大于止损亏损加滑点，否则市价平仓会和交易所的止损单撞车。这是新增检查，用户已授权（决定 5）。

### 4. API key 和时钟（20261107-124）

原来代码不检查 key 权限。出口只放行 `fapi.binance.com` 和 `fstream.binance.com`（`engine/egress.py:16`），Paper 也用这份名单。出口只按主机过滤，如果放行 `api.binance.com`，持有 key 的容器就能访问钱包接口。

做法：

- **不改出口名单。** `live preflight` 和 `live start` 在占账户槽之前，由主机进程查一次 `GET /sapi/v1/account/apiRestrictions`。主机进程本来就读凭据文件。开了提现权限报 `LIVE_KEY_WITHDRAWAL`，查询失败或返回不是明确的 true/false 报 `LIVE_KEY_UNVERIFIED`，没设 IP 白名单在结果的 `warnings` 里提示。`reconcile` 不查，它要能处理已有的仓位。
- **时钟在 runner 里查，不在主机。** 原计划放主机进程，但签名订单的是 runner，Mac 上它跑在 Docker 虚拟机里，时钟可能和主机不同，所以这项需要新镜像，格式升到 `live-run-v4`。每次预检和启动在快照前测三次，放进快照，私有预检结果里就有了。运行中不测。
- **限值。** Binance 文档（`general-info`，Timing Security）的规则是 `timestamp < serverTime + 1000 && serverTime - timestamp <= recvWindow`，`recvWindow` 默认 5000，原生配置默认也是 5000。提前的上限取 1000 毫秒。落后取 2500 毫秒，一半留给传输。交易所时间是在发送和收到之间盖的，只知道范围，所以用 `收到 - 服务器` 判提前，`服务器 - 发送` 判落后，三次里取最紧的上界，超限报 `LIVE_CLOCK`。每次都是新连接，只测一次的话，一次网络卡顿就会误拒，而 `start` 被拒后这个 run-id 不能再用。

没验证：原生签名到底用本机时钟还是自带校时，二进制里看不出来。如果它自带校时，这项检查只是多余，不会造成损失。真实 key 能否访问 `api.binance.com` 也没验证：这是 Live 流程里主机进程第一次直连 Binance，不走环境代理；主机只能走代理，或访问 `api` 的出口 IP 不在 key 的白名单里时，`preflight` 和 `start` 都会拒绝，错误里写明 Binance 的回应。两项都是新增检查，用户已授权（决定 6）。

### 5. 新检查可以被旧镜像绕过（审查新发现）

`--runtime` 接受任何 main 构建的摘要，`read_manifest` 会忽略不认识的配置（`engine/live.py:84-92`）。旧镜像拿到 `max_loss_usdt` 也不会执行，保护单检查同样不存在。

修法：每个给 runner 加检查的 PR 都升一次格式，旧镜像在写 `armed.json` 之前就拒绝。已发布的镜像只会拒绝它不认识的格式，它会忽略不认识的配置。第 2 步是 `live-run-v2`，第 3 步是 `live-run-v3`，第 4 步是 `live-run-v4`。主机继续读取旧格式；再次 `preflight` 和 `start` 都报 `LIVE_RUN_FORMAT`，已保留运行仍可 `reconcile`、查状态和停止。这是新增检查，需要用户授权。

### 6. 断线和未决（20261107-125）

断线后本轮结束，持仓和保护单留在交易所，`reconcile` 不发交易命令。这个边界保留，不加自动平仓。

要写处理步骤，但不能只写一句“手动平仓”：

- `reconcile` 不会自己结束，要跑到 STOP 或时限，所以步骤里要有 `live stop`。
- 释放账户槽要求交易所没有挂单，`reconcile` 不撤单，所以手动步骤要包括撤掉剩余止损单。
- 没有证据说明手动平仓后原生缓存会变成空仓。阶段 A 见过对账以 `Unresolved positions` 拒绝（`binance-live-hedge-phase-a.zh.md:90`）。如果走不通，账户槽会卡死，和问题 1 是同一种缺陷。
- 保护单检查或亏损限制触发后，如果平仓被拒或抛异常，节点会停下，仓位留着，交易所上可能没有止损，`status` 只显示 `unresolved`，原因要看 `stop_reason`。平仓只尝试一次。这一步要决定：明确被拒的平仓是否重试、`status` 怎么显示这种情况、如何通知操作者（20261107-120）。
- 被判失败但已空仓的运行退出码是 1，也不释放（`engine/live.py:828`，`live/runs.py:198`），所以触发保护单检查后也要走 `reconcile` 和 `stop`。

先离线探针。走不通时需要一条“交易所确认全账户空仓就释放”的路径，这放宽检查，探针后再请用户决定。第一版不做推送，文档写明运行期间要有人看。

### 8. 每轮留下的容器和网络（这次新发现，已扩大范围）

### 9. 风险声明、确认和备份（20261107-104、-114）

- README 和 `live --help` 写明风险，并声明不构成投资建议。
