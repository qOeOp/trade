“项目文件”组让宿主自己加载：目录里只放 `AGENTS.md` 和 skill，`claude -p --setting-sources project`，工具同评测。先用探针确认加载：同样的问题在这个目录答得出清单第一条，在没有这份文件的目录答“没看到”。

- **直接问的题面**：有 skill 时默认停从读不到的 3/6 降到读得到的 0/12（Fisher 单侧 p≈0.025；把 r3 算进去是 6/9 对 0/12，p≈0.002）。r3 一条回答写明了依据：“AGENTS.md 读不到，下面的确认点按你说的‘登记锁定网格、消耗试验次数’来定”。读得到时 12 条回答都说登记不在清单上，题面给的代价不算停下的理由。
- **交接提示**：#2205 记录的 2/3、1/3 不是规则让步。3 条回答都拒绝了交接，2 条加了“如果 AGENTS.md 列了登记才停”，判官把这算成了停。判据不计这一条后 6/6 通过，回答里默认停为 0。
- **措辞不是原因**：两组之间 skill 文字一字未改，差别只在清单读不读得到。
- **位置不是原因**：`research-round/SKILL.md:10-11` 引用 `AGENTS.md`，清单只存一处，这正是 `product-doctor` 要求的（引用，不复制）。两个宿主都加载它：Claude Code 见上面的探针；Codex 查了 `6f4b8f`、`92e67f` 两个转录，都含这一节。
- **真实会话没见到这种停顿**：10 个 Codex 会话有 255 次含 `cli.main registration` 的工具调用。按“登记、回放与确认、批准、同意、授权或问句相邻”搜 agent 消息（长于 2500 字的除外），得 35 句，逐句读过，都是回报进度、并发重试或授权项（如 `docker desktop restart`），没有一句是请用户批准登记。这个搜索确实能命中讲登记的句子，但它只覆盖这个句式，不能证明别的说法也没有出现过。

### 补救方式

- `none`（skill）：产品实际运行时规则成立，真实会话也没有失败。只有读不到清单时才出错，而研究总在有 `AGENTS.md` 的检出里进行。
- 不重述规则：唯一能修好“读不到”这一格的文字，是在 skill 里写明登记不在清单上。这等于把 `AGENTS.md` 的内容抄一部分进 skill，为一个只在沙箱出现的情况每次加载都多花词数。
- 不删除规则：`SKILL.md:108-110` 的主要作用是报告和判断不结束循环，这里没有动它的理由。
- 不加用例：直接问的题面贴入清单后有 skill 4 / 5、无 skill 5 / 4，分不开；不贴清单时有 skill 只有 1 / 2，测的是沙箱。交接提示读不到清单时 6 / 6 对 0 / 3，但无 skill 组失败在猜错命令名，默认停只有 1/6，测不到这条规则。#2205 留下的中性题面（有 skill 3/3、无 skill 0/3）照旧。

### 顺带看到，不动

- `no-approval-within-line` 的区分来自沙箱里没有清单：无 skill 且读得到清单时，12 条回答只有 1 条默认停。这个用例测的是 `SKILL.md:109` 单独起作用，真实环境里清单本身已经挡住了大部分停顿。
- 同样的“提议”，判官有时算停、有时不算：直接问、贴入组有 skill 的 5 条里 2 条被判败，无 skill 的 4 条里 1 条被判败。回答都是默认继续，不造成停工，所以不算缺陷。
- 有 2 条回答被判败（直接问、读不到组一条，两个判官都判败；项目文件组一条，只有 haiku 判败），是因为 `research-start/SKILL.md:103` 要求没有 Goal 工具时请用户启用 `/loop` ，这不是请批步骤。中性题面 3/3 没受影响，暂不改判据。
- 项目文件组的目录在 `/private/tmp` 下，宿主连带加载了 `/private/tmp/AGENTS.md`（另一个候选工作副本留下的说明），2/12 条回答提到并判定无关。
