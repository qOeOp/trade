# Binance 双向账户与多策略 Live 设计

日期：2026-11-06。状态：设计稿，供评审；尚未实施账户模式、并发或恢复语义变更。
代码基线：`main` / `dc49edba7751e0732563200fc9347e42aeaac79e`。
原生依赖：`uv.lock` 固定的 Nautilus `2.0.0rc7`。

本稿已吸收 [独立设计与原生能力评审](binance-live-hedge-review.zh.md) 的 R1/R2：
明确原生 UUID 订单 ID，以及 reconcile-only 的无交易成员 OMS 注册。
这两项设计遗漏已修订；[阶段 A 原生验证](binance-live-hedge-phase-a.zh.md) 已完成基础协议
与特定持久恢复对照，并补充配置构造要求。全部异常验收尚未完成，同向并发仍未通过。

本设计承接用户选择的两个 15m 策略：`price-action-retest-midepisode@1` 与
`price-action-retest-mid3r@1`。用户表示账户已设置双向，并要求考虑多个策略可能同时持有多空。
账户实际状态以执行时的新鲜查询为准。这两个策略都能产生多、空信号，但各自一次只持一个方向。

本文替代 [初版 Live 设计](binance-live.zh.md) 中要求把账户改为单向的后续方案；
初版的源码身份、私有凭据、账户占用、停止与冷恢复边界继续作为实现基线。
本次写设计不等于授权改变现有拒绝检查、账户设置或发出真实订单。

## 1. 设计决定

1. **账户保留双向。** 执行层读取真实账户模式并使用匹配的原生适配配置；连接过程不自动改账户。
2. **每个策略保留自己的持仓规则。** 用 Nautilus 原生策略、订单和仓位身份区分归属；
   不新增策略的“账户持仓模式”字段，也不把“能做多和做空”误解成“必须同时持有多空”。
3. **一个账户由一个执行会话持有。** 一个 `LiveNode`、一个 Binance execution client、
   一份原生持久缓存承载会话中的策略。并发通过同节点注册多个策略实现，账户槽仍只允许一个会话。
4. **分两阶段交付。** 先让两个 Retest 在同一账户顺序验收；再支持同一会话内两个固定策略并发。
   首批并发共同启停，不支持运行中增删成员或单独暂停一个成员。
5. **恢复按证据开放。** 首版仍保留“冷重启只能对账”的边界；原生缓存可加载不代表策略可继续交易。

这项设计增加的是执行归属、并发互斥和生命周期信任边界。订单、成交、持仓、资金、费用和
对账继续由 Nautilus 负责；不建设资金分配账本、虚拟账户引擎或新的研究工作流。

## 2. 当前实现与目标

| 事项 | 当前 `main` | 设计目标 |
| --- | --- | --- |
| 账户模式 | `require_admission` 和 reconcile 都要求单向 | 对新会话要求并核实双向，保持其他未获授权的检查 |
| 执行客户端 | `NETTING`、`use_position_ids=True` | 候选为 `HEDGING`、`use_position_ids=False`，经过下述恢复验收才采用 |
| 策略 OMS | 源码未显式指定时继承客户端 | 两个 Retest 明确使用策略级 `NETTING`，每策略每品种一个本地仓位 |
| 客户端订单 ID | 当前 Retest 工作稿沿用默认 O 格式，长 tag 组合可达 45 字符 | 实际适配源码设置原生 `use_uuid_client_order_ids=True`，由 Binance adapter 处理 wire 编解码 |
| 运行成员 | 一个 manifest source、一个 `Session.source` | 阶段一不变；阶段二固定成员列表，同节点注册 |
| 账户占用 | 指定私有 root 内的账户槽 | 保持唯一会话，不放开成每策略一个 runner |
| 冷恢复 | 原 cache + Observer；不恢复 source 回调 | 原 cache + Observer + 同身份的无交易原生成员注册；完整策略恢复另立已验证契约 |
| STOP | 整个运行停止并核实全账户空仓 | 两阶段均为整会话 STOP，退出按原生策略归属执行 |

这里的策略 `NETTING` 描述策略内部的仓位组织方式；交易所账户仍是 Hedge。
官方支持策略 OMS 覆盖客户端 OMS。`use_position_ids=False` 让引擎管理策略虚拟仓位，
而 Binance 的 LONG/SHORT 下单腿仍由原生适配器按实际账户模式、方向和开平意图选择。

首次支持范围保持一个 USD-M 账户、BTCUSDT、固定源码和固定 runtime digest。
资金、单资产、逐仓、杠杆、自动追加保证金、单笔限额各项仍读取实际账户并保留当前检查；
本设计不假定这些设置已经满足，也不顺带修改。策略仓位和每计划风险由源码给出；
会话预算、单笔名义额上限都不代表策略间资金隔离或最大亏损保证。

## 3. 组件与数据流

```mermaid
flowchart LR
    C[Live 控制命令] --> H[账户槽与固定运行输入]
    H --> N[一个原生 LiveNode]
    Q[只读账户与品种查询] --> G[连接与开仓准入]
    G --> N
    N --> A[Retest midepisode]
    N --> B[Retest mid3r]
    A --> E[Nautilus 风险与执行引擎]
    B --> E
    E <--> K[原生持久缓存]
    E <--> X[Binance 执行适配器]
    X <--> V[同一个双向账户]
    K --> O[私有状态与诊断读取]
```

| 所有者 | 职责 |
| --- | --- |
| `live/runs.py`、`live/state.py` | 固定成员输入、账户槽、幂等启动、持久 STOP、原件与进程归属 |
| `engine/live.py` | 组装单节点、注册原生策略身份、开仓准入、会话级停止与结果判定 |
| `engine/live_venue.py` | 读取实际账户/品种设置，检查当前支持范围；不替用户设置账户 |
| `engine/live_cache.py` | 当前会话的原生 cache 持久化和健康度；不增加第二套仓位记录 |
| Nautilus | 路由、风险检查、订单、成交、仓位、余额及启动/运行中对账 |
| 策略源码 | 信号、仓位大小、持仓约束、原生保护单和退出意图 |

订单的 `strategy_id`、`position_id` 与缓存中的原生归属是执行权威。不得按订单方向、品种、
最近一次信号或账户 LONG/SHORT 总量猜测归属。每次退出明确使用目标原生 position ID；
取消仅限该策略拥有的订单。相同方向的两个策略在交易所可能汇总成一条仓位，
这不抹去原生策略归属，也不提供独立的保证金、强平风险或账户损益结算。

可直接复用 `cancel_all_orders(strategy_only=True)` 和 `close_position`；
`close_all_positions` 原生也按调用者 strategy_id 过滤，不是全账户平仓。
需要保留保护时，按原生订单属性选择开仓单后调用 `cancel_order`，不另写归属算法。
当前产品对 `close_all_positions` 的使用仍有拒绝检查；采用该 helper 须先明确处理该检查，
不为绕开它新造等价循环。原生 `manage_stop/market_exit` 会先撤单再平仓，与本设计的保护保留顺序不同。

交易所收到的是账户级 LONG/SHORT 腿，不识别这些虚拟策略 position ID。Hedge 下原生
`reduce_only` 由适配器转成对应开平腿，不向 Binance 发送 wire `reduceOnly`。
因此本地归属正确不等于交易所保护单按策略隔离：A 已退出而其保护单尚未撤成时，迟到触发
仍可能减少 B 所在的同一账户腿。阶段 A 必须专门验证该竞态；通过前不开放同向并发。

当前账户锁只覆盖指定 root，不能排除另一个 root、其他主机或手工交易。
首批部署维持唯一指定控制入口和私有 root，不宣称已实现跨主机账户租约。
观察到无法归属的交易不自动认领、取消或分摊给任何策略；保留未决状态与账户占用。

## 4. 启动、重连和停止

### 初次启动

1. 在现有账户槽锁下解析固定 manifest、源码、universe、runtime 和凭据绑定。
   存在未完成会话时返回原会话或拒绝另起，不因换 key 获得第二个槽。
2. 读取新鲜账户事实；要求实际 Hedge 与原生客户端配置一致。继续检查首次全账户无持仓、
   普通单和算法单，以及当前其余账户、资金和品种限制。观察失败或过期不能按默认值通过。
3. 以固定身份构造节点和策略，默认关闭新开仓许可；原生连接、缓存与启动对账完成后，
   再确认账户事实与有效配置。源码初始化、数据回调和延迟命令均不得越过这个许可边界。
4. 策略历史预热及实时数据边界满足各自验收条件后，才允许对应来源产生新开仓。
   被拒绝的开仓命令不排队等待准入后自动重发。

账户模式是会话级事实，用户不必为两个策略重复填写。现有查询观察可复用；
不新增一份持久化“默认双向”字段，也不以旧预检替代重连后的事实。

直接复用 LiveNode 已有的 load/connect/reconcile/start 顺序，不新建同义的对账状态机。
产品准入只补实际账户模式、私有存储、源码预热等独立事实。rc7 Rust RiskEngine 有
REDUCING/HALTED，但当前 Python LiveNode/Strategy/Controller 没有公开 setter；
不能按不可达 API 设计实现，也不因此自行重写风险计算。验收覆盖实际允许的提交、修改和延迟命令入口。

### 连接中断与冷恢复

- 同一进程断线时，关闭新开仓许可，继续消费可获得的原生成交与状态事件；
  使用原生 socket-state 订阅和适配器恢复路径，不为重连创建第二个客户端或第二份资金视图。
- 原生连接恢复后，账户模式、订单/仓位归属、对账结果与策略数据连续性都重新确认。
  只有该条路径完成原生验收，才允许原进程恢复新开仓；否则保持停止开仓、状态未决。
- 未能确认账户模式或归属时，不擅自撤掉已有保护。新的撤单/平仓命令必须仍有可确认的
  原生归属和有效执行语义；不能保证时保留未决，不报告 clean stop。
- 进程冷重启沿用同 run、同 manifest、同 runtime 和原生 cache，仍是 reconcile-only。
  当前 `load_state/save_state=False`，不实例化旧交易源码重新接管，也不重放任意 source 回调。
- 在原生 load/reconcile 前，按固定声明为每个原成员注册同 StrategyId、`oms_type=NETTING`
  的原生 base `Strategy`。关闭 `manage_stop`、`manage_gtd_expiry`、`manage_contingent_orders`，
  不配置 external-order claim，不加载旧源码、不订阅行情、不发交易命令。Observer 继续负责观察。
  这些对象仅通过公开 `LiveNode.add_strategy` 恢复成员 OMS 注册；不新增持久路由表。
- 已有 position 的 OMS 可随 cache 恢复，但尚未首次成交、未关联 position 的订单没有这层信息。
  因此不能以已有仓位恢复成功，替代上述成员注册或首笔漏成交的恢复验收。
- reconcile-only 只观察、对账，不隐式平仓。它不能作为“异常后一定自动退出”的承诺；
  有仓位或未决订单时账户槽继续占用，由明确的后续操作处理。

### 会话 STOP

用户 STOP、期限到达、任一成员调用 `shutdown_system`、保护失败、存储故障等，
都进入同一个会话停止流程。首批并发选择共同启停，因此一个成员请求结束会使另一个成员也停止。
这是首批范围的明确取舍，不把单策略自然结束隐式解释成可继续运行的另一种状态。

立即关闭所有新开仓许可，再尝试持久化既有 STOP 意图。写入失败不重新开放交易，
也不阻断归属和执行语义已确认的必要退出；会话保持未决，不记录 clean stop 或释放账户槽。
随后由各策略的原生身份取消所属开仓单、保留必要保护、通过原生退出所属仓位。
继续处理部分成交、迟到成交和撤单竞态；
不得先撤掉所有保护再等待平仓，也不得用全品种取消来替代归属检查。

只有全部原生仓位为零、所有所属非终态订单结束、原生处理与持久化完成，并有新鲜交易所
查询确认整个首次托管账户空仓且无工作单，才记录 clean stop 并释放账户槽。
超时、异常退出、缓存或 journal 不健康都保留未决与原件。进程退出码为零不单独证明账户安全结束。

这些流程状态从原生状态及现有生命周期原件读取，不新增一套持仓状态机或持久状态汇总。

## 5. 最小存储与身份

### 阶段一：沿用 `live-run-v1`

每次只运行一个固定 Retest，保持现有单 source manifest；两个候选分别建立独立运行并顺序执行。
新执行配置由固定 runtime 和源码表达，不增加策略账户模式字段。
原候选身份与实际适配源码 hash 继续分开，适配不继承原策略的收益验证结论。

两个阶段的实际交易源码都明确设置原生 `use_uuid_client_order_ids=True`。
确定性的 trader/strategy ID 用于归属；订单 ID 由原生 OrderFactory 生成 UUID，
Binance adapter 自带可逆 broker 编解码处理 wire ID。保持既有归属 ID，不自建短 ID 编码器、
映射表或以随机变更成员身份规避长度问题。配置写入实际源码后重新固定 source hash。

rc7 的完整原生配置必须进入 `Strategy.__new__`，不能仅在 `__init__` 赋给 Python `.config`。
阶段 A 已复现后者令 UUID、GTD 与 stop 管理显示配置却未进入原生消费者；OMS 注册另有路径。
源码在自己的 `__new__` 创建配置，宿主透传既有源码构造参数，`__init__` 保留同一对象；
宿主不枚举配置字段或覆盖源码选择。实际包装后的 Retest 必须生成正确 UUID 并验证实际 OMS，
只检查 `.config` 或裸 base Strategy 不算验收。共享 replay 包装若修改，另做既定原生配对验收。

### 阶段二：下一个 manifest 格式，固定成员

`run_id` 继续表示一次不可变的节点执行会话，拥有一个 runtime、账户槽、cache 和生命周期。
一个会话可以有两个策略，不另加同义的 `session_id`。升级 manifest 格式，避免让旧格式被静默重新解释：

| 内容 | v2 表达 |
| --- | --- |
| 会话事实 | 沿用 `run_id`、runtime、trader/account 标识、credential binding、symbols、universe 与会话 config |
| 成员声明 | 新 `strategies` 有序数组；每项包含既有 `origin_candidate` 与实际 `source` 身份 |
| 源码文件 | ordinal 从 0 开始，以无前导零十进制表示；路径固定为 `/inputs/strategies/<ordinal>.py`，不重复保存可推导路径字段 |
| 原生策略身份 | 按下述 v2 派生规则生成；准备时核实成员 ID 与原生订单 ID 命名空间均不冲突 |
| 运行停止 | 沿用会话级 STOP；不增加成员 STOP 文件或每成员持久停止状态 |
| 非原生逐策略诊断 | 仅在现有事件缺少归属时附一个原生 `strategy_id`，例如 `source_findings`；原生事件已有身份则不再复制 |

成员数组的顺序也是身份的一部分；准备后不可重排、替换、追加或删除。同 run 的重复启动
核对整个固定声明，不能通过修改 manifest 热更源码。实际 source hash 必须匹配对应只读文件；
旧 `live-run-v1` 原件、cache、观察与镜像绑定全部保留，不原地迁移到 v2。
每个成员使用不同原生策略身份和订单 ID 命名空间，重连保持相同身份。

v2 的策略 ID 规则固定为 `LIVE-` 加 SHA256 的前 12 个十六进制字符；哈希输入是
`[run_id, ordinal]` 的 UTF-8 JSON，使用 ASCII 转义、无多余空白，ordinal 为整数。
例如 Python 的 `json.dumps([run_id, ordinal], ensure_ascii=True, separators=(",", ":"))`。
格式验收核实 rc7 的实际 StrategyId 与 OrderFactory 生成结果；若发生碰撞或不满足原生限制，
在准备阶段拒绝，不改序号、随机换 ID 或重解释旧运行。此规则不应用于 v1 身份。

首次 v2 仅两个指定 Retest、同一品种、同一 universe 和 runtime，共同启停；
各自大小与风险仍在各自完整源码中，不新增可任意覆盖策略的参数语言。
不同账户、多品种独立配置、同策略多实例、热加减、单成员停止留作后续需求。

### 独立存储评审

独立子代理 `hedge_manifest_review` 只读审查了当前 `live/runs.py`、`engine/live.py` 和
`live/state.py`。评审要求移除可派生的成员源码路径，补齐非原生逐策略诊断的来源，
并保留共同 STOP。决定与依据如下；这是设计审查，不是存储实现授权。

| 保存的事实 | 消费者 | 为何现有字段、关系或派生不足 |
| --- | --- | --- |
| 不可变成员集合、顺序及各自 origin/source | loader、幂等准备、原生身份注册和重连 | v1 只能表达一个 source；尚未成交的成员不出现在持仓中，cache 也不能倒推启动声明 |
| 非原生逐策略事件的来源 ID | 状态读取、诊断与验收 | 同 run 可交错产生多个 source 事件，仅凭时间顺序不能判断是谁；事件中的来源选择是独立事实 |

不新增账户模式、重复 `session_id`、账户级仓位拆分表、策略余额、派生 PnL 或 SQL 表列。
实际账户模式已有私有观察原件；原生订单/仓位身份已有 native cache；
UI 所需成员状态从固定成员与原生事实读取。私有执行原件不写入公开研究账本。

## 6. Nautilus 原生能力与恢复待验证项

本设计依赖官方 rc7 的能力，而不是自行实现补偿：

- 策略 OMS 可以覆盖客户端 OMS；本地 NETTING 仓位包含策略身份。
- Binance `use_position_ids=False` 可接受引擎管理的虚拟仓位 ID；原生 `close_position`
  指定目标仓位，适配器负责 Hedge 开平腿与参数转换。
- 定期 Live 对账按账户、品种汇总，并核对多空两侧；先前把底层单报告处理等同整个周期流程的推断已撤回。
- 启动对账不同于定期对账，必须分别验收。

尚未闭合的两个问题会决定最终执行配置：

1. **启动时生成缺失订单。** 默认 `generate_missing_orders=True` 的逐报告路径可能在最终
   聚合验证前生成修正。`False` 是原生已有配置；它保留最终校验，但是否能覆盖本产品需要的
   漏成交恢复仍待测试。不能只因为关闭后某个样例通过，就把它定为生产方案。
2. **同向策略退出后的均价。** A、B 以不同价格同向入场，A 退出后，B 的真实入场均价
   可能与账户汇总仓位均价不同。rc7 启动会检查按侧加权均价；原生 report 的 `OPENING_ONLY`
   有不同语义，但当前 Binance adapter 未使用它，不能当成现成开关。
   复现先核实交易所均价语义，再构造报告；不修改策略损益来凑账户均价。

判定顺序是：在当前固定版本验证官方配置；若失败，定位具体原生路径并核对已发布版本的
明确修复，再决定版本升级或上游修复。任何升级都须新 CI digest 和适用的原生配对验收。
不预设必须修改 Nautilus，也不以关闭 position reconciliation、过滤全部仓位报告、
丢弃旧 cache 或人为生成持仓归属作为替代。

## 7. 分阶段实施与验收

### 阶段 A：证明候选原生配置

在隔离环境对固定版本运行真正的原生节点/对账路径。假交易所报告仅提供 IO 输入，
不得 mock 掉归属、cache、执行引擎或对账算法。

| 场景 | 必须核对的结果 |
| --- | --- |
| 原生 UUID 订单经普通/算法下单、撤单与 REST/WS 回报往返 | wire ID 满足交易所字符/长度限制，回报还原到同一原生订单与成员；不以本地 UUID 长度检查代替协议往返 |
| 单策略多/空开仓与部分退出 | native ID 归属、Binance positionSide、保护数量和最终仓位一致 |
| 两策略同向、反向；A 部分退出再全部退出 | B 的数量、原始入场均价、订单归属不被 A 改写 |
| 完整 cache 下启动，LONG/SHORT 报告交换顺序 | 输出不依赖报告顺序；不产生多余外部仓位或修正成交 |
| 净量相同但多空两腿数量不同 | 不能判定一致或放行新开仓 |
| 同向不同价格入场后部分退出、单方退出 | 合法均价差不会被伪造成漏单或改写策略损益；异常差异仍可识别 |
| A、B 同向持仓；A 退出与其保护单触发、撤单确认交错，B 尚未退出 | 用真实原生适配及 IO 报告核对账户腿、全部成交与双方归属；不能以最终全账户空仓掩盖跨策略减仓、反向虚拟仓位或损益错配 |
| 缺失成交、重复成交、迟到成交、撤单与成交交错 | 按原生身份补齐或明确拒绝；无重复成交、抢归属或虚构分摊 |
| 持久 cache 重开、缺失/损坏 cache、声明漂移 | 同身份正常对账或拒绝；不默建新账户、不推断丢失的策略归属 |
| entry 已持久化但尚未首次成交、无 position 映射，冷重启后补到首笔 fill | 对照不中断路径与同身份无交易成员注册后的恢复路径，position ID、OMS 和归属一致；同时保留已有仓位部分成交的对照 |
| 断线、连接后模式不匹配、观察失败 | 关闭新开仓许可；不重发旧开仓或自动改账户设置 |
| STOP 与部分成交/保护单并发、存储失效 | 只处理授权归属；未决时不释放账户槽 |

每次验收记录精确源码、wheel/镜像版本、输入报告及原生前后状态。核对订单、成交、数量、
费用、资金费、账户与策略损益的定义边界，不能以进程成功退出或数量最终归零代替因果正确。
正常执行的四组 Backtest 测试已通过，但不替代启动恢复、Binance 协议或真实账户验收。

### 阶段 B：单成员 Hedge 接入与两个 Retest 顺序实测

- 在阶段 A 的单成员适用项通过后，准备最小产品改动：Hedge 账户检查、匹配的 native client、
  显式策略 OMS、原生 UUID 订单、reconcile-only 无交易成员注册与退出归属。
  沿用 v1、单品种、首次全账户空仓和禁止旧交易源码冷重启的边界。
- `midepisode`、`mid3r` 分别冻结实际适配源码；继续验证历史预热、15m 聚合的首桶与延迟边界、
  独立保护单、部分成交和停止竞态。已有研究审计及原策略收益不能替代这些 Live 证据。
- 按现有规则完成全套产品测试和固定 CI 镜像验收。资金、大小、时限、允许操作范围形成具体
  实盘试验方案后，沿用用户要求逐项确认尚未授权的真实动作。
- 第一个会话达到 clean stop 并释放槽后，才允许第二个会话；不自动循环、重试开仓或扩大数量。

### 阶段 C：固定双成员会话

阶段 A 的双成员启动与恢复项通过、阶段 B 顺序验收完成后，再实施 v2 manifest 和多策略节点。
测试共同 STOP、任一 source 请求停止、同时保护退出及一份 cache 的完整归属。
依然只有一个账户槽；不通过放松 `LIVE_ACCOUNT_OWNED` 创建两个独立 runner。
并发会话整体预算与真实账户风险重新评估，不默认把两个独立小额试验的额度相加。
同向保护竞态未通过时，保持顺序执行，不自动启用两个 Retest 并发后临时禁止某类信号，
也不追加自行分摊成交的执行引擎。

只提供现有私有 Live 控制与状态接口。UI、跨主机高可用、账户池、独立策略资金份额与完整
冷恢复都不在这一轮实现范围；需要它们时再依据实际消费者设计。

## 8. 未来改动的授权与兼容边界

本次只修改设计文档。后续需要变化的拒绝/行为须在具体改动可审阅时明确说明：

| 当前拒绝或行为 | 拟允许的行为 | 不随之放开的内容 |
| --- | --- | --- |
| `LIVE_ACCOUNT_MODE` 要求单向 | 新执行会话在实际 Hedge 且适配配置匹配时启动/对账 | 单资产、资金、保证金等其他限制；自动账户设置写入 |
| v1 只接受一个实际源码 | v2 固定两个已声明成员共用一个节点 | 多 runner 争用账户、热更新、任意多策略或多品种 |
| 单 source 的 STOP/结果处理 | 按各自原生归属退出全部固定成员 | 外来单认领、全品种盲撤、未决释放账户槽 |

`generate_missing_orders` 是否采用非默认值仍由阶段 A 决定；若改变，单独说明当前和变更后的
恢复结果及保留的校验。新增诊断归属与 v2 成员声明按上述独立存储决定审查，不埋进任意 config。
完整策略冷重启、放宽风险数值、账户设置写入和真实订单均不能从本次设计授权推导。

旧会话继续绑定旧 runtime 与原件，不把旧 cache 接到新 OMS 或新策略身份上。
回退发生在未 armed 的新运行；已经尝试交易的会话只能沿原恢复边界处理，不能通过换版本
创建一个“干净的新运行”绕开未决订单。保留镜像、观察和 cache，直到原会话确实结束。
