# 语义指纹：UUID 订单号的同时刻订单（2026-11-10）

用户 2026-11-10 授权（"Authorize the fix"）修改重放一致性检查的编号规则。

## 现象

`replay reproduce --trial-id 2604`（`price-action-retest-mid3r-live@2`）在新运行时 `dd6a8990` 上报 `REPRODUCTION_MISMATCH`
（trial 2608），在它自己的镜像 `05a64b96` 上也一样（trial 2609）：fills、orders、order_events、positions、fill_volumes 不同。

两次重放的最终权益都是 118296.88422993，198 笔成交、99 个周期，头部指标完全相同；去掉 ID 列后成交表和订单表逐行相同。

## 原因

- Live 改写的源码用 `use_uuid_client_order_ids=True`，每次重放每个客户订单号都是新的 UUID。
- `engine/compare.py` 给随机 ID 编号时，先按遮掉随机部分的订单号排序，再按首个事件的时间和标的排序。
  订单号整个是 UUID，遮掉后全部一样；成交时同时下的止损单和止盈单首个事件时间也一样（这次运行里有 252 个订单如此）。
- 剩下的平局按文件顺序，而 `order_events.jsonl.gz` 按订单号写出，于是编号随 UUID 变化，哈希每次都不同。
- 指纹里交易号 `T-<hex>-<n>` 没有问题：两次重放逐笔相同。

## 改法

平局时再按订单整段事件历史（随机部分遮掉后的文本）排序，然后才是事件序号。

- 订单号不含随机部分的运行：遮掉后的订单号各不相同，新键永远不起作用，已存指纹不变。
- 爆仓订单（`LIQUIDATION-<venue>-<uuid>`）：只有时间和标的也相同才会用到新键。
- 两个事件历史完全相同的订单互换编号，得到的文本相同，指纹不受影响。

## 不能挽回的

trial 2604–2607 封存时存的指纹是旧规则下随机编号的结果，修复后也永远对不上；
它们封存时算好的指标、周期和日收益都还在，只是原生报告不能再通过指纹核对后重新生成。修复只对之后封存的运行有效。

## 验证

- 新单元测试：两笔同时下单、订单号排序相反的 UUID 订单，两份报告指纹相等；去掉修复时该测试失败。
- 用两份真实重放（`/tmp/repro-2604-own`、`/tmp/repro-2604-dd6a`）在本地计算，8 张表全部相等。
