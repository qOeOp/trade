# K 线、推算报价和完整成交自动导入：方案（2026-11-01）

本文只有方案，没有代码。§6 的几点用户已批准（§8），按 §7 实现。

初稿经过一个独立子代理对照代码审查，它找到的错误和遗漏都已改进正文，主要有：
- 报价和成交可以导入未收盘的月份，导了就再也补不全；
- 跳过断档月份，只在断档不在月末最后一天时成立；
- 一次调用里几个合约的连带，报价和成交的行为不一样；
- 拒绝的分类有误分，K 线的下载和 REST 退避发生在锁内；
- 第一轮会超过健康检查的启动期；
- 删缓存会删掉原件在本机唯一的副本；
- 改名要动的引用。

采集方式（下载归档还是 WebSocket 实时采集）另经两个子代理调查：一个查 Binance 官方文档和
`binance-public-data` 的 issue，一个查本仓库的代码和方案，结论在 §2。

## 1. 现在有什么

产品里已有的自动导入只有一个：compose 服务 `metrics-import` 跑 `market follow-metrics`，每天把 BTCUSDT、
ETHUSDT、SOLUSDT 的持仓量和多空比导到最后一个收盘日，然后发布（`market/follow.py`，
`docs/plans/daily-metrics-import.zh.md`）。那份方案 §5.4 说 K 线和推算报价"可以照同样的办法做一个每月任务"，
完整成交"会长时间占着导入锁，不建议自动做"。§3 说明为什么这里改变了对成交的判断。

另外三种数据现在还要有人手动导。2026-11-01 的情况：

| 数据 | 命令 | 范围 | 现在到哪 | 谁导的 |
|---|---|---|---|---|
| K 线、资金费、合约条款、当月成员 | `market import --month` | 库的 `--symbols` 清单，30 个合约 | 2026-10 全月，2026-11 成员 | 别的会话 09:09Z 手动导 |
| 推算报价 | `market import-quotes --month` | BTC、ETH、SOL | 2026-09 | 手动 |
| 完整成交（aggTrades） | `market import-trades --month` | BTC、ETH、SOL | 2026-09 | 一个会话的临时队列（不是产品代码） |

没人导会有这些后果：
- **K 线不导：** 研究会话的 readiness 会说最新整月还没有；paper 在新月份第一天启动会被拒为
  `UNIVERSE_NOT_COVERING_WINDOW`（2026-11-01 实际遇到过）。
- **报价和成交不导：** 用报价执行或读成交的回放，窗口没法延伸到新月份。

## 2. 用下载的归档，不用 WebSocket 采集

### 2.1 两种方式比一比

|  | 下载归档（`data.binance.vision`，现在的做法） | WebSocket 实时采集（`fstream.binance.com`） |
|---|---|---|
| 历史 | 有，最早到 2019–2020 | 没有，只能从开始采集那天往后积累 |
| 完整性能否证明 | 每个文件有官方 `.CHECKSUM`；aggTrade 编号连续，缺了能查出来（`SEQUENCE_GAP`） | 没有可对照的官方文件。断线期间的数据就没了：连接最长 24 小时，宿主机休眠时 Docker 虚拟机暂停。aggTrade 编号能看出缺口，但 REST 只能补最近 48 小时 |
| 能否复现 | 任何人重新下载都得到同一个文件；提交里记了每个文件的 SHA-256 | 采一次就没了；按 AGENTS.md 它是"不能重现的观察"，原件要整份存 |
| 延迟 | 日归档约在次日 07:00–13:30 UTC 发布（实测，官方只说"第二天"） | 实时 |
| 最优买卖价 | Binance 从 2024-03-30 起不再发布 bookTicker 归档，只能从成交推算（`binance-aggtrades-bbo-v1`） | 单个合约的 `bookTicker` 流是实时的，能拿到真实观察的最优买卖价；从 2025-11-18 起不含 RPI 挂单 |
| 现有规则 | 三个导入命令和它们的拒绝都按归档写 | 要新写一个采集服务，新的存储格式和新的拒绝 |
| 授权 | 已有 | AGENTS.md 规定研究不用实时连接，唯一授权的是 paper；新的采集连接要用户授权 |

实测和来源：
- 发布时间是调查子代理读 S3 列表量的。
- 连接限制和 bookTicker 的变化，见 Binance 衍生品 WebSocket 文档和 changelog。
- 归档的问题见 `binance-public-data` 的 issue：
  - 补发过缺的日子：#307、#291；
  - 2026-10-07 重新生成过 2023-05 的月归档：#339、#342；
  - 2026-10-28 的日 aggTrades 现在还是 404：#525。
- 本仓库已有结论：`docs/plans/native-mark-liquidation.zh.md` 写了实时采集"只能积累未来数据，不能补回当前历史窗口"；
  `paper-trading-design.zh.md` 把实时 bookTicker 列为以后的事。

### 2.2 结论

市场库存的历史数据照旧只用下载归档：
- 能补历史，能证明完整；
- 能让任何人复现，现有导入规则和拒绝都不用改。

WebSocket 只在一件事上有归档给不了的东西：2024-04 以后真实观察的最优买卖价。这是新的数据来源，需要：
- 新的报价规则，或者一种新的数据；
- 一个新的实时连接；
- 只从开始采集那天往后才有。

所以它不放进这次的自动导入，作为 §6.6 的单独选项让你定。

归档的两个问题和自动导入有关，§4 会处理：
- **会晚到或缺：** 比如 2026-10-28 的日 aggTrades 现在还没有，所以 10 月的报价和成交暂时导不了。
- **会被改：** 缺的日子有时几个月后补上，已发布的文件也被重新生成过。

## 3. 三种导入能不能无人值守

依据：`market/store.py` 的 `import_month`、`import_quotes`，`market/aggtrades.py` 的 `import_month`，
`market/README.md`。

- **K 线可以每天跟。**
  - 当月可以反复导：已存的部分重读后比对，只追加之后的分钟，没有新数据就返回原提交（`store.py:771, 814-842`）。
  - 上个月没导完时，下个月导不了（`store.py:653-657`）。
  - 每月第一天，上个月完整时只写当月成员（`store.py:688`）。
  - 如果月末最后一天的日归档还没出，这一天会全部用 REST 补上（`series.py:179-183`）。月份就此封住，以后不再
    和日归档比对；REST 也没有的分钟会成为永久的缺口。所以封月前要等月末那天的日归档（§4.1）。
  - K 线的下载和 REST 退避都在锁内，没法像 metrics 那样移到锁外。它还要访问 `fapi.binance.com`。
- **报价和成交只能对已收盘的整月导一次。**
  - 两个命令都接受当月：`end` 取下月 1 日和今天里较早的那个（`store.py:1021`，`aggtrades.py:217`）。导了半个月之后，
    这个合约这个月只要有一行，再导就是 `MONTH_EXISTS`，这个月再也补不全。
  - 报价在月初第一天还会提交一份空回执（`days` 为空）。
  - 所以任务只在 `today >= 下月1日` 时导第 M 月，导完核对回执的 `through` 等于下月 1 日。
  - 中间哪一天的归档没出（`ARCHIVE_NOT_PUBLISHED`），整个月回滚，下一轮再试。
- **一次调用里几个合约的连带，两个命令不一样。**
  - 报价：整次调用是一个事务，任何一个合约被拒，整次全部回滚。所以报价按合约分别调用。
  - 成交：几个合约并行，每个合约单独提交，一个被拒不影响别的（`aggtrades.py:205-247`）。所以成交按月份分组，
    同月要导的合约一次调用，和这次批量导入一样；一组被拒再改为逐个合约调用。
- **锁的时长。** 2026-10-30 到 11-01 的批量导入实测：三个合约一个月的成交 16–25 分钟，发布 2–4 分钟。报价还没量过。
  这期间别的导入、`market backup` 和发布都会被挡住（`CONCURRENT_IMPORT`、`PUBLISH_FAILED`）。每月一次，可以接受；
  这也是这里改变 metrics 方案里"成交不建议自动做"的原因。
- **断档。** 2020-01 到 2026-09 有 11 个合约月被 `SEQUENCE_GAP` 拒：BTC、ETH 的 2020-04，三个合约的 2021-02、
  2021-05、2022-09。月度归档也缺同样的编号，REST 只能查最近 48 小时，免费来源都补不上，同一天的报价也会被拒。
  - 导入 M+1 时，要从 M 的最后一天恢复状态，也会检查编号连续（`store.py:1084`，`aggtrades.py:292-302`）。
  - 所以断档如果落在 M 的最后一天，M+1 也会被拒。这 11 个都不在月末。
- **体量。** 三个合约每月的成交约 2–3 GB ZIP。入库后本地约为 ZIP 的 2.7 倍，三个币每月约 3–4 GB 的库增长，
  DoltHub 上约 1.7 倍（`docs/plans/aggtrades-source-import.zh.md`）。

## 4. 做法

### 4.1 一个命令

把 `market follow-metrics` 扩成 `market follow`，替换旧命令，不保留别名。一个进程按顺序做四种数据，这样不会
两个自动任务互相抢导入锁。名字最后在 PR 里定。

**每一轮按这个顺序做：**
1. **K 线：**
   - 范围读 `store.freshness(profile)["scope"]`：是列表就原样传，是 `"all"` 就传 `None`。传任何别的清单都会被拒。
   - 从已存的最后一个月开始，一月一月导到当月。
   - 上个月要等月末那天的日 K 线归档出来再封；在那之前只导到前一天，当月也就先不导。月末那天的归档迟迟不出时，
     按 §4.2 的"落后"处理。
2. **metrics：** 不变。
3. **报价，然后成交：**
   - 只看 `--symbols` 里的合约，只导已收盘的月份。
   - "已有的最新一个月"只认 `through` 等于下月 1 日的回执。最新回执不是整月（手动导了半个月，或空回执），就把这个
     合约这种数据标为停下，不越过它往后导。
   - 一个合约一行都还没有，就不导，标为停下；第一次的历史回补由用户决定，手动做。
   - 只往后导，不回头补中间的洞（比如 ETH、SOL 的 2025-10 成交）。补洞见 §4.3。
   - 导入前在锁外用流式的 `aggtrades.fetch_archive` 把这个月的日归档（连同前一个月的最后一天）下进缓存，全部
     下完才调用导入。
4. **发布：** 和现在一样，市场比 DoltHub 新就发布一次，前面失败的发布在后面几轮补上。

### 4.2 拒绝怎么处理

沿用 `follow.py` 的做法：下一轮再试、停下这一种数据（或这个合约）、停下全部。审查后要改的分类：

- **下一轮再试：**
  - 现有的这些：`ARCHIVE_NOT_PUBLISHED`、`CONCURRENT_IMPORT`、`MARKET_UNREACHABLE`、`LEDGER_UNAVAILABLE`、
    `MARKET_EMPTY`、`SOURCE_UNREACHABLE`、`PUBLISH_FAILED`；
  - 加上 `CONCURRENT_WRITE` 和 `CHECKSUM_MISMATCH`。后者校验不过的文件不进缓存，常常是 `.CHECKSUM` 和 ZIP 不同步，
    是暂时的。
  - 收盘 3 天后还没解决就算"落后"，降为每天一次。
- **停下这一种数据：** 不影响其他三种。
  - 报价、成交的 `RULE_VERSION_MISMATCH`，以及它们的 `SCHEMA_MISMATCH`。
  - K 线的内容拒绝：`IMPORT_SCOPE`、`MONTH_INVALID`、`UNIVERSE_CHANGED`、`SOURCE_CONFLICT`、
    `SOURCE_UNKNOWN_SYMBOL`、`SCALE_RANGE`、`SCALE_LOSS`、`SOURCE_SHAPE`。
  - K 线的 `MONTH_EXISTS`：当月重读后和已存的不一致。它不再归为"再试"。
  - 没有拒绝码的错误，比如磁盘满的 `OSError`，也停下，不再每小时重下几个 GB。
- **停下这个合约的这种数据：** 报价、成交的内容拒绝，比如 `TERMS_UNKNOWN`、`SOURCE_SHAPE`、`SCALE_LOSS`。
- **跳过这个月（§6.3）：** 报价、成交的 `SEQUENCE_GAP`，而且断档那天不是前一个月的最后一天。
  - 先清掉这个月的缓存，连同前一个月的最后一天，重下一次。还被拒就跳过，接着导下一个月。
  - 断档在前一个月的最后一天时，下个月本身没问题，但导不进来，所以不跳过，标为停下，交给用户。
  - 跳过不用另存：只往后导，下个月入库后这个月自然不会再试；重启后最多再被拒一次。
- **停下全部：** `DIRTY_WORKING_SET`、`SCHEMA_VERSION_MISMATCH`、`COMMIT_CHECKS_DISABLED`、`DATA_TESTS_FAILED`、
  K 线的 `RULE_VERSION_MISMATCH`，以及发布被拒的几种。

停下的状态留到容器重启。原因和 metrics 一样：改的是数据还是代码，要人看过才知道。

### 4.3 洞和归档的修改

只往后导会留下两种洞，都由覆盖算得出，不用另存：
- 断档跳过的月份；
- 这次批量导入漏掉的月份。

Binance 补过缺的日子（§2.1），所以建议任务每月一次，在往后导完之后，把这些洞各试一次（§6.4）：
- 试的就是普通的整月导入，同样的检查，一个月只写一次；
- 被拒照旧，下个月再试。

已发布的归档后来被重新生成过，这一点不在这次范围内：
- 已入库的月份不会被重写；
- 提交里记着当时每个文件的 SHA-256，审计重新下载时能看出变化。

### 4.4 多久跑一轮、状态和健康检查

- **多久跑一轮：**
  - 和现在一样：有在等的就每小时一轮，都追上了就等到下个 UTC 日 00:30。
  - 报价和成交在等下一个月收盘时算"已追上"。
- **状态文件：** 按数据种类和合约分开，每项是已追上、在等、落后、停下（附拒绝）或跳过的月份。
  - 每一轮开始时先写一份"进行中"。
  - 第一轮要导 K 线、报价、成交和发布，会超过现在 30 分钟的启动期；没有状态文件时健康检查返回不健康，
    `up --wait` 会失败。
- **健康检查：** 有停下或落后就不健康。
  - 跳过的月份不算不健康，这一点要你定（§6.3），因为它是对健康检查的放宽。
- **启动轮：** 容器被杀（例如 OOM）后，`unless-stopped` 会让它马上重导同一个月。所以启动后先等 5 分钟再开始第一轮，
  避免连续崩溃时一直占着锁。

### 4.5 compose 服务

把 `metrics-import` 改名为 `market-import`，命令换成
`python -m cli.main market follow --market /run/trade/market-import.json --symbols BTCUSDT ETHUSDT SOLUSDT`。

- **不变的：** 档案、账号挂载、tmpfs、加固、日志和依赖。
- **网络：** 要能访问 `fapi.binance.com`。K 线要用 exchangeInfo、klines 和 funding。默认网络本来就能出网，但要实测
  一次，因为现在 metrics 只访问过 `data.binance.vision`。
- **缓存：** 在这个服务的 volume 里，每月约 2–3 GB 的 aggTrades ZIP，加上 30 个合约的 K 线归档。
  - 这些 ZIP 从此是原件在本机唯一的副本：手动导入用的是主机上的 `~/.local/share/trade/market-archive-cache/`，
    `docs/plans/market-archive-retention-inventory.zh.md` 已经记下"原件没有备份"这个缺口。
  - 删不删，要你定（§6.5）。
- **健康检查：** `start_period` 改到 3 小时，配合"进行中"状态。
- **重建：** 合并后 compose 文件里已经没有 `metrics-import`，要先按旧服务名停掉并删除那个容器，再
  `up -d --no-deps --wait market-import`。按 AGENTS.md，停容器要你当时同意。

### 4.6 skill 和文档

- **`research-start`：** 现在 SKILL.md 和 `references/readiness.md` 只说 metrics 是自动导入的。改成：
  - `market-import` 覆盖的数据和合约（K 线是库里的所有合约，报价和成交是 `--symbols` 里的合约）：不再提议手动导入，
    读服务的健康状态和状态文件，按状态报告缺口；
  - 历史回补、`--symbols` 以外的合约：照旧作为公开写入交给用户决定。
- **eval：**
  - 现有用例 `metrics-gap-on-kept-contract` 的 prompt 和 criteria 跟着改名和范围改；
  - 再加一个用例：报价缺口落在自动导入的合约上时只报告，落在别的合约上时照旧提议；
  - `missing-quote-months-offer-import` 讲的是历史回补，不动，但要确认新文字和它不冲突。
- **改名要动的地方：**
  - `deploy/compose.yaml`：服务名、注释，volume `trade-metrics-import`；
  - `deploy/README.md`；
  - `cli/main.py`：命令、帮助文字，`--status` 的默认路径；
  - `market/follow.py`：`default_status` 和健康检查读的路径；
  - `tests/market/test_follow.py`；
  - `market/README.md`；
  - docs/rd 的 market、cli、research-start 设计页，中英文都改。

## 5. 不做的

- 不加新的导入规则、拒绝或存储字段，不改 `SEQUENCE_GAP` 的检查。
- 不做新合约的历史回补。
- 不在 GitHub Actions 或宿主机的定时任务里跑。
- 不自动做 `market backup`（§6.7）。
- 不碰 paper 的实时数据，不新增实时连接。

## 6. 要用户定的

1. **长期授权：** 任务每天把 K 线导进活动市场库，每月把 `--symbols` 里合约的报价和成交导进去，然后发布到 DoltHub，
   不再逐次问你。这把 metrics 的授权扩到另外三种数据。
   - 原来的工程备忘里有"不做每日导入，K 线当月按需重导，约 114 秒"，那是工程判断，不是你的决定。
2. **范围：**
   - K 线：库的 30 个合约，跟库的 `--symbols` 清单走。
   - 报价和成交：BTCUSDT、ETHUSDT、SOLUSDT，和 metrics 用同一份清单。以后加合约每次一个 PR；新合约的历史回补
     手动做一次。
3. **断档月份自动跳过：** `SEQUENCE_GAP` 重下一次还是被拒，而且断档不在前一个月的最后一天，就跳过这个月接着往后导，
   和这次批量导入的规则一样。跳过的月份不让健康检查变成不健康，只在状态和覆盖里看得到。
   - 另一种做法：停下这个合约，等人处理。6 年里断档过 5 天，每次都要人介入才能往后走。
   - 建议跳过。
4. **每月试一次洞：** 断档跳过的月份和以前漏导的月份，每月自动整月试一次（§4.3）。Binance 补过缺的日子，这样补上了
   就能自动导进来。建议做。
5. **缓存要不要删：** 本机这些 ZIP 是原件唯一的副本。
   - 保留：每月三个合约约 2–3 GB 的磁盘。
   - 删除：只能在报价和成交都导完后删，而且月末那天要留到下个月导完。
