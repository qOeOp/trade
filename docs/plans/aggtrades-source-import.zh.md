## 字段独立评审与决定

原方案的只读子代理 `/root/aggtrade_schema_review` 评审八列源事实。本次在实施前由独立只读
子代理 `/root/aggtrade_field_review` 再次对照现有 schema、升级、解析和导入路径，结论通过。
用户已明确批准将原 DECIMAL 基准候选的价量换为逐值证明无损的 ×1e8 BIGINT，不增加事实。

| 字段 | 消费者与独立事实 | 现有字段、关系或推导为何不能恢复 |
|---|---|---|
| symbol | 合约筛选、instrument/lifecycle 关联；归档路径声明的身份 | 官方事件行没有合约名，ID 不跨合约唯一 |
| transact_time | 时间范围扫描与未来事件时钟；源 UTC 毫秒 | bar 聚合，quote 只记录状态变化 |
| agg_trade_id | 源事件身份、同毫秒次序、连续性核对 | 未改变报价的成交不在 quote，bar 没有事件序列 |
| price | 原始实际成交价，供未来成交分析 | 推导报价存在过时侧调整，不能逆向恢复全部成交 |
| quantity | 每笔聚合成交数量，供未来成交量/容量分析 | quote 没有，bar 只有汇总 |
| first_trade_id | 官方逐笔 ID 区间起点 | 不能由 agg ID 或相邻末 ID 推导 |
| last_trade_id | 官方逐笔 ID 区间终点 | 不能由下一行首 ID 推导，尤其源边界/缺口 |
| is_buyer_maker | 原始主动方向信息 | quote 不保存每个源事件方向 |

决定：仅 `agg_trade` 八列，主键 `(symbol, transact_time, agg_trade_id)`，无二级索引。
价量分别 ×1e8 后存 signed BIGINT；时间和 ID 原整数，maker 原布尔值。
不借用 bar `volume_scale`，不存 taker_side、名义额、分钟桶、日日期、来源表或逐行哈希。
`last-first+1` 只是 ID 范围长度，不把它称为经过保证的逐笔成交数。
格式为数值语义完整，不能恢复 CSV 尾零、头行、换行或 ZIP 压缩字节。

`binance-aggtrades-int64-scale8-v1` 编码身份、每日官方归档 SHA-256 与读数进导入提交 metadata。
精确转换用整数比值与整除证明，独立于 Decimal context；任何余数或 signed int64 溢出均
`SCALE_LOSS`，全月回滚，无舍入或退回其他编码。

独立评审指出并落实：旧报价解析整日装入内存，故新完整字段 ZIP/CSV 流读使用独立模块；
连续性跨批次、日和前夕保留；前夕也核验完整字段、数量精度和UTC日归属，虽不插入，其拒绝
同样会拒绝本月；这是新完整源入口的合同，不改变旧quote检查。主键不代替源 ID 连续性核对；升级只追加表，不扩大数据库级
SELECT/INSERT 权限；现有升级不取导入锁，活动升级必须等队列全部 complete。

## DoltHub 容量与大推送：合并门槛

核查日期2026-10-29；本产品推的是公开 DoltHub 库，不能把网页CSV上传上限当作 `dolt push` 上限。

- [官方2026定价说明](https://www.dolthub.com/blog/2026-04-24-announcing-dolthub-pro-for-5-dollars-per-month/)
  明确公开数据库免费；私有库计费门槛不是公开单库硬上限。
- [官方1TB推送记录](https://www.dolthub.com/blog/2022-02-28-dolt-storage-layer-memory-optimizations/)
  记载单个 FBI NIBRS 库完整1TB已成功推入 DoltHub；当时也有远端内存瓶颈及并发大库限制。
  这排除了“DoltHub从来不支持大于100GB单库”的说法，不是2026年任意账户容量/SLA的保证。
- [官方2025 clone 实例](https://www.dolthub.com/blog/2025-02-03-dolt-basics-clone/)
  报告超过100GB的公开库约20分钟克隆。方向、网络与本机不同，不能当作160GB推送耗时。

本次未找到公开文档声明的、会挡住约160GB的单库硬限制；也未找到针对本账户与Dolt2.4.2的
160GB公网上传耗时保证。没有实际公网大推送实测，不伪称已验证全量可推或“无限制”。
理想纯传输下界：160GB在10/50/100Mbps有效上行分别约35.6/7.1/3.6小时，尚未加协议、
查缺块、压缩、重试与服务端处理。逐月增量推送可避免一次发送160GB，不能消除容量风险。
合并前向用户呈现该不确定性；发现实际硬限制会挡全量则停止，不合并。不能擅自联系供应商、
付费、改远端、拆成 market2 或放弃公开发布。正式单月试导要记录实际推送耗时再决定是否全量。
