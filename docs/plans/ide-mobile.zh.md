# 手机访问 IDE：信息怎么展示、服务怎么降级（方案与设计稿）

2026-11-07 用户提出：部署的 IDE 用手机打开还是 IDE 布局，虽然做了自适应，但手机屏幕天然不适合；岛和可伸缩面板也不适合手机浏览。要一个方案和设计稿，可能涉及界面变化和服务降级。

> 2026-11-11：手机上留哪些页面和操作，改由 [`ide-phone-scope-20261111.zh.md`](ide-phone-scope-20261111.zh.md) 决定（待用户定范围）；本文的切换规则、服务降级和手机尺寸 token 仍有效。

本文只是方案，没有改产品代码。设计稿在 [Trade 手机端设计稿](https://claude.ai/artifact/1sEgV9GCX7xf9STYdNWt2C)（私有，明暗各 10 张）。改版前的截图在 `.review-shots/mobile/`（未入库）。

## 结论

- **手机是监视器，不是工作台。** 手机上要回答的是「模拟盘怎么样了、研究走到哪了、市场在干什么、问一句」，不是写策略、看源码、调布局。
- **同一个包，换一层外壳。** `App.tsx` 按屏幕选 `MobileShell` 或现在的 `Shell`，数据层和读数计算共用。不做第二个应用，不判断 UA。
- **四个底部标签：Runs（落地页）、Research、Market、Agent。** 没有岛、没有分隔条、没有面板：一页到边的内容，加底部抽屉、压栈页和横屏全屏图。
- **服务降级先做，桌面也受益。** 现在打开一次页面要下载 3.07 MB（未压缩、每次重下），Runs 页每 3 秒拉一次带整条分钟权益线的列表。压缩、改缓存、去掉列表里的权益线后，Runs 页运行 3 天时的轮询流量按估算从约 175 MB/小时降到约 0.5 MB/小时（薄列表 gzip 后约 1.85 KB，15 秒一次）。
- **不碰账本、不加存储字段、不改拒绝检查和研究目标、不动网络路径。** 全部是 `ide/` 和 `paper/serve.py` 读路径上的改动。

## 现状（实测）

### 布局

375×812 打开时：外壳保留 2 条工具栏和 3 个工具窗，`EDITOR_MIN 45%` 让编辑区只剩约 60 px 宽；工具栏互相覆盖，热力图不可读，Details 被裁掉。代码里没有手机布局，只有个别组件用了 `@container`。

悬停（涟漪、Tip、十字线）、右键菜单、⌘K 和 ⌥ 快捷键在触屏上都不存在。没有 `?line=` 且有多条打开的线时，首屏是一串裸链接；一条线第一次打开要显示约 18 秒的 `Drawing the research graph…`（202 Accepted）。

### 最大的缺陷：列表带着整条权益线

`/api/paper/runs` 给运行中的每条运行附上 `live.equity`，即全部分钟权益点（`paper/serve.py:106-116`，调用在 `:406`）。按每点约 32 字节估算，每天增长约 46 KB：运行 3 天时这个响应约 145 KB，每 3 秒一次，约 175 MB/小时。

这是估算：运行 8 现在没有 bar，没有实测到。桌面同样受影响，不是手机专有问题。

### 其他

- 轮询不看 `visibilitychange`：页面切到后台还在拉。
- HTTP/1.1 每个域名 6 条连接，SSE 流会占满。
- 本地翻译是 3.1 GB 的 WebGPU 模型；鸿蒙切片从 jsDelivr 取。
- 手机 Safari 有地址栏时可用高度约 660 px，关键内容要在这个高度内；加到主屏幕后是 844。

## 怎么切换

```
(max-width: 767px), (pointer: coarse) and (max-height: 500px)
```

第二段让横屏手机不会变回 IDE。外壳里有一项「Desktop layout」（只在当前浏览器标签页内记住），偶尔要在手机上用完整 IDE 时打开。

没选的做法：只靠 CSS 自适应（上面已实测不行）；单独的 PWA 或原生应用（第二份产品，违反「简单扁平」）。

### 手机上的尺寸

沿用桌面的颜色、字体和 `--heat-*` 等 token，只加一组手机尺寸和几处手机取舍：所有分区切换都用文字标签（只有横屏 K 线的周期保留轨道按钮）；标签栏用页面底色加一条细线；不画版本状态圆点，「Recommended」直接写成文字；亮色下热力块统一用深色字。尺寸是正文 14、紧凑 13、数值 16、大数字 38 / 26、最小 12（标签栏 11）；触控 44、列表行 52；输入框 16（低于它 iOS 会放大页面）；用 `100dvh`、安全区和 `viewport-fit=cover`。

## 服务降级

第 1 步已做（用户 2026-11-07「先做服务降级」），下表前三行加后台暂停。本机实测：页面 3.07 MB → 1.01 MB，页面没变时再次打开 304、不带内容；70 个版本的 view 1.72 MB → 308 KB；Market 快照 290 KB → 86 KB；运行 6 的流 1.21 MB → 113 KB，事件仍按到达顺序送到；后台 7 秒内不再请求运行列表，回到前台立刻请求一次。

**还剩一处：** 运行中的流每分钟发一次 `readings`，里面仍是整条权益线（`paper/serve.py` 流的循环）。运行 3 天时未压缩约 145 KB/分钟，这是估算。第 2 步手机上只在打开全屏图时连流，桌面要不要改成只发新增的点，到时再定。

| 改动 | 现在 | 之后 | 位置 |
|---|---|---|---|
| 页面压缩和缓存 | 3.07 MB、`no-store`、每次重下 | gzip 约 1 MB，ETag + `no-cache`，没变时 304 | `serve.py` |
| JSON 压缩 | 全部未压缩 | 大响应 gzip，见上表（3 到 6 倍） | `serve.py` |
| 运行列表变薄 | 带整条权益线，3 天约 145 KB/次 | 列表不带权益线（已做）；手机上要线时单独请求并按点数降采样（第 2 步） | `paper/serve.py`，IDE 的权益线改走单独请求 |
| Runs 轮询 | 3 秒 | 手机 15 秒，后台不拉，回到前台立刻拉一次，显示「Updated N s ago」 | `state/paper.ts` |
| 流 | 选中运行就连，账户约 1.2 MB | 手机上只在打开全屏图时连；最多一条 | `state/paper.ts` |
| Market | 30 秒，289 KB | 只在标签可见时拉，60–120 秒，gzip 后 86 KB | `state/market.ts` |
| Research | 进页面就拉 view | 列表用 `/api/lines` 加每条线的读数，点进线才拉完整 view | `MobileShell`、`serve.py` |
| 后台暂停 | 没有 | 所有轮询看 `visibilitychange`，桌面也一样 | `state/` |

运行列表变薄改的是现有读路径，要保持 `paper/serve.py:141` 用 `len(live["equity"])` 判断变化的逻辑，以及 SSE 的 `readings` 不变。没有新增存储字段，账本和市场目录都不动。

**要先实测的一项：每条线的读数。** 复查认为研究页的主要问题是「哪条线接近目标」，只有把读数放到每一行才答得上；用现在的数据一看就是三条打开的线已经满足两个目标（36.92 / 7.08、32.20 / 7.59、26.39 / 7.58）。但读数现在在算图的结果里（`ide/research_graph/layout.py:192`），一条未缓存的线实测要 18–21 秒，共 17 条。做法是 `/api/lines` 从已缓存的 view 取读数，没缓存的显示 `-`，后台逐条算。动手前要测一次全部算完的时间和内存；不增加存储字段。

**不做：** Web Push（要 HTTPS 和服务端）；Service Worker 离线缓存（个人工具不值得）。

**网络路径不在本方案内。** 手机看到的是服务器 `www.vibe-trading.info`（GitHub OAuth、Caddy、oauth2-proxy 之后的 `ide`），不是这台 Mac 的 compose。合并到 `main` 的镜像通过 CI 后会自动发布到服务器，所以手机外壳要整体合并，不能半成品进 `main`。

## 分步

1. 服务降级：gzip 和 ETag、列表变薄、后台暂停。桌面也受益，可以单独合并。
2. `MobileShell` + Runs：切换规则、标签栏、抽屉、权益图、横屏 K 线。动手前先做下面「手机上保留桌面的设计」的盘点。
3. Research：每条线的读数（先实测）、线列表、线、版本。
4. Market 和 News、币种抽屉。
5. Agent。

第 1 步已合并（#2244）。第 2–5 步合成一个 PR，基于 `main`：合并就会发布到手机，只有 Runs 的外壳不该先到手机上。每条线的读数这一轮没有做，研究列表只有版本数和窗口；单独测算完再加。每次重建 Mac 上的 `ide` 容器前先问。

## 手机上保留桌面的设计

用户 2026-11-07：很多在 Web 端优美的界面到了手机端就像变了一个东西，设计细节和形状都被替换了；手机设计到时候要让审美 agent 用审美设计 skill 再过一遍。

- **只改尺寸和密度，不换形状和细节。** 桌面组件的形状、层次和细节要带到手机上。
- **现在的设计稿要重审。** 下面这轮复查的修改替换了桌面的东西：版本状态标记（`RoleMark`）、分段控件的轨道、热力块的涨跌徽标。复查者当时没看桌面组件的真实样子，这些改动不算定稿。
- **做第 2 步之前：** 从真实截图和代码盘点桌面组件，逐项定手机上怎么适配；复查时把桌面截图并排给审美 agent，要它指出哪里被替换了，而不只是判断好不好看。

## 审美复查的结果

实现后审美 agent 对照桌面截图复查。上面第一版方案关掉的谱系画布、散点图、版本表和代码视图，复查认为正是用户说的「被替换」，全部装回；关闭的只剩上表那些操作型功能。Runs 标签没有画线，它的 Backtest 段点开后进版本页并直接显示回测，只在点的时候才读线。
