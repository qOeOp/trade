# 报价导入的月份存在性查询

## 问题与改动

`market import-quotes` 每次导入前按时间筛选整张 `quote`，再按 symbol 分组计数，
用来拒绝请求合约已经存在的月份。Dolt 2.4.2 的原查询计划是 `Table → Filter → GroupBy`。
时间列不是主键的首列，报价历史增大时，这一步会反复扫描其他合约和其他月份。

改为对每个请求合约执行：

```sql
SELECT 1 FROM quote WHERE symbol = ? AND ts >= ? AND ts < ? LIMIT 1;
```

原有主键 `(symbol, ts, agg_trade_id)` 足够；不新增索引、列或持久化状态。
Dolt 2.4.2 的新计划为 `IndexedTableAccess(quote) → Project → Limit(1)`，范围包含
symbol 等值和当月半开时间区间。所有请求合约仍逐一检查，完整收集已存在的合约，
使 `MONTH_EXISTS` 的排序、消息和 missing 保持一致。未请求合约不参与拒绝。
默认 universe 的解析、导入锁、事务、推导、日档校验、提交和发布不变。

## 隔离验证

`tests/market/test_quote_precheck.py` 使用独立的临时 Dolt 服务及数据库：

- 把新查询替换为原来的分组计数作为对照，运行同一导入入口。
- 检查月初包含、月末不包含、月前记录不匹配、未请求合约不阻断和多合约完整拒绝消息。
- 比较完整月份的每条报价、导入返回读数、归档 SHA-256、提交消息和提交数量。
  不比较不同临时库的提交 hash 和运行耗时；它们不是报价内容。
- 对 `SEQUENCE_GAP`、`SCALE_LOSS`、重复月份和缺失 universe 比较完整错误对象；
  源数据拒绝后两个库均无报价、无报价提交、无未提交修改。
- 原生 `EXPLAIN FORMAT=tree` 检查主键范围查找及 `LIMIT 1`。

既有报价测试继续覆盖规则版本拒绝、报价规则、coverage 和导出。
不涉及执行引擎或数据适配变动，不运行研究回放。

## 2026-10-29 隔离测量

同一台宿主机、Dolt 2.4.2、200,000 条临时报价：BTCUSDT 的 100,000 条在查询月前，
ETHUSDT 的 100,000 条在查询月内。每种查询运行 7 次，取中位数；计时包含本地 SQL 往返。
不清理 OS 缓存，不称为冷读，也没有在活动市场库执行原来的全表计数。

| 情况 | 原分组计数 | 新主键存在性查询 | 结果 |
| --- | ---: | ---: | --- |
| 请求合约当月不存在，其他合约存在 | 31.637 ms | 0.402 ms | 均不存在 |
| 请求合约在给定区间存在 | 31.771 ms | 0.448 ms | 均存在 |

两种情况的新计划均使用现有主键和 `Limit(1)`，原计划均扫描 quote。
这些数字只说明存在性查询的改善，不能按比例外推整月导入加速；下载、推导、插入、
提交与 DoltHub 发布还各有耗时。临时原始测量在
`/tmp/trade-quote-precheck-20261029/benchmark.json`，重启或清理后可能丢失。

## 运行队列切换

用户授权在当前月份成功提交后切换。活动月份使用原进程完成，不中断，不启动第二个
写入者。优化代码只有经过隔离验证后才可在成功的月份之间切换；失败仍按既有队列
规则处理。完整成交试导继续等报价队列全部完成，然后只试 BTCUSDT 2025-10 一个月。
