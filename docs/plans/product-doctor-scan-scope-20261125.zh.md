# product-doctor：清单由代码列，范围先声明（2026-11-25）

起因：#3779（架构）与 #3762、#3764–#3766、#3769–#3778、#3706。用户 2026-11-25：「我们需要先处理这些关于诊断的问题 把技能搞好 尤其3779 基本是要把整个doctor重构了」。

改判定的四处由用户同日逐项选定：#3706（复验技能脚本）、#3775（耗时噪声判断）、#3776（报告合并重试）、#3772（全面审计须覆盖每个包）；视角清单选「分 8 组，保留必查」。

## 量到的事实

| 现象 | 读数 |
|---|---|
| 没有按对象的历史 | 2026-11-24 与 2026-11-25 两份记录的 `[any]` 项没有一个对象名能对上，例如 `results` 一次叫 `ledger-identity-vs-binance-archive`，一次叫 `conservation-and-archive-originals` |
| 覆盖表被重试占满 | 2026-11-25：`results` 7 行、`flow/single` 6 行、`storage` 5 行 `no artifact` |
| 主题审计必然“部分” | `report` 对任何审计都按 28 项算缺项 |
| 干净的耗时曲线被拒 | 2026-11-24 `reports` 规模 1/8/64 的九个热读数重算仍判 `noisy`：13.9 s 的散布 2.2 s，比最小两档的差 1.07 s 大 |
| 解包代价 | `git archive origin/main` 加解包不到 1 s |

## 决定

1. **`doctor.py scan`**：从树列出对象（顶层目录，只含 Markdown 或链接的除外；根目录文件算 `root`），两周提交、修复与净行，修得最多的文件，以及每个对象、每个视角在审计记录里最后被跑到的日期。日期从既有记录的覆盖表读，不加存储。
   理由是信任边界：对象清单由 Agent 自己写，就由它决定漏掉什么。
2. **对象写法**：`OBJECT:SCENARIO`。对象是树里的路径、两个用 `+` 连的路径（接口一趟）或树外的 `@name`。以后的记录因此能算出久未审的对象；旧记录的名字对不上，不迁移。
3. **`doctor.py scope`**：主题审计在任何证据之前声明视角与对象，只此一次；`report` 按它算缺项，题为 `Themed audit`；视角要落在声明的对象上才算。`harm` 只声明对象，看有没有成立的探针。没有声明仍按全部算，`Full audit` 的要求不因此放宽，并加上每个对象。
4. **视角**：28 条照旧，分八组，主题对应到组。开头一段通用要求代替逐条加产品名词（#3762、#3773）：先从代码列出模式、数据轨与状态，起止一致的数据与空闲成功的状态不算跑过。
5. **主题次序**：`Find` 改为兜底；`Stop harm` 不计只等授权或已被认领的；`scan` 的久未审日期覆盖没有提交也会坏的面。
6. **二次复查**：移到每个视角与对象都有首趟之后，每个对象至多一次，轻微的不触发。
7. **反驳**：同一对象的说法归一批，每批至多八条，只带对象、触发、应得、实得。

## 没采纳

| 提议 | 理由 |
|---|---|
| `scan` 进 CI、发现“毕业”为 CI 检查 | 没有使用者；修复自带的回归测试就是毕业。新 CI 门要另外授权 |
| 28 条压成 8 条通用维度 | 必查场景是为堵“自述覆盖”加的（IDE 四页其实是同一页，见 [doctor-product](doctor-product-20261123.zh.md)）；压掉就退回自述 |
| `audit-plan.json` 与全部 对象×维度 格子 | 18 个对象 × 28 项约 500 格，每次几乎全是“未做”，没有读者；`scan` 的两列日期足够排序 |
| 缓存解包的树（#3776） | 不到 1 s；共享可写副本还会让探针互相污染 |
| `run` 要求断言（#3776） | 脚本判不出断言是否有意义，靠独立反驳 |
| 为系统级缺陷另设证据（#3776） | `probe()` 是普通 Python，可以起容器、浏览器、发信号；异步不是限制 |
| `recheck --command`（#3777） | 退出码分不清崩溃与断言失败；已有路径是该缺陷的探针加 `--control-tree` 修复的父提交，写进 `fixed` 一行 |
| attach 采集脚本（#3778） | attach 自 2026-11-12 后没有用过，先不加代码 |

## 评审与未证

独立评审找出：视角与对象各算各的、从子目录运行会缩小清单、重试盖住失败、合并提交重复计数、坏探针也算 `harm` 完成；都已修。留着没动的：`run` 以非零退出（`failed`）仍算跑过，这是原有判定，收紧另需授权。

还没有用新流程做过一次真实的主题审计或全面审计。#3762 要的盲测用例没有做。

## 枚举不拟合现有结构（同日补）

用户：「doctor的枚举项目没有搞一些拟合当前项目结构的操作吧 别以后随着项目变化 doctor开始漏列了都没人能发现 做不到的话就尝试agent能力」。查出四处拟合，改法：

| 拟合 | 会怎样漏 | 改成 |
|---|---|---|
| 只列顶层目录 | 改成 `src/` 或 `packages/` 后塌成一个对象，查一处算全查 | 按行数占比切：占全树一成以上的目录拆开，孩子占百分之一以上单列，更小的留在父对象并列出名字；每个受控文件恰属一个对象 |
| 排除只含 Markdown 或链接的目录 | 静默丢弃 | 不排除 |
| 树外对象手写在技能里 | 新服务、新外部方没人加 | 派一个全新子代理从树推出，逐个给文件与行；`scan` 列出历次记录的 `@name`，全面审计报告列出这次没碰的 |
| 必查场景写死（`consumers`、`cost` 等），且拒绝别的写法 | 新读者、新长路径连记都记不进去 | 必查是下限，别的场景照收；同一子代理核对它们漏了什么、哪些已不存在 |

对象按当前树归属，旧记录里已不存在的路径不给任何对象记日期，所以搬家的代码显示为没查过，而不是查过。

局限：树外对象靠 Agent 推，代码只能发现“以前有、这次没有”，发现不了从未列过的。
