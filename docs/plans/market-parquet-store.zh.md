# 市场库整体迁出 Dolt，改成 Parquet 文件

2026-11-02。用户的问题：Dolt 是不是最优的存储？实测（`market-dolt-memory.zh.md`）的结果是：市场库放在 Dolt 里，
体积是 Parquet 的 2.6–2.8 倍；Dolt 服务刚启动就常驻约 11 GB，还会随库变大而涨，16 GB 的机器跑不了 gc，也跑不了第一次克隆。
用户选了"市场库换 Parquet"，之后又说为了一体式设计，整个市场库都迁，不再分大表小表。本文按这个方向设计。
**研究账本留在 Dolt，不在本文范围。** 独立子 Agent 的审阅结论已并入正文，摘要在文末。

## 0. 建议

- 市场库的全部表（`instrument`、`bar`、`funding`、`universe_month`、`metrics`、`quote`、`agg_trade`，以及待合并的爆仓记录）
  都改成不可变的 Parquet 文件，按内容（SHA-256）命名。每个市场版本对应一份"版本文件"（JSON），列出这个版本的全部文件。
- 账本里的 `market_commit` 从"Dolt 提交号"改成"版本号"：新版本的版本号由版本文件的内容算出，任何人都能自己复算。
  账本里被钉住的 7 个 Dolt 提交转换过来，**沿用原来的提交号**，并在市场代码里写死它们对应的版本文件 SHA-256。
- 存储不用 DuckDB 的库文件，也不用 DuckLake，读写都用 pyarrow（依赖里已经有）。版本文件已经是目录，
  再加一个数据库目录就有两处记录"哪个版本有哪些文件"。查询只有 5 处带连接或分组，pyarrow 够用（§1"读"）。
- Dolt 现在替市场库做的检查，一项不少地搬到代码里。另外新写一个 `market review`，任何读者都能对任何版本整体复核（§3）。
  这些检查改了实现，按 AGENTS.md 要用户授权（§8）。
- 公开副本放 Cloudflare R2（用户 2026-11-02 选定，§7）。DoltHub 的 `vincent/trade-market` 冻结，作为归档。
- 分 7 个 PR（§9），先改蓝图。新旧两套不并行运行：转换核对全部通过后一次切换。

## 1. 存储长什么样

```
<市场目录>/
  files/<sha256>.parquet   数据文件：不可变，按内容命名
  files/<sha256>.json      导入回执：不可变，按内容命名
  versions/<版本号>.json    每个版本一份版本文件
  head                     最新版本号
```

**数据文件。** 一次导入写的东西，就是一个或几个文件。列和整数缩放与现在的表完全一样，按原来的主键排序，用 zstd 压缩，
写入参数固定在代码里。

| 表 | 一个文件装什么 | 一年大约多少个文件 |
|---|---|---|
| `bar`（LAST 和 MARK）、`funding` | 一次每日导入的全部合约 | 各约 365 |
| `metrics` | 一个合约一次导入的日子（每个合约各成一个版本，一个合约被拒不撤销其他合约） | 每个合约约 365 |
| `quote`、`agg_trade` | 一个合约一个月（三个合约） | 各 36 |
| `instrument` | 一次观测到的全部条款 | 很少 |
| `universe_month` | 一个月的成员 | 12 |
| 爆仓（待合并） | 一天 | 365 |

加上回执，`files/` 每年增长两三千个文件。Hugging Face 建议一个目录少于 1 万个，以后按 SHA-256 前两位分子目录。

**导入回执。** 现在写在 Dolt 提交信息里的内容（归档 SHA-256、每日读数、报价规则、成交编码、`scope` 合约名单），
改成单独一个按内容命名的 JSON 文件。版本文件按导入先后列出各回执的 SHA-256。这样，读任何一个版本的数据都只需要
它自己那一份版本文件，不用顺着链往回走；回执也不会在每个版本里重复一份。回执条目不记"属于哪个版本号"：
版本号由版本文件算出，版本文件又列着这个回执，记了就成了循环。哪次导入写的，按位置定：第 i 份回执由链上回执多于 i 份的最老版本写入（两次导入的回执可以完全相同，见 `market-receipt-attribution.zh.md`）；
覆盖报告要这个值时，`market.imports` 沿父版本链只读版本文件找出来。

**版本文件。** 一份完整快照，只记这几样：

- `market_schema` 的事实：表结构版本、价格与成交量缩放、成员规则。父子版本之间必须相同。
- 父版本号。转换来的 `l1kfbo4…` 没有父版本，见 §4。
- 数据文件条目：表、合约、导入声明覆盖的区间 `[start_ms, end_ms)`、SHA-256。区间取导入声明要覆盖的范围，
  不是行里的最小、最大时间，因为覆盖核对要靠它算出"没被覆盖的区间"。回执里的 `month`、`from`、`through` 仍然存：
  月初第一天只写名单的导入没有 K 线条目，推不出 `through`。只在一次导入有新行的表才写文件，所以重导当月不会和已有条目重叠。
- 回执条目：SHA-256，按导入先后排列。

审阅后删掉了三样能推出来的：行数（Parquet 文件尾就有）、每个条目由哪次导入写的（就是最早列出它的那个版本）、
`import_seq`（等于版本链的长度）。

**版本号。** 版本文件用固定格式序列化（键排序、`separators=(",", ":")`、UTF-8、不转义非 ASCII），算 SHA-256，
把这 256 位从高位起每 5 位映射到 Dolt 的字母表 `0-9a-v`，取前 32 个字符（160 位）。和 Dolt 提交号同一个字母表、同样长度，
所以账本的 `CHAR(32)`、`LENGTH(market_commit) = 32` 和市场代码里的提交号正则都不用改。

**引用方式。** 现在的 `resolve_commit` 能认分支名、标签、完整提交号和唯一前缀，`--market-at` 默认是 `main`。迁移后：
`main` 和 `head` 都指最新版本；完整版本号和唯一前缀照常能用；`legacy-20261025` 等分支名和标签名不再保留，
因为账本里引用的都是完整提交号（§4 的表）。

**读。** 一个读取模块负责"在某个版本下，读某张表、某几个合约、某个时间区间"：打开版本文件，挑出区间相交的文件，
用 pyarrow 按时间过滤后读出。本机有一个文件缓存目录，缺的文件从公开副本下载。SHA-256 对实际读进来的字节算，
不是"先核对文件、再打开读"，免得核对和读取之间文件被换掉。表在某个版本"不存在"和"存在但为空"要区分：
看 `market_schema` 的表结构版本。导出现在靠 `SHOW TABLES AS OF` 判断，表不存在时直接跳过，不会报错。

市场代码里带 `JOIN` 或 `GROUP BY` 的查询只有 5 处：成员月份连 `market_schema`（`coverage.py:92`、`universe.py:151`）、
`TESTS` 里的成员 K 线检查（`store.py:70`），以及每个合约最新、最早的一条条款（`store.py:677`、`847`）。
其余都是"一张表、按合约和时间过滤"。这 5 处用 pyarrow 的过滤、`group_by` 加连接就能写，所以不引入 DuckDB。
如果第 5 步发现哪处改写后和 Dolt 的结果对不上，再考虑在那一处用 DuckDB 查询读取模块已经读进内存、核对过哈希的
Arrow 表。DuckDB 不能自己打开文件，否则读到的字节没核对过。Agent 在 `/tmp` 里用 DuckDB 直接查缓存目录里的
Parquet 做分析，属于 Agent 的工作，不进产品代码。

## 3. 新的 `market review`

在 Dolt 上，表约束由服务器执行，跟写入的是哪段代码无关；搬到导入代码里，就成了写者自己检查自己。
所以要有一个不依赖写者的复核，任何读者都能对任何版本跑，查这几项：

1. 版本文件列出的每个文件都在，SHA-256 对得上。
2. 每个数据文件都满足原来的 `CHECK` 规则；最新的成员月份满足原来的 3 条提交检查；同表同合约的条目区间不重叠，
   主键跨文件也不重复（写者的 `ENTRY_OVERLAP` 由这里独立复核）。
3. 沿着父版本链：每个版本都包含它父版本的全部条目，而且原样不变；`market_schema` 的事实不变。
4. 历史没有被改写（对应原来的 `HISTORY_REWRITTEN`）：账本引用的每个市场提交都在当前 `head` 的链上
   （没有父版本的 `l1kfbo4…` 除外），公开副本的 `head` 也在本地 `head` 的链上。不用另存"上次复核到哪"。
5. 账本里引用的每个 `market_commit` 都能解析到版本；7 个转换来的版本，版本文件的 SHA-256 等于代码里写死的值。

它只报告问题、不改任何东西，和现在的 `market review` 一样。

## 4. 旧数据怎么迁

1. **转换主线。** 从 Dolt 市场库 `main` 逐表读出，按 §1 写成文件、回执和版本文件。报价和成交按合约、按月读写，内存有上限。
   `main` 的版本号由内容算出，父版本是下表最后一个 `iv711v5…`；之后的导入都接在它后面。
2. **转换被钉住的 7 个提交。** 账本里引用的市场提交（2026-11-02 实测）：

   | 提交 | 日期 | 里面已有的导入 | 引用方 |

   | `gc305h705ocn5fm3lcjjerln283gek2t` | 10-26 | 12 次报价导入 | 3 个证据包 |
   | `6ho8evfcea6p4680qbkeo3mdhaqjscp5` | 10-28 | 25 次报价导入 | paper 运行 1 次 |
   | `1kcbv73ptu3l3clg37g0f0k77c370kk8` | 10-29 | 54 次报价导入 | 97 个证据包 |
   | `dbnggsrnquf09evsncorvngiuan1br6a` | 10-29 | 161 次报价导入 | 92 个证据包 |
   | `pn5bee9mvj18qj1boc5v9b5faotu4ehb` | 10-31 | 211 次报价、109 次成交导入 | 样本外登记 1 条 |
   | `iv711v5dpnv5qr62i5ejk3udk431f5k6` | 11-01 | 211 次报价、190 次成交导入 | 样本外登记 1 条 |

   每个提交各转出一份版本文件，版本号就是原来的提交号。内容相同的文件按内容命名，各版本共用。主线上的 6 个按提交先后串成父子链；
   `l1kfbo4…` 不在主线历史上，作为没有父版本的独立版本，只有"在 `head` 的链上"这一项复核跳过它，其余复核照做。
   子版本必须原样列出父版本的全部文件，所以转换按父版本的条目切分文件：父版本里只到月中的 K 线，子版本保留同一个文件，
   再加一个从月中往后的尾段文件。
3. **为什么必须沿用旧提交号。** 提交号不只出现在成员文件里（`registration/inputs.py:215`），还出现在每个合约导出目录的
   `export.json` 回执里，包括里面的覆盖事实（`market/export.py:534`、`coverage.py:102`）。导出指纹 `export_content_sha256`
   是对这些内容算的，换了号，指纹就变了。输入身份里其余要比对的字段不受影响：`market_database` 在新的市场配置里仍叫 `market`；
   `exporter_source_sha256` 只作来历记录，不参与比对（`registration/comparability.py:17-20`）。
4. **核对。** 对每个转换来的版本：
   - 逐个导入提交比行数：`DOLT_DIFF_STAT`（相对前一个提交）证明它只加行、不删不改，它各表加的行数等于它的文件的行数。
     实测对一个提交是毫秒级（一次 288 行的 metrics 导入，旁边 155 万行没动，0.01 秒）。导入把行补进自己区间之外的地方时
     （例如补某个合约前几天缺的 K 线），这一项点名提交和表报出来。
   - 逐表比行数：Dolt 在对应提交上的 `COUNT(*)` 等于版本各文件的行数之和。
   - 两项合起来，两边的行就相同，不再逐行算哈希（逐行哈希要把 200 多 GB 再读一遍；`DOLT_DIFF_STAT` 隔着几百次导入
     算一对提交，十几分钟没算完）：每个提交只加行；每个文件的行都读自它那个版本或祖先版本，各文件区间不相交、每行都在
     条目区间内，所以文件的行都在 Dolt 里、互不重复，个数又相等。这条论证不依赖导入账户的权限。
   - 每个版本跑 `data_tests`，转换出的整个目录跑一遍 `market review`。
   - 对试验实际用过的合约和窗口，从两边各导出一次，导出指纹必须相同，并且等于账本里记的指纹。这一项要等第 5 步改完读取才能做。

   任何一处不一致，就不切换。
5. **锚定转换结果。** 新版本的版本号由内容算出，可以自证；转换来的旧号不能。7 个旧号各自对应的版本文件 SHA-256，
   写死在市场代码里，经切换那个 PR 审阅。读取模块遇到这 7 个号，先核对版本文件的哈希，不对就拒绝。
   不写进账本：`evidence add` 写的是 Agent 可写的命名空间（`ledger/evidence.py:23`），而且没有代码会读它。
   任何人都能从冻结在 DoltHub 的归档重新转换一遍，核对这 7 个值。
6. **切换。** 新存储成为活动市场。Dolt 里的 `market` 库和 DoltHub 的 `vincent/trade-market` 原样保留，不再写入。
   本机 207 GB 的 Dolt 库和 206 GB 的备份删不删，另外问用户（删除需要授权）。

## 6. 体积与内存（推算）

- 报价和成交实测只有 Dolt 的 1/2.6 到 1/2.8（`market-dolt-memory.zh.md`）。K 线、资金费、metrics 没量过，在 207 GB 里只占几 GB。
  据此估计，新存储装下现在的全部内容约 75–80 GB；被钉住的旧版本大多和主线共用文件。

## 10. 风险与没验证的

- §6 的体积和内存都是推算，第 2、4 步之后实测。
- 写 Parquet 的字节由 pyarrow 版本和写入参数决定。版本升级后，同样的行可能写出不同的字节、不同的哈希。
  这不影响正确性（哈希在写的时候就记下了），只是之后的去重会失效。
- 不上传 R2 的文件只能靠重新导入找回，依赖 Binance 归档不变（§7）。
- R2 在本机线路下只测了 Cloudflare 边缘的速度，开账户后再测一次。
- Dolt 导出与新存储导出逐字节一致，要到第 3、5 步才验证。
- 代码里"manifest"这个词已经用在三处（供数传输、生命周期、`ledger export` 的回放清单），所以新代码里叫"版本文件"（version），不叫 manifest。
