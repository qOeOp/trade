# 市场数据按工厂管理：回执记输入、`market rebuild`、转换来的文件按代码重建

2026-11-03。接 `market-parquet-store.zh.md`（§1、§4、§7、§9 第 6b 步）和 `market-receipt-writer.zh.md`。

用户的原则：导入从公开归档算出来的数据，不靠存数据来管，而靠管"工厂"：写它的代码修订（回执的 `writer`）、
归档的 SHA-256、回执里的规则版本。同一个工厂、同样的输入，写出逐字节相同的文件。版本文件里记的文件 SHA-256
留着，用来核对重建是否得到了同样的字节。只有再也取不回来的观测才存到本机之外（R2）。

用户 11-03 又定：转换来的版本里的 `metrics`、`agg_trade`、`quote` 文件哪里都不存，用当时生成它们的代码重建
（"有了脚本随时能复原出数据，那数据就是不用存储的了"）。#2080 加的"每次发布补传转换文件"由另一个会话撤回
（分支 `fix/market-no-converted-upload`）；Dolt 市场要等转换文件全部重建出相同字节之后才删。

本文定四件事：K 线与资金费的回执记输入（§2）、REST 补的行（§3）、`market rebuild`（§4）、转换来的文件按代码重建（§5）。
要用户定的在 §6，分步在 §7，独立审阅在文末。

## 0. 建议

- K 线导入的回执补记它从父版本之外读到的东西：用到的每个归档（按月或按日，各自的 SHA-256）、这次新加区间里
  进了结果的 REST 行、每个候选合约在 exchangeInfo 里的状态。条款不重复记，它们本来就在本版本的 `instrument` 文件里。
- 发布规则只看回执：一个数据文件上传 R2，当且仅当它是观测表（`instrument`，以及合并后的爆仓三张表），或者它是
  一次没记 `archives` 的 K 线导入写的（转换来的 K 线、本文第 1 个 PR 之前的 K 线）。`UPLOADED` 和 `converted_files`
  都删掉，不加新的标记字段。
- REST 补的行写进回执，每天几 KB。归档后来出现时和 REST 行比对，是 `market review` 里一项随时能算的读数，不另存。
- `market rebuild` 按链从旧到新，对父版本重跑缺文件的那次导入，输入换成回执记的归档和 REST 行，要求重放出的
  **版本号**等于原版本号，再把文件放回市场目录。版本号相同就证明全部数据文件和回执逐字节相同。
- 转换来的 `metrics`、`agg_trade`、`quote` 文件：11-03 用当前代码（main `596a94802`）试了 7 个文件，覆盖最早一批和
  #1929/#1930 之前的导入，SHA-256 全部等于转换版本的条目，回执也逐字节相同（§5）。接着对全部 617 个文件跑同样的核对；
  全部相同，就在代码里写死"这些版本由哪个修订重建"，不再需要任何拷贝。

活动市场目录 `~/.local/share/trade/market`，head 是转换来的 `5sjp1u…`。`market-import` 已停（容器约 1 小时前退出），
切换以来没写过新版本。

| 表 | head 列出的文件 | 大小 | 现在上不上传 R2 |
|---|---|---|---|
| `agg_trade` | 223 | 59.67 GB | 只有转换来的（#2080，正被撤回） |
| `quote` | 211 | 23.56 GB | 同上 |
| `metrics` | 183 | 0.06 GB | 同上 |
| `bar` | 84 | 2.25 GB | 上传（`UPLOADED`） |
| `funding` | 84 | 约 0 | 上传 |
| `universe_month` | 82 | 约 0 | 上传 |
| `instrument` | 1（30 行，都在 10-26 观测） | 约 0 | 上传 |

回执 704 份共 4.3 MB：K 线 85、报价 211、成交 223、metrics 183、表结构升级 2。K 线回执只有
`{import, month, through, universe_rule, scope}`；`scope` 是 30 个合约（含 `币安人生USDT`）。

K 线导入现在读的外部输入（`market/store.py` 的 `_import`、`market/series.py` 的 `stitch_series`、`funding`）：

- `exchangeInfo`：候选合约（再并上有月归档的合约名单 `archive_symbols`）、是否 `TRADING`、条款、首次见到的合约的分类；
- 每个合约 LAST、MARK 的月归档和日归档（按发布的 `.CHECKSUM` 核对），资金费的月归档；
- 公开 REST：缺口、没有归档的日子和合约的分钟 K 线；资金费没有日归档，当月的资金费全部来自 REST；
- 原生日 K 线（`_derived_findings`），只进导入结果，不进文件；
- 当前时间：决定 `through`。

跟随（`market follow`）等最后一个已收盘日的日归档出来才导入（`_bars_ready`，最多等 3 天），所以 K 线的 REST 行
平时只有真正的缺口和没有归档的日子（例如 `币安人生USDT` 10 月的日归档：klines 30 天，markPriceKlines 只有 15 天）。
同一个月再导入时从月初重读，已存的分钟和重读不一致就停在 `MONTH_EXISTS`，所以月内 REST 行和后来出现的日归档
已经在比对。资金费不同：月归档在下个月初才出（11-03 已有 BTCUSDT 2026-10），那时这个月已经封口，没人再比对。

## 2. K 线与资金费的回执记输入（第 1 项）

**做法：导入读外部输入只经过一处。** 把导入用到的外部读取（归档按键取、归档列表、REST K 线、REST 资金费、
`exchangeInfo`、`archive_symbols`、当前时间）收到一个来源对象里。正常导入用真实来源，并把实际给出的东西记进回执；
重建用回执当来源。两条路径跑同一段导入代码。

**K 线回执新增三项：**

| 键 | 内容 | 为什么不能从已存的东西推出来 |
|---|---|---|
| `archives` | `{合约: {"klines" / "markPriceKlines" / "fundingRate": {期间: SHA-256}}}`，期间是 `YYYY-MM` 或 `YYYY-MM-DD`；含月初到 `through` 之间读过的全部归档 | 归档列表随时间变（日归档陆续出、合约陆续加），重建必须恰好用当时那些归档 |
| `rest` | `{合约: {"LAST": 行, "MARK": 行, "funding": 行}}`，只记最后进了结果、且在这次新加区间 `[held, through)` 里的 REST 行，原样记交易所的字符串 | REST 的回答过后可能变，也可能再也取不到 |
| `status` | `{候选合约: exchangeInfo 里的 status 或 null}`，null 是"没上架、只在归档里" | 候选集合和 `TRADING` 决定取哪些行、缺口从哪算；状态不在 `instrument` 表里 |

`[月初, held)` 里的 REST 请求，重建时用父版本已存的 K 线和资金费回答：导入本来就要求重读等于已存的行
（`_compare_bars`、`_compare_funding`），所以这样答出的结果和当时一样，也不依赖更早的回执（接着转换来的月份导入的
第一份回执，前面没有带 `rest` 的回执）。

不记的：

- 条款：变了的已经写进本版本的 `instrument` 文件，没变的等于父版本里最新的那一行。观测时间就是 `instrument`
  条目的区间起点。
- 原生日 K 线：只进导入结果，重建时跳过（它会实时请求 REST，还可能拒绝）。
- 首次见到的合约的分类输入：改成按这次追加的条款行分类（`_item_of`），和之后每次导入一样。原来用 exchangeInfo
  原条目，两者只在 `baseAsset` 不等于"合约名去掉报价资产"时不同；11-03 的 942 个合约里没有一个不同。

**量。** 正常每天一份 K 线回执：资金费 REST 约 30 个合约 × 3 次 ≈ 90 行，约 3 KB；分钟 K 线的 REST 行只在缺口，
一个合约一种价格缺一整天约 100 KB；`status` 30 项。导入会把 head 列出的全部回执读一遍（`versions.receipts`），
`scope` 改成全部合约后 `status` 约 1000 项、资金费约 2000 行一天，第 1 个 PR 量一年后的读取耗时，过大再把它们挪到
回执点名的单独文件里。

**`universe_month` 和 `instrument`。** 成员由本版本的条款、K 线和规则算出，跟着 K 线一起重建，不再上传。
`instrument` 是 exchangeInfo 的观测，留在 R2；重建 K 线导入时它是输入，不是产物。

## 3. REST 补的行（第 2 项）

- **存在哪：** 回执里（§2 的 `rest`）。回执全部上传，所以 REST 行永远在 R2 上，数据文件不用再传。
- **归档后来出现：** 回执不可改，不会因为归档对上了就删掉 REST 行；它们每天几 KB，不值得另设可删除的文件。
  "对上了就算归档产物"是一项读数：`market review` 对每份回执的 REST 行，看现在有没有覆盖它的归档，有就逐行比，
  报出"已被归档证实""和归档不同""归档还没覆盖"三类计数，不同的列出合约和时间。读数不存，谁都能随时重算。
- **不同的怎么办：** 只报告，不拒绝，不改数据。月内的 K 线已有 `MONTH_EXISTS` 拦着；跨月的资金费是新报的，
  出现过再决定要不要停跟随。
- **之后：** `bar`、`funding`、`universe_month` 离开 `UPLOADED`（§4 的发布规则）。

## 4. `market rebuild`（第 3 项，原第 6b 步）

**发布规则（取代 `UPLOADED` 和 `converted_files`）。** 一个数据文件上传 R2，当且仅当它是观测表，或者写它的是一次
没记 `archives` 的 K 线导入。判断只看回执，不加标记字段。读者缺文件一律先问 R2，404 时拒绝并说"按回执重建
（`market rebuild`）"。

**怎么重建一个版本。**

1. 按 head 的链从旧到新，找出列出了本机缺失文件的版本。从旧到新，所以重建一个版本时它之前的文件都已在本机：
   导入锁要求 head 列出的文件齐全（`HEAD_INCOMPLETE`），`data_tests` 和成员回看也会读导入月份之外的文件。
   新机器因此要从头重建整条链（包括转换来的约 83 GB），见下面"新机器"。
2. 对每个这样的版本：取它新加的那份回执；在临时目录里放好父版本，用回执当来源、回执的 `through` 当当前时间，
   重跑那次导入。归档按键取来后，直接对字节算 SHA-256 和回执比，不看缓存里的 `.CHECKSUM`。metrics 的
   "最近缺的日子先等"（`SETTLE_DAYS`）不在重建时重算：恰好用回执列出的归档和 `unpublished`。
3. 重放出的版本号必须等于原版本号；相同就把新写的文件移进市场目录（持导入锁，只加文件，不动版本文件和 head）。
   不同就拒绝，报出 `writer` 和不一致的条目。
4. 归档现在的字节和回执记的 SHA-256 不同，拒绝：Binance 改了归档，这个版本重建不出来。

**用哪一版代码。**

- 回执的 `writer` 是当前代码：在本进程里重放。
- `writer` 是别的修订：拒绝，给出镜像 `ghcr.io/qoeop/trade-service:sha-<writer>` 和在那个镜像里要跑的
  `market rebuild` 命令，由操作者（Agent）去跑，跑完再接着跑当前代码。不在产品代码里编排 Docker：这是 Agent 能做的事。
- `writer` 早于 `market rebuild` 的回执（转换来的、第 2 个 PR 之前写的）：它们的镜像里没有这个命令。由一个经过全量核对的
  修订重建，代码里写死 `REBUILT_BY = {修订, 它覆盖到的最后一个版本}`（§5 第 4 步）；链上这个版本及之前的，都用它。
- 镜像不在：`trade-service` 只在列出的路径变化时构建，且只有 arm64；部署里的导入在镜像里跑，`writer` 就是镜像自己的
  构建提交，镜像存在。宿主上导入时的 `writer` 可能没有镜像，那就按修订重新构建（Dockerfile 按摘要钉住基础镜像，
  `uv sync --frozen` 钉住 pyarrow）。

考虑过的另外两种：一律用当前代码重放（导入代码一改，旧版本就悄悄重建不出来）；检出修订后在宿主上 `uv sync` 再跑
（依赖宿主的 Python 和平台，不是当时写字节的环境）。

镜像按 `ghcr-image-retention.zh.md` 选项 2 从不删除。那份文档说 trade-service 镜像"没有持久记录依赖"，之后不成立了：
删 trade-service 的 `sha-` 镜像要和删运行镜像一样经用户授权（AGENTS.md 那一条在第 2 个 PR 里补上）。

**新机器。** 先从 R2 取版本文件、回执和上传的文件，再 `market rebuild` 按链重放，期间按 `writer` 换镜像。
第一次要下载全部归档（成交与报价约 200 GB，§7 已接受的代价），K 线再加 30 个合约每月 60 个月归档。

## 5. 转换来的文件按代码重建（第 4 项）

**它们是怎么来的。** 两步：Dolt 时代的导入代码把行写进 Dolt，再由 `market convert`（删于 #2080，最后在 main
`d0fec2464`）按 Dolt 的导入提交切成文件。

- **写行的代码。** 回执里没有 `writer`，但 Dolt 提交带时间（转换用的 Dolt 副本 `market-convert-dolt` 还在，11-03 读了
  `dolt_log`，UTC）：

  | 种类 | 导入次数 | 时间 | 期间合并的、改输出的 PR |
  |---|---|---|---|
  | 报价 | 211 | 10-26 06:55 – 10-31 07:17 | #1930（10-31 01:48）之前 210 次、之后 1 次 |
  | 成交 | 223 | 10-29 18:36 – 11-01 15:04 | #1929（10-31 01:40）之前 44 次、之后 179 次 |
  | metrics | 183 | 10-31 12:40 – 11-02 06:52 | #1978 引入，#1994（11-01 03:32）改过等待规则 |

  导入当时是从镜像还是宿主工作树跑的，没有记录，所以按"哪个修订能重出同样的字节"认工厂，而不是按日期猜修订。
- **切分。** `market convert` 每个导入提交、每个合约写一个文件，区间从同月上一次导入的 `through` 起，行按主键排好，
  经 `versions.write_file` 写出；`write_file` 和 pyarrow 自转换以来没变。所以切分就是版本文件里每个条目的区间，
  重建不需要再跑 `market convert`，也不需要 Dolt：用导入代码对条目的区间重写那一个文件即可。

**11-03 的一个月试验（当前代码 main `596a94802`，写到临时目录，脚本在会话草稿区）：**

| 文件 | 当时导入 | 结果 |
|---|---|---|
| BTCUSDT `agg_trade` 2020-02 | 11-01，#1929 之后 | SHA-256 相同，回执相同 |
| SOLUSDT `agg_trade` 2026-07 | 10-30，#1929 之前 | 相同，回执相同 |
| SOLUSDT `quote` 2026-07 | 10-29，#1930 之前 | 相同，回执相同 |
| BTCUSDT `metrics` 2022-01 整月 | #1994 前后之一 | 相同，回执相同 |
| BTCUSDT `metrics` 2026-10-31 一天 | 同上 | 相同，回执相同 |
| BTCUSDT `agg_trade` 2025-10 | 最早一次成交导入（10-29 18:36） | 相同，回执相同 |
| BTCUSDT `quote` 2025-10 | 最早一次报价导入（10-26 06:55） | 相同，回执相同 |

#1929/#1930 只改"Binance 重复编号的后一笔成交"的处理；在它们之前，这种月份整月拒绝，所以早期导入的月份里
没有这种行，新旧代码对它们给出同样的行。

**接下来：**

1. 对全部 617 个文件（成交 223、报价 211、metrics 183）跑同样的核对，只写临时目录，每个文件比完就删；归档缓存约
   200 GB，下载按 Binance 约 3 MB/s 估计要十几到二十小时。结果（相同、不同、拒绝）写成报告，摘要进本文。
2. 有文件对不上，不拿当前代码的新数据顶替（旧试验钉的是这些字节）。先按上表的时间在那一段的修订上重跑；
   还对不上（例如 Dolt 读回来的行序或切分重现不了），在本文里如实写出是哪些文件、差在哪，交用户决定。
3. 全部相同之后，Dolt 市场和 DoltHub 的 `vincent/trade-market` 才能删（另一个会话跟进，删除由用户执行）。
4. 第 2 个 PR 合并后，用 `market rebuild` 本身再对转换版本跑一遍，通过后把那个修订写进 `REBUILT_BY`。
   之后转换版本和普通版本一样按 §4 重建，研究线和旧试验不用换版本。

转换来的 `bar`、`funding`、`universe_month` 是 Dolt 时代带 REST 行导入的，没有记输入，继续上传（共约 2.3 GB）。
过去的日子现在都有归档，可以另外试试它们能否从归档重建出同样的字节；不在本文范围。

## 7. 分步（每步一个 PR，都基于 `main`，一次一个）

1. **K 线回执记输入。** 导入的外部读取收进来源对象；K 线回执加 `archives`、`rest`、`status`；首次见到的合约按追加的
   条款行分类。发布规则不变（K 线照传）。测试：同一次导入用记录重放，版本号相同；改一个归档 SHA 或一行 REST，
   版本号不同。量一年回执的读取耗时。
2. **`market rebuild` 与发布规则。** 重放全部导入种类（K 线、metrics、成交、报价），§4 的拒绝；发布与读取改成 §4 的规则，
   删掉 `UPLOADED` 和 `converted_files`（观测表名单留下）；`ghcr-image-retention.zh.md` 和 AGENTS.md 补镜像依赖。
   测试在临时目录里删文件再重建。合并后跑 §5 第 4 步，另一个小 PR 写入 `REBUILT_BY`。
3. **`market review` 的 REST 读数**（§3）。

§5 第 1 步的全量核对是 Agent 的工作，不进产品代码，现在就可以在后台跑。
#2081（爆仓导入）也动 `market/follow.py`、`market/versions.py`。哪个先合并，另一个就在它之上改；
爆仓三张表按观测表处理，留在 R2。蓝图（`docs/rd/design-code-market`、`design-database-market`）在第 1、2 个 PR 里一起改。

## 8. 风险与没验证的
