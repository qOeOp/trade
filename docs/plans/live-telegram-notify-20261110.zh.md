# Live Telegram 通知：两个新的私有文件（2026-11-10）

连续运行设计（`live-continuous-operation-design-20261110.zh.md`）§3.6 和 §4 第 1 步。用户 2026-11-10 决定：通知发到
Telegram；授权把机器人令牌作为 Live 私有凭证保存，并授权控制程序向 Telegram 发出站连接。令牌由用户在 Live 页面
输入，Agent 不经手。

## 做了什么

- `live/notify.py`：控制程序（`live serve`）开一个独立线程，每 10 秒读一次各运行的页面视图（`live/views.py`
  `run_view`），把新事实发到 Telegram：运行开始、结束（结束状态、停止原因、结果、是否要人处理）、未解决、每笔成交，
  以及 UTC 0 点后第一次检查时的每日概况（读到的最新钱包观测、没有平仓记录的持仓、前一天的成交笔数）。
  独立线程是为了不让 Telegram 的 10 秒超时拖慢运行维护；通知出错只记在状态文件里，不影响维护。
- 三个写操作经固定的 Live CLI（`web-command`）：保存令牌并绑定聊天、发送测试、移除。它们不是账户操作，不进请求日志，
  不拿账户锁，只用 `notify/lock`；发送中的 control 占着锁超过 30 秒就拒绝（`LIVE_NOTIFY_BUSY`）。
- `GET /api/live` 多一个 `notify`：`configured`、`last_sent_ns`、`last_error`（只有 HTTP 状态类别或 `network`）、
  `dropped`。不含令牌和聊天 ID。保存时必须恰好绑定一个私聊，否则拒绝且不保存，所以"已配置"就是"已绑定"，
  不另给 `chat_bound`。
- 新的写路由让旧 control 无法服务新页面，按 `live-web-first-release-20261108.zh.md` 把 `PROTOCOL` 从 1 升到 2，
  并记录 `tests/live/protocol-2.json`。下一次 Live 忙时的发布不能走 Web 先行，等 Live 空闲后成对发布。
- 新拒绝码 `LIVE_NOTIFY_*`，是新增的，不改动已有检查。

## 新增的存储

都在 `LIVE_ROOT/notify/`（0700，属主同 root），不进账本、DoltHub 或 Git，随 Live root 备份。

### `telegram.json`（0600）：`bot_token`、`chat_id`

- **消费者**：发送线程和"发送测试"。
- **独立事实**：令牌是用户给的凭证。聊天 ID 是绑定时从 `getUpdates` 观察到的唯一私聊；Telegram 只保留 24 小时内
  未确认的更新，之后无法再推导，所以要存。
- **为什么现有的不行**：`credentials/` 是币安密钥的不可变版本，带"保存/选中/移除"历史，被运行引用，空闲检查会
  阻止移除；机器人令牌不属于任何运行、可直接覆盖，放进去会让这些检查都要区分种类。部署声明
  （`configuration.json`）只读挂载，页面输入写不进去。

### `state.json`（0600）：`format`、`done`、`attempts`、`closed`、`last_sent_ns`、`last_error`、`dropped`

- **消费者**：发送线程（去重、重试、关闭）和 `GET /api/live` 的 `notify`。
- **独立事实**，运行记录都推不出来：
  - `done`：哪些消息已经送到 Telegram，这是对外的效果。每条消息有固定的键（运行 ID 加事件；每日概况是
    `@daily:<日期>`，运行 ID 不含 `@`，不会混淆）。首次启用时把当时已有的事实全记进去、不发，并记下当天的概况键；
    之后"有没有概况键"就表示"已取过基线"，不另存基线字段。只留最新的一个概况键；运行关闭时删掉它的全部键。
  - `attempts`：等待重试的消息、失败次数和下次时间。发布交接时两个 control 会先后拿到锁，所以重试状态要放在
    共享文件里。
  - `closed`：已平仓结束且资源已归档、不会再变的运行，发送线程不再读它。没有它，连续运行几个月后每 10 秒都要重读
    全部历史运行；而判断"已关闭"本身又要读一遍记录。
  - `last_sent_ns`、`last_error`、`dropped`：页面显示的发送结果。
- **不存**：消息正文、令牌、运行事实的副本。每日概况的成交笔数和钱包都从读到的运行记录现算：一个运行要等它最后
  一笔成交或结束那天之后的概况发出后才关闭；持有最新钱包观测的运行不关闭。所以算概况时需要的运行总还在读。
- 移除通知时两个文件一起删除，再次启用重新取基线。

### `lock`

空文件，`flock`。发送线程用非阻塞锁，拿不到就跳过本次，所以同时存活的多个 control 只有一个发送。

## 送达语义

- 严格按顺序：一条消息在等重试时，后面的都不发；每日概况排在最后，所以它算前一天成交时，之前的成交消息都已处理。
- 网络错误、5xx 和 429 按 10 秒起倍增、最长 5 分钟的间隔一直重试，不丢；Telegram 以其它 4xx 拒绝的消息丢弃并计入
  `dropped`（令牌失效时每次检查只试一条，不会空转）。一次检查遇到失败就停，最多发 5 条。
- 至少一次：发送成功后、写状态前进程中断，下次会重发这一条。
- 只看当前事实：一个运行在两次检查之间（或重试等待中）开始又结束，只会收到"结束"。页面视图每个运行只保留最后 200 条
  订单事件，积压超过 200 条时更早的成交不会单独通知，也不计入概况。首次启用时读不到的运行，之后读到时其已有成交会
  作为新消息发出。
- 令牌不出现在日志、argv、环境变量、异常文本或任何读接口里；失败只记 HTTP 状态类别（如 `http_4xx`）或 `network`，
  不记 URL。

## 独立评审

按 AGENTS.md，存储字段由一个独立子 Agent 评审（只读，2026-11-10）。结论和处理：

- `bot_token`、`chat_id`、`done`、`attempts`、`closed`、`last_sent_ns`、`last_error`、`dropped`、`lock`：保留，
  理由同上。令牌放 `notify/` 而不是 `credentials/`：同意。
- 初稿的 `baseline_ns`：只当标志用，改为由概况键推出，已删。
- 初稿的 `fills`（按日成交计数）和 `wallet`（最新钱包）：由运行记录派生，改为上面的关闭规则后现算，已删。
- 指出的缺陷已修：`http.client` 的协议错误未被归为失败会导致每 10 秒重发；固定 6 次后丢弃会在约 5 分钟的断网中
  丢掉未解决告警，改为只丢被 4xx 拒绝的消息；等重试的消息会被后面的消息超过，改为严格顺序；`done` 无限增长，
  改为关闭时删运行的全部键并只留最新概况键；写操作可能被发送线程阻塞很久，改为最多等 30 秒后拒绝；未解决的键含
  终止事件时间会重复告警，已去掉。
- 未改、记在上一节：200 条事件窗口、短运行没有"开始"、首次启用时读不到的运行；停在 `prepared` 或预检状态的运行
  永不关闭，每次都会读，只是性能代价。
