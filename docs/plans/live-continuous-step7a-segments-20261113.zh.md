# 连续运行第 7a 步：`live compare` 按交易启动分段，加每周汇总（2026-11-13）

依据：`live-continuous-operation-design-20261110.zh.md` §3.6、§4 第 7 步（"无需授权；用已有运行回放"），
圆桌 D 结论（`live-entry-hold-20261113.zh.md`）把暂存统计放进第 7 步。只读，不进账本，不改归因规则、原因和拒绝。

## 为什么要分段

一个永不结束的运行会重启。每次交易启动（不是持仓保持的启动）重新预热、重建源码，源码状态从这一次的 T 开始。
`live compare`（#2823）用第一次的 T 回放整段，重启之后的决策必然对不上。

## 做了什么

- **分段**：日志里每个进程从它的 `connecting` 开始（没有 `connecting` 的旧日志算一个进程）。有 `warmup` 的进程是一段
  交易启动；只保持持仓、没预热的进程不算。
- **一段的内容**：
  - 这一段的 T；
  - 这一段 `started` 时观察到的钱包，作为起始资金；
  - 这一进程写的日志行和证据行，按 `wall_ns` 在本进程开始到下一进程开始之间；
  - `ts_init` 在 T 到下一进程开始之间的订单。
- **每分钟结果**：Nautilus 缓存在 Redis 里跨进程保留（`flush_on_start=False`），`minute_result` 是从第一次启动累计的。
  交易启动要求账户为空，所以本进程第一个已知结果就是继承下来的部分。这部分已经在起始钱包里了，减掉。缓存被清空时
  第一个结果是 0，同样成立。
- `live compare` 默认比最近一段，`--segment N` 比第 N 段（1 是第一段）；没有这一段时用已有的 `LIVE_COMPARE_EMPTY` 拒绝。
- **汇总** `measures`：`--from/--to`（UTC）只限定按决策时间计入的组，回放仍从段首的 T 开始。
  - 未成交的入场单：回放成交而 Live 没成交；
  - 部分成交：Live 成交量小于下单量；
  - 平均不利滑点：成对成交的 `price_bps`，买高卖低为正；
  - 费用：Live 手续费、回放手续费和两者之差；
  - 权益变化：窗口内首尾分钟，Live、回放和两者之差；
  - 暂存：`entry_held` 数、从暂存到发出或拒绝的 `held_ns` 中位数和 p90、因暂存结束的运行数。
- 输出多了 `segment {number, of}` 和 `measures`，原有字段不变。

## 验证

- `tests/live/test_compare.py`：
  - 重启三次的运行：第一段交易，第二段只保持，第三段从 `RESTART` 交易。默认比较第三段，它是第 2 个交易启动；
    回放的 T、终点和起始钱包都是这一段的，只有本段的订单、K 线和预热；
  - 第一段的窗口、钱包和订单单独取；
  - 不存在的段被拒绝；
  - 汇总各项在窗口内外的计数；
  - `--from/--to` 按 UTC 读。
- 反向对照（每次改完都恢复）：
  - 不减继承结果，权益首值变成 58.5，测试失败；
  - 不按段过滤订单，订单数变成 6，测试失败；
  - 不按段过滤证据，预热摘要对不上，测试失败。
