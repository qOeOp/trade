# Live 证据包的 metrics 退订行：存储字段审阅

2026-11-15。修复 `live-evidence-funding-metrics-field-review-20261115.zh.md` "仍然留下的"第一条：源中途退订 metrics 时没有任何记录，`live compare` 会把退订之后档案里的每一行都算成缺失。按 AGENTS.md 的要求，加字段前先由一个独立子代理审阅，审阅只读代码，基于 `origin/main` d3e2f0fd4。

## 结论

新增 Live 证据包行 `metrics_unsubscribed`，字段为 `wall_ns`、`kind`、`instrument_id`，不存其他字段。只在源确实跟随着该合约的 metrics 时写入（`engine/live_source.py` 的 `_metrics_unfollow`）。

这一行只在 Live 私有目录的 `evidence/market.jsonl` 里，不进研究账本、DoltHub 或 Git。

## 审阅

- **谁读它**：
  - `live/compare.py` 的 `run_record` 把它和 `metrics` 行一起交给比较；
  - `replay.comparison.compare_metrics` 按合约算出跟随区间：从收到的第一行起，到下一次退订的 `wall_ns` 为止（不含）；退订之后收到的第一行开始下一个区间；最后一个区间到比较窗口结束；
  - 只有落在跟随区间里的档案行才算预期的行。
- **独立事实**：源在什么时刻不再要 metrics。现有的数据都给不出来：
  - `Feed._metrics_unfollow` 只删掉跟随状态，日志和证据包都没有记录；
  - 回放也不记录源读了哪些 metrics。就算记录了，它给的也是回放里的退订时刻；两边决策一旦分岔，这个时刻正好不同。
- **为什么不能推出来**：曾考虑不加字段，把每个合约的预期截在最后收到的那一行，就像停止后窗口截在最后一根 K 线。这样会藏住真正缺在尾部的行：`Feed._metrics_step` 在没有持仓量时跳过的行，正是"缺失"要报告的。这样做也仍会把"退订到重新订阅"之间的空档算成缺失。
- **为什么放在证据包而不是日志**：
  - 这一行和它所界定的 `metrics` 行写在同一个文件，失败时也同属 `market` 这一部分（`Evidence._append`、`_fail`），两者一起丢或一起在；
  - 写在日志（`events.jsonl`）里，可能只丢掉退订这一行，缺失又会被误报回来；
  - `segment()` 和 `cut()` 本来就按 `wall_ns` 过滤证据行。
- **字段**：`instrument_id` 加 `wall_ns` 就够了。Live 的 Feed 用的是墙钟（`Feed._metrics_clock`），迟到检查本来也用 `wall_ns`。
- **边界**：
  - 一行在退订之前就该送达、但还在重试、因此没送到，算缺失。回放会在它的 `ts_init` 送达这一行，这是真实的差异。
  - 送达时刻落在 5 分钟整点，这也是 K 线收盘的时刻。源若在那根 K 线上退订，同时送达的那一行可能显示为缺失。这个读法是如实的，写在了 `compare_metrics` 的文档字符串里。
  - 停止：窗口已经截在最后一根 K 线，停止时写下的退订落在窗口之后，没有影响。
  - 重启：每个进程都有新的 Feed，`segment()` 按 `wall_ns` 分段。
- **重新订阅**：不另存记录。退订之后收到的第一行就是新区间的开始，和运行首次订阅时"从收到的第一行起"是同一条规则。要把这两处的盲区都补上，需要再记录订阅时刻，那是另一项决定。

## 审阅附带的两个条件

1. 退订之后不能再有行送达，否则这一行会被当成重新订阅。审阅指出，在同一个线程里也可能出现这种情况：`Feed._metrics_tick` 遍历的是跟随状态的副本，如果某一行的 `on_data` 退订了另一个合约，那个合约当拍已读完的行仍会送出。现在的处理：`_metrics_tick` 每送出一行之前，都先确认该状态仍是被跟随的那一个；`tests/engine/test_metrics_feed.py` 对此加了测试。Live 的定时器回调是否可能在另一个线程上跑，没有用原生方式探查过。
2. 本文件即是这条记录。旧审阅里"仍然留下的"那一条已改为指向这里。
