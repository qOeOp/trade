## 推导规则（写入数据合同）

- 输入：每日 `aggTrades` 文件，字段 `agg_trade_id, price, quantity, first_trade_id, last_trade_id, transact_time, is_buyer_maker`，数量单位已是 BTC。
- `is_buyer_maker = true`：卖方吃单，`price` 为该时刻的最优买价；`is_buyer_maker = false`：买方吃单，`price` 为该时刻的最优卖价。每一侧保持到该侧下一笔成交。
- 一侧过时导致买价 ≥ 卖价时，以较新一侧为准，另一侧按合约最小价位推开一格；逐日计数写进导入回执（四个样本日此类秒占 1%–6%）。
- 挂单量：不可观测。QuoteTick 两侧数量统一填市场库 `instrument.max_quantity`（即 exchangeInfo `LOT_SIZE.maxQty`，BTCUSDT 为 1000），含义是"不模拟深度、按最优价全成交"，写进模型声明；不新增 `MARKET_LOT_SIZE` 字段。
- 时间：`ts_event = ts_init = transact_time × 1e6`，声明"按交易所成交时间回放、零额外接收延迟"。同毫秒多笔按 `agg_trade_id` 顺序。跨日：每一侧从前一日末状态延续，导入时多读前一日；首个导入日的开头两侧未齐前不出报价。
- 这是一个**声明的近似报价模型**，不是盘口观测：成交价是成交瞬间所在一侧的最优价，但两次成交之间该侧的真实报价可能已经移动；aggTrades 把同一吃单在同一价位的成交聚合为一条，不含盘口状态。已验证误差（对 Tardis 免费公开的 Binance 真实 bookTicker，四个月初日）：逐秒中价绝对偏差中位数 0.00 bps、p99 0.2–0.7 bps；每分钟最低买价与最高卖价 p99 0.02–0.7 bps。误差主要方向是盘口偏宽（买价偏低、卖价偏高），但不是单向：过时一侧也会落在真实点差之内（2025-10-01 买价 p99 +0.009 bps、最大 5.8 bps），对被估值一侧偏乐观、延迟触发。验收因此增加一项：在每月 1 日用真实 bookTicker 跑同一强平夹具，比对触发时刻、成交价与账户结果。

## 实施顺序

每步独立可验，前一步的产物是后一步的输入。

1. **先量一天。** 用 2025-10-01 跑完整链路（下载→校验→推算→抽稀→导入→导出→回放），记录报价条数、库体积、导入与导出耗时，并与同日 Tardis 免费 bookTicker 复核一次偏差分布，再决定全年与多标的的节奏。
2. **市场库报价表。** 新表存抽稀报价（symbol、ts、bid、ask、整数定标；数量由导出器按规则填，不入库）、来源标识（归档文件名与 SHA-256、推算器身份、过时侧调整计数）。按 AGENTS.md 先做独立子代理字段评审并记录在本目录。导入沿用 `market import` 的纪律：按月、一次事务一个提交、只增不改、通过验收项才落库。
3. **导入验收项。** zip 与 `.CHECKSUM` 一致；CSV 完整读到末尾；`agg_trade_id` 日内连续且与前一日末尾衔接（`SEQUENCE_GAP`）；`transact_time` 非减；推算后无买价 ≥ 卖价；价格精确落在存储定标。任何一项不过即整月拒绝，不补行、不改值。读数（随导入结果打印、不作拒绝阈值）：每合约成交数、状态变化数、过时侧推开次数、有成交的分钟数、成交间隔最大值与 p99。原计划的「每日 1440 分钟都有报价」改为读数：报价是向前延续的，分钟覆盖只反映活跃度，低活跃度合约的适用性按下方“低活跃度适用性边界”逐合约、时段和用途验证，缺证据明确报告。每月 1 日与 Tardis 免费 bookTicker 的逐秒比对作为单独的核对步骤，不在导入里下载。
4. **导出与运行环境。** 导出器增加 QuoteTick 写入（数量填 `instrument.max_quantity`）；运行器增加"报价撮合 + 原生强平"环境：L1 venue 读显式报价（不需要派生报价）、**`bar_execution=False`**（现有合同是 L1 venue 加 `bar_execution=True`，分钟线会继续按开高低收合成路径驱动撮合，必须显式关闭，分钟线只供策略信号）、`liquidation_enabled=True`、显式 `default_leverage=1` 与 `StandardMarginModel`（或按策略条款显式映射）、`margin_init/margin_maint` 取 Binance 该策略最大仓位所在档位的费率，模型声明写入运行合同。接入时用原生探针验证同一时间戳上报价、分钟线、资金费与策略回调的处理顺序。新 CI 镜像。
5. **修比较器。** 强平订单编号带随机 UUID，`engine.compare` 按原始订单编号遍历导致报告指纹不稳定（Codex 发现）。改为按确定性场所订单身份对齐后再编号，保留订单关联与经济字段。这是现有缺陷修复，属于产品代码。
6. **验收回放。** 用已知会爆仓的工程场景做多空各一次：触发、先撤挂单、只减仓 IOC、跳空负权益如实进账户与报告；同一输入重放一致；健康仓位不误触发。
7. **报告 skill。** `nautilus-report-analysis` 增加一段规则：对每笔成交（含 LIQUIDATION），取 Binance `bookDepth` 当分钟 ±1% 价带挂单量，标出成交量超过该深度的笔数；说明本环境按最优价全成交、不模拟深度。

## 报价表字段评审（2026-10-24，独立子代理，按 AGENTS.md 三问）

评审对象：方案 A（新表 `quote` + 可选 `quote_source` 回执表）与方案 B（只存来源哈希、报价由导出器直接从归档生成）。结论：**采用 A，去掉 `quote_source`，规则版本写进导入提交信息**（A2）。

- 否决 B：AGENTS.md 把市场数据列为"不可重现的观测"，`bar` 同样可重下却入库，先例一致；若 Binance 改动或撤下归档，只存哈希的提交将无法再生产输入（bookTicker 归档已在 2024-04 停更，这是真实风险）；B 还把 310 GB 下载与推算成本挪到每次导出。"存一次、不存推导"针对的是已存数据的推导，aggTrades 并不入库，抽稀报价是回放消费的最小确定形式，与只存 1 分钟线同理。
- `quote` 三问：消费者是 `export.py` 的 QuoteTick 写入（按提交 `AS OF` 读常量 `ts` 区间）；记录的独立事实是 Binance 成交对最优买卖价的证据（`bar` 只有高低收、无买卖侧）；无法由现有表推导，因为 aggTrades 不入库。
- 字段：`symbol`、`ts`、`agg_trade_id`（同毫秒内区分三条抽稀行、可对重下归档逐行核验，不造序列号）、`bid`、`ask`（×10^price_scale）。**主键改为 `(symbol, ts, agg_trade_id)`，不建二级索引**：原方案 `(symbol, agg_trade_id)` 加 `ts` 索引会让十亿行表体积近乎翻倍，且合约代码复用时 aggTrade 序列若重启会冲突；导出按主键常量区间扫描，与 `bar` 一致。同一 aggTrade 产生的三条抽稀行合并为一行。
- 不存：挂单量（导出时填 `instrument.max_quantity`）；逐行"推开过"标记（无消费者，且无法事后区分真实一格点差）；`quote_source` 表的输入行数、输出行数、调整次数（导入即检、`COUNT(*)` 可得、属质量读数随导入结果打印）。**修正（2026-10-24 晚，Codex 审阅）**：归档 SHA-256 是输入身份，消费者是独立审计（没有它就无法判断重下的归档是否仍是当初的输入）；每日归档哈希写进该次导入的提交信息（`archives`，与 `quote_rule` 同处），不建表、不加字段。**再修正（Codex 第二轮）**：每日读数（成交数、状态数、过时侧推开次数、最大成交间隔）也写进提交信息（`readings`），审计无需重跑即可核对转换；原始归档保留在持久目录 `~/.local/share/trade/market-archive-cache`（导入时传 `--cache-root`），其备份与 Dolt 备份一并由用户安排，哈希在提交信息里可核对原件是否仍是当初的输入。
- 规则版本 `quote_rule` 作为导入提交信息 JSON 的一个键，像 `scope` 一样每次导入必须相同否则拒绝；不加 schema 版本、不改 `market_schema` 触发器。
- 评审指出的两处修正已改入本页：挂单量来源应为库内 `instrument.max_quantity`（`LOT_SIZE.maxQty`），不是 `MARKET_LOT_SIZE`；跨日两侧状态延续、导入多读前一日。
- 评审附带条件：建表前实测 Dolt 在 2 千万行/标的年的插入速率、库与 `dolt_backup` 增量、导出读取时间与导入内存（本机受内存约束），并另量一个低活跃度币种；新增提交测试只做最新月份的全键查找；Dolt 不达标时的退路是缩少标的或月份的 A，不是 B。

建表 DDL：

```
CREATE TABLE quote (
  symbol VARCHAR(40) NOT NULL,
  ts BIGINT NOT NULL,            -- transact_time, UTC ms
  agg_trade_id BIGINT NOT NULL,  -- 产生该状态的 aggTrade；区分同毫秒的行
  bid BIGINT NOT NULL,           -- × 10^price_scale
  ask BIGINT NOT NULL,
  PRIMARY KEY (symbol, ts, agg_trade_id),
  CHECK (bid > 0 AND ask > bid)
);
```

## 执行环境进入运行身份（2026-10-25，Codex 发现，用户授权）

Codex 指出：第 4 步把环境选择放在策略源的 `QUOTE_EXECUTION` 声明里，而 `check_comparable` 只比镜像摘要、有效配置（runtime_contract、窗口、symbols、account 合同）和输入身份，声明不在其中，同镜像同数据同窗口下一边报价强平、一边 K 线环境会被当作同条件通过。核实属实，且有效配置里的 `account` 合同是常量，报价模式下运行记录仍写 `bar_execution: True`，对环境失实。根因：注册时的环境身份来自镜像 `--describe` 探针，探针不加载策略，放在源里的声明永远进不了身份。

改法（合同升到 `replay-contract@v7`）：

- 执行环境改为运行器参数 `--execution bars|quotes`，报价环境再带 `--initial-margin`、`--maintenance-margin`（十进制，0 < 维持 ≤ 初始 < 1，`MARGIN_RATES_INVALID`；K 线环境不收费率）。参数与窗口、symbols 一样经 `runner_argv` 传入，注册、探针、回放走同一条路。
- 有效配置的 `account` 合同按环境真实生成（`engine.execution_account`：撮合方式、强平开关、保证金模型、两档费率），于是探针、执行绑定校验、`check_comparable`、复现比对一行不改就区分两种环境；同一镜像同输入下两种环境或不同费率都是 `COMPARABILITY_MISMATCH`。
- 删掉策略源的 `QUOTE_EXECUTION`/费率声明；源里再出现即 `ENVIRONMENT_DECLARED` 拒绝。摘要新增 `execution` 键，limitations 按环境陈述。
- 旧 v6 镜像与账本里的 v6 候选不再兼容（重构期不留兼容层）。
- **正式回放已完成（2026-10-25，#1669 合并后的 v7 镜像）**：`replay explore -- --symbols BTCUSDT --start 2025-10-09T00:00:00Z --trade-start 2025-10-10T00:00:00Z --end 2025-10-12T00:00:00Z --execution quotes --initial-margin 0.05 --maintenance-margin 0.025`，探针为第 6 步的 10 倍多头（源里不再有环境声明）。账本探索试验 198（passed），镜像 `sha256:8d373a4e…`、合同 `replay-contract@v7`、市场提交 53tgna1p；执行绑定里的 `account` 合同记为 `execution: quotes`、`bar_execution: false`、`liquidation_enabled: true`、`StandardMarginModel`、费率 0.05/0.025。结果与工作树原生回放逐项相同：10-10 00:00:59.999 以 121,601.5 买 8.224 BTC，21:13:05.183 被 `LIQUIDATION-BINANCE-…` 以 112,535.40 全平，期末权益 24,429.15 USDT，完整性检查通过；limitations 按报价环境陈述。本机坑：Docker Desktop 的凭据助手（`credsStore: desktop`）让匿名拉取 GHCR 公共镜像卡住，产品 300 s 超时报 `RUNTIME_UNAVAILABLE`；用一个没有 `credsStore` 的 `DOCKER_CONFIG` 目录即可，14 s 拉完。

## 低活跃度适用性边界（2026-10-25，用户已确认）

低活跃度合约是否适用于强平研究，按具体合约、UTC 时段和实际使用场景（杠杆、敞口与强平情景）验证，并标明市场提交、报价规则和运行镜像。推算报价的买卖两侧各自沿用旧值，成交稀疏时可能陈旧；误差可使强平提前或延后。一分钟决策、数据覆盖完整、原生回放通过，均不能证明分钟内报价适用。成交间隔、活跃分钟和过时侧调整次数只作诊断，不等于逐侧报价年龄，也不设未经校准的准入阈值。应在有独立真实买卖报价的范围内核对来源、时间语义、覆盖及误差分布，并在策略、配置和镜像相同、只替换报价输入的原生回放中比较强平是否发生、时刻、价格和账户结果；样本内未强平不证明其他情景。BTC 或少数日期的结果不外推到其他合约、时段或用途。证据不足就逐项报告未验证范围、缺失证据及受限结论，区分“技术上可运行”和“已有适用性证据”；不自动删币、缩窗、更换输入或调整产品指标资格，不补造或过期替换报价。若缺口阻断目标研究，由用户选择补证据或调整研究范围。执行规则见 [research-start 的就绪检查](../rd/design-skill-research-start.zh.mdx#def-file-research-start-references-readiness-md)。

本项仅同步文档、research-start 与 nautilus-report-analysis 的证据边界和针对性评测，并让 research-round 在路线内遇到相关数据异常时调用既有就绪规则；不增加自动准入分类、阈值、字段或引擎逻辑，不改 Nautilus，不修改历史市场数据或封存运行。既有成交间隔 p99 是逐日计算、返回汇总取最大日 p99，日内间隔不覆盖跨日空档，也不是逐侧报价年龄；它只能帮助定位待核对时段。保留既有深度快照的两分钟匹配规则，不能借其作为报价适用性阈值。

规则确认不补出证据：现有 BTC 抽样及历史低活跃度抽稀测量都不能代替当前完整报价模型逐合约、逐时段的实际适用性验证。未覆盖范围继续列在设计文档的数据缺口中；本项评测只验证 Agent 行为，不代表任何真实低活跃度合约已通过。
