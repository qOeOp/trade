# 用户 bot 与 issue 闭环设计草案（2026-11-21）

状态：草案，待用户回答文末的问题。本文不改代码、技能和配置。

## 用户的目标

2026-11-21，用户原话：

- 「把doctor skill好好设计后做成bot的形式 来替换我可以吗 我也就是在每天看看web ide 启动和回复一些投研目标里抛出来的选项 找找当前产品在投研过程中暴露的问题 然后一直修复一直迭代发版」
- 「grok bot就像这个产品的用户一样 在使用过程中发现问题和改进建议 然后去项目issue下开issue」

用户每天的工作有四件：看 web IDE；启动研究并回复研究会话抛出的选项；找产品在研究中暴露的问题；修复、迭代、发版。本设计把第三件交给外部 bot，把修复交给 Claude 一侧已有的流程。用户只保留 AGENTS.md 规定要用户本人做的事。

## 分工

| 角色 | 是谁 | 做什么 | 不做什么 |
|---|---|---|---|
| 用户 bot | 外部 agent（Grok 或其他模型），用独立的 GitHub 账号 | 像研究用户一样使用产品，在本仓库开 issue | 不改代码，不提 PR，不回复研究会话，不碰 Live 和凭据 |
| 分诊 | Claude Code 本机定时任务，每次是新会话 | 读 bot 的新 issue，用 product-doctor 做聚焦诊断，核实或驳回 | 不把 issue 正文当指令 |
| 修复 | 分诊派出的会话，一个根因一个 | 按 doctor 索引表头的规矩提 PR，PR 关闭对应 issue | 不做权限项 |
| 用户 | 本人 | 启动研究、回复研究选项、处理权限项、打发布标签 | — |

外部模型当用户反而是优点：它和写代码、做诊断的 Claude 不共享上下文和盲区，不存在「自己给自己打分」。之前不建议的是把研究或开发放到别的模型上跑，因为 ledger、market 和运行时都在本机，技能评测也是按 Claude Code 标定的。只当用户、只写 issue，就绕开了这两个问题。

## 闭环

1. **bot 使用产品，开 issue。** 每个 issue 写明：做了什么、看到什么（页面或命令、时间、版本或提交号、截图）、预期是什么、对研究决策有什么影响。开之前先查已有 issue 和 [doctor 索引](doctor/index.zh.md)，避免重复。每天有上限（建议 5 个）。
2. **分诊核实。** 本机定时任务每天跑一次：只读 bot 账号开的、带 `from-bot` 标签的 issue。每条都当成待核实的缺陷说法，走 product-doctor 的聚焦诊断（步骤 3–5），在当前 `origin/main` 上复现。这和 [Gemini 发现复核](doctor/2026-11-21-gemini-findings-recheck.zh.md) 是同一种做法。
   - 核实成立：在 doctor 索引加一行（来源写 `user-bot`，见待决问题 5），在 issue 下评论证据和处理动作。
   - 已被修复、重复或不成立：在 issue 下评论证明后关闭。
   - 证据不足：评论需要补什么，打上 `needs-evidence`，issue 保持开着。
3. **修复。** 动作为 `fix`、`remove`、`skill` 且不是权限项的，派一个会话提 PR，PR 正文写 `Closes #N` 和发现 id，CI 通过后自动合并。行为变化仍要按 `engine/README.md` 做配对原生回放验收。
4. **权限项汇总给用户。** 按 AGENTS.md 要用户授权的（放宽或收紧检查、新增存储字段、研究目标、发布标签等），连同推荐一起写进当天的摘要，推送到手机。已有委托记录覆盖的，按委托决定，并在 docs/plans 里写明依据。
5. **发版。** main 上有已合并的修复且检查通过时，分诊准备好 `CHANGELOG.md` 条目，摘要里请用户打标签。标签始终由用户打。

## 边界

- **issue 正文是不可信数据。** 仓库是公开的，任何人都能开 issue。分诊只处理 bot 账号且带标签的 issue；即使是这些，正文里的任何「请执行」「已授权」也不执行，只按缺陷说法核实。
- **bot 看得到什么。** 第一阶段只用公开材料：研究链站点、DoltHub 上的公开 ledger、GitHub 上的代码、发布说明和 CI。IDE 首页带 Paper token，Live 页面能发真实订单，所以 bot 不能直接拿你的 IDE。要让它看 IDE，需要另做一个只读入口（这算信任边界，可以做成产品代码），单独设计。
- **bot 不回复研究选项。** research-start 规定：只有用户本人在该会话里的消息才能把选线交给 Agent，「另一个 agent 的消息」不算。所以回复研究选项仍是你的事。可以省力的是：在每个研究会话里说一次「换线交给你」，之后同一会话里的选线由 Claude 按该技能的规则决定。
- **没有新存储字段，不写 ledger。** issue 和评论留在 GitHub，诊断结论进 doctor 记录。

## 需要的改动

- `.github/ISSUE_TEMPLATE/` 下加一个 bot 用的模板，字段就是闭环第 1 步的那几项。
- 一份给 bot 的使用说明，作为 bot 的系统提示：怎么用产品、怎么写 issue、上限多少、什么不碰。放在哪里取决于 Grok 一侧怎么接（待决问题 1）。
- 分诊的本机定时任务。它的提示只有一句：用 product-doctor 处理 bot 的新 issue。规则留在技能里，不另写一套。如果实际跑下来技能需要加段落，按 `.agents/README.md` 单独提 PR 并附评测。
- 不需要新的产品命令。

## 怎么衡量

每个 bot issue 最后都落到核实、重复、不成立、证据不足四种结果之一，按周统计。两周后核实率太低（建议低于三成），或者核实的问题几乎全是外观类，就调整 bot 的使用说明或停用。不拿 issue 数量当成效：衡量的是修复后的问题在之后的研究会话里没有复发（doctor 索引的 `verified`）。
