# Live 连续运行设计（2026-11-10，用户逐条决定后改写为单个运行）

## 1. 问题

用户要让一个策略在真实账户上连续跑几个月、几年，像回测那样。现在的 Live（`engine.live`）按小额工程试验设计，
一次运行最多 24 小时，实际能交易的时间更短。以下事实以 `origin/main` bf447f4ec 为准。

| 限制 | 现在的行为 | 位置 |
| --- | --- | --- |
| 时长上限 | `duration_seconds` 必须在 1 到 86400 之间，超出时 runner 以 `LIVE_MANIFEST_INVALID` 拒绝；到点走 STOP：撤入场单、平仓、保护单保留到平 | `engine/live.py:69`，`engine/live_session.py:106`，`engine/live_lifecycle.py:118-150` |
| 断线即结束 | 任何来自 BINANCE 的 `DISCONNECTED` 都调用 `lose_connection`：撤入场单、停策略、停节点、记为未解决；之后的 `CONNECTED` 不恢复交易 | `engine/live_lifecycle.py:67-71`，`engine/live_session.py:181-198` |
| 断线期间一律拒单 | 源码的下单、撤单、平仓和 Observer 自己的 STOP 平仓都先过 `require_connection`。被拒会让运行失败 | `engine/live_source.py:97,116-126,141-190`，`engine/live_commands.py:57-59` |
| 币安 24 小时断连 | 币安期货 WebSocket 连接只保持 24 小时，到点由服务器断开（[文档](https://developers.binance.com/docs/derivatives/usds-margined-futures/websocket-market-streams/Connect)）。按上两条，就算去掉时长上限，运行也活不过第一次断连 | — |
| 没有预热 | Live 构造源码时历史为空，`DAILY_WARMUP` 源码被 `LIVE_WARMUP_UNSUPPORTED` 拒绝。两份 Retest 要先攒 80 根 15 分钟线（约 20 小时）才可能出信号 | `engine/live_source.py:34-35,74-81` |
| 不能接着跑 | 同一运行不能重启（`LIVE_COLD_RESTART`、`LIVE_RESTART_REQUIRES_RECONCILIATION`）；中断后只能对账。对账只观察、不交易，空仓状态只在开始和结束时读 | `engine/live.py:156-161,213-217`，`live/runs.py:529-531` |
| 主机重启 | runner 和出口容器都没设重启策略；关机时 SIGTERM 走 STOP 平仓，平不完就是未解决 | `runtime/container.py:152-154`，`engine/egress.py:16`，`engine/live.py:166-171` |
| 入场被拒就结束 | 每次入场都重查账户：整个账户空仓、现金 ≥ 预算、入场名义 ≤ 单笔上限 ≤ 3 × 预算。任一不满足，运行结束 | `engine/live_commands.py:107-156`，`engine/live_venue.py:197-242` |
| 亏损按单次运行 | `max_loss_usdt` ≤ 预算，按本次运行的盈亏算，不含资金费；持仓 60 秒无标记价格即视为触发 | `engine/live_session.py:140-165` |
| 每次运行都要确认 | 启动时 `confirm_real_orders` 必须等于源码哈希 | `live/requests.py:168`，`live/control.py:136-140` |
| 发布要等空闲 | 有运行占用账户时，Live 控制程序不会换新版本 | `deploy/remote/README.md:130-141` |
| 只查一次 | 时钟偏差和 API 密钥权限只在预检时查 | `engine/live.py:129-138`，`live/runs.py:535` |
| 缓存只增不减 | 原生缓存的 Redis AOF 关闭了重写，每秒还写一次健康标记；内存缓存没设清理 | `engine/live_cache.py:99-100,143`，`engine/live_node.py:33-35` |
| 没有通知 | 未解决、失败都不通知 | `engine/README.md:580-581` |

Nautilus 本身会处理断线：锁定的 2.0.0rc7 币安适配器在行情流断开后会无限重连，重连后重新订阅。账户流在重连或
listenKey 过期时，会换新 key、补发所有挂单状态，再接上新连接（`adapters/binance/src/futures/websocket/streams/recovery.rs:207-274`）。
补发不包括缺口期间已经成交或撤掉的单，这部分由节点的定期对账修复；本仓库挂单每 10 秒、持仓每 30 秒对账一次。
真正让运行停下的是本仓库的规则，其中大多数是拒绝检查，按 AGENTS.md 改动需要用户授权。

## 2. 不变的边界

- 一份策略源码，回测、Paper、Live 不改一字。同样的输入必须得到同样的决策；Live 只多出现实避免不了的东西（断线、拒单、部分成交、滑点）和平时不触发的刹车，刹车一触发就停下并通知，不悄悄改变交易方式。
- Nautilus 管订单、成交、持仓、风控和账户状态，不另写引擎、对账或通用调度。
- 预算上限 100 USDT、单笔上限 ≤ 3 × 预算、用户的两个研究目标都不变。
- 不伪造订单事件。
- 执行记录只在 Live 私有目录，不进账本、DoltHub 或 Git。

## 3. 方案：一个运行一直跑

第一稿把一个长期运行拆成首尾相接的 7 天段。段只是绕开本仓库自己的规则（时长上限、断线即结束、发布要等空闲、
只在预检时查时钟和密钥、缓存只增不减），而且段末停止开新仓，这是回测里没有的行为。用户否决了分段（2026-11-10）。
改为：一个运行不设结束时间，由用户停止；上表每条原因单独解决。

### 3.1 运行的开始与结束

- **开始**：照现在的预检和启动检查执行，用户确认一次源码哈希和配置；然后按 §3.3 预热，预热完成前不做业务决策。
- **不设时长**：`duration_seconds` 不再要求在 1 到 86400 之间，可以不设。到点 STOP 的路径只留给用户设了时长的运行。
- **结束**：只有以下情况结束运行：用户 STOP、刹车触发（§3.5）、决策不一致（§3.6）、恢复核对失败且用户决定停止、
  用户换版本或镜像（§3.8）。现有的失败原因（`protection_missing`、`source_failure`、`native_order_failure`、
  `INFLIGHT_TIMEOUT` 等）照旧结束运行并通知。

### 3.2 断线不结束运行

1. **断线时**：
   - 关闭入场，撤掉在途入场单，因为缺口期间成交不会有进程补挂止损。
   - 只减仓的单、撤单和平仓照常放行，走 REST，不依赖 WebSocket。这样策略在缺口期间仍能为已成交的单挂止损、按时平仓，Observer 也能平仓。这是放宽 `LIVE_CONNECTION_UNVERIFIED`。
   - 已有的止损、止盈单留在交易所。
2. **重开入场前的核对**：所有端点重新 `CONNECTED` 后，以下条件都满足才重开入场。
   - 两次比对一致：两次间隔覆盖一个挂单对账周期（10 秒）和一个持仓对账周期（30 秒），每次都用 REST 读本策略的持仓、挂单（含条件单），再和 Nautilus 缓存比；
   - 账户模式没变；
   - 没有本策略以外的持仓或挂单；
   - 行情连续：缺口期间 1 分钟线一根不少。
3. **任一项不通过**：
   - 交易所上有本地不认识的单（比如断线前发出、本地记为超时拒绝的入场单）：立即撤掉该合约上的全部挂单，入场保持关闭，通知用户。
   - 行情缺根：不修补数据。入场保持关闭，持仓照常管理；重新预热（§3.3）通过后再开入场。
   - 其它不一致：入场保持关闭，通知用户。
4. **断线容忍时长**：有持仓时沿用"60 秒没有标记价格就停"；空仓时容忍到约定时长（建议 10 分钟），超过就通知用户，入场保持关闭直到核对通过。
5. **定期比对**：无论连接状态如何，每 5 分钟做一次上述比对，防止连接显示正常、账户流却已失效。
6. **主动换连接**：账户空仓时，在某分钟的第 20 到 40 秒调用 Nautilus 原生的 `reconnect_socket`，把币安的 24 小时断连挪到空仓时段。

rc7 没有"恢复完成"信号，本方案用第 2 步的显式比对代替。先做原生探针：断线前刚发出的单、断线中成交、重连后的超时拒绝和对账结果都要实测。

### 3.3 启动预热

按 `live-modularization-single-source-20261108.zh.md` 的预热方案做：三种模式都由策略源码在 15 分钟边界 T 调用一次
Nautilus 原生的 `request_bars`，请求 81 根 15 分钟原生 K 线（`EXTERNAL`，`start=T−81P`，`limit=81`），在 `on_historical_bars` 里
收到后验证最后 80 根的精确时间。

- 启动后最多约 16 分钟能开始交易，而不是现在的约 20 小时。回测一开始就有历史，所以预热缩小而不是扩大与回测的差别。
- 该方案的边界负例探针（T+29/30/31 秒、缺根、重复）还没做。
- 信号线来自 15 分钟原生 K 线，是另一个候选版本，要逐根核对两种 K 线并重新回放（`research-round`）。旧源码不动。
- Paper 用公开行情、不需要凭证，先在 Paper 上验证同一份新源码。

### 3.4 进程中断

- **关机（SIGTERM）不再平仓**：撤掉未成交的入场单，持仓和交易所上的只减仓 GTC 止损、止盈单留着。这几份源码成交后在交易所挂止损，止损被接受后再挂止盈，程序停着时持仓仍受保护。
- **程序停着时没人做的事**：8 小时到时平仓和"一边成交后撤另一边"。另一边是只减仓单，不会开出反向仓位。币安在持仓被平后是否自动撤掉剩下的只减仓单，要核实。
- **重启后**（runner 和出口容器都设自动重启，出口容器要能自己重建）：
  - 自动对账。空仓且没有挂单：预热后接着跑，并通知用户。
  - 有持仓：核实交易所止损单存在且数量与持仓一致；源码从 Nautilus 缓存和交易所状态重建自己的状态（到期时间按开仓时间算、止损止盈的对应关系），然后接着跑，并通知用户。
  - 任何核对不过：入场关闭，保护单不动，通知用户，等用户处理。
  - 1 小时内重启超过 3 次：不再自动接着跑，通知用户。
- **分两步上线**：源码能重建状态、并在隔离环境模拟 runner 被杀之前，重启后有持仓一律入场关闭、保护单不动、通知用户。

### 3.5 仓位与刹车

- **仓位**：源码按权益乘倍数下单，同时在源码里给每单设一个固定 USDT 上限，比如 297。回测用和实盘钱包相同的
  `starting_balance_usdt`（例如 100），上限在回测里同样生效。Live 运行的单笔上限不低于源码的上限，只在源码出错时触发。
  现在的 4 个 Live 版本按整个账户的 `portfolio.equity` 乘 1 或 2 封顶，没有固定上限：2 倍版在权益约 148 时会被
  `LIVE_BUDGET` 拒绝并结束运行，账户里多放的钱也会算进仓位。要发新版本源码。
- **主刹车**：从历史最高权益回撤 15%（最大回撤研究目标）就停，手续费和资金费都算在内，用 REST 读到的钱包权益计算。
  触发后平仓、停止、通知，不自动重启。它取代每次运行的 `max_loss_usdt`（只算本次盈亏、不含资金费）。
- **底线**：保留每次入场"现金 ≥ 预算"，预算设成钱包 × 85%，作为主刹车失效时的最后一道防线。
- **入场被拒仍结束运行**：源码看不到产品层的拒绝，也不能伪造订单事件，所以不放宽。

### 3.6 实盘与回测的对照

| 差别 | 判定 | 处理 |
| --- | --- | --- |
| 同样的 K 线，决策不同（开不开仓、价格、止损） | 缺陷 | 入场关闭，持仓按自己的止损止盈或到时平仓走完，通知用户 |
| K 线本身不同（实时推送与第二天的归档不一致） | 数据差别 | 只记录 |
| 成交不同（限价单回测成交而实盘没成交、部分成交、滑点、手续费、资金费） | 实盘差距的主要来源 | 每周对比报告：未成交单数、部分成交单数、平均滑点、费用差、累计收益差；明显超出回测假设时通知，不自动停 |

- 每天归档出来后，用实盘时段重跑回测，先比 K 线再比决策。要核实 Live 是否保存了它实际看到的每根 K 线。
- 同一份 Live 版本源码同时在 Paper 上跑，实盘成交和 Sandbox 成交的差别当天可见。
- 重启后按交易启动分段对照，汇总见 `live-continuous-step7a-segments-20261113.zh.md`。

### 3.7 通知

已上线（#2539，Telegram，用户在 Live 设置里保存机器人令牌后生效）。补充的触发：断线超过 1 分钟、恢复核对没通过、
自动重启与接续、刹车触发、决策不一致、每周对照报告、每天一条概况。

### 3.8 更新

| 更新什么 | 处理 |
| --- | --- |
| 策略源码（新版本） | 用户发起。旧运行关闭入场，持仓按自己的出场走完；空仓后以新运行启动新版本，预热，用户确认一次新哈希 |
| 运行镜像（Nautilus 或 `engine/`） | 发布后只提示有新镜像，先做配对回放。用户确认后在下一个空仓时刻切换：停旧运行，用新镜像跑同一份源码并预热 |
| Live 控制程序和网页 | 随时更新，不打断运行 |

现在只改网页的版本可以在 Live 忙时发布；改了控制程序的版本要等 Live 空闲才配对新控制
（`deploy/remote/README.md`，`live-web-control.zh.md`：发布事务开始时必须空闲，提交前在同一账户锁内再查一次）。
运行永不结束就永远等不到空闲，所以要让新控制接管正在跑的 runner：runner 是独立容器，发布本来就不重启它；
要设计的是账户锁、运行原件和维护职责在新旧控制之间的交接。这部分先做设计和独立评审。
实现见 `live-continuous-step6-adopt-20261113.zh.md`（runner 合同号相同即接管，声明变更仍要求空闲）。

### 3.9 其它长期运行事项

- **时钟和密钥**：运行中定期检查时钟偏差和 API 密钥权限（现在只在预检时查）；每次入场前读账户时也读交易所时间，偏差超限就拒绝这一笔。
- **API 密钥**：连续运行要求密钥设置 IP 白名单。
- **缓存增长**：打开 Redis AOF 自动重写，内存缓存用 Nautilus 原生的定期清理（按 `uv.lock` 锁定的版本核实配置项）。
- **交易所维护和合约状态**：合约状态离开 TRADING 时关闭入场，持仓由止损单管理；维护结束、核对通过后重开。

### 3.10 页面

显示运行时长、预热是否完成、入场开关及原因、最近一次重连、权益与历史最高权益、当前回撤与刹车距离、最近一次对照结果、待确认的新镜像。

## 5. 用户决定

### 第一稿（2026-11-10 "按建议来"），已被下面的决定取代的部分

段长 7 天、段末只关入场不平仓、每组确认一次、空仓自动接续下一段、整组亏损上限按本组开始时的权益计算，都随分段一起取消。
仍然有效：断线时放行只减仓的单和撤单、断线不结束运行；连续运行要求密钥 IP 白名单；通知渠道选 Telegram（已上线）；
真实账户试验每项单独授权。

### 逐条决定（2026-11-10，用户对每条回复"按推荐的设"）

1. 仓位按 §3.5：权益乘倍数，源码自带固定上限，回测用实盘钱包作起始资金。
2. 刹车按 §3.5：从历史最高权益回撤 15%，含手续费和资金费；底线预算 = 钱包 × 85%；触发后平仓、停止、通知、不自动重启。
3. 对照按 §3.6 的三类处理，并在 Paper 上同时跑一份 Live 版本。
4. 中断按 §3.4：关机不平仓；重启后核对通过就接着跑；源码能重建状态之前，有持仓时等用户。
5. 更新按 §3.8：换版本和换镜像由用户发起、在空仓时切换；控制程序和网页随时更新、不打断运行。

### 授权（2026-11-10，用户回复"全部授权"）

以下改动放宽或改变现有拒绝检查，用户全部授权，只限本方案描述的范围：

- 去掉 `duration_seconds` 的 86400 上限，允许不设时长（第 4 步）；
- SIGTERM 不再平仓，允许同一运行在中断后重启并接着交易（第 4 步）；
- 以从最高权益回撤 15% 的刹车取代每次运行的 `max_loss_usdt`（第 5 步）；
