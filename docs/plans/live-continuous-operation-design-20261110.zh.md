# Live 连续运行设计（2026-11-10，待用户审）

## 1. 问题

用户要让一个策略在真实账户上连续跑几个月、几年，像回测那样。现在的 Live（`engine.live`）按小额工程试验设计，
一次运行最多 24 小时，实际能交易的时间更短。以下事实以 `origin/main` bf447f4ec 为准。

| 限制 | 现在的行为 | 位置 |
| --- | --- | --- |
| 时长上限 | `duration_seconds` 必须在 1 到 86400 之间，超出时 runner 以 `LIVE_MANIFEST_INVALID` 拒绝；到点走 STOP：撤入场单、平仓、保护单保留到平 | `engine/live.py:69`，`engine/live_session.py:106`，`engine/live_lifecycle.py:118-150` |
| 断线即结束 | 任何来自 BINANCE 的 `DISCONNECTED` 都调用 `lose_connection`：撤入场单、停策略、停节点、记为未解决；之后的 `CONNECTED` 不恢复交易 | `engine/live_lifecycle.py:67-71`，`engine/live_session.py:181-198` |
| 断线期间一律拒单 | 源码的下单、撤单、平仓和 Observer 自己的 STOP 平仓都先过 `require_connection`。被拒会让运行失败 | `engine/live_source.py:97,116-126,141-190`，`engine/live_commands.py:57-59` |
| 币安 24 小时断连 | 币安期货 WebSocket 连接只保持 24 小时，到点由服务器断开（[文档](https://developers.binance.com/docs/derivatives/usds-margined-futures/websocket-market-streams/Connect)）。按上两条，就算去掉时长上限，运行也活不过第一次断连 | — |
| 没有预热 | Live 构造源码时历史为空，`DAILY_WARMUP` 源码被 `LIVE_WARMUP_UNSUPPORTED` 拒绝。两份 Retest 要先攒 80 根 15 分钟线（约 20 小时）才可能出信号 | `engine/live_source.py:34-35,74-81` |
| 不能接着跑 | 同一运行不能重启（`LIVE_COLD_RESTART`、`LIVE_RESTART_REQUIRES_RECONCILIATION`）；中断后只能对账。对账只观察、不交易，空仓状态只在开始和结束时读 | `engine/live.py:156-161,213-217`，`live/runs.py:529-531` |
| 主机重启 | runner 和出口容器都没设重启策略；关机时 SIGTERM 走 STOP 平仓，平不完就是未解决 | `runtime/container.py:152-154`，`engine/egress.py:16`，`engine/live.py:166-171` |
| 入场被拒就结束 | 每次入场都重查账户：整个账户空仓、现金 ≥ 预算、入场名义 ≤ 单笔上限 ≤ 3 × 预算。任一不满足，运行结束 | `engine/live_commands.py:107-156`，`engine/live_venue.py:197-242` |
| 亏损按单次运行 | `max_loss_usdt` ≤ 预算，按本次运行的盈亏算，不含资金费；持仓 60 秒无标记价格即视为触发 | `engine/live_session.py:140-165` |
| 每次运行都要确认 | 启动时 `confirm_real_orders` 必须等于源码哈希 | `live/requests.py:168`，`live/control.py:136-140` |
| 发布要等空闲 | 有运行占用账户时，Live 控制程序不会换新版本 | `deploy/remote/README.md:130-141` |
| 只查一次 | 时钟偏差和 API 密钥权限只在预检时查 | `engine/live.py:129-138`，`live/runs.py:535` |
| 缓存只增不减 | 原生缓存的 Redis AOF 关闭了重写，每秒还写一次健康标记；内存缓存没设清理 | `engine/live_cache.py:99-100,143`，`engine/live_node.py:33-35` |
| 没有通知 | 未解决、失败都不通知 | `engine/README.md:580-581` |

Nautilus 本身会处理断线：锁定的 2.0.0rc7 币安适配器在行情流断开后会无限重连，重连后重新订阅。账户流在重连或
listenKey 过期时，会换新 key、补发所有挂单状态，再接上新连接（`adapters/binance/src/futures/websocket/streams/recovery.rs:207-274`）。
补发不包括缺口期间已经成交或撤掉的单，这部分由节点的定期对账修复；本仓库挂单每 10 秒、持仓每 30 秒对账一次。
真正让运行停下的是本仓库的规则，其中大多数是拒绝检查，按 AGENTS.md 改动需要用户授权。

## 2. 不变的边界

- 一份策略源码，回测、Paper、Live 不改一字。
- Nautilus 管订单、成交、持仓、风控和账户状态，不另写引擎、对账或通用调度。
- 预算上限 100 USDT、单笔上限 ≤ 3 × 预算、用户的两个研究目标都不变。
- 不伪造订单事件。
- 执行记录只在 Live 私有目录，不进账本、DoltHub 或 Git。

## 3. 方案：一组首尾相接的有限运行

不把一个运行拉长到几个月，而是让一组运行首尾相接。每段运行有固定长度（建议 7 天），段与段之间在空仓时交接，
下一段重新预热、重新检查账户、时钟和密钥，并用最新发布的镜像。这样：

- 缓存（AOF、内存）的增长被每段的长度限住；
- 段与段之间 Live 空闲，发布能换上新的控制程序和 runner；
- 时钟、密钥和账户模式每段都重新检查；
- 断线处理（§3.2）只需应付段内的 24 小时断连和偶发掉线。

### 3.1 段的开始与结束

**开始**：
- 照现在的预检和启动检查执行。
- 然后按 §3.3 预热。预热完成前不做业务决策。

**结束**：
- 到段长后关闭入场，但不平仓。
- 持仓由策略自己的止损、止盈或 8 小时到时平仓结束。段长只是"不再开新仓"的时刻，不是强制平仓的时刻。
- 设一个上限（段长 + 最长持仓 + 余量，例如 + 9 小时），到了仍未空仓才走现在的 STOP 平仓。

**交接**：
- 账户空仓、上一段干净结束后，控制程序用同一组的源码和配置，以新的运行编号启动下一段。
- 只有以下结束原因允许接下一段：到段长、对账确认空仓的进程中断、长时间断线后确认空仓。
- 以下结束原因一律不接，停下并通知：`max_loss`、`protection_missing`、`loss_unverified`、`source_failure`、`native_order_failure`、`INFLIGHT_TIMEOUT`、整组亏损上限、恢复核对失败。
- 自动接续有次数上限（参照 Paper：每小时最多 3 次），超过就停下。

**确认**：
- 启动一组时，用户确认一次：源码哈希、配置、段长、自动接续上限和整组亏损上限。
- 这份确认覆盖本组后续各段，但不覆盖新的镜像。
- 镜像换了，下一段先停在"待确认"，等用户确认。这把现在"每个运行确认一次"放宽为"每组确认一次"，需要授权（§5）。

### 3.2 段内断线不结束运行

1. **断线时**：
   - 关闭入场，撤掉在途入场单，因为缺口期间成交不会有进程补挂止损。
   - 只减仓的单、撤单和平仓照常放行，走 REST，不依赖 WebSocket。这样策略在缺口期间仍能为已成交的单挂止损、按时平仓，Observer 也能平仓。这是放宽 `LIVE_CONNECTION_UNVERIFIED`，需要授权。
   - 已有的止损、止盈单留在交易所。
2. **重开入场前的核对**：所有端点重新 `CONNECTED` 后，以下条件都满足才重开入场。
   - 两次比对一致：两次时间间隔覆盖一个挂单对账周期（10 秒）和一个持仓对账周期（30 秒），每次都用 REST 读本策略的持仓、挂单（含条件单），再和 Nautilus 缓存比；
   - 账户模式没变；
   - 没有本策略以外的持仓或挂单；
   - 行情连续：缺口期间 1 分钟线一根不少。
3. **任一项不通过**：
   - 发现交易所上有本地不认识的单（比如断线前发出、本地记为超时拒绝的入场单），立即撤掉该合约上的全部挂单，本段记为未解决并通知。
   - 行情缺根时不修补数据。本段剩余时间不再开仓，持仓照常管理到空仓，下一段重新预热。
   - 其它不一致：继续关着入场，发通知。
4. **断线容忍时长**：
   - 有持仓时：沿用现在"60 秒没有标记价格就停"的规则，所以有持仓时实际只能容忍约 60 秒的断线。
   - 空仓时：容忍到约定时长（建议 10 分钟），超过本段记为未解决并通知。
5. **定期比对**：无论连接状态如何，每 5 分钟做一次上述比对，防止连接显示正常、账户流却已失效的情况。
6. **主动换连接**：账户空仓时，在某分钟的第 20 到 40 秒调用 Nautilus 原生的 `reconnect_socket`，主动换一次连接，把币安的 24 小时断连挪到空仓时段。

现在代码说 rc7 没有"恢复完成"信号，所以不允许重开入场。本方案不等这个信号，而是用第 2 步的显式比对代替。
这一步要先做原生探针：断线前刚发出的单、断线中成交、重连后的超时拒绝和对账结果都要实测。

### 3.3 启动预热

按 `live-modularization-single-source-20261108.zh.md` 的预热方案做：三种模式都由策略源码在 15 分钟边界 T 调用一次
Nautilus 原生的 `request_bars`，请求 81 根 15 分钟原生 K 线（`EXTERNAL`，`start=T−81P`，`limit=81`），在 `on_historical_bars` 里
收到后验证最后 80 根的精确时间。

- **何时能交易**：启动后要等到下一个 15 分钟边界，第一根 1 分钟线在 T + 60 秒才到，所以最多约 16 分钟能开始交易，而不是现在的约 20 小时。
- **还缺的验证**：该方案的边界负例探针（T+29/30/31 秒、缺根、重复）还没做。
- **信号线来源要换**：现在的 Live 源码用 1 分钟线内部聚合成 15 分钟线；新方案的信号线来自 15 分钟原生 K 线，是另一个候选版本，要逐根核对两种 K 线，并重新回放（`research-round`）。旧源码不动。
- **Paper 先验证**：Paper 用公开行情，不需要凭证，可以先在 Paper 上验证同一份新源码。

### 3.4 进程中断

- **默认处理**：主机关机（SIGTERM）仍像现在这样平仓。关机时保留持仓和止损要另外满足两个条件，留作以后的选项：
  - 止损必须是 GTC，并在交易所上核实过；
  - 对账模式能持续检查止损覆盖。
- **对账能自己结束**：runner 意外退出后，控制程序自动对该段执行 `reconcile`。
  - 对账改为定期读交易所是否空仓，空仓就结束，并设一个上限时长，不再"观察到时长或 STOP 为止"。
  - 交易所空仓：按 §3.1 交接下一段。
  - 还有持仓：通知，由人处理。
- **出口容器**：runner 的出口容器也要能在中断后被重建，否则它会成为单点故障。

### 3.5 额度与亏损

- **入场被拒仍结束本段**：源码看不到产品层的拒绝，也不能伪造订单事件，所以不放宽。
  - 权益变化后入场名义超过单笔上限，或现金低于预算，本段结束并通知。
  - 页面提示权益是否在范围内：1 倍版是预算到 3 倍预算，2 倍版是预算到 1.5 倍预算。超出时用户可以把多出的钱转出，产品不自动划转资金。
- **整组亏损上限**：用 REST 读到的钱包余额（含资金费）相对本组开始时的权益计算，到了就停整组。这是一条新的停止规则，需要授权，默认值也要用户定。
- **每段的 `max_loss_usdt`**：保留不变。

### 3.6 通知

**触发情况**：
- 运行未解决或失败；
- 断线超过 1 分钟；
- 恢复核对没通过；
- 段结束、交接下一段，或接续停止；
- 止损覆盖出现缺口；
- 触发亏损上限；
- 每天一条概况：权益、持仓和当天的交易。

**实现方式**：控制程序读生命周期记录生成通知，发到用户选定的渠道。渠道令牌是凭证，和 API 密钥一样存在 Live 私有目录；
出站连接可能改动网络路径。这两点都需要授权。

### 3.7 其它长期运行事项

- **时钟**：每次入场前读账户时顺带读交易所时间，偏差超限就拒绝这一笔，本段结束。
- **API 密钥**：连续运行要求密钥设置 IP 白名单。现在没有白名单只给出警告。
- **交易所维护**：币安公告维护时，按流程手动停止本组，维护结束后重新启动。
- **合约状态**：合约状态离开 TRADING 时，关闭入场；持仓照常由止损单管理。

### 3.8 页面

页面显示以下内容：
- 本组状态：第几段、本段剩余时间、预热是否完成、入场许可开关及原因、最近一次重连；
- 权益是否在范围内；
- 整组盈亏和最大回撤；
- 待确认的新镜像。

## 4. 分步实施与验证

| 步 | 内容 | 需授权的改动 | 验证 |
| --- | --- | --- | --- |
| 1 | 通知（§3.6） | 渠道凭证、出站网络 | 用已有运行记录回放触发 |

每一步单独一个 PR，每个 `engine/` 改动都要发新运行镜像。各步完成前，现在的单次运行照常可用。

## 5. 需要用户决定的事项

1. **授权放宽或新增以下规则**：
   - 段长到时只关入场，不平仓；
   - 断线时放行只减仓的单、撤单和平仓，断线不结束运行；
   - 每组确认一次，而不是每个运行确认一次；
   - 中断后自动对账，空仓就接续下一段；
   - 新增整组亏损上限；
   - 连续运行要求 API 密钥设 IP 白名单。
2. **通知渠道**：Telegram、邮件、ntfy、Bark 等选一个，并授权保存其令牌和出站连接。
3. **段长**：建议 7 天。
4. **整组亏损上限的默认值**：例如取最大回撤研究目标。
5. **真实账户试验的范围**：第 3 到 5 步的受控试运行、断线和重启，每一项都要单独授权真实下单。
