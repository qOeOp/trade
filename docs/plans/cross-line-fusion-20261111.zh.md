# 跨线融合、多腿策略与持仓管理（2026-11-11）

用户 2026-11-11 提出两件事：

- 产品的顶层对象是单文件策略，没有组合层。研究线之间如果只能各做各的、一条做完才开下一条，就会丢掉"把两个已关线的好策略合在一起"这类改进。
- "有持仓或挂单时不开新仓"不对，不应该限制死："挂着空单、有多单持仓，或者多笔多单持仓、多笔空单持仓、多空单一起挂单，都是允许的。我授权的。产品做好持仓管理、风险控制就行，不需要限制持仓数量。"

本计划说明现在能做到哪一步，补上融合的路径（第 3 节），把"一时一仓"换成持仓管理和风险控制（第 4 节），并把跨合约多腿和 Live 多合约排进后续（第 5 节）。

## 1. 场景

- 一条已关的线里有一个 DAO 策略，关线历史回测（[关线计划](line-close-history-test-20261110.zh.md)）各年份都还可以，已经进了 Paper。
- 新开的线还在研究 DAO。研究 Agent 读到旧线的结果，也看到问题：DAO 只做多，熊市年份回撤大。
- 台账里另有一条已关的线，做的是做空策略，熊市年份成绩好。
- 研究 Agent 提出：把做空策略的规则并进 DAO，变成多空两套规则的策略，用来降低回撤、提高夏普。

本计划把这件事叫"融合"：从两个或更多已发布候选里各取规则，写成一份新的单文件策略，再按现有流程登记、回放和关线。

结论：
- 同一合约、同样输入的融合，登记流程已经支持，缺的是 skill 里一条成文的路径（第 3 节）。但两套规则要各自持仓、各自止损，要先做第 4 节。
- 需要别的合约或输入的融合，可以另开一条线来做，不用放宽可比性检查（3.4）。
- 跨合约多腿和 Live 多合约是另外两个产品缺口（第 5 节）。

## 3. 融合怎么做（Agent 的工作，不加产品代码）

### 3.1 什么时候提出

- 在 `research-round` 需要换方法时（`feedback.md` 的 Change approach），或在 `research-start` 选线时。
- 起点是本线候选的一个具体缺陷，而且这个缺陷在已关线的热力图上能找到能补它的候选。例如本线候选在下跌年份回撤超标，另一个候选恰好在这些年份盈利。
- 只在融合能做出和单个组件不同的预测时提出。不做随机拼装，也不批量试组合。

### 3.2 先用已封存的日收益粗筛

- 组件在关线历史回测的每一段都有封存的日收益（`run_return`），不用再回放。
- 在 `/tmp` 里按计划的资金分配把组件的日收益合成一条组合曲线，看开发期之外各整年的回撤和年化收益，以及组件之间的相关性。计算方法按 `nautilus-report-analysis`。
- 粗筛只用来排序和挑选，不能当作结论：
  - 同一账户里的保证金和资金占用算不出来，第 4 节的总额上限也可能挡住一部分入场。
  - 两个组件的历史段各自从零仓位、同样的起始资金开始，和融合后一份源码共用一个账户连续运行不是一回事。

### 3.3 写成一个文件

- 把两边的规则写进一个入口类，遵守 R1 源码契约和第 4 节改后的订单规则。
- 源码要写明（`strategy-authoring.md` 已要求资金分配写在源码里）：
  - 两套规则怎么分资金，碰到总额上限时谁让步；
  - 每套规则的持仓用自己的止损和退出，只平自己的持仓；
  - 同一根 K 线上两套规则同时触发时怎么处理。
- 规则从哪个候选来，写在登记的 `rationale.local` 里：组件的 `strategy_id@revision`、源码哈希、所在线，以及让它入选的关线热力图读数和年份。

### 3.4 登记：两种情况

**同样的合约、输入和镜像**（可比）：
- 在接收线里做派生登记：parent 是本线的候选，改动是"并入候选 X 的某条规则"，对照是 parent 在本线开发期上的运行。
- 现有检查全部适用。
- 对照必须用同一个运行镜像。第 4 节的改动会出新镜像，之后的融合要先在新镜像上把 parent 重跑一次作对照。

**需要别的合约或输入**（不可比）：
- 另开一条线。开发期按开线日期定（关线计划 3.1）。
- 接收方组件不能直接拿来在新线上作对照：
  - 它有父，作为根登记会被 `LINEAGE_MISMATCH` 拒绝（`registration/register.py:319`）；
  - 同样的字节也不能再发布一次，因为源码哈希是候选的身份。
- 可行的做法：把组件发布成一个字节不同的重启副本，作为根登记（`register.py:289-292` 的拒绝文案就建议这种重启）。它在新线的合约和输入上跑出的运行作对照，再把融合版作为它的派生登记。
- 这条路要先在隔离库里走一遍，确认可行后才写进 skill。
- 这样不用放宽 `COMPARABILITY_MISMATCH`，融合版的效果仍然有一个可比的对照。

### 3.5 怎么判断

- 融合版和线里其他候选一样，参加关线历史回测。
- 但组件是按它们在历史年份上的成绩挑出来的（3.1），这些年份对融合版来说是挑选用的数据，不是检验。关线计划 3.6 说过后开的线都看得到之前的热力图；融合比一般情况更直接，因为它挑的正是这些年份上的表现。
- 所以融合版在挑选组件用过的年份上的成绩，只当筛选，不算达标的依据。达标看前瞻段、验证登记和 Paper。怎么落实见第 7 节 D1。
- 多重比较：关线热力图已经显示本线的参与候选数。融合版的报告另外写明组件来自哪几条线、那些线各有多少参与候选。

### 3.6 存储

按第 7 节 D1 的建议，不加字段：
- "融合版用了哪些候选、挑选用了哪些年份"写在登记的 `rationale.local` 里，读者是用户和后面的 Agent。
- 组件的日收益、热力图读数都已经封存，可以随时推导。
- 代价是热力图不会自动标出融合版的挑选年份，要靠 Agent 在关线判断里手工说明。如果融合常用，或者 IDE 要在研究图上画融合关系，就需要结构化的引用，到时按 AGENTS.md 先做独立的字段评审。

### 3.7 Skill 改动

- `research-round`：
  - `feedback.md` 的 Change approach：把"借用其他线的想法、重组部件"改写成本节的路径（触发条件、粗筛、两种登记、判断边界），替换现有那一句，不并列。
  - `strategy-authoring.md`：把"从别的版本合并的规则"那一条扩展为 3.3 的要求。
  - `hypothesis.md`：说明需要别的合约或输入时，走 3.4 的新线路径。
- `research-start`：选线时，已关线的热力图可以作为融合的来源，与继续本线、开新线并列提出。
- 这些段落并进新账本的 skill 整体重写（新账本计划第 6 节），不单独改旧 skill，避免改两遍。
- 按 AGENTS.md 报净字数，增改评测用例并运行。至少两例：
  - 同合约同输入的融合，应在本线派生登记；
  - 需要别的输入的融合，应另开线，不应试图在本线登记或要求放宽可比性。

## 4. 持仓管理：取消"一时一仓"（用户 2026-11-11 授权）

### 4.1 为什么只删检查不够

- 持仓按净额（NETTING，runner 在 `engine/strategy.py:125` 注入，Live 对账在 `engine/live_node.py:69` 也用它）时，同一策略在同一合约上的多笔成交会合成一个持仓，多空会相抵。
- 只删"有持仓或挂单不能入场"，第二笔多单会加到第一笔上，第二笔空单会减掉多单。做不到"多笔多单各自止损"或"多空同时持有"。
- 所以要一起改持仓方式、风险上限、止损覆盖、Live 的入场流程，以及假设"一时一仓"的报告。

### 4.2 改成

1. **持仓。** runner 注入的策略持仓方式从 NETTING 改成 HEDGING。每个入场订单开自己的持仓（`position_id`），这个订单的部分成交并入同一持仓。同一合约上可以同时有多个多仓、多个空仓，多空单可以同时挂着。
2. **入场。** 删去"该策略在该合约上没有持仓和未结订单"（`order_rules.py:87`）。其余不变：只收基础数量的 LIMIT 或 STOP_MARKET 入场；不改单；不用订单列表、括号单、关联单；GTD 至少 600 秒；只撤自己的单。
3. **退出。** 仍然必须 reduce-only、带 `position_id`，不超过那个持仓的方向和数量，只平它自己。
4. **风险上限。** 取代"每笔入场不超过 3 倍权益"（`order_rules.py`，Live 的 `require_entry_size` 在 `live_commands.py:131`）：
   - 入场时，这个策略在这个合约上全部未平持仓的名义价值、全部未结入场单的名义价值（LIMIT 按限价，STOP_MARKET 按触发价）、再加这一笔，合计不超过 USDT 权益的 3 倍。
   - 多空分开相加，不相抵。
   - 倍数仍是 `ENTRY_EQUITY_MULTIPLE = 3`（用户 2026-11-09 定）。Live 的权益仍取账户快照的 `min(钱包, 可用)`。
   - 按"每合约每策略"算，与今天每个合约最多一个 3 倍持仓的水平相同。改成整个账户合计会比今天严得多（今天 10 个合约可以各有一个 3 倍持仓）。
   - 从逐笔改成累计，本身是一项检查改动，见第 7 节 R1。
5. **止损覆盖。** 改为按持仓判断：每个未平持仓都要有平仓方向、reduce-only、状态 ACCEPTED 的止损单，归属这个持仓，剩余数量不小于它。允许时长不变（回放和 Paper 60 秒，Live 60 秒加 30 秒检测延迟）。
   - Paper（`engine/paper.py` 的保护检查）和 Live（`engine/live_session.py` 的保护检查）现在是"每个持仓把同方向的止损都加起来"，多个同向持仓时会重复计算。改用 `cache.position_id(client_order_id)` 取止损所属的持仓。
   - 研究审计从原生事件重建，按（策略，合约）求净额。一多一空净额为零，两边都不会被检查。原生的下单和接受事件不带 `position_id`，只有成交事件带。审计怎么拿到"止损属于哪个持仓"要先实测（4.3）。
6. **Live 入场流程。**
   - 开跑时账户必须是空的，这条不变。
   - 删去每次入场都要求整个账户无持仓无挂单（`live_commands.py:123-126`）。
   - 同一时刻到达的多笔入场排队，逐笔做账户读取和上限检查，不再因为"已有一笔待处理"而停止运行（`live_source.py:86-87`）。
   - 每笔入场仍然重新读账户，现金、预算和上限检查保留。
7. **报告和对账。**
   - 指标的 `PLAN_OVERLAP`（`ledger/metrics.py:581-588`）在计划重叠时把计划胜率置空。改为按计划（入场订单和它的持仓）计算，重叠是正常情况。
   - `report/runs.py:178` 的"每个 NETTING 周期一行"改成每个持仓一行。按持仓的周期（`metrics.py` 的持仓周期）不用改。
   - Paper 对账（`paper/reconcile.py`）现在按合约、方向和订单角色按时间配对成交。同向计划同时存在时会配错，改成按入场订单配对。
8. **Skill。** `strategy-authoring.md:150-152` 改写为：源码写明同一合约上多个持仓怎么管理，也就是各自的止损和退出、碰到总额上限时怎么办、同时信号怎么处理。这一条随 4.4 的 PR 一起改，不等 skill 整体重写，否则产品和 skill 会互相矛盾。

### 4.3 要先实测的

在回放和 Paper（Sandbox）上用测试源码探针，结果写回本计划。Paper 探针从隔离账本读候选，不碰活动账本。

- **模拟交易所。**
  - 回放和 Paper 的交易所持仓方式是 NETTING（`engine/config.py:86`）。
  - 已从 rc7 源码确认：HEDGING 策略的持仓得到生成的 `position_id`，模拟撮合按订单自己的持仓核对 reduce-only，不看交易所的净额。实测确认这一点。
  - 要测：交易所 NETTING 下相反方向的虚拟持仓怎么算保证金，资金费按虚拟持仓还是净额收，和 Binance 双向持仓模式是否一致。不一致就把模拟交易所也改成 HEDGING。
- **Binance 真实账户。**
  - Live 已经要求账户是双向持仓模式，Nautilus 在这个模式下发 `positionSide`、不发 reduceOnly，所以多空同时持有在交易所层面可行。
  - 要测（只在 Paper 和离线原生测试上做）：
    - 多个虚拟持仓共用 Binance 的同一个 LONG 或 SHORT 方向时，执行客户端用 `use_position_ids=False`（`engine/live_node.py:50`），对账结果是否正确。`engine/README.md` 说这种情况下交易所的持仓会以外部持仓出现。
    - 交易所的止损按方向汇总，和产品按持仓核对的覆盖怎么对应。
- **审计的止损归属。** 原生 `orders.csv` 对从未成交的止损是否带 `position_id`。
  - 如果不带，就要在捕获里多一个文件记录"订单属于哪个持仓"。这是新的存储内容，要先按 AGENTS.md 做独立评审，再请用户决定。
- **配对回放怎么算"相同"。** HEDGING 下持仓 ID 从 `{合约}-{策略}` 变成生成的值，持仓和敞口里的 `position_id` 会变。要先定义比较时把它当作可变列（`engine/compare_reports.py:28` 已经这样处理），才能用 4.4 的配对回放证明旧行为没变。

**实测结果（2026-11-11，rc7 原生探针和配对回放）：**

- 交易所 NETTING、策略 HEDGING 时，持有净多仓的情况下，虚拟空仓的 reduce-only 平仓单被撤（CANCELED）：模拟交易所按净额核对 reduce-only。所以回放和 Paper 的交易所也改成 HEDGING（`engine/config.py`），和 Live 的 Binance 双向持仓一致。
- 保证金：Sandbox 按净额算，多空相抵时可能低于 Binance 双向模式下的实际占用。这是已知差异，写进 PR，没有改。
- 未成交止损的 `position_id`：原生订单事件和 `orders.csv` 都不带，只有成交事件带。没有加存储，用下单规则代替：一个持仓的未成交止损合计不超过它的数量。这样审计按（策略, 合约, 方向）汇总持仓和止损，结果和逐个持仓核对相同（`engine/audit.py`）。
- 配对回放（BTC、ETH，2026-01-01 至 01-15，main 5f901dfc5 对本分支，单仓源）：订单、成交、持仓、成交量的语义对比相同，账户和日收益逐字节相同，敞口表在屏蔽持仓 ID 后相同，审计结论相同。唯一的表示差异：NETTING 下同一持仓 ID 反复开平留下的 1069 行快照（`is_snapshot=True`），在 HEDGING 下是 1069 个普通的已平持仓。产品代码不读 `is_snapshot`。
- 多仓源（同一合约每 15 分钟同时挂多空限价单，每个持仓一张自己的止损）：同一合约最多同时 6 个多仓、5 个空仓，多空并存 3824 个时刻，0 笔拒单，审计没有止损缺口。

## 5. 跨合约多腿和 Live 多合约

### 5.1 跨合约多腿运行

先探针，再设计。用一份测试源码在隔离环境里实测：
- 一个合约的实例能不能订阅另一个合约的 K 线，能不能给另一个合约下单，订单规则和审计（`ENTRY_SCOPE_INVALID`）是否放行；
- 模板说明里要求的四种情况：一条腿先成交另一条没成、一条腿始终没成交、合约失去资格、两腿的止损覆盖。

探针之前设想了两种形式：
- **(a) 一个实例管一组合约。** runner 支持源码声明"按组运行"，每组只起一个实例，构造参数给出组内全部合约。要改 `engine/`、出新镜像。
- **(b) 领头合约的实例管全部腿，其他合约的实例什么都不做。** 不改 runner，但每个合约仍要起一个空实例，源码里要写判断。

探针时发现活动线的候选 `dow-theory`（两条"平均线"是 BTCUSDT 和 ETHUSDT）已经用了第三种：
- **(c) 每个合约一个实例，各自只交易自己的合约，实例之间通过源码里的类变量共享状态。** `DowTheory.BOARD` 和 `STATES` 是类变量，两个实例写入各自的日收盘、读取对方的，"两条平均线同时确认"才改变主趋势。回放和 Paper 的全部实例在一个进程里，所以能共享。这种形式不改 runner，也不碰订单规则和审计。

不论哪种，如果要改订单规则或审计对合约范围的检查（放宽或收紧），都要用户单独授权。

**实测结果（2026-11-13，隔离的临时账本，CI 镜像 `trade-runtime@sha256:578cc863…`，即 main `c554d6aca`）：**

回放窗口 2024-02-29T20:00Z 至 03-01T04:00Z，`--universe pool`。WIFUSDT 从 2024-03-01 起才进入 universe，用来测"腿的合约不在资格内"。

- **(b) 领头实例交易别的合约**（`probe-multileg@2`，BTCUSDT 实例下 ETHUSDT 和 WIFUSDT 的单，其他实例不动）：
  - 订阅：领头实例订阅 ETH、WIF 的 1 分钟 K 线被放行，各收到 480 根。预热只给它自己的合约：BTC 30 根历史，ETH、WIF 0 根。每次启动（Live 里包括每次重新预热）它对腿的合约都是冷的。
  - 下单：订单规则放行。原生正常成交，ETH、WIF 的持仓归 `R1-BTC`。3 倍上限按（合约, 实例）算，所以领头实例在 ETH 上的 3 倍和 ETH 实例自己的 3 倍是分开的。同一份源码在一个合约上最多可达 6 倍，只靠源码约定 ETH 实例不动。
  - 审计：`ENTRY_SCOPE_INVALID` 不会触发，它只在订单的合约不在运行里时触发，而那种订单原生就会被拒。资格检查按订单自己的合约：领头实例在 02-29 23:35 下的 WIF 入场单被判 `ENTRY_ORDER_OUTSIDE_MEMBERSHIP (R1-BTC, WIFUSDT)`。但源码只拿到自己合约的 `universe_membership`，领头实例无从知道 WIF 不在资格内，避免不了。
  - 止损覆盖：按（实例, 合约, 方向）判断。ETH 腿的止损晚 3 分钟，被判 `UNPROTECTED_POSITION: ETHUSDT (R1-BTC, SHORT)`。归属正确。
  - 四种情况：两腿都成交（c1）、BTC 成交而 ETH 的 GTD 腿到期未成交后回滚 BTC（c2）、ETH 腿挂到结束都没成交而 BTC 腿带止损持有（c3），都按源码写的执行，审计没有异议。
  - 报告：一个计划标签跨两个合约，报告里 `PLAN_MULTI_INSTRUMENT`，计划胜率为空。这只影响报告维度，不拒绝运行。每条腿用自己的计划标签就没有这个问题。
- **(c) 共享状态、各自交易**（`probe-sharedleg@1`，BTCUSDT 实例在类变量里登记计划，每个实例只给自己的合约下单）：precheck 通过，审计无异议，计划胜率正常。
  - c1、c2、c3 同上。
  - 合约不在资格内（c4a）：WIF 实例按自己的资格拒绝这条腿并标记失败，BTC 实例在下一分钟平掉已成交的 BTC 腿。资格内（c4b）两腿都成交、各自止损、按时平仓。
  - 腿的下单时间：回放里同一时刻的 K 线按合约顺序送达，这次腿和领头在同一分钟下单。但这只是因为 BTC 排在前面。Live 里同一分钟各合约的 K 线先后不定，源码要按"在第 t 根决定、在第 t+1 根各腿下单"来写，不能依赖送达顺序。
- **Paper（Sandbox，公开数据，无凭证）**：(b) 的源码按压缩的时间表在 BTCUSDT、ETHUSDT 上跑了 19 分钟（`python -m engine.paper`，2026-11-13 03:03–03:22Z）。两腿都成交、GTD 腿到期后回滚、腿挂到结束（停止时撤单），都和回放一样；0 笔拒单。Paper 自己的保护检查按持仓判断，ETH 腿止损晚 3 分钟，60 秒后记了 `protection_gap`（`R1-BTC` 的 ETH 持仓）。
  - 读代码确认：Paper 的资格闸门（`engine/paper.py` `submit_order`）查的是下单实例自己的合约，不是订单的合约。(b) 的领头实例在腿的合约失去资格后仍会把腿送出，而回放审计会判它违规，两边不一致。Paper 开跑时要求每个合约都在 universe 里（`PAPER_NOT_IN_UNIVERSE`），所以只有月中失去资格时才会遇到。
- **Live（读代码，不运行）**：`engine/live_source.py:73` 的 `LIVE_INSTRUMENT_SCOPE` 拒绝不是 manifest 合约的订单，(a)、(b) 在 Live 都要放宽它。(c) 每个实例只交易自己的合约，保留这条检查。

**结论：**
- (b) 在回放里能跑，但有三处缺口：腿的合约没有预热；源码拿不到腿的资格；Paper 资格闸门查错合约。另外，同一合约上的 3 倍上限会被拆成两份。补这些就等于做 (a)，还要放宽 Live 的检查。
- (c) 在回放里已经覆盖四种情况，不需要改代码，也不需要改任何检查。它对 Live 的要求只有一条：同一份源码的全部合约在一个进程里运行。这正是下面 5.2 的 (i)。
- 所以跨合约多腿不需要等新的运行形式，可以并进 Live 多合约，同时把 (c) 写进 skill（`template.md` 里"每个合约一个实例不等于两腿协调"一句要改写成怎么协调）。

### 5.2 Live 多合约

把计划里捆在一起的两件事分开：
