# 产品更新后迁移旧研究（设计）

2026-11-04 用户问：旧镜像的研究运行能不能解决，我们是不是漏了每次更新的自动迁移。接着问：如果能解决，该用 skill 还是脚本。这份设计回答这两个问题，用户同日同意（“同意这个设计”，含 §6 全部事项）。它接在 [`input-identity.zh.md`](input-identity.zh.md) 之后。

## 1. 结论

- **确实漏了。** 产品更新时，没有任何东西去处理旧研究。现在的规则（`research-round` 的 `changes.md`）默认旧运行变成历史、研究线重开。可实测结果是经济结果根本没变。
- **能解决。** 下面实测的所有样本，换到新镜像后成交、持仓、敞口、日收益都逐天相同。
- **用命令加 skill，不写单独的脚本。** “结果是否相同”由代码判定；什么时候迁、迁哪些、不同了怎么办，由 skill 指导 Agent。

**成员文件裁剪：** 输入指纹方案把成员文件裁到窗口。研究运行里 89 个的源码把成员结束时间当 GTD 截止时间，所以这 89 个即使在原镜像上重放，订单表也会变（229 实测：只有 20 个挂单的 `expire_time` 不同，其余都相同），而跨镜像判定不看订单表。迁移之后它们的严格复现以迁移那次为准，见 §3。

**依赖关系：** 这 70 个运行都在两条早期研究线上（`ema-cross-btc-daily` 64 个，`ema-entryvar-rollingref` 6 个），没有任何当前镜像的运行拿它们当对照。所以这次迁移它们不紧急，紧迫的是以后每次更新不再让开着的研究线失效。

## 3. 设计

**“迁移”就是把旧运行放到新环境重放一次，结果相同就并入，不同就报告。** 这和输入指纹方案里“复现成功的运行也认复现时的输入”是同一个关系，只是多认一个镜像。

| 谁做 | 做什么 | 为什么 |
|---|---|---|
| **代码** | `replay reproduce --image <镜像>`：在指定镜像上重放，判定结果是否相同，相同就让旧运行也认这个镜像和输入 | 这是信任边界。让 Agent 自己判定，就是自己给自己打分 |
| **skill** | 重写 `changes.md`：更新后什么时候迁、迁哪些运行、结果不同时怎么办 | 这些要判断，也会变。Agent 能做 |
| **report status** | 列出开着的研究线上还没到当前镜像的运行，从现有记录推出 | 让下一次研究开始时能看到，不用人记 |
| **不写** | 单独的迁移脚本、定时任务、CI 步骤 | 循环一条命令不值得维护一个脚本；`AGENTS.md` 不让建调度器；CI 没有市场数据，也连不上币安 |

**判定规则：**

- 同一镜像：所有表都相同，和现在一样。
- 不同镜像：成交、持仓、敞口、日收益四张表都相同。手续费在成交里，权益路径落在日收益里。账户表和订单表只作报告，不参与判定，因为 §2 显示它们在 Nautilus 版本之间会变而经济结果不变。这是这份设计唯一放宽判定的地方。
- 只有一边有的表（如 `fill_volumes`）不比较。

**迁移之后怎么复现：** `replay reproduce <运行>` 不带 `--image` 时，用这个运行最近一次迁到的镜像和输入重放，和那次迁移的结果比全部表。旧镜像不再用。

**“自动”做到哪一步：** 不是合并 PR 时自动跑，因为回放要用本地市场数据，还会写公开账本。做法是下一次研究开始时，`research-start` 从 `report status` 看到这些运行，先迁移再继续。结果相同的，研究线不用重开，对照、推荐和 p 值都继续有效。结果不同的，Agent 列给用户，那才是真正的研究问题，按现有的 `retry_of` 重建或重开研究线处理。

**合约升级：** 走同一条路。旧源码能跑且结果相同就迁过去，跑不了才按现在的规则重开。

## 4. 新存的东西

要多存一样东西：这次 explore 的四张表的合并哈希，约 64 字节，放在它的 capture 里。

现在 explore 的 `fingerprint.json` 只存文件哈希，事后算不出每张表是否相同。整个文件存下来每次约 150 KB，112 次就要十几 MB，太大。按 `AGENTS.md`，新增存储字段要独立审阅并记录决定，实现前做。

## 5. 对重跑的影响

可以少跑一遍。输入指纹方案原来要先把 112 个运行在原镜像上重跑。现在改成合并两个 PR 之后，把开着的研究线上的 112 个运行**一次**迁到最新镜像，重放一遍同时解决新指纹和新镜像。

70 个旧运行也一起迁，约 1 小时，这样“所有实验都重算”就做全了。预检和 explore 仍不重跑（理由见输入指纹方案 §5）。

## 6. 需要用户决定

| 事项 | 现在 | 改后 |
|---|---|---|
| 跨镜像比较 | `changes.md`：“never rebuild them across identities”；`check_comparable` 要求同一镜像 | 四张表相同的迁移，新运行可以和旧运行比较 |
| 复现判定（`REPRODUCTION_MISMATCH`） | 只在同一镜像，比全部表 | 跨镜像只比四张表 |
| 曝光（`SOURCE_ALREADY_EXPOSED`） | 跨镜像的重放算新曝光 | 判定相同的迁移不算 |
| 旧结论 | “Old p values … stay as history” | 判定相同时继续有效 |
| 合约升级 | 旧合约的候选永远不能当对照 | 判定相同时可以 |
| 账本 | | 最多 182 个 explore 试验，每个多存约 64 字节，发布到公开的 DoltHub |

**代价：** 账户表和订单表的差别不再挡住迁移。如果某次升级只改了这两张表而经济结果没变，我们不会被拦下；如果日收益也变了，判定会拦下，这是我们要的。
