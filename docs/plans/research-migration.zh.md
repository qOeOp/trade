# 产品更新后迁移旧研究（设计）

2026-11-04 用户问：旧镜像的研究运行能不能解决，我们是不是漏了每次更新的自动迁移。接着问：如果能解决，该用 skill 还是脚本。这份设计回答这两个问题，用户同日同意（“同意这个设计”，含 §6 全部事项）。它接在 [`input-identity.zh.md`](input-identity.zh.md) 之后。

## 1. 结论

- **确实漏了。** 产品更新时，没有任何东西去处理旧研究。现在的规则（`research-round` 的 `changes.md`）默认旧运行变成历史、研究线重开。可实测结果是经济结果根本没变。
- **能解决。** 下面实测的所有样本，换到新镜像后成交、持仓、敞口、日收益都逐天相同。
- **用命令加 skill，不写单独的脚本。** “结果是否相同”由代码判定；什么时候迁、迁哪些、不同了怎么办，由 skill 指导 Agent。

**没有查清的：** 200 和 3 的账户表和订单表为什么不同。原镜像已经跑不了，账本里只有哈希，没有文件。日收益相同，说明账户表的差别不影响收益；这和 rc3 到 rc7 改过报告表示形式相符，但这是推断。

**成员文件裁剪：** 输入指纹方案把成员文件裁到窗口。研究运行里 89 个的源码把成员结束时间当 GTD 截止时间，所以这 89 个即使在原镜像上重放，订单表也会变（229 实测：只有 20 个挂单的 `expire_time` 不同，其余都相同），而跨镜像判定不看订单表。迁移之后它们的严格复现以迁移那次为准，见 §3。

**依赖关系：** 这 70 个运行都在两条早期研究线上（`ema-cross-btc-daily` 64 个，`ema-entryvar-rollingref` 6 个），没有任何当前镜像的运行拿它们当对照。所以这次迁移它们不紧急，紧迫的是以后每次更新不再让开着的研究线失效。

## 3. 设计

**“迁移”就是把旧运行放到新环境重放一次，结果相同就并入，不同就报告。** 这和输入指纹方案里“复现成功的运行也认复现时的输入”是同一个关系，只是多认一个镜像。

| 谁做 | 做什么 | 为什么 |
|---|---|---|
| **代码** | `replay reproduce --image <镜像>`：在指定镜像上重放，判定结果是否相同，相同就让旧运行也认这个镜像和输入 | 这是信任边界。让 Agent 自己判定，就是自己给自己打分 |
| **skill** | 重写 `changes.md`：更新后什么时候迁、迁哪些运行、结果不同时怎么办 | 这些要判断，也会变。Agent 能做 |
| **report status** | 列出开着的研究线上还没到当前镜像的运行，从现有记录推出 | 让下一次研究开始时能看到，不用人记 |
| **不写** | 单独的迁移脚本、定时任务、CI 步骤 | 循环一条命令不值得维护一个脚本；`AGENTS.md` 不让建调度器；CI 没有市场数据，也连不上币安 |

**判定规则：**

- 同一镜像：所有表都相同，和现在一样。
- 不同镜像：成交、持仓、敞口、日收益四张表都相同。手续费在成交里，权益路径落在日收益里。账户表和订单表只作报告，不参与判定，因为 §2 显示它们在 Nautilus 版本之间会变而经济结果不变。这是这份设计唯一放宽判定的地方。配置只比两边都有的键，不比运行契约。
- 只有一边有的表（如 `fill_volumes`）不比较。

**迁移之后怎么复现：** `replay reproduce <运行>` 不带 `--image` 时，用这个运行最近一次迁到的镜像重放，仍和运行的记录比四张表。`report compare_runs` 仍用运行自己的镜像，所以那 89 个不能再做这种配对。

**“自动”做到哪一步：** 不是合并 PR 时自动跑，因为回放要用本地市场数据，还会写公开账本。做法是下一次研究开始时，`research-start` 从 `report status` 看到这些运行，先迁移再继续。结果相同的，研究线不用重开，对照、推荐和 p 值都继续有效。结果不同的，Agent 列给用户，那才是真正的研究问题，按现有的 `retry_of` 重建或重开研究线处理。

**合约升级：** 走同一条路。旧源码能跑且结果相同就迁过去，跑不了才按现在的规则重开。

## 4. 新存的东西

换镜像重放时，在这次 explore 的 capture 清单里多存每张表的语义哈希（`table_hashes`，`{表: sha256}`，约 635 字节，182 个共约 116 KB）。只有 `replay reproduce` 换镜像时才写，`replay explore` 不写，所以普通探索永远算不上迁移。

**独立审阅（2026-11-04，子 Agent 只读代码，没有跑）：**

| 问题 | 结论 |
|---|---|
| 消费方 | `reproduction.matches`，一个就够 |
| 独立的事实 | explore 的 capture 只有 `fingerprint.json` 的文件哈希，没有运行行，所以每张表的语义哈希存在哪里都没有 |
| 不存行不行 | 只比 `returns_series` 和 `exposures` 的文件哈希不用新存，但丢了成交和持仓，而且文件哈希跨镜像不一定相等（gzip 依赖 zlib） |
| 其他做法 | 存布尔值没法核对；给 explore 加运行行会改变计数；新关系表多了表结构却没多得什么 |
| 形式 | 原设计存一个 64 字节的合并哈希。审阅否定：说不出哪张表不同，还把表的名单冻结了。改存每张表的哈希 |

**审阅发现、已改进设计的：**

- `--image` 没有查镜像来源，而这些哈希是那个镜像自己算的。现在要求 `require_main_build`，只认 main 的 CI 构建。
- 对照的身份要成组比较：只分开比镜像和输入，会放过从没跑过的组合（A 次的镜像配 B 次的输入）。
- 迁移那次重放不能算新试验（`counted_trials`）。原设计的 §6 没列这一条，它已包含在“判定相同的迁移不算”里。
- 配置怎么比原设计没定义：实测 v6 到 v7 只差运行契约，以及 `execution`、`liquidation_enabled`、`margin_model` 三个新键（新契约写明了旧契约的默认值）。规则定为只比两边都有的键，不比运行契约。
- “和迁移那次比全部表”没有依据（`matches` 不接受 explore 作原始运行），代码也多。去掉：迁移后再复现，仍和运行的记录比四张表。

**审阅指出、这次不处理的：**

- 指纹表里的 UUID 编号共用：多一个事件 UUID 可能让成交和持仓的哈希也变。这只会让判定更严，不会放过差异，结果是列给用户。
- 指纹没有算法版本：`engine/compare.py` 以后改算法，会被当成结果变化。同样偏严，到时候表现为全部不匹配，不会静默通过。

## 5. 对重跑的影响

可以少跑一遍。输入指纹方案原来要先把 112 个运行在原镜像上重跑。现在改成合并两个 PR 之后，把开着的研究线上的 112 个运行**一次**迁到最新镜像，重放一遍同时解决新指纹和新镜像。

70 个旧运行也一起迁，约 1 小时，这样“所有实验都重算”就做全了。预检和 explore 仍不重跑（理由见输入指纹方案 §5）。

## 6. 需要用户决定

| 事项 | 现在 | 改后 |
|---|---|---|
| 跨镜像比较 | `changes.md`：“never rebuild them across identities”；`check_comparable` 要求同一镜像 | 四张表相同的迁移，新运行可以和旧运行比较 |
| 复现判定（`REPRODUCTION_MISMATCH`） | 只在同一镜像，比全部表 | 跨镜像只比四张表 |
| 曝光（`SOURCE_ALREADY_EXPOSED`） | 跨镜像的重放算新曝光 | 判定相同的迁移不算 |
| 旧结论 | “Old p values … stay as history” | 判定相同时继续有效 |
| 合约升级 | 旧合约的候选永远不能当对照 | 判定相同时可以 |
| 账本 | | 最多 182 个 explore 试验，每个多存约 635 字节，发布到公开的 DoltHub |

**代价：** 账户表和订单表的差别不再挡住迁移。如果某次升级只改了这两张表而经济结果没变，我们不会被拦下；如果日收益也变了，判定会拦下，这是我们要的。

## 7. 全部研究运行的试跑（隔离账本）

2026-11-04，用迁移分支把 182 个研究运行都放到当前镜像 `a46c…`（隔离账本和隔离市场）。**170 个通过，12 个不同**，比 §1 的“所有样本都相同”差。通过的 170 个里，75 个所有表都相同，58 个账户、订单和订单事件表不同，37 个只有订单和订单事件表不同。

12 个全在最早的 v6 镜像 `11e4…` 上，都是 BTC 一年的运行。v6 共 64 个，另外 52 个通过。为了查原因，用它们自己的 rc3 镜像重放（手工把今天的导出转成 rc3 的 Catalog 格式，不经过产品，不写账本）。对照：试验 9 七张表全部等于账本里的原始指纹；下面 12 个里，除试验 12 外的 11 个也都相同。

| 运行 | 原因 | 收益（rc3 → 当前） | 证据 |
|---|---|---|---|
| 36、39、42、103、106、109、112、133 | **判定过严，经济结果相同。** 它们用括号单或止损单，rc3 和 rc7 的订单事件不同；事件 UUID 编号在全部表之间共用，所以成交和持仓的哈希也跟着变 | 相同（如 39 为 13.2345%） | 成交、持仓把 UUID 遮掉后逐行相同，日收益逐天相同 |
| 130 `ema-halftarget-dailyspec` | 源码在新版跑不了：`contingency_type: "NO_CONTINGENCY"`，rc4 起报错 | 16.91% → 0%（一笔没成交） | `runtime_failures.jsonl`；rc7 升级时已记录 |
| 184、187 | **真实变化。** 源码用原生 `EfficiencyRatio`，rc3 和 rc7 算出的值不同 | 4.55% → 4.86%；−0.15% → 2.24% | 同一组价格喂给两个镜像的指标，满周期后第一个值 0.054 对 0.131 |
| 12 `ema-staticvarref` | **市场数据变了，和镜像无关。** 源码用输入前的全部日线算风险因子；当时的回执有 638 根日线，今天的目录回填到 2020 年，有 2465 根 | 记录 17.20%；今天 rc3 和 rc7 都是 11.02% | 回执的 `daily` 计数；rc3 和 rc7 成交逐行相同 |

**判定不改。** 这 8 个的旧哈希是 rc3 当时按编号算的，账本里没有原始行，新代码也无法把旧的一边重算成遮掉 UUID 的形式。今后也只有在 Nautilus 改变事件数量时才会这样误拒，方向是偏严，不会放过真实变化。试验 12 和 184、187 被拦下，正是这个判定该做的事。

**这 12 个的处理：** 不迁移，留在原来的镜像和输入上，作历史记录。它们都不在开着的四条研究线上，当前镜像的运行也没有拿它们当对照（§2）。

**旧结论：** 184、187、12 的记录值在今天不能复现。8 个的结论不受影响。130 要在新版运行得先改源码，产生新候选。

**对输入指纹的提醒：** 目录往更早的月份回填时，同一窗口的日线文件会变，指纹也跟着变。现在目录固定从 2020-01 开始，所以不会再发生；如果以后改起始月份，要预计受影响的运行需要重算。
