## 0. 结论

- **正确性全部通过。**
  - 13.78 亿根 1m 与币安原生归档逐根比对，零差异。
  - 5m 到 1w 的派生周期，每处差异都能归入可解释的类别（第 4 节），派生规则本身没有错误。
  - 用新市场库导出的 37 币一年数据做配对原生回放，与旧 Catalog 的订单、成交、持仓、资金费、账户、收益和暴露序列完全一致，日线预热也一并比对过（第 5 节）。
  - 币池抽查 4 个月份，与独立重算的结果在名单和顺序上都一致（第 3 节）。
- **WS8a 的 7 道门槛里有 2 道不达标**：Dolt 服务端峰值内存超过 16GB；按全币池规模算，单月追加 4.2 分钟，超过 3 分钟。原因和可选的修法见第 7 节。按要求停在这里，等你决定。

## 1. 实现

- **库与档案。**
  - 市场库是 WS2 那个 Dolt 服务（`~/.local/share/trade/dolt`）上的独立库 `market`，档案类型为 `market`。
  - 研究 CLI 不传 `--ledger` 时取研究账本（与 WS10 对齐）；市场库档案的状态只给新鲜度。
  - 写账号只能插入，只能在 `main` 上提交；读账号只读。导入不需要 FILE 权限（第 2 节）。
- **表**：`bar`（1m LAST、MARK）、`funding`、`instrument`、`daily_volume`、`pool`，以及 `market_schema`（价格缩放 10⁸、量缩放 10⁴、币池规则 `usdt-perp-top50-30d-v1`）。设计见字段评审。
- **获取。** 只用币安公开数据：
  - data.binance.vision 的月归档和日归档，每个文件都核对 `.CHECKSUM`；
  - 公开 REST，用于当天尾部、当月 funding、2020 年前的日成交额，以及归档完全没有的序列；
  - 合约条款来自 exchangeInfo。

  拼接对上层不可见。两个来源对同一分钟不一致就拒绝；任何来源都没有的分钟如实记为缺口，不填补。
- **币池**（WS9 第 1 项）：每月初，在上市满 30 天、前一天仍在交易的加密 USDT 永续中，按过去 30 天成交额取前 50 名，已下架合约也算。排除的是：
  - 212 个 TRADIFI 永续（用户 2026-10-11 确认）；
  - 5 个指数类合约；
  - 1 个稳定币对。
- **派生与导出**：各周期按 WS8a 第 3 节的规则从 1m 派生；每个合约导出一个 Nautilus Catalog，含 5m LAST、MARK 价格更新、funding 和起点之前的日线。探索按 commit 和窗口缓存，封存每次都重新导出。
- **运行器**（契约 `r1-native-v5`）：
  - 输入是市场库 commit 加合约列表（`--symbols`，或 `--universe pool`）；
  - 每个策略实例收到 `pool_membership`。按用户 2026-10-11 的决定，"掉出前 50 只平不开"由策略自己执行，审计不判；
  - `run.input_identity` 改为 `{market_database, market_commit, pool_rule, universe, symbols}`，目录树哈希和 `artifacts input-identity` 删除；
  - 日线预热改为"截止到起点、中间不断的那一段日线，至少 200 根"。
- **新鲜度**（`python -m research.market.cli status`，供 WS9 研究入口使用）：commit `ebg4rg1g…` 覆盖到 2026-10-11（不含），最新完整月 2026-09，当月补到 2026-10-10。

途中发现并修正的问题（都在 PR 里）：

1. Dolt 的 `LOAD DATA LOCAL` 要求 FILE 权限，会让写账号能读写服务器上的文件。改为多行 INSERT，吞吐相当（约 16 万行/秒），写账号仍只能插入。
2. 已下架合约在 REST 上返回 400：现在按"没有数据"处理。
3. fundingRate 有单独的限额（每 IP 每 5 分钟 500 次），触发过币安的 403 限流。funding 改为单独限速，403/418/429 改为长退避后重试。
4. 每个请求新开一个连接，导致本机临时端口耗尽（Errno 49）。改为按线程复用 HTTPS 长连接。
5. 币安不为中文名合约发布 markPriceKlines 归档，REST 却有完整历史。归档完全没有时改用 REST 取整段，补导入了 1,257,090 根 MARK。
6. 某个合约准备失败时，进程池会先把其余任务跑完才报错。现在失败即取消其余任务。

## 4. 派生回归（commit `ebg4rg1g…`，420 个合约，全窗口）

做法：
- 从库里读每个合约的全部 1m，按导出用的同一段代码派生 5m 到 1w；
- 与币安原生归档逐根比对：先用月归档，月归档缺的天用日归档补，没有归档的月份用公开 REST；
- 用归档自带的样本数（count 列）给差异归类。

耗时 38 分钟，客户端峰值 4.5GB。

| 序列 | 比对根数 | 差异 | 原生缺、派生有的桶 |
|---|---|---|---|
| LAST 1m | 689,023,480 | 0 | 0 |
| MARK 1m | 689,028,792 | 0 | 1,236（月、日归档都缺，REST 有且逐根一致） |
| LAST 5m 到 1d | 5m 1.38 亿 … 1d 47.9 万 | 每个周期约 1,400～1,900 根"原生样本数 ≠ 所含 1m 样本数之和"，36～68 根只有量不同 | 41 根，REST 有且逐根一致 |
| LAST 1w | 66,599 | 2,558 根样本数不符，42 根只有量不同 | 1,996：1,322 根 REST 一致；659 根没有原生来源（周线月归档 2024-01 后停发，合约已下架、REST 不认）；15 根是边缘的不完整周 |
| MARK 5m 到 1d | 5m 1.38 亿 … 1d 47.9 万 | 样本数不符（5m 29,425 根，随周期增长递减）；零样本分钟（5m 636 根）；不完整桶（132～330 根）；**规则差异 3 根** | 5m 1,211、15m 275 根：246/82 根 REST 一致，965/193 根 REST 也没有（如 2023-11-10 03:40–04:05 全市场 MARK 5m 缺失，而 1m 完整） |
| MARK 1w | 67,203 | 1,468 根样本数不符，287 根不完整周，2 根零样本 | 1,392：994 根 REST 一致，385 根没有原生来源，12 根不完整，**1 根 REST 不一致** |

差异类别及其解释：

- **原生样本数不符。** 原生 K 线自带的 count，不等于它所含 1m 的 count 之和。也就是说，币安生成这根 K 线时用的样本和 1m 归档不同，例如 2020-01-19 的数据事故、MARK 服务重启后只聚合了重启后的分钟。这是源数据自身不一致，派生按 1m 是对的。
- **MARK 零样本分钟。** 价格服务中断的分钟 count 为 0，币安用旧值填充，而 1m 和高周期的填充值不同；原生高周期只取有样本的分钟。库里不存 MARK 的样本数（字段评审已定），所以这类桶复现不了。事件集中在 2020-07-27、2020-12-17、2021-02-19、2025-05-12 等全市场同一时刻。
- **只有量不同。** 价格相同、样本数相同，量不同，是源数据内部不一致，数量很少。
- **不完整桶。** 桶里的分钟数少于它应有的长度，出现在上市、下架和缺口边缘。
- **原生缺这根。** 能对上 REST 的，是归档漏发；REST 也没有的，是交易所自己的高周期缺失（1m 完整），或者合约已下架、没有任何原生来源可比。
- **剩下的 4 根**：
  - 1INCH、OGN、STORJ 各 1 根 MARK 5m（2022-07-12/13）：原生 5m 的样本数等于 5 个 1m 之和，价格却没有反映最后一分钟。例如 1INCH 02:25 这根，第 5 分钟的低价 0.5725 不在原生 5m 里，归档和 REST 都是如此，是币安 1m 与 5m 之间的不一致。
  - COMP 1 根 MARK 周线：2026-10-05 这周还没收盘，REST 返回的是未完成的 K 线。

- 追加的做法：用 APFS 克隆把库复制到一个临时隔离服务，按合约删掉 2026-09-01 起的数据并提交，再导入到 2026-10-01。

  - 按月份直接取已知文件名；
  - 已有月归档的月份不再向 REST 要 funding。

  改完后时间主要花在写入上（240 秒）。
- 导出的服务端 RSS 约 6.3GB，是共享服务在导入后留下的基线，不能归到导出本身。

## 7. 不达标的两项

1. **Dolt 服务端峰值内存**：导入中 17.1GB，导入后的 `dolt gc` 中 20.5GB；客户端和导出都在 16GB 以内。
   - 3,000 万行未提交数据的独立基准服务只到 1.2GB，所以不是工作集本身。
   - 服务端内存随导入总量增长，单月追加时只有 2.9GB。看起来与一次写入的总数据量有关（推测是 chunk journal 的内存索引，未证实）。
   - 这台机器有 128GB，没有出问题；但一次全量导入超过了门槛。
   - 可选的修法：
     - (a) 首次全量导入在一个分支上分段提交并 gc，最后合并回 main。这正好是 WS10 提到的"市场数据的分支用法"；
     - (b) 给服务设置 Go 的 `GOMEMLIMIT`，未测；
     - (c) 接受：全量导入是一次性的，月度追加远低于门槛。
2. **单月追加**：全币池规模 4.2 分钟，超过 3 分钟。
   - 门槛原本按 37 币定，全币池的数据量约为它的 9 倍；写入吞吐（约 14 万行/秒）是瓶颈。
   - 可选：(a) 接受，按月跑一次，4 分钟可以接受；(b) 研究并行写入，前面实测 4 路并行只快约 20%。
