# 信任边界检查：暂缓与不做的几项

2026-11-01。竞品矩阵剩余项小范围验证后，按价值从高到低修了三项：

- 策略源码伸进运行器，加载前静态检查并给缓存只读代理（#2020）；
- 审计按导出回执的费率逐笔重算手续费（#2021）；
- 登记引用的预检须与登记同配置（#2023）。

下面几项验证过，但这次不改，记下依据，等条件变了再看。

## 价格刻度按窗口放宽

现象：`market.instrument` 发现窗口里有价格不在当前交易规则刻度上的 K 线，就把整段运行的价格刻度放宽到
精度允许的最细一档。2024-02-14 有一根 BTC 分钟线不在 0.10 刻度上，所以窗口含不含这一天，1 月的挂单价
就不同（44014.71 对 44014.80），`price_precision_widened` 一个是 true、一个是 false。同一策略、同一段
行情，结果随窗口终点变。

为什么不改：

- 放宽本身是必要的。探针实测：不放宽时 Nautilus（2.0.0rc7）撮合会整根忽略刻度外的 K 线，止损单被推迟到
  99.50 成交，放宽后在 99.13 成交。
- 把刻度定为“全历史扫描后的结果”可以与窗口无关，但逐合约扫描全部分钟线约 133 秒（BTCUSDT 133.4 秒、
  ETHUSDT 135.5 秒，约 358 万行），每次导出都要付；结果也要随新数据进库而变，问题只是换个位置。
- 全局固定放宽到最细一档，会改变所有现有 BTC 运行的挂单价，打断已封存运行之间的可比性，要按身份变化处理
  （新研究线），代价大于收益。

以后可以做：导出时把刻度扫描结果按市场提交缓存一次，刻度就只跟市场提交有关，与窗口无关。等需要改导出或
升级运行契约时一起做。

## 改几个字节的源码变体

现象：暴露计数按 `source_sha256` 逐字节匹配。同一策略只改注释或空白，就算一份没跑过的源码，可以借此
重看数据或样本外区间。

为什么不改：

- 审查后改格式再发布是正常流程，按语义等价拒绝会误伤；AST 归一也挡不住改个变量名或常数的变体。
- 在正式账本里没找到实际借变体规避暴露的例子。
- 变体在账本里都有完整源码和发布记录，开题审阅能看见同一路线里内容几乎相同的源码。

以后可以做：报告里列出同一路线下 AST 归一后相同的源码，作为审阅提示，不当拒绝。

## 封存读数来自未提交的代码

现象：封存把检出的 HEAD 记为读数的代码版本，工作树里未提交的改动不核对。

不改：用户 10-20 明确决定未提交或未跟踪的文件既不拒绝、也不改变返回值。研究开始时 research-start 另核
HEAD 在 origin/main 上且工作树干净。要收紧须用户重新决定。

## 自己审自己的源码审查

现象：`record_review` 的审查人字段只要求非空，同一个 Agent 可以给自己写的源码签审查。

不改：产品里没有可信的 Agent 身份，代码分不出两份审查是不是同一个 Agent 写的，加检查只会是形式。审查原件
和执行捕获都在账本里，事后可复核。

## 中途打断后换假设重登记

读代码判断已被现有规则挡住：中断的尝试也用掉网格点；重试须 `retry_of` 且研究声明不能改
（`RETRY_NOT_ALLOWED`）；不连链的新登记引用同一源码会因源码已暴露被拒（`SOURCE_ALREADY_EXPOSED`）。
`test_continuity` 里有对应用例。

## 未实测的一项
