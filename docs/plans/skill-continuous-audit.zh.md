# Skill 持续审计：名字检查与使用热力图

2026-11-09。目标：项目变复杂时，skill 不因代码改名、删除和段落堆积而腐烂。最初写 product-doctor 也是为了这个。本文把已有的 doctor、评测和两个新工具按触发时机分层，每层只回答一个问题。设计经过独立子代理评审，评审意见和处理见文末。

## 现状证据

- **CI 不读 skill 文字。**
  - `quality.yml` 的测试任务按路径过滤，只改 `.agents/evals/**` 或 `docs/**` 的 PR 不跑测试（`quality.yml:34-37`，`tests/test_ci_gates.py:77-79` 断言了这一点）。
  - 现有测试只把 skill 路径当样例，或测 skill 的 assets 脚本。
- **死引用反复出现，都是事后由 doctor 人工发现的。**
  - 20261020-26：nautilus-report-analysis 仍用已改名的周期字段，#1615 修复。
  - 20261105-46：其中 `bundle.md:52` 引用了不存在的文件，可能属于规则 1 的路径检查范围（未核实当时引用的是什么）。
- **阳性对照：#1577。** 它是 2026-10-19 合入的 CLI 重构，squash 提交为 `c964a009f`。
  - 这次合入删掉了 23 个仍被 skill 和评测引用的名字，共 31 处，包括 `closing_order_tags`、`duration_ns`、`progress_check_due`、`ledger status`、`--dir`、`--source-bundle`。
  - `closing_order_tags` 就是 20261020-26，一天后才由 doctor 发现。
  - 基线快照导入不了 CLI（缺 `engine.live_errors`），所以这个对照只说明"规则 1 加规则 2 能报出它们"。评审者另用纯文本探针确认，`ledger status`、`--dir`、`closing_order_tags` 等确实在基线代码里出现、在合入后消失。
- **"名字必须存在"的写法行不通。**
  - 在 `02651c498` 上，原型对 skill 反引号片段报出 92 个外部名字（OpenAlex、FRED、CFTC 字段，whisper 参数，video-evidence 产物文件名），都不是缺陷。
  - 评审者把范围扩到评测后，又发现 8 处 CLI 形状的片段不能解析，同样不是缺陷：
    - 3 处是故意的反例（评测 `reviewer-reads-terms-by-command` 测的就是"`market terms` 不存在"）；
    - 4 处是"名词 + 记录号"（`validation 31` 到 `validation 34`）；
    - 1 处是正文（`live stream recording is not available`）。

## 分层

| 层 | 回答的问题 | 触发 | 跑在哪 |
|---|---|---|---|
| 名字检查 | 本 PR 有没有让 skill 引用的产品名字失效 | 每个 PR | CI，独立于 tests 的任务 |
| 评测 | 改动后 Agent 还做对吗 | 改 skill 的 PR | 本机 `claude plugin eval .agents`（已有） |
| 使用热力图 | 哪些段落在真实会话里被用到 | 整体审计时，可选 | 本机，由 Agent 在 `/tmp` 编写和运行 |
| doctor | 为什么用错或没用、怎么改、要不要授权 | 定期或出问题时 | 本机会话（已有） |

消融确认（ablate-cli）暂不计划。它需要 API key 授权、带确定性断言的研究任务集和几千次付费运行，而且它测的是"文本始终加载"，和 skill 按需加载不同。

## 名字检查

### 规则 1：skill 里的 CLI 调用和相对路径必须能解析

- **范围**：只看 `.agents/skills/**/*.md`，代码块除外。评测不查，因为评测会故意引用不存在的命令当反例。
- **哪些片段算 CLI 调用**，满足任一条件即可：
  - 带 `python -m cli.main` 前缀；
  - 首词是 CLI 名词，第二个词符合 `[a-z][a-z-]+`，并且整个片段不超过 3 个词或者带有 `--` 参数。
- **调用片段的检查方法**：
  - 名词和动词必须在 `cli.main._parser()` 里；
  - 独立的 `--` 之前的参数必须属于这个动词；
  - `--` 之后的参数只在 runner 动词上检查，必须属于 `engine/config.py` 的解析器，但要去掉 CLI 自己重建的那几个（`--market-root`、`--market-commit`、`--strategy-file`）。
- **路径**：Markdown 相对链接，以及 `references/…`、`templates/…`、`assets/…` 形式的片段，必须指向存在的文件。
- **当前状态**：在 `02651c498` 上只有 `acquire.md:73` 一处会被首词规则匹配，3 词上限把它排除了。
- **链接的识别**：链接目标只认路径字符，避免把缩进代码块里的正则 `](ip|oi|…)` 当成链接。

### 规则 2：本 PR 不得删掉 skill 和评测仍在引用的名字

- **比较的两端**：PR 的 base 提交（与 `ci-paths` 一样取 `github.event.pull_request.base.sha`，即 main 的当前 tip）和检出的 merge commit。这样被检查的就是合入后的那棵树，main 在分叉之后才新增的引用也能覆盖到。
- **跟踪哪些名字**：形状是标识符（含点号形式，`tables()` 按 `tables` 算）或长参数（`--dir`）的反引号片段。多词命令交给规则 1。
- **名字"存活"的判据**：作为整词出现在任一受版本控制的文件里。排除的文件：
  - `.agents/skills/**/*.md`、`.agents/evals/**`、`docs/**`；
  - 其他 `.md`，`cli/templates/**` 除外。

  skill 的 assets 脚本算在内。
- **报错条件**：某个反引号片段在第一父提交时存活、在 merge commit 时不再存活，而 merge commit 里的 skill 或评测文字仍在引用它。
- **已知的漏报**：一个旧名字只要还留在测试、升级路径或拒绝消息里，就算存活；同名字段只在一张表里改名，也看不出来。这些留给 doctor。
- **已知的误报**：PR 删掉了某个外部名字在代码里的最后一处（比如去掉 `engine/live.py` 里对 `submit_order_list` 的守卫），或者删掉了最后一条提到它的注释，而 skill 仍正当地引用它。这种情况应该很少见，而且多半本来就该回头看一眼 skill。真遇到再加最小的豁免方式，现在不预设。

### 放在哪里

- 脚本是 `.github/scripts/skill-names.py`。quality 里新增 `skill-names` 任务，它只依赖 `uv sync --frozen`，PR 上总是运行，不走 tests 的路径过滤，这样只改评测的 PR 也会被规则 2 覆盖。
- 总闸 `gate` 要求这个任务成功，`tests/test_ci_gates.py` 覆盖了它的各种结果组合。
- push 到 main 时没有 base，只跑规则 1。
- `tests/test_skill_names.py` 覆盖以下情形：
  - 规则 1 对真实解析器的解析结果；
  - 正文、记录号和占位符不算调用；
  - 规则 2 的改名样例：代码把 `closing_order_tags` 改名，skill 和评测还引用旧名，应当报错；
  - 同步改了 skill、或名字只是挪到别的文件，应当放行；
  - 设计页面和 skill 文字不能让一个名字算作存活；
  - 链接和路径的检查。

### 实现后的读数（2026-11-09）

- main 的 `02651c498`：规则 1 是 0 处，规则 2 对比 20 个提交之前也是 0 处，耗时约 10 秒。
- #1577 的阳性对照：规则 2 报出 23 个名字、35 处，包括上文点名的 `closing_order_tags`、`duration_ns`、`progress_check_due`、`--dir` 和 `--source-bundle`，不报任何外部名字。`ledger status` 这类多词命令不在规则 2 的范围内，归规则 1。

### 授权

这是一道新的拒绝检查：
- 拒绝两类 PR：skill 写了解析不到的 CLI 调用或相对路径；PR 删掉了 skill 或评测仍在引用的名字。
- 其余 PR 全部放行。
- 它新增了一个连只改评测的 PR 也会运行的任务，不改 tests 现有的路径过滤。

用户 2026-11-09 先对分层方案回复"可以的"。评审之后范围变了（独立任务、评测纳入规则 2），于是按上面的表述再次请用户确认，用户回复"授权，开始实现"。

## 使用热力图

不进产品，不改 skill。它是读两种宿主会话格式的启发式统计，格式会漂移；没有测试的话它自己就会腐烂。需要时由 doctor Agent 按下面的方法在 `/tmp` 重新编写和运行，结论写进当次诊断记录。

**方法**（2026-11-09 原型：`segment.py`、`scan.py`、`aggregate.py`）

- **切段**：以空行和顶层列表项为界；标识符取反引号片段，去掉占位符、纯小写单词、`True`/`False`/`None` 和数字。
- **会话来源**：`~/.claude/projects/*trade*` 和 `~/.codex/sessions` 中 cwd 在本仓库的会话，排除评测沙箱。改过 skill 或跑过评测的会话算维护会话，默认不计。
- **加载**：Skill 调用、`Base directory for this skill` 消息，或读取 skill 文件的工具调用。
- **机会**：在该段落现写法（`git blame` 中最新一行的时间）之后加载过该文件的会话数。
- **命中**：机会会话里，加载之后有工具调用用到该段某个标识符的会话数。同一工具调用 id 只计一次；读写 skill 和评测本身的调用不计。
- **2026-11-09 读数**（数据截至 `082ea043d`）：
  - 1,012 个会话、459 段、24,043 词；
  - 42.8% 的词在没有标识符的段落里；
  - 15 段、493 词有至少 10 个机会会话，但命中为 0。

**已知缺陷**：同一标识符在多个段落出现时，一次使用会同时点亮这几段。例如 `submit_order_list` 在 `strategy-authoring.md:120` 是研究策略的正当用法，在 `:206` 是 Live 适配的禁令；原型把前者的 23 个会话也算成了后者的命中。所以在按出现段落分摊命中、或按上下文区分之前，不能拿单段命中数下结论，尤其是禁令段落。

**用法约束**：冷不等于可删，热不等于写得好，热力图只用来挑候选。也不要为了让热力图看得见而往 skill 里加反引号。

## 不改的东西

不新增账本字段、不写账本、不改 skill 和评测、不改研究目标、不改已有的拒绝检查和 tests 的路径过滤。总闸只多要求一个任务成功。
