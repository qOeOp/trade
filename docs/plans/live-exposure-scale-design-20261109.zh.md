# Live 敞口倍数与启动推荐值设计

日期：2026-11-09。状态：已经一次独立复审并按复审修订；用户 2026-11-09 按推荐批准第 5 节（“Approve as recommended”），决定见 5.7。本稿本身不改产品代码、检查、配置、技能或账本。基线 `origin/main` `2a962b38e`。

## 1. 问题

用户的需求：同一个策略规则，按自己愿意承受的回撤选择放大倍数。例如一个开发期约 20% 年化、15% 回撤的规则，按 2 倍、3 倍跑成大约 40/30、60/45，只要离爆仓足够远。启动页应替用户算好可填的范围和推荐值，而不是让用户自己推算。

现状做不到，原因有三层：

1. **Live 检查写死了 1 倍。**
   - 启动准入（`engine/live_venue.py` `require_admission`）要求 `budget_usdt ≤ 100`、`max_notional_per_order ≤ 150` 且不超过 budget，USDT 钱包与可用余额都 ≥ budget。
   - 每笔入场（`engine/live_commands.py` `require_entry`）要求按限价计算的名义金额 ≤ 单笔上限 ≤ 预算 ≤ 100，并且**每笔入场前都重新读取账户、重复上面的准入**。任何一项不满足即拒单，并以失败结束本轮运行。
   - 策略按原生账户权益定仓，空仓时权益约等于钱包现金。所以 k 倍权益的入场 ≥ k × 现金 ≥ k × 预算 > 上限，k > 1 在 Live 必被拒。k = 1 也要求单笔上限约等于预算、现金约等于预算，只靠最小步长取整留出一点余地（预算 90 USDT、BTC 约 75,836 时实际是 0.84 倍）。研究技能因此写成 Live 候选“最多 1 倍权益”（#2522）。
2. **启动页四个数互不关联，也不连到策略。** 表单的 Budget、Entry limit、Loss threshold、Duration 是独立输入（`ide/web/src/model/liveTradingMap.ts`），策略看不到预算，界面也不显示：
   - 账户余额应落在哪个区间，按当前价格和最小步长是否下得出单；
   - 一笔止损大约亏多少，亏损阈值应设多少；
   - 策略需要多长的运行内预热。Live 不提供历史，两份 Retest 要先攒 80 根 15 分钟线，约 20 小时。
3. **研究规则把仓位放在源码里。** AGENTS.md：仓位、单笔风险和名义上限是 Agent 的设计变量，写在策略源码中，不变成用户约束。用户在启动页任意设倍数与这条规则冲突，需要用户决定（第 5 节）。

## 2. 证据：倍数在同一路径上近似线性

2026-11-09 研究线 `research-line-20261104-price-action-breakout-retest-15m` 上，两份 Retest 的 Live 单文件版把名义上限从 2 倍降到 1 倍。下表读自 `hypothesis compare` 与 `replay report`（BTCUSDT，开发窗口 2025-10-01 至 2026-11-01，bars 执行环境，起始 100,000 USDT）：

| 规则 | 1 倍：年化 / MARK 回撤 | 2 倍：年化 / MARK 回撤 | 交易配对 |
|---|---|---|---|
| mid3r（trial 2596 对 1892） | 16.8% / 4.45% | 32.3% / 8.86% | 96/99 配对，出场类型相同，无盈亏翻转 |
| midepisode（trial 2594 对 1912） | 16.5% / 4.04% | 32.4% / 5.19% | 66/68 配对，出场类型相同，无盈亏翻转 |

这不是纯倍数对照：两边还差下单形式（bracket 对独立订单、GTD 对 GTC 加定时撤单）和运行镜像，成交笔数也差一笔（136 对 137、198 对 199）。解读见 judgment 2172、2173。

- mid3r 的收益和回撤都约按倍数放大。
- midepisode 的回撤只降了约两成，最深一段移到一笔宽止损的计划上。推测（尚未用产品指标核实）：那类计划按 2% 风险定仓本就低于上限，不受上限影响。所以“回撤按倍数放大”只是近似，只有上限真正约束仓位的那部分计划会放大。

放大还有几个代价，必须写进页面说明或只用实际回放数体现：

- **波动拖累**：相对“k × 回放的复利收益”，对数增长约少 ½k(k−1)σ²。倍数越高，越达不到 k 倍收益；超过某一倍数后增长率反而下降。每个倍数版本自己的回放已经包含这一项，页面不另算模型值。
- **爆仓距离**：名义 N = k × 权益时，空单逆向约 (1/k − m)/(1 + m) 处达到维持保证金（m 为 Binance 该名义所在档位的维持保证金率；m = 0.004 时 1 倍约 99%，3 倍约 33%，5 倍约 20%）。有止损时通常碰不到，但跳空、断线或止损未按价成交时可能碰到。bars 回放不建模爆仓，所以页面只显示距离，不显示“回放未爆仓”。
- **开发期回撤偏乐观**：经过挑选的开发期回撤会低估未来，选倍数时要留余量，必要时以样本外验证为准。
- **最小步长**：小资金下仓位只能一档一档跳。预算约 90 USDT、BTC 约 75,836 时只能是 0.001 BTC（约 0.84 倍）或 0.002 BTC（约 1.69 倍），实际执行的倍数不等于回放里的 k。

## 3. 设计原则

- **一份源码不变。** 回测、Paper、Live 跑同一文件、同一 hash；不为倍数另写 Live 适配版。
- **收益与回撤只显示实际回放过的数。** 研究规则禁止用估算替代原生结果；不把 1 倍结果乘以 k 当作 k 倍的预期，每个可选倍数都要有自己的封存回放。爆仓距离、步长取整后的实际倍数、余额区间是由条款和输入算出的约束，不是收益预测，可以计算显示。
- **不新增账本或运行存储字段。** 推荐值都由已有事实派生：候选的封存回放、预检时的账户与行情读取、用户输入。
- **Live 安全边界保留其意义。** 现有“单笔名义 ≤ 现金预算”是首轮实盘不加杠杆的边界；改成“≤ L × 预算”是放宽拒绝检查，需要用户授权。预算上限、亏损阈值、保护覆盖、一次一笔入场、仅 LIMIT 入场等其他检查保留。

## 4. 方案

### 4.1 倍数放在哪里（二选一，见 5.1）

**方案 C（推荐）：倍数是候选的一部分。** 同一规则按倍数发布一组候选版本，例如 `price-action-retest-mid3r-live-x1`、`-x2`、`-x3`。差别只是源码里的名义上限常量，各自预检、独立审查、登记为“只改仓位”的派生并回放。

- 符合 AGENTS.md：仓位仍在源码里，由研究决定提供哪些倍数；用户在启动页从已回放的版本中选一个，看到它自己的封存结果。
- research-round 已有对应规则：只改仓位的运行不计入、也不解除“换研究方法”，按目标判断（feedback.md）。
- 回放环境：倍数越高，爆仓距离越近。research-round 规定当窗口内价格可能在持仓期内走完这段距离时改用 `quotes` 并给维持保证金率。两份 Retest 最多持仓 8 小时、有止损，3 倍约 33% 的距离远超此类行情，bars 足够，但要在回放说明里报告该距离。
- 代价：每多一档要多一次预检、审查和完整回放（BTCUSDT 一年窗口每档十多分钟）。倍数是离散的，但小资金本来就受最小步长限制，连续倍数没有实际意义。

**方案 A：倍数是运行参数。** 新增运行合同输入（例如 `exposure_scale`），三种模式都传给策略，源码按它放大名义上限。

- 选择最灵活，但需要新的 runtime contract 和三个 runner 的构造参数改动；研究回放要把倍数记入有效配置；还要修改 AGENTS.md 中“仓位不变成用户约束”的规则。
- 页面依然只能显示回放过的倍数，所以对用户而言与 C 差别不大。

### 4.2 Live 检查（见 5.2）

把“单笔名义 ≤ 单笔上限 ≤ 预算”改为“单笔名义 ≤ 单笔上限 ≤ L × 预算”，L 为产品写死的最大倍数（建议首版 L = 3）。

**每笔入场都重复准入，所以余额必须全程落在一个区间里，不只是第一笔。** 设策略倍数为 k、单笔上限为 L × B（B 为预算）：

- 钱包与可用余额 ≥ B，否则下一笔入场以 `LIVE_FUNDS` 失败结束；
- 取整后 k × 权益的名义 ≤ L × B，否则以 `LIVE_BUDGET` 失败结束。

因此权益只能在约 [B, (L/k) × B] 之间（步长取整会略放宽上沿）。k = L 时区间收缩成一个点：第一笔无论盈亏，下一笔就会失败。所以选用的倍数必须严格小于 L 并留余量，例如 L = 3 时提供 x1、x2，不提供 x3。B = 90、k = 2 时，权益须在约 90 到 135 USDT，起始余额放在中间（约 110），上下各约 20% 的余地。

如果这个区间太窄，另一条路是把每笔入场的复核从“现金 ≥ 预算”改为“现金 ≥ 本笔所需保证金”，并以亏损阈值约束整轮损失。这是另一项检查放宽，列在 5.3。

其他前提与风险：

- **账户杠杆设置。** 产品只读取、从不修改 Binance 账户的杠杆（`engine/live_venue.py`，README Live 一节）。k 倍的单子要求账户在该合约上的杠杆设置 ≥ k，否则会因保证金不足被交易所拒绝。修改杠杆是账户设置变更，需要用户单独授权（5.4）；预检应显示当前杠杆是否够用。
- **全仓与 Multi-assets。** 账户是 CROSS 加 Multi-assets，其他抵押品也会为这笔仓位担保，亏损可以超过预算；亏损阈值只触发一次平仓尝试，不界定跳空或断线时的损失。

### 4.3 启动页推荐值（派生，无新字段）

选定候选（某一倍数版本）后，启动页显示以下各项，并据此给默认值和允许范围：

| 显示项 | 来源 | 用途 |
|---|---|---|
| 该版本的年化、MARK 回撤，与用户研究目标并列 | 候选的封存研究回放（`replay report`） | 用户按风险偏好选版本 |
| 最差单笔计划亏损（占权益）、最长持仓 | 该回放已存的 cycles，经 `report.runs.tables()` 派生 | 建议亏损阈值、最短运行时长 |
| 策略倍数 k | 该回放的资金占用（`replay report` capital 中的峰值名义 ÷ 权益），不另读源码常量 | 推算单笔上限与余额区间 |
| 当前价、最小步长、最小名义、账户杠杆与余额 | 预检时的账户与行情读取（不用 `market coverage` 的日切条款） | 判断取整后是否为 0、实际执行倍数、杠杆是否够用 |
| 余额区间 [B, (L/k) × B] 与建议起始余额 | 由上面各项算出 | 默认值；预检把实际余额与区间比对并提示 |
| 实际执行倍数（取整后） | 价格、步长、余额 | 让用户看到 0.84、1.69 这样的真实值 |
| 建议亏损阈值 | 最差单笔计划亏损 × 实际名义，加手续费与滑点余量 | 默认值；避免阈值小于一次正常止损 |
| 最短运行时长 | 源码声明的预热时长 + 最长持仓 | Duration 下限提示；两份 Retest 约为 20 + 8 小时 |
| 爆仓距离 | k 与 Binance 该名义档位的维持保证金率 | 只显示，不作推荐依据 |

**超出研究目标的版本**（例如回撤高于 15%）照样列出，但标明超出目标；研究目标是研究判断的参照，部署倍数由用户选，页面不隐藏也不替用户挡掉。预检本身不要求验证，结果里会显示该候选有无样本外验证。

**预热声明。** 预热时长无法从回放或账本推出，需要源码声明。可沿用 `DAILY_WARMUP`、`USES_STOP_LOSS` 的方式加一个类属性（例如 `WARMUP_MINUTES`），但要注意：

- 读取它要执行源码，只能在运行镜像里做（例如 Live 预检的 runner），不能在 IDE/Web 进程里读；
- 不能放进现在随回放写入 `summary.json` 的 `strategy_metadata`，否则会改变原生报告内容；
- 改动 `engine/` 要发新运行镜像。

不声明的源码显示“未知”。这一项可以单独拆出，不阻塞其余部分。

## 5. 需要用户决定的事项

1. **倍数放在哪里**：方案 C（推荐，不改规则）或方案 A（改运行合同，并修改 AGENTS.md 中“仓位是设计变量、不变成用户约束”的规则）。
2. **放宽单笔上限检查**：从“单笔上限 ≤ 预算”改为“≤ L × 预算”，L 取值（建议 3，提供的倍数严格小于 L）；`max_notional_per_order ≤ 150` 的硬上限如何随之调整。现在被拒的 k > 1 入场将被允许；不放宽就只能在 Live 跑 1 倍版本。
3. **（可选）放宽每笔入场的现金复核**：从“现金 ≥ 预算”改为“现金 ≥ 本笔所需保证金”，用来放宽 4.2 的余额区间。不改则按区间运行。
4. **账户杠杆设置与首轮下单**：在 Binance 上把该合约杠杆设到 ≥ k 是账户设置变更；x2 等倍数版本的第一次真实下单是一次新的下单测试。两者都需要用户各自给出范围。
5. **预算 100 USDT 上限是否保持**：本稿默认保持。
6. 研究目标（年化 ≥ 20%、回撤 ≤ 15%）不变；倍数版本按目标判断，不改目标。

### 5.7 决定（用户 2026-11-09，“Approve as recommended”）

- 5.1：方案 C。倍数是候选版本的一部分，AGENTS.md 不改。
- 5.2：L = 3。启动准入与每笔入场改为“单笔上限 ≤ 3 × 预算”，原先独立的 150 USDT 硬上限由此取代（预算 ≤ 100 时上限 ≤ 300）。最小下单量检查改为与单笔上限比较。提供的倍数严格小于 3（x1、x2）。
- 5.3：不采纳。每笔入场仍要求 USDT 现金 ≥ 预算，按 4.2 的余额区间运行。
- 5.4：本次没有授予任何账户杠杆修改或真实下单的范围；每次执行前仍须用户各自给出。
- 5.5：预算上限 100 USDT 保持。
- 5.6：研究目标不变。

## 6. 实施拆分（授权后）

每项单独开 PR，基于 `main`：

1. 产品：按 5.2（及 5.3，若采纳）放宽 Live 准入与入场检查，测试覆盖 k = 1、区间上下沿、L + ε 的边界；`engine/README.md` Live 一节同步。
2. 产品：预检结果加入派生提示（余额区间、实际执行倍数、杠杆是否够用、第一笔是否可下），只提示不新增拒绝；预热声明（若采纳）按 4.3 的限制实现。
3. IDE：启动页按 4.3 显示派生值、默认值与范围，浅色和深色截图审查。
4. 技能：research-round `strategy-authoring.md` Live 一节由“最多 1 倍权益”改为“严格小于 L 倍”，说明倍数版本按只改仓位的派生登记；运行受影响的评测用例。
5. 研究：为两份 Retest 发布并回放 x2 版本（方案 C），各自预检、独立审查、登记、回放与解读。把倍数版本加入服务器 Live 可选源码属于主机配置，另请授权。

## 7. 不做的事

- 不用 1 倍结果外推 k 倍的收益或回撤，不显示模型化的波动拖累。
- 不在 runner 里自动缩放策略下单数量，不让产品替源码改仓位。
- 不新增账本或运行存储字段；不改历史记录。
- 不放宽保护覆盖、亏损阈值、一次一笔入场、仅 LIMIT 入场等其他 Live 检查。
