# 数据采集上服务器

2026-11-03。用户的问题：有几种数据要靠一直开着的机器采集，本机经常重建、关机，需要稳定的脚本和稳定的环境来跑采集；
R2 只是存储。

前提是 `market-parquet-store.zh.md` 里用户定的两件事：市场库迁出 Dolt，改成按内容命名的 Parquet 文件，公开副本放
Cloudflare R2；R2 只放重新生成不出来的数据（§7，2026-11-03），能从 Binance 公开归档重新导入的只留在本机。
2026-11-02 曾有一稿让服务器做 Dolt 市场库唯一的写者（要 400–500 GB 的盘），这两件事定了以后不再需要，本文取代它。

建议：
- **服务器只跑爆仓记录**，把每天的落盘文件传到 R2 的采集桶。不跑 Dolt，不碰市场目录，不写版本。
- **本机仍是市场目录唯一的写者**：本机开着时从 Binance 归档导入，并从采集桶取落盘文件导入。
- **拆的是部署，不是代码**：采集代码留在本仓库，服务器用一份单独的 compose 文件、同一个镜像。

## 1. 哪些数据需要一直开着的机器

`market-parquet-store.zh.md` §7 列了各表能不能重新生成。K 线、资金费率、metrics、aggTrades、推算报价都来自一直在的
公开归档（资金费率另有 REST 的全部历史），本机关几天只是晚导入。剩下两种：

| 数据 | 来源 | 本机关机期间会怎样 |
|---|---|---|
| 爆仓 | Binance `!forceOrder@arr`、Bybit `allLiquidation` 的推送 | **永久丢失**，两家都没有免费历史 |
| 合约条款（`instrument`） | 导入时读的 `exchangeInfo` | 观测晚了：两次导入之间变了两次，只看到最后一次；关机期间上线又下线的合约，`exchangeInfo` 从没见过，条款只能按成交推断，分类也取不到（`market/store.py:387-397`、`669-671`） |

`universe_month` 由每个合约最早一次观测到的条款分类加 K 线算出（`market/store.py:845-849`），条款在 R2 上，它就能重算；
它本身也上 R2，是为了不依赖重算。

第一批只上爆仓。条款的问题见 §7。

## 2. 分工

### 2.1 服务器

两个服务，镜像都是本机同一个 `trade-service`（CI 构建，按摘要拉取）：
- `market-record`：和本机现在的一样。每个交易所每个 UTC 日一个落盘文件，写在服务器的卷里。本机实测 11-02 09:30
  起一天多共 5.3 MB，一年几 GB。
- 上传：一个常驻循环的服务，每隔几分钟把可以上传的落盘文件传到采集桶。

**什么时候算一天写完。** 落盘文件以追加方式打开；第 D 天的文件要等第一行属于 D+1 的行写入时才关，而且零点附近
两个连接抢锁、或者主机时钟回调时，旧文件还会被重新打开追加（`market/record.py:64-93`）。所以第 D 天的文件要满足两条
才上传：D+1 已经过了一段宽限（比如 10 分钟），文件的修改时间也早于这段宽限。

**上传。**
- 对象名固定为 `<交易所>/<日子>.jsonl`，只建不覆盖（`If-None-Match: *`，R2 对它和写入原子执行，并发时只有一个成功，
  其余返回 412）。文件的 SHA-256 记在对象的元数据里。
- 传完读回，SHA-256 对得上才算传过。
- 已传过的那天，本机文件后来又变了：拒绝，报出来，不传第二份。
- 传失败就留在原地，下一轮再传。
- 不用 rclone 之类的现成工具：它们不在按摘要钉住的镜像里，也不做读回核对。上传是产品代码，理由是信任边界：
  落盘文件是观测原件，导入之前丢了或被改了就拿不回来。

**卡住了怎么办。** `restart: unless-stopped` 只在进程退出时重启；健康检查不过，Docker 只把容器标成 unhealthy，不重启
（不用 Swarm 时）。`market-record` 自己会不停重连（`market/record.py:183-217`），但进程卡死就没人管了。所以改成：
`market-record` 自己的健康检查连续 10 分钟不过，进程就以非零码退出，由 Docker 重启。

服务器不对外开端口，只开 SSH。没有 Dolt、没有市场目录、没有 DoltHub 密钥、没有交易所凭据，也不放主检出的 `.env`。
Docker 日志设上限（`deploy/compose.yaml` 已有），开机由 systemd 启动 Docker，compose 随之起来。

### 2.2 R2 的两个桶

- **市场桶**：市场的公开副本（版本文件、回执、重新生成不出来的数据文件，含爆仓的数据文件）。只有本机能写，公开读。
- **采集桶**：服务器传上来的落盘文件。只有服务器能写，不公开。

分两个桶，是因为 R2 长期有效的 API 令牌只能按桶限定权限；能按前缀限定的只有临时凭据，最长 7 天，要用父令牌签发，
对常驻服务器不实用。这样服务器被攻破，也改不了市场的公开副本。

采集桶开桶锁定：对象在一段时间内（比如 90 天）不能被覆盖或删除，被拦的请求返回 409；改锁定规则要编辑桶配置的权限，
服务器那把读写对象的密钥改不了。生命周期规则过一年删除。

落盘文件只是导入前的中转：导入后，爆仓的数据文件进市场桶，落盘文件就不再需要（`liquidation-recording.zh.md` 原本就把
落盘文件当缓存）。采集桶因此不公开、不永久保留，用户批准公开的仍然只是导入后的爆仓表。代价：本机一年都没导入，
最早的落盘文件就会被删掉。

来源：Cloudflare R2 文档的 API tokens、Temporary credentials、S3 API compatibility、Bucket locks、Public buckets 页面
（2026-11-03 查）。

### 2.3 本机

- 本机的 `market-record` 照常跑，但它的落盘文件不上传，只留在本机，用来补服务器缺的时段。
- `market-import`（`market follow`）多做一件事：按日子从采集桶取落盘文件（对象名固定，按名字读，不用列目录），核对
  SHA-256，和本机同一天的落盘文件一起交给爆仓导入。
- **同一天两份怎么选。** 每个交易所每天只用一份，不合并：连接编号各自从头数，时刻按各自主机的时钟记，合并会让
  “第一次见到”的时刻在两台机器之间来回换。用导入推出的记录时段覆盖更长的那份，一样长用服务器的。这样服务器上线
  当天、或者宕机几个小时的那天，本机记得更全就用本机的。只有两台都没开着的时段才真的丢。
  - 导入记下的“第一次见到”从此是“那一天被选中的机器第一次见到”，爆仓导入的说明要跟着改。
  - 用的是哪一份，回执要记下来，作为来源。这是新的存储字段，在爆仓导入的 PR 里先做独立审查。
- 爆仓导入本身是 `liquidation-recording.zh.md` 的第二批（#2068，现在按 Dolt 写，暂停中），改成写新存储，随市场存储
  第 4 步一起做。
- `market-import` 把采集桶最新一天的日子写进它现有的状态文件，IDE 状态栏照旧读这个文件，显示采集到哪一天。服务器停了，
  本机能看出采集在变旧，不另建告警通道。ide 容器不拿任何 R2 密钥。

## 3. 服务器的要求

- **架构 arm64**：镜像现在只构建 arm64。
- **很小就够**：1 核、1 GB 内存、10–20 GB 盘。不跑回放、不导入、不放市场库。
- **网络**：不能在美国（Binance 451），不能在中国大陆（Bybit 拒绝）。日本、德国没查到被拦的说法，必须在机器上实测
  `fstream.binance.com` 的爆仓流和 Bybit 的 linear 推送。

候选（价格在选的时候重查）：Oracle Cloud 东京或大阪的 Ampere A1（免费额度够用；免费账户的闲置机器会被回收，升级成
按量付费可避免）；Hetzner、netcup 最小的 ARM 机型。

## 4. 步骤

0. **试机**：在候选机器上测两家推送的连通性和 R2 的写入，结果写进本文。
1. **上传与自我重启**（产品代码，一个 PR）：上传命令（一天写完的判定、只建不覆盖、读回核对、已传过又变了就拒绝）；
   `market-record` 健康检查连续不过就退出；`deploy/collector.yaml`（`market-record` 和上传两个服务）。用本地的 S3 兼容
   服务测试，不碰真的桶。
2. **服务器上线**：拉镜像、`up -d`，开始记录和上传。本机的 `market-record` 继续跑。
3. **本机读采集桶**：随市场存储第 4 步和爆仓导入一起做：按日子取落盘文件、同一天两份的选择、状态文件里记采集到哪一天。

第 1、2 步不依赖市场存储的迁移，服务器到手就能做。第 3 步之前，落盘文件在采集桶里锁定存着，不丢。

## 5. 要用户做或授权的事

1. **开服务器账户、付费**：只能用户自己来。之后给一个 SSH 入口，或者用户自己按第 4 节操作。
2. **服务器的主机配置**：装 Docker、SSH、防火墙、systemd 开机启动。到时逐项确认。
3. **R2 的两个桶和密钥**：用户自己建。服务器一把，只能读写采集桶的对象；本机一把，能读采集桶、写市场桶。采集桶的
   锁定和生命周期规则由用户在 Cloudflare 控制台设。按 AGENTS.md，密钥我不能读也不能建。
4. **新拒绝**（第 4 节第 1、3 步）：上传读回对不上；已传过的那天本机文件又变了；导入时采集桶对象的 SHA-256 和元数据
   不符。拒绝码在各自的 PR 里定。
5. **爆仓导入的变化**（第 4 节第 3 步）：同一天两份按覆盖时长选一份；“第一次见到”的含义随之改变；回执记下所用的那份。
6. **从服务器连 Binance 和 Bybit 的公开推送**：已批准的爆仓记录没有限定地点，这里只是说明连接从服务器发出。

不需要授权：服务器选哪家、哪个机型，在第 3 节的范围内按试机结果定。

## 6. 以后再定

- **服务器定时抓 `exchangeInfo`**：让条款的观测不受本机开关机影响，也不会漏掉关机期间上线又下线的合约。要改导入：
  条款从采集桶里的快照取，而不是导入当时现抓。等第 4 节第 3 步之后再看值不值得。
- **paper 上服务器**：模拟盘也要一直开着，但它要 docker-api、要建容器，另议。
- **用别人采好的爆仓数据**：2026-11-02 查过，没有一家同时满足逐笔、免费、许可公开再发布（CryptoHFTData 条款禁止
  再发布；Coinalyze 只有汇总；Tardis、Crypto Lake 付费且禁止再发布；交易所自己的归档都不全）。
