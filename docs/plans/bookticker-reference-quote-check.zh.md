# 用官方 bookTicker 一次性对照推算报价（提案）

2026-10-28。提案，未实施。用币安官方归档里仅存的 U 本位 bookTicker（2023-05-16 至 2024-03-30）作为独立参照，由产品用一个固定方法，把 `binance-aggtrades-bbo-v1` 推算报价逐合约、逐日比一次，并把读数留下。这样研究会话在这个范围内引用结果即可，不必每次开始研究都重新取证。本文说明它能证明什么，需要哪些产品改动，以及每一步要用户授权的地方。

## 要解决的问题

- **每次开始研究都在重新取证。** readiness 要求推算报价用于清算研究前，先按合约、时段和用途验证；有独立 BBO 证据时要用上（“where available”，`research-start/references/readiness.md:100-105`）。但它没说证据怎样算够（[20261028-02](doctor/index.zh.md)）。01a17cec 会话把第 4–17 轮花在取证上，翻了 Wayback 和 Common Crawl，最后结论仍是“规则变更链未闭合”（[完整审计](doctor/2026-10-28-codex-01a17cec-full-audit.zh.md)）。
- **以前的对照都只留在 `/tmp`，没有一次能被引用。**
  - [十二个月首日工程对照](monthly-quote-liquidation-validation.zh.md)用的是 Tardis 免费样本，留了三个缺口：五月 Tardis 采集断连 12.37 秒；推算侧按 T、观测侧按 E，时间口径不同；旧参考原件和当时的哈希找不到。
  - [整月事后补证](quote-readings-posthoc-202510-11.zh.md)只核对了推算序列能重算一致，没有独立参照。
  - 这些都不是产品读数，下一个会话无法引用。

## 官方 bookTicker 的事实（2026-10-28 实测）

从 `data.binance.vision` 的 S3 目录完整读取，`IsTruncated=false`：

- `data/futures/um/daily/bookTicker/` 有 315 个代码，其中 U 本位 USDT 永续 270 个，zip 合计约 1.05 TB。最早 2023-05-16，最晚 2024-03-30。monthly 目录到 2024-04，但四月文件只到 04-01 06:46 UTC（[原生强平计划](native-mark-liquidation.zh.md)）。
- 币安在 [binance-public-data#334](https://github.com/binance/binance-public-data/issues/334#issuecomment-2109510370)（2024-05-14）确认已停供期货历史 bookTicker，没有恢复时间表。现有文件是将来不会再有的观测。
- 公开市场库 main 上，2023-05 至 2024-03 每月有 20–23 个 universe 成员，共 23 个不同合约。这 23 个都有 bookTicker：
  - 除 WIFUSDT（2024-01-18 起，73 天）外，每个都有 318–320 天，zip 合计约 300 GB。
  - 最大的是 BTCUSDT，52.6 GB；最小的是 TRXUSDT，3.6 GB。
- 每个 zip 都有官方 `.CHECKSUM`，可以沿用 `sources.fetch_archive` 的校验。列中有 `transaction_time`（T）和 `event_time`（E），所以参照侧可以和 aggTrades 一样按 T 对齐。这样就消掉了 Tardis 对照里 T/E 口径不同的缺口。
- 来源与现有 K 线、MARK、资金费、aggTrades 相同，都是币安官方公开归档，没有 Tardis 那样禁止再分发的许可问题。
- `update_id` 是订单簿更新序号，BBO 变化之间会跳号，不能用来证明消息完整。完整性只能按时间间隔读出并报告，不能证明。

## 能证明什么，不能证明什么

- **能：** 在 23 个合约 × 2023-05-16 至 2024-03-30 的范围内，量出推算报价与官方 BBO 在报价层面的差异分布，包括买、卖两侧，以及按分钟的不利极值。readiness 所说的验证范围还包括用途、杠杆/敞口和强平情景（`readiness.md:100-101`），这份读数只覆盖其中报价层面的部分。
- **不能：**
  - 不能推广到 2021-01 至 2023-05、2024-04 以后，或其他合约。readiness 明确禁止推广，本提案也不改这一条。
  - 不能单凭报价层差异证明强平行为。readiness 要求配对原生回放，见下面的第 4 步。
  - 不提供挂单量：官方 BBO 有量，但产品的 `quote` 表没有。
  - 不设任何准入阈值。

所以它的价值有两层：
- 它是那 11 个月内唯一干净的第一方参照；
- 它让以后对其他时期的判断，有一份同交易所、同规则的实测误差可以参考。至于怎么判断，是用户的决定，见“授权”第 5 项。

## 需要的产品改动

**第 0 步：先决条件**
- **历史规格。** [20261028-05](doctor/index.zh.md)：quote 导入对所有历史月份用最新存的价格步长（`market/store.py:981-986`）。
  - 步长只用在过时侧推开一格的那一行（`market/quotes.py:69-74`）。存储按全局 8 位小数定标，不按步长（`quotes.scaled_rows`），所以 2023–2024 年若有合约改过步长，不会 `SCALE_LOSS`，只会让推开的那几行偏一格。
  - 所存的 `quote` 行不标明哪些行是推开的。对照命令只报告参照价格和推算价格不在所用步长网格上的条数，不把差异归到推开上。
  - 20261028-05 计划的修法只是在 help 和 README 写明，不会让历史步长变对。所以对照不等这个修复，而是把网格冲突作为读数报告出来。
- **导入这 11 个月的 quotes。** 用现有 `market import-quotes --month`，按月份逐月导入（#1803 写明的途径）。导入会发布到公开 DoltHub。导入量没测过，先导一个月，量出行数、库体积和耗时，再决定其余月份。

**第 1 步：只读对照命令**

提议 `market check-quotes --month YYYY-MM [--symbols ...] --at <market commit>`。它的工作：
- 只读市场库，按固定提交读出所存的 `quote` 行；
- 逐日下载并校验官方 bookTicker 到现有归档缓存；
- 按 T 对齐，算出每个合约、每天一组固定读数，输出 JSON；
- 不写数据库。

读数的定义写在代码和 `--help` 里，方法只有一种，Agent 不再各写各的脚本。只有当产品自己把结果写下来（第 2 步），这个命令才算 AGENTS.md 所说的信任边界：方法固定，写入者是产品，Agent 不能给自己的输入打分。若最后仍由 Agent 转写结果，一个由 skill 指导的 `/tmp` 脚本就够了，不值得加产品代码。

对齐与口径（必须写进 `--help`，否则读数会误导）：
- **成交前还是成交后。** 推算的买价是一笔成交打到的那一档；同一 T 的 bookTicker 显示的是成交之后的盘口。一笔扫多档的成交，会在强平最关心的时刻造成单向偏差。读数要写明同一 T 的参照更新算在成交前还是成交后。`agg_trade_id` 与 `update_id` 是两套无关的序号，不能用来给同一毫秒内的成交和盘口更新排序。
- **状态延续。** 两侧各自沿用上一状态，直到下一次更新。参照自身有空档时也照此延续，并单独报告空档。
- **日界。** 推算从前一日的归档接续状态，而每个参照文件都从零开始。首日 2023-05-16、WIFUSDT 的首日、2024-03-30 前后这些不完整的日子要标出来。
- **身份。** 读数绑定一个市场提交和一条规则。重新导入（步长修复或规则 v2）后，旧读数即失效。

拟定的读数（逐合约、逐日；阈值一个也不设）：
- 参照：消息数；最大时间间隔及其位置；时间倒序和重复状态的条数。
- 网格：参照价格与推算价格不在所用步长网格上的条数。
- 每秒末状态的买价、卖价、中间价差异：中位数、p99、最大值，单位 bps。只看秒末会掩盖上面的成交前后偏差，所以下一项必须同时报告。
- 每分钟最低买价、最高卖价相对参照的不利差：p99 和最大值，单位 bps。这是对清算最直接的一项。
- 只有一侧有报价的秒数，按哪一侧分开。
- 两侧的交叉秒数。
- 当天的 `stale_side_adjustments`，以及成交间隔的 p99 和最大值，方便与差异放在一起看。

**第 2 步：读数存在哪里（独立评审结论见下）**

| 方案 | 做法 | 评审结论 |
|---|---|---|
| A | 在市场库加一笔空提交，提交消息里放读数 JSON | 不采用。`_commit` 用 `DOLT_COMMIT('-A','-m',…)`，没有 `--allow-empty`（`market/store.py:739-752`），要为公开市场库另开一条写入路径；它也破坏“一次导入一笔提交”（`market/schema.sql:5-6`），钉在 `main` 的回放会在数据不变的情况下指向一个新哈希 |
| B | 市场库新表 `quote_check` | 不采用。市场库存的是交易所事实和声明的推算，评估读数不属于这里；改动最大，还要加提交测试 |
| C | 不存，Agent 用 `evidence add` 自己记一条证据 | 不采用。字节和名字都由 Agent 决定，正是要避免的自评 |
| **D** | 产品写一个保留名的证据包 `quote-check-<market commit>-<YYYY-MM>`，内容是读数 JSON 和参照归档的 SHA-256 | **推荐。** 现成的先例是 `market lifecycle` 写的 `lifecycle-<commit>` 证据包（`registration/inputs.py:85-113`）：保留名由 `ledger/evidence.py:21-22` 的 `RESERVED` 挡住 `evidence add` 伪造（`:140`），`market coverage --lifecycle-bundle` 读它（`cli/main.py:914-931`）。只用现有的 `evidence_bundle`/`evidence`/`evidence_content` 表，没有新字段，按内容寻址，公开 |

D 也要等第一个月的读数和口径定下来再落存储。在那之前，命令只把 JSON 输出到 `/tmp`。

**第 3 步：消费者**
- `market coverage` 在 #1805（quote 覆盖，尚未合并）之后，照 `--lifecycle-bundle` 的做法，读对应的 `quote-check-…` 证据包，按合约和区间报告。
- readiness：如果只按合约和时段写“已有对照就引用、不重新取证”，会放宽现有规则，因为它的验证范围还包括用途、敞口和强平情景（`readiness.md:100-101`）。所以 readiness 的改动单列为一项授权（见下第 5 项），本提案不自行加句。

**第 4 步（可选，后做）：配对原生强平回放**

把参照报价写入工程用的 Catalog，按[十二个月首日工程对照](monthly-quote-liquidation-validation.zh.md)的夹具，只换报价输入，比较强平的时刻、价格和现金。这需要导出器支持写参照 `QuoteTick`，改动更大。等第 1–3 步的读数出来，再判断是否值得做。

## 需要的授权

依 AGENTS.md，逐项说明：

1. **产品代码 PR：** `market check-quotes` 命令，加 `market coverage` 的读面。现在没有固定方法，每个会话各写脚本、各下结论；改动后由产品用同一个方法算一次，并由产品写下结果。
2. **公开市场库写入：** 把 23 个合约 2023-05 至 2024-03 的推算 quotes 导入并发布到 DoltHub。现在这些月份没有 quotes：窗口全在这段时间的 quotes 回放会被 `QUOTES_MISSING` 拒绝。窗口只部分落在这里时不会被拒（`engine/run.py:855-859`，即 [20261028-03](doctor/index.zh.md)），缺的月份会静默没有报价。导入后，这段时间可以用 quotes 回放。
3. **保留名证据包：** 在 `ledger/evidence.py` 的 `RESERVED` 加上 `quote-check-…`，产品往公开研究账本写这类证据包。这会让 `evidence add` 多拒绝一类名字，属于收紧一项拒绝检查，按 AGENTS.md 需要用户授权。它不加字段，独立评审已做（见下）；product-doctor 也要求存储改动逐项取得用户授权。
4. **原件保管：** 约 300 GB 的 bookTicker 原件放不进 Dolt，提案只存 SHA-256，原件留在本机归档缓存。币安若撤下这些文件，读数将无法重新核对，而它们恰恰是不会再有的观测。这与 [20261028-07](doctor/index.zh.md) 的保管规则冲突是同一个问题，要用户定：只存哈希；另存一份不进 Git 的本机备份；或者只保留抽样日的原件。
5. **readiness 怎样引用对照：** 让已有对照的合约和时段不必重新取证。只凭报价层读数做这件事，会放宽 readiness 对用途、敞口和强平情景的要求，需要用户授权。不放宽的做法是：先做第 4 步配对原生强平回放，把强平情景也覆盖到，再按现有“在已证明范围内复用”的规则引用。
6. **对照范围以外的时期：** 2021-01 至 2023-05 和 2024-04 以后，本提案不提供证明，readiness 照旧禁止推广。若希望在这些时期也用 quotes 做清算研究，现有的出路有：
   - 用户决定把推算报价作为声明的近似模型，并在报告里附上本对照的实测差异。这是对 readiness 规则的放宽，必须由用户明确授权，本提案不包含；
   - 购买 Tardis。它不能进公开库，与“账本和市场库全部公开”的决定冲突；
   - 维持现状，不对这些时期下强平结论。
7. **网络和磁盘：** 约 300 GB 下载，存在现有归档缓存，不放进 `/tmp`。不需要任何凭据。

不需要授权、也不做的：不改 `binance-aggtrades-bbo-v1` 规则；不设阈值；不自动删除合约或缩短窗口；不购买数据；不碰研究账本。

## 独立评审

2026-10-28 由一个不带本会话上下文的只读子代理评审。它读了本草稿、AGENTS.md、`market/`、`ledger/`、`registration/inputs.py`、`cli/main.py`、`engine/run.py` 和 readiness。下列结论中，凡是关于代码的，本会话已逐项核对文件和行号。

- **消费者：** `market coverage` 和 readiness 的取证判断。
- **独立事实：** 推算报价相对官方 bookTicker 的差异读数。产品不存 bookTicker 原件，所以现有数据推导不出这些读数。
- **为什么现有字段和关系表达不了，以及选了哪种：**
  - 市场库的表和提交消息都不该放评估读数（方案 A、B 不采用）；
  - 研究账本现有的保留名证据包，已经能按市场提交存产品写下的事实，不需要新字段（方案 D）；
  - Agent 自写的证据包等于自评（方案 C 不采用）。
- **代码还是 Agent：** 只有产品自己写下结果时，加产品命令才说得通；否则用 skill 指导的 `/tmp` 脚本就够了。
- **评审纠正的草稿错误（已改）：**
  - 步长不对不会导致 `SCALE_LOSS`；
  - `QUOTES_MISSING` 只在整个窗口一条 quotes 都没有时才拒绝；
  - readiness 的验证范围还包括用途和强平情景；
  - 原来提议的 readiness 加句会放宽规则。
- **评审补充的口径（已写进第 1 步）：** 成交前还是成交后、秒末取样会掩盖偏差、状态延续、日界和不完整的日子、参照倒序与重复、读数绑定提交和规则。
- **没有核对的：** S3 计数与体积、23 个合约、#334 的说法、2023-05 至 2024-03 目前没有 quotes。本会话复查了前三项，第四项见第 0 步的实测要求。

决定：如果实施，采用方案 D，并在第一个月的读数和口径定下之前不落存储。

## 开放问题

- 一个月 quotes 导入的实际行数、库体积和耗时（第 0 步先量）。
- 2023–2024 年这 23 个合约有没有改过价格步长；对照命令会报告网格冲突，但历史规格的修复是 [20261028-05](doctor/index.zh.md)。
- 参照侧是否有采集断档：只能按时间间隔报告，不能证明完整。
