# 输入指纹只算回放真正读的内容（方案）

2026-11-04 用户：“我们的指纹计算，之前想当然的设计，现在实践发现很多的不必要设计在给我们添加麻烦”“那跑所有实验都重算，也要把这块给他摆正”。这份方案一次改对，不留兼容层。代码还没有改，等用户同意（§7）。方案已经过独立审阅（§8），下面是按审阅改过的版本。

它取代还没合并的 `market-restore-terms` 方案：那条路是补回观测时间去迁就指纹，这里直接把观测时间从指纹里拿掉，也不新增恢复命令。

## 1. 问题

`export_content_sha256` 现在哈希导出目录里的所有文件，包括 `export.json` 和 `membership.json`。这两个文件里混着很多回放根本不读的东西。比较两次运行时，还会把市场名字、截至日、合约池规则、选择方式一起比；配置里也带着截至日和合约池文件的哈希。

后果都已经发生过：

- 观测时间不同，内容相同，指纹不同（目录重建后旧运行全部对不上）。
- 改一句说明文字，所有运行的指纹都变（#2104 为此把那句话冻结了）。
- 同一窗口的数据一个字节没变，只要截至日不同就不能比较。
- 111 个 `l1kf` 运行无法复现。下面实测的原因：合约池开始时间不同（2025-02 对 2020-02），差别在窗口之外。

## 3. 指纹里留什么

回放读什么，指纹就算什么。逐项：

| 内容 | 回放用途 | 决定 |
|---|---|---|
| Catalog 数据文件（K 线、资金费率、标记价、合约、报价、成交、metrics）的路径和字节 | 全部数据 | **留** |
| `assumed`（手续费、保证金） | `engine/run.py` 按它收手续费，审计也读，数据文件里没有手续费 | **留** |
| `pieces[].episode` | 决定上市退市切分和入场范围 | **留** |
| 合约池区间 | 决定哪段时间能开仓，也传给策略 | **留。写文件时就裁到输入窗口内**，策略拿到的和指纹算的是同一份，窗口之后的信息也不再传给策略 |
| `lifecycle-evidence/` | 引擎不读，里面还带截至日 | 去掉 |
| `terms_observed_at`、`terms_source` | 回放不用，只用于审计提示 | 去掉 |
| `coverage`（覆盖统计、说明文字、`member_months`、`data_bounds_proxy`） | 引擎不读 | 去掉 |
| `commit`、`start_ns`、`end_ns`、`timeframe`、`historical_terms` | 只用于核对 | 去掉，窗口在配置里比较 |
| `pieces` 的其他字段（行数、首末 K 线、精度等） | 都由数据文件得出 | 去掉 |
| `metrics_rule`、`format`、`symbol` | 说明或重复 | 去掉 |
| `membership.json` 的 `commit`、`universe_rule` | 只用于核对 | 去掉 |
| `seconds` 特殊处理 | 新算法不读它 | 删除代码 |

`export.json` 不变，继续作为回放输入和账本里的记录。`membership.json` 只多了裁剪。输入身份不再另存一份 `membership`（2026-11-11，见文末）：`membership_unchanged` 直接拿覆盖回执里的成员文件和合约池比较。引擎不改，所以不产生新的回放镜像。

算法是排除式的：除了上表去掉的，目录里其他文件都算。将来多出的文件默认进指纹，只会多拒绝，不会漏掉。

`episode` 整个算，里面可能带窗口之后的事件，这种情况下不同截至日的指纹可能不同。这只会多拒绝，账本目前也没有用上市退市事件的运行，所以不再细分。

回放前后检查目录有没有被改（`INPUTS_CHANGED`）继续按所有文件的字节算，不走新算法。

**数据文件继续按字节算，不改成按行。** 我试过按行哈希：要解压所有数据，大的导出明显变慢；哈希又依赖 Arrow 的序列化方式，升级 pyarrow 一样可能变，只是换了一种脆弱。字节不同只会发生在锁文件升级了 Parquet 写入库的时候，而锁文件变化本来就产生新镜像，比较本来就要求同一镜像。复现只比结果（§4），也不受影响。

## 4. 其他要改的

**比较的键。**

- `input_key` 只留 `export_content_sha256`。不再比较 `market_database`、`market_commit`、`universe_rule`、`selection`、`symbols`、`membership`、`lifecycle_bundle`：它们要么已经由内容覆盖，要么和回放无关。
- `config_key` 再去掉 `market_commit`、`universe_sha256`，都已由内容覆盖。
- 这些字段继续记录在账本里。`market_commit` 用来重新导出，研究线继续按截至日归属。
- 绑定运行和注册时（`register.py` 的 `bind`）单独比较 `market_commit`，不一致仍是 `EXECUTION_MISMATCH`。研究线归属依赖这一点，以前是输入键顺带保证的。
- 新注册存的 `effective_config` 不再带 `market_commit`、`universe_sha256`。截至日已经在同一份记录的 `input_identity` 里，合约池哈希可以推出，每个试验的 `input-coverage.json` 也仍有完整配置。
- 预检的两条规则（`EXEMPT_INPUT_KEYS`、`PRECHECK_INPUT_KEYS`）比较的本来就是截至日这些字段，不是哈希。不改语义，只把调用方改成传完整身份。

**复现只比结果。** `replay/reproduce.py` 和 `reproduction.matches` 去掉输入哈希比较。保留：源码、镜像、合约、窗口、配置、报告指纹、审计通过。账户、收益和持仓都在报告指纹里，换了输入也改变不了经济结果。同时删掉 `reproduce.py` 里“旧导出带报价就重新带报价”的分支，复现不再需要逐字节还原输入。

**旧运行怎么继续当基线。** 一个运行的输入身份是一组：它自己的，加上每次完全复现（`reproduction.matches`）它的运行的。比较时看对方的输入键在不在这一组里。

- 用一组而不是替换，因为旧注册存的是旧哈希：替换之后 `report compare` 反而对不上旧注册。之后在别的截至日再复现一次，也不能让已有的比较失效。
- `register.control_trial` 带上这一组，`check_comparable` 按组判断，所有比较路径都经过它。`report/reproduce.py` 看两组有没有交集，`report/status.py` 的 `_same` 同样。
- 不存新字段，关系从现有记录推出。
- 这不是兼容层：规则不认新旧格式，含义是“这两次运行输入不同、结果相同，所以结果可以用在后一次的输入上”。
- 重新注册同一份源码本来就被 `SOURCE_ALREADY_EXPOSED` 拒绝，所以这也是不放宽曝光规则时唯一可行的路。

**一个实验只算一次。** 这正是用户 11-03 选的“旧记录保留、重跑算同一个”。

- `report/status.py` 现在把“同身份同输入键”的 explore 算作复现，不计数。输入键变了以后这条不再成立。
- 改成：身份相同且 `reproduction.matches` 成立的也不计数（现在只对预检成立，放开到研究运行）。
- 原始研究运行继续显示，复现是 explore，不进研究图谱，不增加 `research_trials`。

- 副作用：以前按“输入不同”算新曝光的旧 explore，如果结果相同也会变成复现，`all_purpose_trials` 可能回溯变小。`research_trials`、`effective_trials` 只数研究运行，不变。

**条款选择。** `market/instrument.py` 的 `terms`：取截至日可见的最新一行。没有的话，如果这个合约在截至日有可见的 K 线，取最早一行；否则仍是 `NO_TERMS`。`market/coverage.py` 的 `UNKNOWN_SYMBOL` 用同一条件。

所以截至日之后才上市的合约仍被拒绝，历史上的 tick 变化仍按截至日取，只有目录重建才会走到这条退路。走到时报告里的 `CURRENT_SNAPSHOT_APPROXIMATION` 会说明条款是窗口之后才观测到的。

**清理。**

- 删除冻结说明文字的测试（`tests/market/test_coverage.py`），这句话以后可以随便改。
- 修 `deploy/README.md` 里“so the host never fetches or publishes”。
- 同步蓝图中英两份、`market/README.md`、命令帮助、拒绝表文字和 `research-round` 里说比较规则的地方。

## 7. 需要用户决定

| 事项 | 现在 | 改后 |
|---|---|---|
| 比较（`COMPARABILITY_MISMATCH`、`PAIR_INPUT_MISMATCH`） | 市场名字、截至日、规则、选择方式不同，或说明文字、观测时间不同，都拒绝 | 内容相同就能比较，可以跨截至日。推荐候选的范围也随之跨截至日 |
| 对照运行 | 只认运行当时的输入身份 | 也认完全复现它的运行的输入身份 |
| 绑定（`EXECUTION_MISMATCH`） | 输入键不同就拒绝 | 内容不同或截至日不同拒绝，后者改成单独比较，效果不变 |
| 复现（`REPRODUCTION_MISMATCH`） | 重新导出的输入哈希不同就拒绝，不写记录 | 不看输入哈希，会真的跑完。结果相同算复现，结果不同也写下这个 explore 试验（这条路径现在就有） |
| 曝光（`SOURCE_ALREADY_EXPOSED` 第 4 条） | 输入相同且结果相同的复现不算新曝光 | 结果相同就不算，输入可以不同 |
| 条款（`NO_TERMS`、`UNKNOWN_SYMBOL`） | 截至日看不到条款就拒绝 | 截至日有 K 线就退回最早一行；没有 K 线仍拒绝 |
| 计数 | explore 按同输入键判断是否复现 | 结果相同的复现也不计数 |
| 换镜像重试（`_runtime_transition`，影响 `RETRY_NOT_ALLOWED`） | 比较输入键 | 跨截至日内容相同也算连续；新旧哈希之间不算，目前没有等待中的注册 |
| 组合对照（`INTERACTION_UNATTESTED`） | 要求恰好一个可比较的运行 | 可比较的运行变多时，可能从一个变成多个而拒绝 |
| 策略看到的合约池 | 带窗口之后的结束时间 | 裁到窗口内，读 `high` 的策略结果可能变。这种运行复现时会显示不同 |
| 正式账本 | | 写入至多 112 个 explore 试验，自动发布到公开的 DoltHub |

没有变的：不新增存储字段，不改回放引擎，不改风险和审计规则，不改用户的研究目标，不删不改任何已有记录。

**失去的东西：** 输入哈希不再能证明覆盖统计或观测时间相同，这些本来就不是回放输入。旧运行的已存哈希和新哈希永远不相等，没有复现成功的旧运行不能再和新运行比较。

**不改的做法：** 保持现状，目录丢失就重跑基线。这样 §1 的麻烦都还在。

## 8. 独立审阅

2026-11-04 一个独立子 Agent 对照代码审了初稿，只读代码，没有运行。我逐条核对了：

| 发现 | 处理 |

| `report status` 多读记录的成本 | 实测一次 `matches` 约 3 ms，不是问题 |
| §7 漏了一些受影响的拒绝 | 已补 |

**实现后的实测修正（2026-11-04）：** 成员文件裁到窗口，会改变策略读到的值。112 个 `9da1…` 运行里有 89 个的源码用 `min(b for a, b in self.membership …)` 当 GTD 挂单的截止时间：裁剪前是 2026-11-01，裁剪后是窗口结束 2026-10-01。在原镜像上复现 229，只有 `orders`、`order_events` 对不上（20 个挂单的 `expire_time`），成交、持仓、敞口、账户、日收益都相同；同一次复现不裁剪，所有表都相同。所以 §2 的“按结果复现”只对另外 23 个成立，这 89 个不能在原镜像上严格复现，要靠 [`research-migration.zh.md`](research-migration.zh.md) 的跨镜像判定（四张表）迁过去。裁剪保留：这些值在窗口之后，本来就不该让策略看到，也只有这样指纹才覆盖策略读到的全部内容。

审阅核实无误的：引擎不读 `coverage`、`metrics_rule`，只用 `commit`、`timeframe`、`historical_terms` 做核对；`assumed`、`episode` 是真正影响结果的；观测时间只进提示文字，不进报告指纹；所有比较路径都经过 `control_trial`；预检、explore 不依赖已存哈希；验证和纸面交易不用这两个键；没有发现能借复现洗白运行的路径。

## 删掉输入身份里的 `membership`（2026-11-11）

用户 2026-11-11 对这一项回「按建议」：删输入身份里的 `membership`，保留成员文件。删之前，按 AGENTS.md 先由一个独立子 Agent 只读审了一遍。结论是可以删，但有条件：

- **谁在读。** 只有验证登记的绑定在读（`registration/validation.py`）。一处是 `membership_unchanged` 的逐合约覆盖比较，另一处是"交易的合约等于成员的合约"。Paper 自己从市场推出成员；Live、报告、技能、`docs/rd` 都不读；引擎读的是回执里的成员文件。
- **它是推导值。** 它完全由市场提交、窗口终点和选择决定（`membership_path`），验证本来就照这样重算了一遍。成员文件只比它少输入窗口之前的区间，而比较前派生值已经先裁到登记窗口，那一段没人读。登记窗口落在输入窗口之内，由 `WINDOW_MISMATCH` 保证。
- **改读成员文件，检查更强。** 成员文件是策略真正拿到的那份（挂载进容器），也算进了 `export_content_sha256`；它的内容整份存在账本的开始包里（覆盖回执）。原来比较的是策略看不到的一份副本。
- **哈希。** `export_content_sha256` 只算成员文件，不受影响；所有身份比较的键集合（`INPUT_FIELDS`、预检、登记绑定、复现）都不含它。回执的整份哈希会变，但新账本里只有一个写入方，前后一致。

实现：`registration/inputs.py` 不再放进身份。验证绑定改读回执的 `membership`。测试改为修改成员文件的内容，做删除合约、缩短区间、多出合约三种情况，仍然都被拒绝。
