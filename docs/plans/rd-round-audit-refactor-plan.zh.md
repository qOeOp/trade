# 研发轮审计与重构计划（RONNIE-RESTART-20261011）

状态：计划稿。逐项与用户达成共识后，再交给独立会话实施；本文件随共识更新。

## 0. 为什么要重构，而不是打补丁

2026-10-11 04:34–11:11 这一轮，Codex 写了 47 个 attempt、1543 个产物文件，只做了 2 次经济读数，两次都是毛收益为负（D11：胜率 47.9%、CAGR −7.4%；D22：胜率 57.1%、CAGR −3.0%）。

问题不是哪一条规则写错了，而是整个工作台以"证明每一步正确"为中心：每个小问题都要单独登记 attempt、dry-run、发布、留证、回读；产品缺少可信的读数，Agent 只能手写 reader 自己评自己；记录层又在膨胀。继续打补丁，只会让仪式更重、有用部分占比更小、代码更难维护。

修复原则：

1. 每个工作项**先回答删掉什么**，再回答加什么。
2. 产品代码只放在信任边界和 Agent 做不到的地方（AGENTS.md）；但信任边界上缺的读数必须由产品给出，不能让 Agent 每轮手写。
3. 用下面的基线来衡量重构是否有效，而不是用"测试变绿"来衡量。

## 1. 已定的用户决定（2026-10-11）

- 用户只定三项目标：最大回撤、年化收益下限、胜率下限。年化收益**越高越好**，"18%–22%"不是双边区间。
- 每包风险、单币名义上限、组合风险等仓位方案是 Agent 的设计变量。Agent 在回撤预算内自己定，随时可以改，**不需要授权**；改它不算"为救结果改风险限额"。

## 2. 工作项

### WS1 目标契约：用户拥有的目标与 Agent 的设计变量分开

- **根因**：AGENTS.md 把"改风险限额"一律列为需授权；`feasibility.md` 写着"Take the goal and risk limits from the user or the latest goal-level decision"，没有区分谁拥有。结果 Agent 自定的 25bp/5%/1.5% 被锁死。
- **证据**：
  - `goal-contract.json`：用户原话"其余风险方案由Agent决定"，Agent 却写进 `do_not_modify_user_targets_or_risk_to_rescue_results`；P6 源码里不一致就 `raise ValueError('risk contract differs from authorized goal')`。
  - S06/S10/S15/S17/S19/S20 的"容量不足"所需胜率在 0.754 到 9.85 之间，实际回撤只用到 9.7%（D11）和 5.9%（D22）。
  - D21 为收紧 Agent 自定的限额申请用户授权。
- **重构方向**：
  - 目标只含三项用户指标，其中收益是单边下限。
  - 可行性检查改成在回撤预算内反解仓位和频率，不再拿固定仓位当门槛。
  - AGENTS.md 中的授权条款只覆盖用户目标和代码里的拒绝/审计。
- **待议**：
  - 目标存在哪里：现在是 material 文件，要不要成为账本里的类型化对象？（新增存储字段前须先做子代理评审，见 AGENTS.md）
  - 回撤预算怎么换算成仓位：用历史分布、蒙特卡洛，还是简单的 R 倍数上界？
  - 仓位变化以后，旧的经济读数还能不能复用？
- **验收**：给出一份新的可行性计算样例，在 20% 回撤预算内为 S08/D11 的几何反解出可达的仓位，并说明能否达到 18%。

### WS2 研究流程瘦身：research-round 重写

- **根因**：每个小问题都是一个完整的 attempt，验证没有预算；skill 的 L1–L5 与 schema 的 `layer` 四个值对不上；只有 `economics` 层失败才计数。
- **证据**：
  - D01–D10 共 10 个 attempt、69 分钟，经济结论为 0；D06 已显示年化 0.07%，之后仍做了 4 个风险/保护证明。
  - P5 先做风险证明（D18–D21），后读经济（D22），而 S08 早已显示上限约 8%。
  - S10/S15/S17/S19/S20 本质是经济不可达，却登记为 `data/failed`，进度检查从未触发。
  - 6 个 family 之间切换 13 次。来源复核 S01/S04/S09/S11/S16/S18 每次都落在同一分支。
  - 12 条 `execution/passed` 大多只是归因读数。
- **重构方向**：
  - 先做便宜的经济试探（毛边际是否为正），重的 L2 证明只做在有希望的候选上。
  - 一个研究问题对应一个 attempt，中间检查不再单独登记。
  - 层级定义只保留一套，任何关门决定都计入进度。
  - 选择压力按"对已暴露数据的读取次数"计数。
  - 来源层每个 goal 做一次。
- **待议**：
  - 允许多少未登记的探索？要不要"探索预算"？
  - 进度检查的触发条件是什么？是否在 N 次关门后强制把问题交给用户？
  - layer 是改 schema，还是删掉 skill 里的 L 编号？
- **验收**：用本轮的问题重放一遍纸面流程：attempt 数、每个 attempt 的文件数、到第一次经济读数的时间，都要明显低于基线。

### WS3 记录层：连接、查询、证据、可读性

- **根因**：`dolt_store.py:185` 每读一个对象就新建一个 TCP 连接，并先执行一次 `SELECT DOLT_VERSION()`；`find` 对每个 attempt 遍历整张图；material 不区分大小和类型；决策只有自由文本。
- **证据**：
  - 一次 `find` 约 12,450 个连接，本机临时端口只有 16,384 个；两个读取同时进行就出现 Errno 49，`find` 返回 `matches: []` 加 unreadable，退出码仍为 0。
  - 40/47 个 attempt 引用了空文件证据 `review_evidence:e3b0c442…`。
  - 约 120 张视频帧 PNG 内联在 objects 表里；`show --brief` 把超过 1536 字节的字段截断；scope 越写越长，英文部分越来越不留空格。
- **重构方向**：
  - 每条命令只用一个连接（或 unix socket）。
  - `find` 改为从索引或投影查询，不再遍历整张图。
  - 连接失败必须是非零退出，不能伪装成"不可读记录"。
  - 拒收空证据；证据引用带上角色。
  - 大媒体移出行存储，改为内容寻址托管。
  - 决策里的结构化事实（数值结论、失败部件）不再塞进自由文本。
- **待议**：
  - 大媒体放到哪里（违背"Dolt 拥有证据原件"吗）？
  - 决策结构化到什么程度，才不会变成新的仪式？
  - 是否允许决定之后再修改 next_action？
- **验收**：账本规模扩大到 10 倍时 `find` 小于 2 秒、连接数恒定；并发读不再出错；material 体积下降。

### WS4 可信读数：产品给出风险、保护、订单历史和信号导出

- **根因**：审计只检查回放结束时的状态。历史保护覆盖、逐小时组合风险、订单事件历史、信号/几何导出都不在产品里，Agent 只能手写 reader 自己评自己。
- **证据**：
  - D11–D25 手写了 18 个 reader、共 1774 行，反复出错：D07→D08 只差一行 sort key；D11 的读者断言"只会单笔全额成交"引出 D12–D14；D19 有 TypeError，D23 有 KeyError。
  - `audit_tiered_native.py:79` 写明 "No … historical protection reconstruction"。
  - **潜伏缺陷**：`D25-mechanics-ledger/fourth-result.json` 显示，母单部分成交后按 GTD 到期，止损和止盈随之被撤，已成交仓位没有保护。P1–P6 用同一套下单代码。已核查：D11-C37 和 D19-C37 的封存订单里没有"部分成交后到期/取消"的母单，两次经济失败没有被这个缺陷污染。
  - 订单事件历史只在 draft PR [Wfchang666/trade#1510](https://github.com/Wfchang666/trade/pull/1510) 上。
- **重构方向**：
  - 原生审计在整段回放中检查保护覆盖和组合风险，限额由运行配置给出，不在 reader 里写死。
  - 订单事件历史进入产品：决定 #1510 是合并还是重做。
  - 策略编写指南给出 Nautilus 原生的、能正确处理部分成交的保护模式。
  - 优先复用 Nautilus（RiskEngine、bracket/OCO），不自建平行引擎。
- **待议**：
  - 哪些读数属于信任边界（必须产品给），哪些仍是 Agent 的描述统计？
  - 部分成交时保护单失效，是策略的责任还是审计拒绝的责任，还是两者都要？
- **验收**：本轮 D07/D08/D11/D19/D20 的风险和保护问题，用产品读数一条命令就能回答，不需要手写 reader。

### WS5 运行时身份、配置与环境

- **根因**：
  - 没有"当前运行时"指针；`artifacts run` 只核对镜像 digest，不核对镜像代码来源。
  - 运行配置（如 `--exit-variant`）与策略源分离，封存前没有预检。
  - 研究会话在落后的 worktree 上跑；读者脚本没有 `python -m` 入口；隔离账本只靠环境变量区分；进程用完不关。
- **证据**：
  - 同一份 BTC/ETH 回放跑了 4 次（4 个镜像），结果逐字段一致；D05 选到没有 exposures 输出的旧镜像。
  - D07 之后的已登记运行用的镜像，是从 #1510 的 worktree 构建的（`order-history-derived-runtime.Dockerfile`）。
  - D23 照抄 P5 的 exit variant，照样走完封存才失败。
  - PYTHONPATH 漏设出现在 D01、S06、D11，D25 的 3 个探针也失败；13336 端口的 Dolt 空跑 6 小时（已于 10-11 停掉）。
  - Codex 用的 CLI 和 skill 来自 143b50357，缺少 #1505 的修补。
- **重构方向**：
  - 一个从 main 构建的当前运行时登记；已登记的研究运行只接受有来源记录的镜像。
  - 策略在源码里声明自己的配置；封存前做预检。
  - 研究会话开跑前检查自身是否基于最新 main。
  - 账本使用具名档案（profile），不再只靠环境变量。
- **待议**：
  - 是否允许研究在未合并镜像上跑（作为工程用途）？边界在哪里？
  - 开跑前的新鲜度检查放在 skill 里，还是放在 CLI 里？
- **验收**：本轮 D05/D23 这类失败在预检阶段就被拦下。
