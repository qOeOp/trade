## 0. 为什么要重构，而不是打补丁

2026-10-11 04:34–11:11 这一轮，Codex 写了 47 个 attempt、1543 个产物文件，只做了 2 次经济读数，两次都是毛收益为负（D11：胜率 47.9%、CAGR −7.4%；D22：胜率 57.1%、CAGR −3.0%）。

问题不是哪一条规则写错了，而是整个工作台以"证明每一步正确"为中心：每个小问题都要单独登记 attempt、dry-run、发布、留证、回读；产品缺少可信的读数，Agent 只能手写 reader 自己评自己；记录层又在膨胀。继续打补丁，只会让仪式更重、有用部分占比更小、代码更难维护。

修复原则：

1. 每个工作项**先回答删掉什么**，再回答加什么。
2. 产品代码只放在信任边界和 Agent 做不到的地方（AGENTS.md）；但信任边界上缺的读数必须由产品给出，不能让 Agent 每轮手写。
3. 用下面的基线来衡量重构是否有效，而不是用"测试变绿"来衡量。

### WS1 目标契约：用户拥有的目标与 Agent 的设计变量分开

- **证据**：
  - `goal-contract.json`：用户原话"其余风险方案由Agent决定"，Agent 却写进 `do_not_modify_user_targets_or_risk_to_rescue_results`；P6 源码里不一致就 `raise ValueError('risk contract differs from authorized goal')`。

- **共识（2026-10-11）**：
  1. **门槛与仓位无关。** 设计够不够，只看三样：按交易计划计的净胜率，收益回撤比（CAGR ÷ 最大回撤），以及交易所杠杆和流动性是否放得下。机制过关以后，最后一步再按回撤预算定仓位：只是一次缩放和一次确认运行，不是网格，不计入选择压力。删掉逐笔风险上限的证明链。
  2. **回撤边际。** 开发期（已暴露数据）原生 MARK 权益的最大回撤，不超过预算的 2/3，以 20% 预算计约 13%。因此开发期收益回撤比须达到 18 ÷ 13.3 ≈ 1.35。
  3. **胜率按交易计划（整包）计。** 一次信号产生的多档入场加共同止损/目标算一笔；净额包含手续费和资金费；打平算非赢。

  5. **删掉跑前的名义容量和频率扫描**（S06/S08/S10/S13/S15/S17/S19/S20/S22 一类），只保留样本量下限：开发窗口内至少 100 个已平仓的交易计划。

  7. **目标存为固定格式的 material 文件。** 只含三项用户指标、回撤时钟和窗口；目标变化就换 goal_id。不新增存储字段。

  9. **当前 Codex 轮次停在这里**，WS1 和 WS2 落地后再重开。

- **共识（2026-10-11）**：
  1. **账本只登记两种记录。**
     - 候选冻结：固定的策略修订 + 一次封存的开发期运行 + 产品给出的验收读数（WS1：计划级胜率、收益回撤比、样本数）+ 产品报出的试验次数 + 判定。冻结一次写入完成，不预登记，因为门槛已由 goal 固定，等于现成的结果映射。失败的冻结照样登记。

     - 来源阅读、定义、实现调试、事件研究、试跑，全部是不登记的探索。

     - 每 3 次失败冻结做一次进度检查；
     - 自上次冻结以来，试验日志里超过 20 个不同策略源仍未冻结，也必须检查；
     - 连续两次检查既没有排除什么、也没有佐证什么，就把问题交给用户。
  5. **判定结构化。**
     - 用记录类型（冻结/确认）取代 layer 枚举；
     - 结果为 passed、failed 或 invalid（完整性不过）；
     - 失败时必填失败部件：毛边际、成本、频率、尾部、完整性之一；
     - 数值来自产品读数，不进文本；自由文本限长。
     - 按 AGENTS.md，新增字段前先做独立子代理评审，结论写进 docs/plans。
  6. **判定不可修改，只能追加更正。** 更正是一条引用原判定的新记录。
  7. **删掉 family**，选择压力和进度检查都按整个 goal 计，换题不重置。
  8. **来源每个 goal 一份笔记。** goal 开始时用 video-evidence / research-sources 产出，冻结记录引用它。不再有来源 attempt，也不再有重复的独立复核轮次。
  9. **只留不可重建的证据**：策略源（Dolt）、封存运行（含产品读数），另可附一份简短的探索笔记。手写 reader、日志、空 stderr 都不再留证。
  10. **取消写入仪式。** 不再强制 dry-run、写后回读、validate 和回执文件；写入本身原子且先校验，CLI 的返回就是回执。dry-run 保留为可选。
  11. **存储重新设计（2026-10-11，基于 Dolt 2.4.2 实测和需求盘点，取代原第 11–15 条）。**
      - **新开一个干净的数据库，不导入旧账本。** 开发期旧数据不重要，也不需要保留：旧账本在 WS7 统一删除，WS2 本身不删。"哪些窗口已被看过"这一事实仍要写进新 goal 的 material（一句声明，不导入旧记录）。
      - **轮次用分支和标签管理。** main 只放当前 schema。每个 goal 从 main 开一条 `round/<goal_id>` 分支，结束时打只读标签。"开新一轮"和"结束本轮"各是一条命令；写入只允许在活动分支上。schema 只在 main 上改，新一轮自动用上；旧标签用 `AS OF` 读当时的表结构，不依赖当前代码。
      - **有类型的表取代通用的 objects/relations JSON。** 表包括 goal、source_note、strategy_revision（源码字节存 Dolt）、run（产品读数是真实列，成本口径从运行产物读出，不由 Agent 填写）、trial、freeze、confirmation_plan、confirmation_verdict、correction、evidence（证据字节存 Dolt）。约束和外键由数据库负责。
      - **运行报告全量入库，取代封存托管目录。** 回放在临时目录产出报告，审计（含 WS4 的裸仓审计）通过后一次提交入库：orders、fills、positions、account、order_events 等按 run_id 进有类型的表，逐时刻暴露序列（exposures）存压缩 BLOB。运行身份就是这次提交，加上策略修订、市场数据 commit 和镜像 digest。删掉 artifacts 的托管目录、manifest 哈希、verify、backup、restore 和 0700 目录检查。审计失败的运行只入库摘要和失败原因。
      - **只插入、不更新。** 并发控制只靠一行 `ledger_head`，每次写入都改它，后到者收到 1213 后重读或拒绝（实测：只比较分支头 hash 拦不住并发）。幂等用每行的 `op_id` 唯一键。去掉 `write_head` 版本号、`operations` 表、`publication` 对象和回执链。每次发表只开一个事务、只用一个连接；不使用 `dolt_commit('-am')` 去提交别人的改动。
      - **时间由服务器生成。** BEFORE INSERT 触发器把 `created_at` 设为服务器当前时间；提交日期可以被 `--date` 伪造，不采信。
      - **试验日志进 Dolt 的 `trial` 表。** `artifacts run` 的探索和封存两种模式都写一行；冻结时用 SQL 统计试验次数，删行会在 `dolt_diff` 里留痕。WS5 只负责"所有回放都走一个入口、每次运行报一次"。
      - **SQL 账号最小权限。** 写入账号只有 SELECT、INSERT，`ledger_head` 加 UPDATE，并单独授 EXECUTE ON PROCEDURE `dolt_commit`；不授库级 EXECUTE（实测库级 EXECUTE 能 reset、删标签、amend）。读取方用只读账号。同一系统用户仍能绕过，所以保证程度是"改了会留痕"，不是"改不了"。
      - **外部见证。** 冻结和确认预登记写入后，把提交 hash 和时间追加提交到一个私有 GitHub 仓库，分支保护禁止强推和删除，只存 hash 列表，不含研究内容。仓库和保护规则由用户创建，用用户已有的 gh 登录，不新增凭据。确认的"预登记早于数据形成"以它为准来核对。
      - **连接与读取。** 一条命令一个连接，走 unix socket 并显式配置路径。读取时不重新校验整张图，完整校验改成单独的审计命令。连接失败非零退出。常用 JSON 字段用生成列加索引。
      - **提交前检查。** 用 `dolt_tests` 配合提交验证组检查外键和不变量。它可以被跳过，只用来防误操作，不作为信任边界。
      - **导出。** `dolt sql -r parquet … AS OF <tag>` 包成一条只读导出命令；skill 里附几条常用的 `AS OF` / `dolt_diff` 查询。
      - **备份。** `dolt_backup sync` 到本机另一个目录，取代自制快照和恢复演练；这是 Dolt 的副本，不算另一个数据来源。
      - **测试隔离。** 集成测试自己起临时 Dolt 服务，用完关掉并删除目录；检测到活动账本配置就拒绝运行。实测活动库里积了 851 个测试残留库、共 869MB，就是测试连活动服务器造成的。

      - **新鲜度检查（自 WS5 移入）。** 冻结和确认写入前，CLI 先 git fetch，检查自身代码是否包含 origin/main 的最新提交，落后就拒绝；探索不拦。
      - **账本具名档案（自 WS5 移入）。** CLI 用 `--ledger NAME` 选择账本，去掉 `TRADE_RECORDS_CONFIG`。隔离账本的库名必须不同于活动账本，写入时校验。临时账本由启动它的命令负责关闭；`ledger status` 列出所有在跑的账本。
      - **字段评审。** 新增表和字段前，按 AGENTS.md 做独立子代理评审，结论写进 docs/plans。

### WS9 研发方向性：让每次失败都缩小搜索空间（2026-10-11 新增并议定）

- **问题**：研发的斜率不够。三个阶段约 40 次完整经济回放，没有一次同时达到三项目标，后一轮也没有比前一轮好：
  - 阶段 0 的前沿两端是 H01（年化 23.2%，胜率 36.6%）和 H27a（胜率 62.3%，年化 7.9%）；
  - 阶段 1 的 12 次经济判定全部失败，没有超过起点 B00（年化 12.0%，胜率 42.7%），3 条父链的 8 个配对区间都跨零；
  - 本轮只有 2 次经济读数，D22 扣费前毛利就是负数（−2398 USDT）。
- **根因**（WS2 解决的是"仪式太重"，这里是"方向不对"，两者不同）：
  1. **假设没有经济理由。** 用户提示词把研究问题定成了"研发罗尼的策略"，来源忠实度变成了目标；没有一个假设回答过优势从哪来、谁在付钱。Arnott、Harvey、Markowitz（2019）第一类控制"研究动机"要求事前给出经济基础，但 research-round 只留下了它的程序部分（预登记），没有留下实质部分。AGENTS.md 写的是研究问题由 Agent 选择，用户提示词实际上替代了这一步。
  2. **结论太窄，什么也排除不了。** 例如 S19 的结论是 "closes this exact impulse-high target center"，只关掉了它自己。agent-rd-methodology-plan 引用了 Platt 的强推断，要求每轮排除一个具名的解释，落地时却变成了一层一层地证明部件（47 个 attempt 里有 45 个是非经济判定），排除的范围也太窄，搜索空间始终剪不下去。
  3. **没有前沿。** 每个尝试只在自己那一层判通过或失败，没有一个持续更新的"当前最好"，流程里也就没有"斜率"这个量。
  4. **失败后不拆部件，下一个想法来自来源而不是诊断。** 产品报告已经把价格盈亏、手续费和资金费分开（`research/records/analysis.py`），但规则没有要求用它来决定下一步。结果本轮在 6 个方向之间切换了 13 次。
  5. **筛选指标不是验收指标。** S 链用 12 小时价格响应筛选，验收看的却是按计划计的净盈亏。S19 通过了筛选，但按它的几何，胜率要超过约 72% 才能打平。
- **共识第 1 项：前沿普查（2026-10-11）**：
  1. **删掉**：goal 合同里"第一阶段先做来源"的入口（本轮的 `first_stage: L1 source`），以及普查之前的任何来源核查。
  2. **不能等普查结果再议后面各项。** 普查要等多年数据（见下一条），WS9 的其余各项照常议定。
  3. **窗口**：只用 USDT 永续，从 **2020-01** 起，约 6.75 年，覆盖 2020 年 3 月崩盘、2021 年牛市和 2022 年熊市。

     - 现有的一年 Catalog 不单独跑普查。
  4. **币池按当时的市场动态选。** 从当时全部 USDT 永续里选，包括后来下架的合约，不用 2026 年回头挑出来的 37 个币。

  5. **基线**：
     - 文献里有证据的几类：时序趋势、通道突破、截面动量、短期反转、只用永续的资金费信号；再加一个等权持有作为零参照。

- **共识第 2 项：用户提示词只给 goal（2026-10-11）**：

- **共识第 3 项：开题标准（2026-10-11）**：
  1. **三个状态**：
     - draft：一张假设卡，加一次粗糙的探索回放；
     - open：允许细化，即多次探索回放；
     - 冻结：按 WS2。
     开题标准只管 draft → open 这一步。
  2. **删掉**：来源核查轮次；价格响应这类代理筛选（S 链）；"先把规则写细再动手"。
  3. **假设卡写四样**：
     - 经济理由：优势从哪来，谁在付钱；
     - 一条可证伪的推论，不能是"它会赚钱"，要能用同一次回放检验；
     - 针对的是哪个前沿缺口；
     - 失败时排除哪一大类。
  4. **独立子代理在粗糙回放之前审假设卡。** 审阅者是干净上下文，只看假设卡、普查前沿和知识清单，不看任何回放结果。以下情况拒绝开题：
     - 经济理由是套话，或是事后编的；
     - 推论检验不了；
     - 排除范围窄到只排除自己；
     - 与已排除的大类重复。

     - 扣费前价格盈亏总体为正；
     - 去掉贡献最大的那一年之后，扣费前价格盈亏仍为正。这一条防的是 2020–2021 年牛市里偏多策略白拿的收益；
     - 可证伪推论成立。
     费用问题留给细化阶段。没过门槛，就按卡上事先写好的大类记入排除。
- **共识第 4 项：知识清单（2026-10-11）**：
  1. **删掉**：

     - 当前前沿；

  1. **删掉**：失败后直接换机制或换来源片段的做法。

     | 部件 | 判据 | 下一步 |
     |---|---|---|
     | 毛边际 | 扣费前价格盈亏 ≤ 0，或只靠一年撑着 | 换信号，按假设卡上写定的大类记入排除；不准再调执行和出场 |

     | 频率 | 单笔赚钱，但计划数太少、年化不够 | 扩到更多币或更多周期，或放宽进场条件 |

  3. **读数分工**：
     - 产品报告新增**按年拆分**的扣费前价格盈亏、手续费和资金费，在已对账的持仓周期上计算。它决定开题门槛和排除，算错会误杀。

     - 尾部集中度只影响下一步的方向，由 Agent 用 nautilus-report-analysis 计算，不进产品。
     - 这一条与 WS2 第 5 条"失败时必填失败部件"合并，部件取值以此表为准。
- **共识第 6 项：进度检查（2026-10-11）**：
  1. **触发**：以下三条任一满足就检查。
     - 3 次失败冻结；
     - 自上次冻结以来，超过 20 个不同的策略源没有冻结；
     - 每关闭 5 个 draft，包括被排除和没过开题审阅的。
     前两条沿用 WS2，第三条是新加的，原因是大部分假设在 draft 阶段就被排除，走不到冻结。
  2. **检查看两样**：
     - 前沿有没有外移。差距 = max(0, 胜率目标 − 计划胜率) / 胜率目标 + max(0, 收益回撤比目标 − 收益回撤比) / 收益回撤比目标；所有点中最小的差距变小，就算外移。
     - 排除了几大类。
     开发期读数只用来判断方向，不当证据。
  3. **交给用户**：连续两次检查前沿既没外移、也没有新的大类被排除，就交给用户。附上三样东西：
     - 前沿图；
     - 排除清单；
     - 建议：目标看起来是否可达，卡在哪一项，下一步怎么走（换假设来源、等更多数据，或请用户重新考虑某一项目标）。
     目标只能由用户来改，Agent 只给建议。
  4. 这一项取代 WS2 第 4 条停止规则中"检查看什么"的部分，触发条件和交给用户的规则合并为上面三条。

  2. **先收集上下文**：
     - 账本状态，以及有没有未结束的轮次；

### WS10 账本作用域：全局事实、按数据窗口的知识、按 goal 的判定（2026-10-11 新增，计划稿）

- **状态**：方向已与用户确认（2026-10-11）；下面各条待逐条议定后，再交给独立会话实施。
- **根因**：WS2 把每个 goal 做成一条从 main 分出、永不合并的分支 `round/<goal_id>`，结束时打只读标签。main 上只有表结构；`goal` 表强制只有一行；trial、运行、策略源、证据、冻结、确认全部写在这条分支上。这等于默认"一个 goal 是一个封闭的世界"。按真实用法，大部分记录是跨 goal 的事实，只有目标和判定才属于单个 goal。设计时没有对照真实使用场景，区分哪些是局部的、哪些是全局的。
- **证据（真实场景）**：
  1. **第一次使用，跑不了前沿扫描。** 前沿扫描是 WS9 原称的普查，改名见 [qOeOp/trade#1535](https://github.com/qOeOp/trade/pull/1535)。WS9 规定没有起点时先扫描、再问三项目标。但 `artifacts run` 没有打开的轮次就拒绝运行（每次回放要先写一行 trial），而开轮要先有带三项目标的 goal（数据库要求回撤在 0 到 1 之间、年化大于 0）。知识清单存成证据，也只能写进打开的轮次。可能的绕法都不好：
     - 填一组占位目标开轮：账本里记下一个不是用户定的目标；
     - 绕过 `artifacts run`：回放不进试验记录，选择压力漏记。
  2. **第二个 goal 低估选择压力。** G1 在 2020-01 至 2026-09 上扫描加研究，共约 46 个策略源，H7 冻结并确认通过。随后 G2 用同一窗口，比如找与 H7 低相关的组合策略，或者用户提高了年化目标。G2 的分支从 main 分出，trial 表是空的；G2 冻结时，产品报 `distinct_sources = 3`。被反复挖掘的是**数据窗口**，选择压力却按 goal 分开算；"上次冻结以来超过 20 个策略源"的进度检查计数也跟着归零。
  3. **策略和运行不能跨 goal 引用。** G2 要把 H7 和新策略写进一个文件组合交易，还要算两者的相关性。H7 的源码和运行都在 `closed/G1` 里：源码只能导出后在 G2 重新发表，两边的身份就断了；运行只能用 `AS OF` 去旧标签读，冻结又只能引用本分支的运行。
  4. **来源不能跨 goal 复用。** skill 要求早先轮次用过的来源要复用并引用，但 `freeze.source_bundle` 的外键只能指向本分支的 evidence bundle。
  5. **知识清单要翻旧标签。** 清单按市场加窗口共用，每个新 goal 却都要列出所有标签、逐个找最高版本（`research-round/references/knowledge.md` 现在就是这样写的，是在绕这个问题）。trial ID 在每条分支上都从 1 开始，跨轮次引用时会撞号。
  6. **暴露声明每个 goal 手抄一遍。** WS9 的 goal 字段评审（[qOeOp/trade#1535](https://github.com/qOeOp/trade/pull/1535) 的 `ws9-research-direction.zh.md`）已指出，`known_exposure` 是市场加窗口的事实，不属于 goal。
  7. **档案的作用域也混了。** WS8b 把市场数据库登记成第二个 `active` 档案后，研究 CLI 不传 `--ledger` 就报 `LEDGER_UNSELECTED`（2026-10-11 实测）；市场数据库的档案也带着 `open_round` 和 `closed_rounds` 字段。
- **作用域划分（已与用户确认）**：

  |---|---|---|

- **共识第 1 项：单分支、goal 多行（2026-10-11）**：

  2. **goal 是多行，同一时间只有一个进行中的 goal。** 开始一个 goal 就插入一行；结束就插入一条关闭记录。有 goal 进行中时，不能再开新的。冻结、确认、更正都指向当前进行中的那个 goal，不用显式写 `--goal`。

  2. **扫描的回放就是普通的探索回放**，每次照样先写一行 trial。基线代码发表入库，假设卡可以以它为父版本往下改；基线的成绩作为前沿点记进知识清单，引用 trial ID。要用详细结果就重跑。不新增"没有 goal 也能封存"的路径。
  3. **放宽一条拒绝条件（用户按上述流程同意，2026-10-11）**：没有进行中的 goal 时，允许探索回放。封存回放、冻结和确认仍然要求有进行中的 goal。

  5. **进度检查的"超过 20 个不同策略源"只在当前 goal 内计数**：从本 goal 开始或本 goal 上次冻结算起。
  6. **trial 属于哪个 goal 不加字段**：同一时间只有一个 goal，按写入时间推出；不在任何 goal 期间的 trial，就是扫描或工程回放。
