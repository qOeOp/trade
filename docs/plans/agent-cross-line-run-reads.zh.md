# IDE 聊天 Agent 按指标跨研究线查运行

**设计稿 · 2026-11-08 · 已经独立审阅（第 10 节），第 7 节已定，已实现。** 起因是生产上的一次提问没有得到回答；[#2460](https://github.com/qOeOp/trade/pull/2460)
修好了「没有回答」和「截断切掉后面的键」。剩下的问题是：数据都在账本里，但聊天 Agent 的工具读不到一张能回答
这类问题的表。

## 1. 起因

2026-11-07 15:01Z，生产 IDE 的聊天 Agent（DeepSeek `deepseek-flash`）被问「当前研发出来的所有策略中夏普最高
最高频的是哪个」。它调了 12 步、19 次工具，0 段文字（线程 `ee20120c…`）。按顺序看它走过的路：

| 步 | 读了什么 | 卡在哪里 |
|---|---|---|
| 1 | `research state --full`、`candidate list` | 分别 811,192 和 800,839 字符，只看到前 20,000 |
| 2–6 | `SHOW TABLES`、`DESCRIBE run_sealed` 等 | 找不到存夏普的列（设计上就不存，见第 2 节） |
| 6 | `research status` 一条线 | 151,065 字符；对比表排在最后，截断正好切在 `"measures":{"ann` |
| 7 | `replay report --trial-id=585` | 一次一个运行，有 `sharpe_365`，但全账本 526 个 |
| 8–12 | 用 `ledger_sql` 读 `run_return`，打算自己算夏普 | 步数用完 |

#2460 之后，最后一步会给出回答，`research status` 的对比表也能看到（每条线约 8 个运行，注明其余的被省略）。
但「所有策略里谁最高」依旧答不出：每次只能看一条线，且一条线的运行放不进 20,000 字符。

## 2. 数据都在，缺的是读法

**存储。** 按 [报告存储字段决定](report-storage-fields.zh.md)，账本存每日收益和持仓周期，年化、胜率、夏普这类
能从它们算出来的量不存，由 `report/measures.py` 在读时按「度量名@定义版本」算。所以问题需要的事实都在账本里，
加存储字段既不需要也违背 AGENTS.md「不存派生量」。

**现有读法。** 能给出指标的只有：

| 读法 | 范围 | 大小（本地账本 2026-11-08） |
|---|---|---|
| `replay report` | 一个运行 | 约 16,000 字符 |
| `research status` 的 `comparison` | 一条线窗口和选币规则下的全部运行 | 一线 134 个运行、约 150,000 字符；每行带 9 个输入键哈希和 `dominated_by` 列表 |
| `ledger_sql` | 任意只读查询 | 拿不到指标，只有原始收益 |

研究会话里的 Agent（Codex、Claude Code）有命令行，可以把输出写进文件再用 `jq` 筛，所以没碰到这个问题。聊天
Agent 没有命令行，一次只能看 20,000 字符、最多 12 步。它的七个工具是把研究会话用的命令原样包了一层（见
[聊天 Agent 设计](product-agent-chat-design.zh.md) 第 4 节），没有为「在对话里按指标找运行」设计过。

**本地实测读全部运行的代价。** 用对比表同样的函数（`metrics.load_runs`、`report.candidates.assess_listed`、
`measures.derive_measures`）读本地账本：561 个通过的研究运行里 526 个有经济证据，逐个算出全部指标（对比表只取其中
四项）共 7.7 秒（列表 0.7、载入 0.3、资格 0.3、逐个读事实并计算 6.4 秒，约 12 ms/运行），常驻内存峰值 218 MB。

## 3. 要回答的问题

都是「在一批运行里按某个指标找」：

- 所有策略里夏普最高 / 年化最高 / 回撤最小的是哪几个；
- 交易最频繁的是哪个；
- 某条线上的运行和用户的两个目标比起来怎样；
- 某个版本在各条线上的表现。

## 4. 约束

- **代码不排序、不打分。** [F-2-1-1](../rd/feedback.zh.mdx) 写明代码只给绩效指标和计数，不给优先级、推荐分数
  或调度建议；[F-3-2-1](../rd/feedback.zh.mdx) 写明对比表「不带分数和排序」，`report/status.py:464` 写着
  *Nothing is ranked, scored or stored*。
- **不同执行身份不互相排名。** F-3-2-1：别的执行身份的运行只作历史，不与之排名。执行身份的键包含有效配置里的
  `start`、`trade_start`、`end`、`symbols`、`account`（`registration/comparability.py:18`，`report/status.py:94-99`），
  所以**窗口不同的两条线，运行之间一定是不同身份**。「所有策略里夏普最高」必然是跨身份的比较，这一条直接
  冲突，要用户定（第 7 节第 1 项）。
- **目标不贴到运行上。** `ledger/targets.py:5`：目标用来读报告，从不决定候选资格；`report/status.py:4-5`：
  什么都不带目标或资格标记。`research graph` 是把目标和指标并列，让读的人自己比（`report/graph.py:468`）。
- **数字要和单运行报告一致。** 只用 `report/measures.py` 已有的度量，不在别处另写公式，更不让模型用 SQL 自己算。
- **AGENTS.md 的「代码还是 Agent」。** 加产品代码的理由：聊天 Agent 自己做不到（没有命令行、20,000 字符、
  12 步）；数字口径是信任边界（模型自己算会和报告对不上）。
- **不加存储字段，不改拒绝、审计和目标。**

## 5. 方案比较

| 方案 | 做法 | 结论 |
|---|---|---|
| **A. 新只读命令 `research runs`**（建议） | 全账本每个有经济证据的研究运行一行，只带几项指标值，可按线筛选、按一个点名的指标排列、限制行数；聊天 Agent 加一个工具包它 | 一次调用回答第 3 节的问题；运行总体和对比表共用一个函数；研究会话也能用 |
| B. `research status` 加精简选项 | 对比表去掉哈希和 `dominated_by` | 还是一次一条线；17 条线要 17 次调用、每次约 6 秒 |
| C. 只在聊天服务里裁剪 | TypeScript 工具逐线调 `research status` 再拼 | 绕开产品命令，在聊天服务里再抄一份「读哪些运行」；慢 |
| D. 让模型用 SQL 从 `run_return` 算 | 只改提示词 | 公式在产品之外又抄一遍，数字可能和报告不一致；拒绝 |
| E. 放大 20,000 字符上限 | 改常数 | 一条线就 150,000 字符，放大也装不下，还拖慢每次回答；拒绝 |

现有读法里没有覆盖全账本的：`research graph` 每个试验带四项度量，但只读一条线且带完整源码；`research status`
只读一条线；`candidate list` 只有资格，没有度量。

## 6. 设计（方案 A）

### 命令

```
research runs [--line LINE] [--by MEASURE] [--limit N] [--at REF]
```

- **读哪些运行。** 和对比表同一总体：`purpose = 'research'`、`status = 'passed'`、有经济证据（`assess_listed`）。
  把 `comparison_table` 里选运行的那段（`report/status.py:474-485`）抽成一个函数，两处共用，免得以后两边不一致。
  没有经济证据的只给个数。`--line` 只留该线窗口和选币规则下的运行（等于该线对比表的 `runs`）；不给时是全账本。
- **按执行身份分组，组只列一次。** 用对比表的 `_identities` 和 `_same`（键集合有交集即同一身份，复现运行的键
  并在原运行里）把行分组。每组列一次：`group`（本次输出里的序号）、`runtime_contract`、`execution`、
  `image_digest`、`window_start`、`window_end`、`universe_rule`。读不出身份的运行单独一组，写明原因。
- **每行**只带值，为空时写原因码：

  | 字段 | 来源 |
  |---|---|
  | `candidate`（ID@N）、`trial_id`、`group` | 试验、候选表；上面的分组 |
  | `lines`：这个运行归属的研究线 | `lines.line_trials`，和 `research graph` 同一归属规则（`report/graph.py:356-358`） |
  | `annual_return@1`、`mark_max_drawdown@2`、`sharpe_365@1`、`sharpe_lo@1`、`plan_win_rate@1`、`cycles@1`、`daily_turnover@1` | `derive_measures`，和 `replay report` 用同一函数；不读市场（和 `_headline` 一样传 `market={"error": ...}`） |

- **涉及的研究线列一次**：`lines: [{bundle, targets}]`，`targets` 是该线当前的两个目标，原样列出，不和运行比，
  不在行上贴是否达标。
- **`--by`** 只接受上表的一个度量名，按它排列（回撤由小到大，其余由大到小），空值排最后，同值按 `trial_id`；
  不给时按 `trial_id`。`--limit` 截前 N 行，输出给出 `runs_listed`（截之前的行数）。
- **返回** `ledger_commit`、`runs_listed`、`without_economic_evidence`（个数）、`by`、`groups`、`lines`、`runs`。
- **`--help` 的 returns 段写明**：
  - 排列只是按点名的一个度量排序，不是推荐，也不是对比表；
  - 不同组的运行窗口、标的或镜像不同，名次不能直接比；
  - 名列第一的值是 `runs_listed` 个运行里的最大值，有选择偏差。全账本没有多重检验调整，按线的调整看
    `research status` 的 `multiple_testing`；
  - 按回撤排时，几乎不交易的运行会排在前面，要同时看 `cycles@1`。

### 大小

分组和研究线各只列一次以后，每行约 200 字符（候选名、7 个数、组号、线名）。526 行约 105,000 字符，所以
聊天工具默认 `--limit=30`，约 6,000 字符。#2460 的截断按最大数组的尾部截，`--by` 排过序后前面的行会留下来。

### 聊天 Agent 的改动

- 新工具 `research_runs`：参数 `line`、`by`、`limit`（默认 30，最大 100）、`at`。
- 系统提示词加一句：「按度量在多个运行或多条线里找，先用 `research_runs`；名列前面不等于推荐。回答时要写出
  各行属于哪一组（窗口、标的），不同组的名次不能直接比。」
- 工具列表的只读测试（`tools.test.ts` 的 `READ_ONLY`）加入 `research runs`。

### 代价

每次调用都从头算，不缓存（一个对话先按夏普、再按年化查，就付两次）。服务器上 Agent 容器限 0.5 CPU、1024 MB
（`deploy/release_host.py:292-297`），工具超时 180 秒。实现后在本地真账本上拆开测（566 个运行）：

| 部分 | 墙钟 | Python CPU |
|---|---|---|
| `run_facts`（读 Dolt） | 5.2 秒 | 2.2 秒 |
| `derive_measures` | 1.1 秒 | 1.1 秒 |
| 全部研究线的 `line_trials` | 0.7 秒 | 0.2 秒 |
| `research_runs` 整体 | 8.8 秒 | 4.0 秒 |

计算只占 1.1 秒，只算 7 项省不了多少，不改。Python 部分在 0.5 CPU 下约 8 秒，再算上服务器 CPU 慢一些和 Dolt
读的时间，估计 20–40 秒，在超时之内；内存约 220 MB。本机没法模拟服务器的 CPU，所以准确的耗时在发布后测
（第 8 节）；超过 60 秒，就把 `run_facts` 的逐运行查询批量化。

## 7. 用户的决定（2026-11-08）

1. **允许跨执行身份按一个度量列出**（用户：「Allow, as proposed」）。F-3-2-1 已经补上说明。以下是当时的选项：
   - 现在：F-3-2-1 写「别的执行身份的运行只作历史，不与之排名」；窗口不同就是不同身份，所以「所有策略里夏普
     最高」没有允许的读法。
   - 改后：加一句说明，`research runs` 是按一个点名度量排列的描述性读法，不是对比表、不是推荐，可以跨身份列出，
     行按身份分组，回答必须写明各组的窗口和标的。推荐和复盘的规则不变。
   - 不改的话：`research runs` 只能在一组之内排列，原来的问题要回答成「每条线各自最高的是谁」。
   - 建议：改。用户问的是一个查询，并没有要选一个版本去推进或上线。
2. **「频率」用已有的两个度量**（按建议办，没有另问）。以下是当时的选项：
   - 建议：直接用已有的 `cycles@1`（交易窗口内开平仓的次数）和 `daily_turnover@1`（每日成交额 ÷ 初始资金），
     并说明不同窗口的次数不能直接比。
   - 另一种：在 `measures.py` 加一个带版本的「每日周期数」度量。但这份目录也是登记预测用的
     （`registration/duties.py:1-6`），加度量的影响面更大，要另走一次改动。

## 8. 验收

- 单元测试：
  - 排列方向，空值排最后；
  - `--line` 选出的 `trial_id` 集合等于该线对比表 `runs` 的集合（两处共用一个函数后，这条是防回归）；
  - 分组和 `_same` 一致；
  - 首行的度量等于 `replay report` 的 headline。
- 本地真账本：`research runs --by sharpe_365@1 --limit 5` 的首行，值和它自己的 `replay report` 相同。
- 发布后：在生产重问原问题，3 次工具调用以内给出回答，按组写明窗口，数字和工具卡片一致；同时记下
  `research runs` 在服务器上的耗时。

实现时的结果：
- 单元测试全部通过。
- 本地真账本：账本在 2026-11-08 比第 2 节测量时多了运行 2557，它排第一（夏普 2.71），之后依次是 1912、2539、
  2130，和第 2 节的顺序一致；2557 的五项 headline 和它的 `replay report` 逐值相同。
- 改用共用函数后，`research status` 在同一账本提交上的输出和改动前相比，只有代码版本
  `metrics_revision` 不同。

## 9. 不做

- 不存度量、不加字段，不改 `research status`、对比表、拒绝、审计或目标。
- 不做综合分数、跨身份的支配关系或默认名次；行上不贴是否达标。
- 不加新度量（除非第 7 节第 2 项选了另一种）。
- 不改研究会话的 skill。
