# 代码设计：引擎运行器与审计器

`engine/`　运行环境内的运行器、原生报告写出与独立审计器。运行器只装载源码、固定账户与撮合配置、接入导出数据；交易事实全由引擎产生；审计器只读报表对账。不知道账本。

每个函数一条：签名、用途、参数、返回、期望行为、拒绝码、使用的别处定义、关联章节与参考资料。

### `audit_main` [#def-engine-audit_main]

审计器进程入口；报表不全不运行；以退出码报告通过与否

```python
def audit_main(run_dir: Path, output_path: Path) -> None
```

<TypeTable type={{ "run_dir": { type: "Path", description: "运行器写出的报表目录（只读）：summary.json、orders.csv、fills.csv、positions.csv、account.csv、returns_series.csv、order_events.jsonl.gz；覆盖回执 input-coverage.json 位于其上一级目录" }, "output_path": { type: "Path", description: "审计结果文件路径（JSON），位于唯一可写的审计输出目录；父目录不存在则创建" } }} />

**返回**　None；退出码 0 = 通过，1 = 有发现（结果已写），2 = 报表不全或摘要不可读、审计未运行（不写结果文件）

**期望行为**

1. 核对报表集合齐全：摘要、五张报表与订单事件史均存在且非空；任一缺失即 REPORTS_INCOMPLETE，退出码 2，不写结果文件。
2. 调用 audit 读摘要并执行通用审计；摘要不可读即 SUMMARY_UNREADABLE，退出码 2。
3. 把结果原样写入 output_path（含 scope、coverage_limits、报表哈希、计数、findings、passed）。
4. passed 为假即 AUDIT_FINDINGS，退出码 1；为真退出码 0。进程全程不导入策略源码，不读账本。

| 拒绝码 | 条件 |
|---|---|
| `REPORTS_INCOMPLETE` | 报表目录缺任一必需报表或订单事件史：审计不运行，退出码 2，无结果文件 |
| `SUMMARY_UNREADABLE` | summary.json 不存在或不是合法 JSON 对象：退出码 2 |
| `AUDIT_FINDINGS` | 审计结果 passed 为假：结果文件已写出，退出码 1 |

### `event_report_findings` [#def-engine-event_report_findings]

事件史与订单、成交报表完全一致、有序、不换范围

```python
def event_report_findings(
    events: list[dict],
    orders: list[dict],
    fills: list[dict],
) -> list[str]
```

<TypeTable type={{ "events": { type: "list[dict]", description: "订单事件史：按订单分组、组内按引擎原生顺序，每条含 client_order_id、事件类型、ts_event、范围字段、数量、方向、类型与成交字段（event_id、trade_id、last_qty）" }, "orders": { type: "list[dict]", description: "订单报表行" }, "fills": { type: "list[dict]", description: "成交报表行" } }} />

**返回**　list[str]：不一致发现，每条带 client_order_id（成交项另带 event_id、trade_id）

**期望行为**

1. 订单集合：事件史涉及的 client_order_id 集合必须等于订单报表集合，多出或缺少均记 EVENT_ORDER_SET_MISMATCH。
2. 每个订单的事件以唯一一个初始化事件开头（EVENT_NOT_INITIALIZED），后续时间不倒序（EVENT_OUT_OF_ORDER），strategy_id、instrument_id、account_id 在全部事件中不变（EVENT_SCOPE_CHANGED）。
3. 事件史推出的终态、数量、已成交量、方向、类型与订单报表逐项相等（EVENT_ORDER_STATE_MISMATCH）。
4. 事件史成交与成交报表按 event_id、trade_id、数量、时间逐一匹配，多出或缺少均记 EVENT_FILL_MISMATCH。

| 拒绝码 | 条件 |
|---|---|
| `EVENT_ORDER_SET_MISMATCH` | 事件史与订单报表的订单集合不相等 |
| `EVENT_NOT_INITIALIZED` | 订单无初始化事件、初始化事件多于一个或不在首位 |
| `EVENT_OUT_OF_ORDER` | 同一订单内事件时间倒序 |
| `EVENT_SCOPE_CHANGED` | 同一订单事件间范围字段变化 |
| `EVENT_ORDER_STATE_MISMATCH` | 终态、数量、已成交量、方向或类型与订单报表不符 |
| `EVENT_FILL_MISMATCH` | 事件史成交与成交报表在 event_id、trade_id、数量或时间上不一致 |

### `generic_audit` [#def-engine-generic_audit]

字段齐全→身份→被否被拒→保护与终止→订单成交持仓佣金资金费账户逐项对账→汇总核对；只对账不重算；并发成交时刻与期末持仓两条边界记入覆盖局限

```python
def generic_audit(run_dir: Path, summary: dict) -> dict
```

<TypeTable type={{ "run_dir": { type: "Path", description: "报表目录；读 orders.csv、fills.csv、positions.csv、account.csv 与订单事件史，覆盖回执 input-coverage.json 从上一级目录读" }, "summary": { type: "dict", description: "原生摘要：integrity_passed、denied_orders、rejected_orders、starting_balance_usdt、final_equity_usdt、period_end_utc、strategy_uses_stop_loss、per_coin 逐合约事件计数" } }} />

**返回**　dict：generic_result 形态；findings 为空即 passed；native_economics 含期初与期末余额、已实现盈亏、成交佣金合计、资金费调整条数与金额、并发成交时刻数

**期望行为**

1. 字段与身份：四张报表每行必含 strategy_id、instrument_id、account_id 与各自必需列（REPORT_FIELDS_MISSING）；订单状态只允许已知终态或在途态（ORDER_STATUS_UNKNOWN）；client_order_id 与 position_id 非空且唯一（IDENTITY_MISSING_OR_DUPLICATED）。
2. 被否被拒：摘要 integrity_passed 为假或报表中存在 DENIED/REJECTED 订单即 INTEGRITY_REPORTED_FAILED；两类计数与摘要自报不符另记 DENIED_REJECTED_COUNT_MISMATCH；不区分原因。
3. 保护与终止：调用 protection 取对账与裸仓发现；覆盖回执存在则用 lifecycle_events 构造生命周期事件并调用 lifecycle_findings；摘要有状态或关闭事件计数而无覆盖回执即 LIFECYCLE_COVERAGE_MISSING。
4. 逐项对账（只比引擎产出，不重算）：成交对应唯一同范围订单、filled_qty 等于成交量和、FILLED 满额（ORDER_FILL_MISMATCH）；持仓事件恰好覆盖全部成交一次且买卖量、净量、开平仓订单、佣金一致（POSITION_FILL_COVERAGE_MISMATCH）；资金费只认 FUNDING 类型并在无并发成交的时刻等于账户总额变动（FUNDING_BALANCE_MISMATCH）；账户每行 total = locked + free、币种一致、时间有序、同一账户（ACCOUNT_REPORT_INCONSISTENT）。
5. 汇总核对：期初余额等于摘要；期末余额减期初等于已实现盈亏；期末无持仓时期末余额等于摘要期末权益；闭仓与盈利计数等于持仓报表统计（SUMMARY_TOTALS_MISMATCH）。
6. 任何解析、字段或算术异常记为 REPORT_PAYLOAD_INVALID 而不中止；最后交 generic_result 组装结果，并发成交时刻数写入 native_economics。
7. 事件史格式错误由 engine.protection 记录，本函数不中止，订单、成交、持仓、资金费与账户的对账照常进行。

| 拒绝码 | 条件 |
|---|---|
| `REPORT_FIELDS_MISSING` | 任一报表缺必需列或范围字段 |
| `ORDER_STATUS_UNKNOWN` | 订单状态不在已知终态或在途态集合 |
| `IDENTITY_MISSING_OR_DUPLICATED` | client_order_id 或 position_id 为空或重复 |
| `INTEGRITY_REPORTED_FAILED` | 摘要 integrity_passed 为假，或存在 DENIED/REJECTED 订单 |
| `DENIED_REJECTED_COUNT_MISMATCH` | 报表统计的被否或被拒数与摘要自报不符 |
| `LIFECYCLE_COVERAGE_MISSING` | 摘要含状态或关闭事件计数但覆盖回执缺失 |
| `ORDER_FILL_MISMATCH` | 成交找不到唯一同范围订单、filled_qty 不等于成交量和、FILLED 未满额、数量或方向非法 |
| `POSITION_FILL_COVERAGE_MISMATCH` | 持仓事件未恰好覆盖全部成交一次，或买卖量、净量、开平仓订单、佣金与成交不一致 |
| `FUNDING_BALANCE_MISMATCH` | 出现非 FUNDING 类型调整，或某无并发成交时刻的资金费与账户总额变动不等 |
| `ACCOUNT_REPORT_INCONSISTENT` | total ≠ locked + free、币种不一致、时间倒序或跨账户 |
| `SUMMARY_TOTALS_MISMATCH` | 期初余额、已实现盈亏、无持仓时的期末权益或闭仓与盈利计数与摘要不一致 |
| `REPORT_PAYLOAD_INVALID` | 任一报表字段类型错误、算术或读取异常 |

```python
def generic_result(

```

<TypeTable type={{ "run_dir": { type: "Path", description: "报表目录，用于逐文件计算 SHA-256" }, "orders": { type: "list[dict]", description: "订单报表行" }, "fills": { type: "list[dict]", description: "成交报表行" }, "positions": { type: "list[dict]", description: "持仓报表行" }, "findings": { type: "list[str]", description: "全部发现；每条带定位（订单号、持仓号、品种、时刻）" }, "economics": { type: "dict", description: "对账后的 native_economics；对账未完成时为空字典" }, "protection": { type: "dict | None", description: "protection 返回的 info：strategy_uses_stop_loss、native_order_events、uncovered_intervals" } }} />

**期望行为**

1. 对存在的报表文件逐个计算 SHA-256 写入 file_sha256，供入账与资格视图核对原件未变。
2. 写入订单、成交、持仓三类报表行数作为原生计数。
3. scope 固定写：原生报表身份、链接、保护历史与自报经济数。
4. coverage_limits 固定写不查项：不重建信号与目标几何；保护只比只减仓止损未成交量不比价格；同一纳秒事件一起应用且容忍至多一根执行 K 线的未覆盖；资金费只认原生调整不按费率重算；并发成交时刻不对账资金费；有持仓时不对账期末权益。
5. 合入 protection 信息与 economics，passed = findings 为空；本函数不产生新发现。

### `lifecycle_findings` [#def-engine-lifecycle_findings]

未定价终止前每个原生仓位归零且全部订单已结束；终止时刻及之后的订单事件视为迟到

```python
def lifecycle_findings(
    lifecycle: list[dict],
    orders: list[dict],
    fills: list[dict],
    positions: list[dict],
    events: list[dict],
    coverage: dict,
) -> list[str]
```

<TypeTable type={{ "lifecycle": { type: "list[dict]", description: "lifecycle_events 从覆盖回执与摘要构造并核对过的事件：{type ∈ InstrumentStatus | InstrumentClose, instrument_id, ts_event, action, close_price}" }, "orders": { type: "list[dict]", description: "订单报表行" }, "fills": { type: "list[dict]", description: "成交报表行" }, "positions": { type: "list[dict]", description: "持仓报表行（events 列为该仓位的成交 event_id 列表）" }, "events": { type: "list[dict]", description: "订单事件史" }, "coverage": { type: "dict", description: "覆盖回执；窗口结束与每个片段的最后一根 K 线只有它记着，窗口内没有终止事件时数据提前中断的检查也要跑" } }} />

**返回**　list[str]：发现列表，每条带品种与终止时刻，订单项带 client_order_id，持仓项带 position_id

**期望行为**

1. 找出未定价终止：状态事件 action = CLOSE 且同一品种同一时刻无 InstrumentClose；有价终止由引擎自行结算，照常走 generic_audit 对账，本函数不处理，也不造结算价。
2. 先核证据一致：持仓 events 恰好覆盖该品种全部成交一次、事件史成交与成交报表相符；否则 LIFECYCLE_EVIDENCE_INCONSISTENT，不继续重放。
3. 对每个未定价终止品种，沿事件史按时间重放到终止时刻之前：登记每个订单的接受与结束状态，按成交方向更新每个（strategy_id, account_id, position_id）的净量。
4. 终止时刻前任一原生仓位净量不为零记 POSITION_OPEN_AT_TERMINATION；任一订单（含休眠与条件单）未成交完、未结束或有在途修改记 ORDER_OPEN_AT_TERMINATION。
5. 终止时刻及之后该品种的任何订单事件（成交、撤单、修改、过期）逐条记 LATE_ORDER_EVENT。
6. 任何终止（有无结算价）之后创建的订单都记发现，引擎自己在终止时刻生成的 EXPIRATION-* 订单除外；同一订单只记一条。
7. 合约最后一根 K 线比窗口结束与它的终止事件都早 60 分钟以上（更短的末尾缺口按标记价缺口处理），或根本没有终止事件时，记发现 DATA_ENDS_WITHOUT_TERMINATION，运行无效：下架公告漏录时策略会以为合约还在。

| 拒绝码 | 条件 |
|---|---|
| `LIFECYCLE_EVIDENCE_INCONSISTENT` | 持仓事件未恰好覆盖成交、事件史成交与报表不符、未知事件类型或非正数量 |
| `POSITION_OPEN_AT_TERMINATION` | 未定价终止时刻前某原生仓位净量不为零 |
| `ORDER_OPEN_AT_TERMINATION` | 未定价终止时刻前某订单未成交完或未结束，或有在途修改 |
| `LATE_ORDER_EVENT` | 终止时刻及之后出现该品种的订单事件 |

### `protection` [#def-engine-protection]

沿事件史重建保护覆盖；事件史缺失即发现；按源码声明决定裸仓是拒绝还是只报告

```python
def protection(
    run_dir: Path,
    orders: list[dict],
    fills: list[dict],
    summary: dict,
) -> tuple[list[str]
```

### `uncovered_intervals` [#def-engine-uncovered_intervals]

同一纳秒事件一起应用后读状态；持仓超出只减仓止损覆盖量并持续超过一根执行 K 线才成裸仓区间

```python
def uncovered_intervals(events: list[dict], end_ns: int) -> list[dict]
```

<TypeTable type={{ "events": { type: "list[dict]", description: "全部订单的事件史，含 ts_event、client_order_id、事件类型、order_side、order_type、reduce_only、quantity、last_qty、position_id" }, "end_ns": { type: "int", description: "回放结束纳秒；期末仍裸露的区间以此为终点" } }} />

**返回**　list[dict]：每条 \{strategy_id, instrument_id, position_id, start_ns, end_ns, position_quantity（区间内最大绝对持仓）, stop_quantity, position_order_ids, ended_stop_order_ids, open_at_end\}

**期望行为**

1. 按 ts_event 分批，同一纳秒的全部事件先一起应用再读状态：初始化登记订单范围、方向、类型与只减仓标志；接受置 accepted；成交累加 filled 并按方向更新该（strategy_id, instrument_id）范围的净持仓；终态事件置 ended。
2. 每批应用后，对本批触及的范围计算覆盖量：平仓方向上已接受、未结束、只减仓的止损单（STOP_MARKET、STOP_LIMIT、TRAILING_STOP_MARKET、TRAILING_STOP_LIMIT）未成交量之和。
3. |净持仓| > 覆盖量即裸露：无开区间则开新区间（记起点、当时持仓订单号、本批刚结束的止损号），否则更新区间内最大持仓量；|净持仓| ≤ 覆盖量时关闭开区间。
4. 关闭的区间时长不超过一根执行 K 线（设计常量：一分钟）则丢弃；回放结束仍开着的区间以 end_ns 关闭并标 open_at_end。
5. 只比数量，不读止损价格，不重算成交；未知事件类型、非正数量、缺初始化事件或方向非法即 EVENT_PAYLOAD_INVALID 抛出。
6. 缺初始化事件包括：某个事件早于其订单的初始化事件。

| 拒绝码 | 条件 |
|---|---|
| `EVENT_PAYLOAD_INVALID` | 未知事件类型、非正数量、缺初始化事件或方向非法：抛出异常，由 generic_audit 记为 REPORT_PAYLOAD_INVALID |

### `parse_window` [#def-engine-parse_window]

把三个 ISO-8601 边界解析成回放窗口：预热段 [start, trade_start) 与交易段 [trade_start, end)，显式 UTC、左闭右开、整分钟对齐，换算为引擎纳秒时钟；不读宿主时区。

```python
def parse_window(
    start: str,
    trade_start: str | None,
    end: str,
    execution_bar_minutes: int,
) -> Window
```

<TypeTable type={{ "start": { type: "str", description: "预热段起点，ISO-8601，须带 Z 或 ±HH:MM 偏移" }, "trade_start": { type: "str | None", description: "交易段起点；省略即等于 start（无预热段）" }, "end": { type: "str", description: "窗口终点（不含），同样格式" }, "execution_bar_minutes": { type: "int", description: "撮合周期分钟数，缺省 1；三个边界须落在它的网格上" } }} />

**返回**　Window（不可变数据类）：start_ns、trade_start_ns、end_ns 三个纳秒整数，以及规范化为 UTC、以 Z 结尾的 start、trade_start、end 字符串，供有效配置与报告原样引用

**期望行为**

1. 逐个边界按 ISO-8601 解析；缺时区即拒绝，不默认任何时区；无法解析、偏移含秒或小数秒超过六位即拒绝。
2. 换算到 UTC；秒与微秒须为 0，自纪元起的分钟数须被 execution_bar_minutes 整除，否则拒绝。
3. trade_start 为空时取 start；核对 start ≤ trade_start \< end，否则拒绝。
4. 换算为自 Unix 纪元起的纳秒整数，生成 Z 结尾的规范字符串。
5. 不访问文件、网络、市场数据或账本；返回 Window。

| 拒绝码 | 条件 |
|---|---|
| `WINDOW_TIMEZONE_MISSING` | 某个边界没有 Z 或 UTC 偏移 |
| `WINDOW_TIMESTAMP_INVALID` | 不是合法 ISO-8601、偏移含秒，或小数秒超过六位 |
| `WINDOW_NOT_ALIGNED` | 某个边界含非零秒或微秒，或分钟不在撮合周期网格上 |
| `WINDOW_ORDER_INVALID` | 不满足 start ≤ trade_start \< end |

### `load_strategy` [#def-engine-load_strategy]

读源码字节核对内容哈希，以哈希命名的独立模块执行；入口类须本文件声明且为引擎策略基类真子类；两钩子与两布尔开关缺一或非布尔即拒绝

```python
def load_strategy(
    source_path: Path,
    entry_class: str,
    expected_content_hash: str,
) -> LoadedStrategy
```

<TypeTable type={{ "source_path": { type: "Path", description: "策略源码文件；须是普通文件，不跟随符号链接" }, "entry_class": { type: "str", description: "声明的唯一入口类名，须是合法 Python 标识符" }, "expected_content_hash": { type: "str", description: "发布记录的内容哈希（64 位小写十六进制 SHA-256）" } }} />

**返回**　LoadedStrategy：source_path、content_hash、entry_class、strategy_class、daily_warmup、uses_stop_loss

**期望行为**

1. 核对 expected_content_hash 为 64 位小写十六进制、entry_class 为合法标识符；以单个只读描述符读取普通文件的全部字节，不跟随符号链接。
2. 计算字节 SHA-256，与 expected_content_hash 不等即拒绝。
3. 以 `_strategy_<content_hash>` 为模块名建立无包名、不能相对导入的独立模块并执行源码；执行抛错即移除该模块并拒绝。同一进程内相同哈希已装载时直接返回已装载的模块，不再执行。
4. 取模块中名为 entry_class 的属性：须是类、在本模块声明、是引擎策略基类的真子类（不是基类本身），否则拒绝。
5. 核对 replay_diagnostics、replay_integrity_findings 两个钩子均可调用；类属性 DAILY_WARMUP（缺省 False）与 USES_STOP_LOSS（缺省 True）均须为 bool。
6. 返回 LoadedStrategy；只证明身份与形态，不担保任意 Python 的安全，执行边界由运行环境容器提供。

| 拒绝码 | 条件 |
|---|---|
| `SOURCE_UNREADABLE` | 路径不是普通文件、是符号链接或读取失败 |
| `CONTENT_HASH_INVALID` | expected_content_hash 不是 64 位小写十六进制 |
| `CONTENT_HASH_MISMATCH` | 源码字节的 SHA-256 不等于 expected_content_hash |
| `SOURCE_EXECUTION_FAILED` | 独立模块执行源码时抛出异常 |
| `ENTRY_CLASS_INVALID` | 入口类不存在、不在本模块声明、不是引擎策略基类的真子类 |
| `HOOK_MISSING` | replay_diagnostics 或 replay_integrity_findings 任一不可调用 |

1. 以（异常类型、阶段、合约、消息）为签名：签名相同只把 count 加一；新签名组装一条 runtime-failure-v2 回执：格式版本、阶段、异常类型名、拒绝码 code（拒绝时，否则为空）、截断后的消息（4000 字符）与首条回溯（20000 字符）、实例的合约标识（未构造时写 unconstructed）与 count。
2. 不同记录满 100 条后，新签名一律计入唯一一条 receipt_overflow 记录；进程内记录供 engine.main 判 NATIVE_EXECUTION_FAILED。
3. 输出目录已设时，新记录出现或 count 达到 2 的幂即把全部记录写到同目录临时文件、fsync 后改名替换 runtime_failures.jsonl；engine.main 结束时再写一次最终计数。进程中途被杀时每条不同的失败都在，计数不少于实际的一半。
4. 只记录 Python 异常事实，不读 stderr、不按文本严重度判错；自身不抛出，写入失败只在该记录的消息里注明。

### `replay` [#def-engine-replay]

按账户常量建唯一场所与回放节点，加入每合约三类数据流与生命周期事件，每个活跃合约一个策略实例，外加恰好一个资金观察器；运行后以引擎原生结果核对消费条数与观察器数

```python
def replay(
    rows: list[dict],
    window: dict,
    strategy: LoadedStrategy,
    pool: dict[str, tuple[tuple[int, int], ...]],
    output_dir: Path,
) -> None
```

<TypeTable type={{ "rows": { type: "list[dict]", description: "每合约一行：合约标识、币种、导出目录路径、导出回执（含各数据类型条数与生命周期片段），来自 engine.read_market" }, "window": { type: "dict", description: "engine.parse_window 的结果：start_ns、trade_start_ns、end_ns，UTC、左闭右开、整分钟对齐" }, "strategy": { type: "LoadedStrategy", description: "engine.load_strategy 的结果：入口类、内容哈希、绑定" }, "pool": { type: "dict[str, tuple[tuple[int, int], ...]]", description: "engine.read_universe 的结果：每合约原成员区间，没有成员文件时为空" }, "output_dir": { type: "Path", description: "敞口表与结构化回执的写入目录" } }} />

**返回**　(Replay, dict[str, Strategy | None], list[str])：Replay 持有节点、原生运行结果、缓存与组合、资金观察器；字典按币种给出实例，窗口内不活跃的合约为 None；第三项是回放产生的局限（推后启动的预热、没有实例的合约、晚于窗口观测的条款），交给 engine.write_native_reports，不走旁路

**期望行为**

1. 不用 BacktestNode：它在多路数据时先把全部事件读进内存排序（约每百万事件 0.26 GB，全池一年 40–60 GB）。运行器直接驱动引擎，按周把导出文件流式送入，事件顺序与分块规则与节点相同；合约逐个加入一次。实测全池一年 1.56 亿事件 575 秒、峰值 4.1 GB，指纹七表与节点方式一致。
2. 流式顺序约定：每个合约按标记价、资金费、K 线、状态、终止的类型次序排列，跨合约按时间戳稳定排序；分块边界对齐到时间戳，不把同一时刻拆到两块；按周划分会话；每块之间检查停止请求。
3. 以 engine.account_contract 的常量建唯一场所与引擎配置（净额保证金账户、固定本金、杠杆、K 线撮合与订单能力、数据序列校验、下单速率上限）；账户、持仓、保证金事实全部归引擎。
4. 每合约加三类数据流（1 分钟 K 线、标记价更新、资金费更新）；回执里生命周期事件条数非零时再加状态与终止事件流。
5. 对 engine.episode_active 为真的合约各加一个策略实例：入口类经 engine.configure_strategy 包装，配置只含合约、交易起点、输入起点（窗口起点与片段起点取大）、策略标识、目录路径与 engine.episode_membership 相交后的成员区间；不传任何策略参数。没有任何合约可建实例拒绝 NO_ACTIVE_INSTRUMENT。
6. 加恰好一个 engine.capital_observer，订阅全部合约标记价，敞口表写到 output_dir。
7. 运行节点后读引擎原生 iterations，不等于全部回执各数据类型条数之和拒绝 DATA_COUNT_MISMATCH；观察器实例数不等于一拒绝 OBSERVER_COUNT_MISMATCH；两处都读引擎原生结果，不信任回执自报。
8. 所有组件停止后调观察器 finish 估值最后一个时间戳并关闭敞口流，返回回放与实例表。
9. 运行中每分钟向标准错误写一行进度：模拟时间、已处理事件数、常驻内存，长回放可观察。
10. 窗口中途上市或日线历史不足的合约：等它满足所需日线预热的那一刻才启动其策略实例（片段起点相应推后），写入局限；始终不满足的合约不建实例并写局限；没有任何合约能启动才拒绝 WARMUP_INSUFFICIENT。

| 拒绝码 | 条件 |
|---|---|
| `DATA_COUNT_MISMATCH` | 引擎实际消费的事件数不等于全部合约导出回执条数之和 |
| `OBSERVER_COUNT_MISMATCH` | 进程内登记的资金观察器实例数不等于一 |
| `NO_ACTIVE_INSTRUMENT` | 范围内没有任何合约的合法生命周期与输入窗口相交，节点无实例可运行 |
