# C　策略文件：一份候选策略文件从发布、加载、回放到登记前必须遵守哪些契约，各由哪一层强制

本章定义候选 candidate 策略文件契约：单文件与内容身份、规则与参数只在源码、依赖边界与必带钩子、文件头九组立场与三条硬契约；交易事实归引擎 engine；只按已收盘信息决策；每个持仓有只减仓 reduce-only 止损覆盖；订单切成计划 plan；登记 registration 前过原生预检 native precheck 与独立源码审查。代码强制身份、加载检查、引擎配置、计划读数与预检绑定；经济设计由 skill 指导、经审查核对。回放环境、账户审计与读数口径分归 W、G、R 章。

## C.1　写成一份可登记的单文件 [#C-1]

<Steps>

<Step>

Agent 按 skill 写单文件源码：唯一入口类、两个钩子、九组文件头与三条硬契约，全部规则与参数在源码。

</Step>

<Step>

<Ref id="cli.candidate_publish" /> 经 <Ref id="ledger.check_source" /> 只解析不执行，<Ref id="ledger.publish_candidate" /> 以内容哈希写一行候选并提交，返回 strategy_id@revision。

</Step>

<Step>

预检或封存回放经 <Ref id="ledger.read_candidate" /> 取候选，把发布哈希与源码绑定交给运行器（<Ref id="replay.seal" />）。

</Step>

<Step>

运行器 <Ref id="engine.parse_configuration" /> 只接受引用、输入、窗口与输出，任何策略参数以 UNKNOWN_OPTION 拒绝。

</Step>

<Step>

<Ref id="engine.load_strategy" /> 按哈希装载并核对入口类、钩子与声明；<Ref id="engine.configure_strategy" /> 只以运行器输入构造实例。

</Step>

<Step>

回放结束 <Ref id="engine.diagnostics" /> 取自报诊断，<Ref id="engine.write_native_reports" /> 调自检；任何发现、被拒订单或异常使运行无效。

</Step>

</Steps>

### C.1.1　单文件、入口与身份一致 [#C-1-1]

发布侧只解析并以内容哈希入账，装载侧按同一哈希执行并核对入口类，两侧都由代码强制。

<Cap id="C.1.1.1" kind="code" tier="verified" tierLabel="已验证" title="策略是含全部规则的 UTF-8 单文件，唯一顶层入口是引擎策略子类">

1. 发布时 <Ref id="ledger.check_source" /> 只解析不执行，确认源码非空、在长度上限内、可解析、与入口类名同名的顶层类恰为一个。
2. 装载时 <Ref id="engine.load_strategy" /> 执行源码，确认入口类在本模块声明并继承引擎策略基类。

- 一个独立策略是一份完整的 UTF-8 单文件源码，含全部交易规则与参数。
- 源码恰有一个与声明的入口类名同名的顶层类，该类在本文件内声明，且是引擎策略基类的真子类。
- 运行器只实例化这个类。
- 策略库模板、用户自建的根节点 root 与派生候选走同一检查，没有第二种入口形态。

**输入**　源码字节与声明的入口类名。

**输出**　通过形态检查的源码，或拒绝码。

**强制**　代码强制：发布时由 <Ref id="ledger.check_source" /> 解析检查，装载时由 <Ref id="engine.load_strategy" /> 执行后核对。

| 拒绝码 | 条件 |
|---|---|
| `SOURCE_SIZE` | 发布时源码为空或超过长度上限。 |
| `SOURCE_SYNTAX` | 发布时源码无法解析。 |
| `ENTRY_CLASS_INVALID` | 发布时缺少同名顶层类；装载时入口类不在本模块声明或不是引擎策略基类的子类。 |
| `ENTRY_CLASS_NOT_UNIQUE` | 发布时与入口类名同名的顶层类不止一个。 |

</Cap>

<Cap id="C.1.1.2" kind="code" tier="rehearsal" tierLabel="演练证据" title="发布只解析不执行，执行字节须等于发布哈希，改动即新候选">

1. <Ref id="cli.candidate_publish" /> 只解析源码、不执行，证明的是形态而非规则正确。
2. <Ref id="ledger.publish_candidate" /> 以源码字节的 SHA-256 为内容哈希 content hash，在一笔事务里写一行 <Ref id="table:candidate" /> 并提交，返回引用名 strategy_id@revision。
3. 任何读取经 <Ref id="ledger.read_candidate" /> 重算存储字节的哈希并与记录比对。
4. 执行时 <Ref id="engine.load_strategy" /> 核对读到的字节哈希等于发布哈希；封存回放还核对与上层写出的源码绑定一致。

- 相同字节不能再次发布，任何改动都产生新候选。
- 研发父版本 parent 与改动说明同有同无，父须存在。

**输入**　源码字节，以及可选的父版本 parent 与改动说明。

**输出**　账本里的一行候选与引用名 strategy_id@revision，或拒绝码。

**强制**　代码与账本共同强制：发布与装载的哈希比对，加上账本对内容哈希的唯一约束。

| 拒绝码 | 条件 |
|---|---|
| `SOURCE_EXISTS` | 相同字节已发布过；附该字节对应的引用。 |
| `LINEAGE_INCOMPLETE` | 父版本 parent 与改动说明只给了其中一个。 |
| `UNKNOWN_CANDIDATE` | 指定的父版本不存在。 |
| `CONTENT_HASH_MISMATCH` | 执行时读到的字节哈希不等于发布哈希。 |
| `BINDING_MISMATCH` | 封存回放的源码与上层写出的源码绑定不一致。 |
| `LEDGER_CORRUPT` | 读取时重算的存储字节哈希与记录不符。 |

</Cap>

### C.1.2　规则与参数的归属 [#C-1-2]

运行器参数面由代码固定，规则与参数只能在源码；选币规则同样归源码，由 skill 指导。

<Cap id="C.1.2.1" kind="code" tier="rehearsal" tierLabel="演练证据" title="全部规则与参数只在源码，运行器不收策略参数，参数变体即新候选">

- <Ref id="engine.build_parser" /> 把运行器命令行固定为策略引用、输入、窗口、输出目录与探针开关，没有策略参数入口，也没有通用键值透传。
- 信号周期与预热声明、仓位、单笔风险、名义上限、杠杆用法等全部规则与参数写在源码，随内容哈希固定。
- <Ref id="engine.configure_strategy" /> 构造入口类时只传运行器输入：合约、交易起点、策略标识、成员区间、按声明取的预热日线。
- 账户与撮合条款取所有候选共用的 <Ref id="engine.account_contract" />，并进入有效配置与执行身份。
- 参数变体就是新源码、新候选。
- 这些参数是 Agent 的设计变量，改动不需用户授权，也不记为用户约束（<Ref id="A.2.2.1" />）。

**输入**　策略引用、输入、窗口、输出目录与探针开关。

**输出**　只以运行器输入与共用账户条款构造的策略实例。

**强制**　代码强制：<Ref id="engine.build_parser" /> 固定参数面，<Ref id="engine.parse_configuration" /> 拒绝未定义选项。

| 拒绝码 | 条件 |
|---|---|
| `UNKNOWN_OPTION` | 命令行出现任何未定义选项，包括任何策略参数。 |

</Cap>

<Cap id="C.1.2.2" kind="skill" tier="unverified" tierLabel="待验证" tierNote="缺的证据：尚无一条选币规则改动作为假设登记并回放的试验。" title="选币规则写在源码，共同可交易范围与成员路径由环境产出">

- 成交额排名、前 N、信号筛选、选币数量与调整频率是策略规则，写在源码。
- 策略只用引擎当时已提供的数据决定实际交易子集。
- 共同可交易范围 universe 及其成员时间路径由环境按月产出，运行器把每合约的成员区间交给对应实例（<Ref id="W.3.2.1" />），策略改不了。
- 两个候选共享范围与成员时间路径就算同一币池，实际交易子集可以不同（<Ref id="V.2.1.3" />）。
- 选币规则的改动是一条假设 hypothesis，照常登记并回放，不要求环境改范围。

**输入**　运行器交给实例的每合约成员区间，以及引擎当时已提供的数据。

**输出**　策略自选的实际交易子集。

**强制**　skill 指导，eval 校验。

</Cap>

### C.1.3　加载时检查：依赖边界与自带钩子 [#C-1-3]

装载器以独立模块执行源码并核对钩子与声明，容器与运行环境给出无网络、只读、锁定依赖的执行边界，均由代码强制。

<Cap id="C.1.3.1" kind="code" tier="rehearsal" tierLabel="演练证据" title="源码只导入标准库、引擎与锁定依赖，在无网络只读容器中独立加载">

- 源码只能导入标准库、引擎与运行环境 runtime image 锁定的依赖。
- <Ref id="engine.load_strategy" /> 以内容哈希命名的独立模块执行源码，无包名，不能相对导入。
- 运行环境只由 CI 构建（<Ref id="runtime.build_image" />），镜像里只有引擎、运行器与锁定依赖，没有研究或策略模块。
- 回放容器由 <Ref id="runtime.container_command" /> 启动：无网络、根文件系统只读、只读挂载声明的输入，唯一可写的是报告目录。
- 除引擎喂给的数据外源码没有其他输入；缺依赖在原生预检的构造阶段暴露。
- 装载只证明身份与形态，不担保任意 Python 安全，执行边界由容器提供。

**输入**　按内容哈希读出的源码字节与只读挂载的声明输入。

**输出**　已加载的策略模块；可写产物只落在报告目录。

**强制**　代码与运行环境强制：装载器的独立模块执行、CI 构建的锁定镜像与容器的网络和文件系统隔离。

| 拒绝码 | 条件 |
|---|---|
| `SOURCE_EXECUTION_FAILED` | 以独立模块执行源码时抛错。 |

</Cap>

<Cap id="C.1.3.2" kind="code" tier="rehearsal" tierLabel="演练证据" title="入口类必带诊断与自检两个钩子，自报诊断不占原生事实键名">

1. 装载时 <Ref id="engine.load_strategy" /> 核对两个钩子存在、两项声明为 bool。
2. 回放结束 <Ref id="engine.diagnostics" /> 取诊断计数，只作自报诊断写入摘要。
3. <Ref id="engine.write_native_reports" /> 调用自检钩子，把自检发现与被拒或被否的订单写入完整性发现。

- 入口类必须实现诊断计数 replay_diagnostics 与完整性自检 replay_integrity_findings 两个钩子。
- 入口类把 DAILY_WARMUP、USES_STOP_LOSS 声明为 bool。
- 诊断须是可序列化为 JSON 的字典，不得占用原生报告事实（合约、数量、计数、持仓等）的键名。
- 诊断只作自报写入摘要，不进审计与读数。
- 任何自检发现、被拒或被否的订单计为审计失败（<Ref id="G.3.2.4" />）。
- 构造或回调异常先写结构化回执再抛出，运行非零退出并无效（<Ref id="G.1.1.3" />）。
- 干净退出不掩盖故障。

**输入**　已加载的入口类及其回放期间的钩子输出。

**输出**　摘要中的自报诊断与完整性发现。

**强制**　代码强制：装载器核对钩子与声明，报告写出时调用自检并记入完整性发现，运行器包裹构造与回调异常。

| 拒绝码 | 条件 |
|---|---|
| `HOOK_MISSING` | 入口类缺少 replay_diagnostics 或 replay_integrity_findings 钩子。 |
| `DECLARATION_NOT_BOOL` | DAILY_WARMUP 或 USES_STOP_LOSS 不是 bool。 |

</Cap>

### C.1.4　文件头的立场与硬契约 [#C-1-4]

文件头先写九组立场、再写三条硬契约，由 skill 指导、代码不裁决，供独立源码审查逐项核对；资金使用率与生命周期审计由代码产出读数。

<Cap id="C.1.4.1" kind="skill" tier="unverified" tierLabel="待验证" tierNote="缺的证据：尚无按九组文件头写出并经独立源码审查查漏的实际候选。" title="文件头九组各写一行立场：采用、缺省或不适用，附理由与出处">

- 九组为：对象与适用性、预测与学习、首次行动与记忆、经济构型、风险与分配、持仓路径、实施、资本、生命周期与可行性。
- 每组一行，取值为采用、缺省或不适用，附一句理由。
- 每行标明出自出处原话、实现者缺省还是研究者推广（<Ref id="L.1.3.3" />）。
- 27 项职责目录只作 skill 参考文件，供登记前的独立源码审查（<Ref id="C.6.2.1" />）查漏，不进正文。
- 发布不核对文件头，形态检查只看单文件与唯一入口。

**输出**　独立源码审查可逐项核对的九行立场声明。

**强制**　skill 指导，eval 校验；独立源码审查结论作为具名证据。

</Cap>

<Cap id="C.1.4.2" kind="skill" tier="rehearsal" tierLabel="演练证据" title="硬契约一：仓位与资金预算写在源码，下单量从引擎账户状态算出">

- 仓位、单笔风险与资金预算规则写在源码。
- 下单数量由引擎账户状态（权益、合约乘数、最小量与最小名义）算出。
- 不另设名义上限去模仿保证金 margin；保证金与杠杆由引擎账户按固定账户条款处理，保证金不足由引擎拒单（<Ref id="C.2.1.3" />）。
- 资金使用率 capital utilisation（时间加权名义敞口、峰值、锁定保证金、在市时间）由运行器逐 K 线按标记价估值写出敞口表。
- Agent 从首个有效根起，每个有效运行都主动读出资金使用率，任何仓位或预算改动后必读。
- 资金使用率读数写进反馈与推荐理由。

**输入**　引擎账户状态：权益、合约乘数、最小量与最小名义。

**输出**　下单数量；运行器写出的敞口表与资金使用率读数。

**强制**　skill 指导；资金使用率读数由代码（<Ref id="engine.capital_observer" />）产出。

</Cap>

<Cap id="C.1.4.3" kind="skill" tier="verified" tierLabel="已验证" title="硬契约二：成员变化时既有持仓与挂单的处置写在源码">

- 合约退出共同可交易范围时只减仓 reduce-only、不开新仓。
- 禁新仓与下架结算按引擎供给的生命周期事件（InstrumentStatus、InstrumentClose）响应。
- 合约退出策略自选子集时按源码规则处理。
- 成员区间由运行器交给实例，开仓范围在禁新仓时结束；生命周期事件由环境随市场提交写出。
- 运行器与审计都不替策略平仓或撤单，也不得靠删币或缩窗绕过。
- 审计只核结果：未定价终止前每个原生仓位须归零、全部订单已结束，否则运行无效（<Ref id="G.3.3.3" />）。

**输入**　运行器交给实例的成员区间与引擎供给的生命周期事件。

**输出**　未定价终止前归零的原生仓位与全部结束的订单。

**强制**　skill 指导；结果由代码的生命周期审计核对。

</Cap>

<Cap id="C.1.4.4" kind="skill" tier="unverified" tierLabel="待验证" tierNote="缺的证据：尚无把联合分配规则写入源码并在同账户多合约回放中读出分配结果的候选。" title="硬契约三：同账户共享资本时，联合分配与落选处置写在源码">

- 同一账户下多个合约实例共享固定本金时，源码写明同批信号如何联合分配资金。
- 源码写明未获资金的机会如何处置：缩量、延后或放弃。
- 不靠回调循环顺序或引擎拒单代替分配规则；拒单是保证金事实（<Ref id="C.2.1.3" />），不是分配规则。
- 合并另一版本的规则后分配仍在同一账户内进行，按一处改动登记（<Ref id="T.2.2.2" />）。

**输入**　同批信号与共享的固定本金。

**强制**　skill 指导，eval 校验。

</Cap>

## C.2　把交易事实交给引擎 [#C-2]

<Steps>

<Step>

运行器配置引擎并回放，见 <Ref id="C.2.1.1" />。

</Step>

<Step>

策略从引擎缓存（cache）与组合（portfolio）读订单、持仓与账户，响应订单与持仓事件并提交订单。

</Step>

<Step>

引擎风控审单并撮合，产生成交、费用、资金费、持仓与账户变化。

</Step>

<Step>

运行器原样写出引擎报告，见 <Ref id="C.2.1.1" />。

</Step>

<Step>

审计按报告对账不重算，见 <Ref id="C.2.1.3" />。

</Step>

<Step>

读数与 Agent 自算统计只从产品报告读，见 <Ref id="C.2.1.2" />。

</Step>

### C.2.1　引擎独占的事实 [#C-2-1]

输入为固定账户配置与引擎回放，输出为原生报告与完整性发现；两条由代码强制，一条由 skill 指导。

<Cap id="C.2.1.1" kind="code" tier="verified" tierLabel="已验证" title="交易事实只由引擎产生，运行器只配置引擎并原样写出报告">

1. 回放前按 <Ref id="engine.account_contract" /> 把所有候选共用的固定账户与撮合常量配置给引擎，经 <Ref id="engine.replay" /> 回放。

3. 在摘要里写身份、窗口、账户条款、撮合与条款局限和完整性发现。

- 成交、手续费、资金费（funding）、持仓、账户余额与订单状态只由引擎产生，以引擎回报的订单事件为准（总则见 <Ref id="A.4.2.2" />）。
- 运行器只做配置回放与原样写出两件事，不计算、不修改、不补造任何交易事实；零行表只补表头。
- 任一拒绝发生时运行器以非零退出结束，回放无效（invalid）。
- 下游审计只对账这些报告，不重算。

**输入**　所有候选共用的固定账户与撮合常量，以及引擎回放。

**输出**　未经加工的原生报告、订单事件史、敞口表，以及含身份、窗口、账户条款、局限与完整性发现的摘要。

**强制**　由代码强制：运行器经 engine.account_contract 配置引擎、engine.write_native_reports 原样写出，并在拒绝时非零退出。

|---|---|
| `NATIVE_ACCOUNT_MISSING` | 账户缺失 |
| `EQUITY_SNAPSHOT_UNAVAILABLE` | 期末权益快照不可用 |
| `GTD_DEADLINE_MISSING` | GTD 订单无到期 |
| `SELF_CHECK_FINDINGS_INVALID` | 自检钩子返回非法 |
| `DIAGNOSTICS_INVALID` | 自报诊断占用原生事实名 |

</Cap>

<Cap id="C.2.1.2" kind="skill" tier="verified" tierLabel="已验证" title="策略与 Agent 只读引擎状态与产品报告，不自算成交、费用或盈亏">

- 策略只从引擎缓存（cache）与组合（portfolio）读订单、持仓与账户状态，以订单与持仓事件回调响应。
- 策略不从 K 线高低区间推断成交，不自算手续费或资金费，不维护私有持仓或资金账本。

- Agent 的读数（reading）只从产品报告读：封存运行的读数来自 <Ref id="ledger.readings" />，自算统计只经 <Ref id="report.tables" />。
- Agent 不从价格触及或代理计数推算成交与盈亏；置空的读数按置空解读。
- 持仓周期每次运行独立，不跨运行配对。

**输入**　引擎缓存、组合与事件回调；产品报告（ledger.readings 与 report.tables）。

**强制**　由 skill 指导：规则写在 <Ref id="research-round/references/strategy-authoring.md#engine-owns-trade-facts" />，登记前的 <Ref id="C.6.1.2">独立源码审查</Ref> 核对源码写法，eval <Ref id="eval:research-round/l3-touch-not-pnl" /> 校验 Agent 不从触及推断盈亏；代码不检查源码写法。

</Cap>

<Cap id="C.2.1.3" kind="code" tier="verified" tierLabel="已验证" title="保证金不足由引擎拒单，回放判无效，产品不另设保证金审计">

1. 保证金或可用余额不足时，引擎风控在订单提交前以标准原因产生 OrderDenied，订单表记 DENIED；场所拒单记为 REJECTED 状态。
2. <Ref id="engine.write_native_reports" /> 把订单表中的 DENIED 或 REJECTED 记为完整性发现。
3. <Ref id="engine.generic_audit" /> 核对被否被拒计数与摘要一致并判审计失败。
4. <Ref id="replay.audit_problems" /> 把它写成无效原因。
5. 回放无效，只留原因与原生原件，读数置空（见 <Ref id="G.3.2.4" />）。

- 账户是引擎的净额（NETTING）保证金（margin）账户，条款由 <Ref id="engine.account_contract" /> 固定。
- 产品不另建保证金、名义上限或杠杆审计。
- 仓位与名义上限是策略源码的设计变量（<Ref id="C.1.4.2" />），源码也不以名义上限模仿保证金。

**输入**　引擎风控对提交订单的审单结果与场所回报。

**输出**　完整性发现、审计失败与无效原因；读数置空。

**强制**　由代码强制后果核对：engine.write_native_reports 记完整性发现，engine.generic_audit 判审计失败，replay.audit_problems 写无效原因；拒单本身由引擎风控产生。

| 拒绝码 | 条件 |
|---|---|
| `INITIAL_MARGIN_EXCEEDS_FREE_BALANCE` | OrderDenied 标准原因举例：初始保证金超过可用余额（另有其他标准原因） |
| `NOTIONAL_EXCEEDS_FREE_BALANCE` | OrderDenied 标准原因举例：名义价值超过可用余额（另有其他标准原因） |

</Cap>

### C.3.1　决策能用的信息与成交时钟 [#C-3-1]

两条能力分别限定决策可读的信息与成交时钟。

<Cap id="C.3.1.1" kind="skill" tier="verified" tierLabel="已验证" title="每个决策点只读引擎时钟上已收盘的 K 线和已到达的事件">

- 可读的已到达事件包括成交回报、标记价、资金费、合约生命周期事件。
- 不用全样本统计；均值、分位、标准化参数只按已发生数据滚动计算。
- 不把未来值移到当前行。
- 不在源码里假设 K 线内的价格路径；引擎按 1 分钟 K 线撮合，K 线内顺序未知，见 <Ref id="W.5.1.1" />。
- 交易起点之前只预热指标，不提交订单。
- 结构事件（摆动点、突破确认等）按它成立的时刻打戳，不在形成它的那根 K 线上行动。
- K 线的可用时刻只有收盘时刻一个定义（<Ref id="W.2.1.3" />），导出时事件时间等于收盘时刻（<Ref id="market.write_bars" />）。
- 高周期 K 线按固定规则从 1 分钟派生（<Ref id="market.derive_bars" />），也在收盘时刻才可用。
- 前视偏差（look-ahead bias）属于实现缺陷，不是经济结果。

**输入**　Agent 写的候选源码。

**输出**　满足上述约束的决策逻辑。

**强制**　skill 锚点 <Ref id="research-round/references/strategy-authoring.md#causal-clock" /> 写成源码规则，无代码拒绝码。违反时独立源码审查的因果一项判失败。失败的后果（拒绝登记、不作经济证据）由 <Ref id="C.3.1.2" /> 的强制环节执行。

</Cap>

<Cap id="C.3.1.2" kind="skill" tier="rehearsal" tierLabel="演练证据" title="成交时刻必须严格晚于决策 K 线的收盘时刻">

1. 在决策 K 线的收盘事件里，源码只确定交易意图。
2. 订单放到其后的引擎事件再提交。
3. 每个计划（plan）留存决策、下单、成交三类时间戳。
4. 原生预检 <Ref id="replay.precheck" />（见 <Ref id="C.6.2.1" />）和完整回放之后都逐计划核对这三类时间戳。

- 成交与决策落在同一时钟即为实现缺陷，账户审计通过也不例外，因为审计不查信号时钟（<Ref id="G.4.1.1" />）。

**输入**　候选源码及其原生预检、回放留存的三类时间戳。

### C.4.1　止损声明与覆盖 [#C-4-1]

源码声明和引擎订单事件史进来，运行身份里的声明字段和审计给出的裸仓区间出去：声明由加载器检查，覆盖要求由 skill 写给作者，裸仓由审计判定。

<Cap id="C.4.1.1" kind="code" tier="rehearsal" tierLabel="演练证据" title="源码声明是否设止损，缺省为设；声明不设时裸仓只报告">

1. 源码在入口类上用类属性 USES_STOP_LOSS 声明是否设止损，不写即为 True。
2. 加载时，<Ref id="engine.load_strategy" /> 检查它的类型恰为 bool。
3. 检查通过后，<Ref id="engine.strategy_metadata" /> 把声明写成运行身份字段 strategy_uses_stop_loss，并入原生摘要与执行身份。
4. 该字段随研究封存进入账本，回放之后不能再改。
5. 审计读摘要里的这个字段（不读源码）：True 时任何裸仓都使运行无效（invalid）；False 时裸仓区间只写进审计结果，运行仍可有效（判定见 <Ref id="G.3.3.2" />）。

- 类型不是 bool 时拒绝加载，运行器非零退出，不产生运行。
- 要改声明只能发布新候选。
- 声明不设止损的理由由文件头立场写明，不靠运行器推断。

**输入**　入口类上的类属性 USES_STOP_LOSS。

**输出**　运行身份、原生摘要与执行身份里的 strategy_uses_stop_loss 字段。

**强制**　代码强制：加载器做类型检查，元数据函数写入运行身份，审计按声明分流裸仓的后果。

</Cap>

<Cap id="C.4.1.2" kind="skill" tier="verified" tierLabel="已验证" title="持仓期间每一刻，只减仓止损量都不少于持仓量">

- 适用于声明设止损的源码：持仓期间任一时刻，平仓方向上已被引擎接受、尚未成交的只减仓止损单，合计数量不少于引擎持仓量。
- 部分成交后，保护数量按引擎实际持仓对齐，不按计划下单量。
- 只减仓单不会开仓或加仓（由引擎保证）。
- 仓位缩小时，引擎让只减仓单随之缩量；仓位归零时撤销它。
- 运行器以账户契约设定 reject_stop_orders=False，保证止损单被接受。
- 源码负责：保护不足时在当前回调里补足。
- 是否覆盖由审计判定，不由源码自报。
- <Ref id="engine.uncovered_intervals" /> 把同一纳秒的事件一起应用后再读状态。
- 持仓超出止损覆盖量、且持续超过一根执行 K 线的区间才算裸仓；容忍长度就是这一根执行 K 线。
- 审计只看数量，不看止损价格与几何，这些属经济设计。
- 裸仓的后果由 <Ref id="C.4.1.1" /> 的声明决定。

**输入**　引擎订单事件史与持仓。

**输出**　审计给出的裸仓区间。

**强制**　skill 节 <Ref id="research-round/references/strategy-authoring.md#stop-coverage" /> 把覆盖要求写给源码作者；是否做到由审计的覆盖重建判定。

</Cap>

### C.4.2　保护单的挂法与收束 [#C-4-2]

引擎原生的括号单与撤子单由运行器经账户契约开启，补挂与收束是 skill 指导的源码规则，两者都受审计的覆盖重建检查。

<Cap id="C.4.2.1" kind="code" tier="verified" tierLabel="已验证" title="入场连同止损止盈用括号单一次提交，母单终止时引擎撤子单">

- 入场与保护用引擎括号单一次提交，构成一个订单组，入场为 OTO 母单。
- 止损与止盈是子单，都只减仓、互为 OUO，母单成交后才激活。
- 入场单的有效期用 GTD 加到期时刻 expire_time 表达，源码不自行计时撤单。
- 母单到期、撤单或改量而终止时，由引擎撤销或调整其子单；没有另建的订单组管理，也没有自写的撤单逻辑。
- 括号单的每张订单都带同一个计划标签（见 <Ref id="C.5.1.1" />）。
- 源码选不选括号单不由加载器检查；没有保护的持仓由 <Ref id="C.4.1.2" /> 的覆盖审计发现。
- 引擎版本变更后，括号单激活与撤子单的顺序须经运行环境配对重放（<Ref id="research-round/references/changes.md#runtime-parity-replay" />）复核，才算行为未变。

**输入**　源码提交的括号单（入场母单加止损、止盈子单）。

**输出**　引擎内一个订单组，子单随母单成交激活、随母单终止撤销或调整。

**强制**　代码只强制引擎配置：运行器在 <Ref id="engine.account_contract" /> 里设 support_contingent_orders=True 与 support_gtd_orders=True，交给场所配置。

</Cap>

<Cap id="C.4.2.2" kind="skill" tier="rehearsal" tierLabel="演练证据" title="母单终止留下已成交量时，源码按缺口补挂只减仓止损止盈">

1. 入场母单部分成交后又到期或被撤，引擎撤掉其子单，已成交部分失去保护。
2. 源码在到期与撤单回调里算缺口：引擎持仓减去仍存活、未成交的只减仓止损量。
3. 缺口为正时，在同一回调内补挂独立的只减仓止损与止盈，数量等于缺口，沿用原子单的触发价、限价与计划标签。
4. 持仓归零时，源码撤该计划的全部剩余单，计划结束时订单组无残留。

- 补挂须在同一回调内完成，以免超出 <Ref id="engine.uncovered_intervals" /> 容忍的一根执行 K 线。
- 补挂单不与母单关联，引擎不会替源码撤它，所以收束由源码负责。
- 一个计划只对应一个持仓周期（见 <Ref id="C.5.1.2" />）。
- 登记前的原生预检要覆盖“部分成交后到期或撤单”这个场景。

**输入**　母单到期或撤单回调，引擎持仓与存活的只减仓止损量。

**输出**　数量等于缺口的独立只减仓止损与止盈单；持仓归零后该计划无残留订单。

**强制**　skill 节 <Ref id="research-round/references/strategy-authoring.md#orphaned-fills-reprotect" /> 指导写法；做没做到由审计的覆盖重建判定。

</Cap>

### C.5.1　计划的定义与标签 [#C-5-1]

策略源码在提交订单时写入计划标签，代码据此读出计划。

<Cap id="C.5.1.1" kind="code" tier="verified" tierLabel="已验证" title="每张订单恰带一个全回放唯一的计划标签，一个计划只涉及一个合约">

- 计划（plan）指一个信号提交的全部订单：分批进场单、共用的止损止盈单，以及之后的改仓单和平仓单。
- 每张订单恰好带一个计划标签，包括括号单（bracket order）的入场单和两张子单，以及母单终止后补挂的只减仓（reduce-only）单。
- 标签值在整次回放内唯一；一个计划只涉及一个合约。
- 计划数和计划胜率只从计划读数得出，计划读数是唯一来源。
- 赢的定义：周期已平，且实现盈亏（含手续费和资金费 funding）大于零；持平和期末未平都不算赢。
- 计划胜率的分母是已平计划数加期末未平计划数。
- 计划读数是描述统计，不改任何原生行。
- 读数抛出具名原因后，按 <Ref id="C.5.2.1" /> 处理。

**输入**　订单、成交和持仓报告的原生行，以及 <Ref id="ledger.cycles" /> 重建出的周期。

**输出**　已平计划数、赢数、期末未平计划数和计划胜率。

**强制**　读数由代码强制：<Ref id="ledger.plan_reading" /> 在封存入账时读订单报告上的标签；标签由策略源码负责写入，由独立源码审查核对。

| 拒绝码 | 条件 |
|---|---|
| `PLAN_TAG_MISSING` | 订单没有计划标签 |
| `PLAN_TAG_MULTIPLE` | 订单带了多个计划标签 |
| `PLAN_MULTI_INSTRUMENT` | 一个计划跨了多个合约 |
| `NATIVE_VALUE_UNREADABLE` | 标签无法解析 |

</Cap>

<Cap id="C.5.1.2" kind="code" tier="rehearsal" tierLabel="演练证据" title="计划与持仓周期一一对应，同一合约同时至多一个活跃计划">

- 持仓周期（position cycle）从持仓报告逐行重建，只支持以 USDT 计价并记有乘数的线性合约。
- 每个周期给出：是否已平、实现盈亏、价格盈亏（成交现金流乘以合约乘数）、手续费和资金费。
- 资金费只接受不改数量的 FUNDING 调整。
- 全部周期的成交 event_id 必须恰好覆盖成交报告里的每笔成交，且每笔只覆盖一次。
- 一个计划的成交至多落在一个周期里；一个周期只装一个计划的成交，且不能为空。
- 周期里的每笔成交都必须在订单报告里找到对应订单。
- 在同一合约上，前一计划从首单创建起，到持仓归零且全部订单终止为止，期间不得开始新计划。
- 持仓归零时，策略撤掉剩余订单，以免残留档位重新开仓。
- 分批加仓算同一计划的多档，不算新计划。
- 任何违例只使计划读数为空并写原因，见 <Ref id="C.5.2.1" />。

**输入**　持仓报告和成交报告的原生行，以及订单报告。

**输出**　逐个周期的平仓状态和经济拆分，以及计划与周期的一一对应关系。

**强制**　由代码强制：<Ref id="ledger.cycles" /> 负责重建周期并核对成交覆盖，<Ref id="ledger.plan_reading" /> 负责核对一一对应和不重叠；撤剩余单由策略源码负责，由独立源码审查核对。

| 拒绝码 | 条件 |
|---|---|
| `FILL_COVERAGE_MISMATCH` | 全部周期的成交没有恰好覆盖每笔成交一次 |
| `NON_USDT_MONEY` | 计价币种不是 USDT |
| `UNSUPPORTED_INSTRUMENT` | 合约类型超出支持范围（不是记有乘数的线性合约） |
| `UNSUPPORTED_ADJUSTMENT` | 出现除不改数量的 FUNDING 之外的调整项 |
| `PLAN_MULTI_CYCLE` | 一个计划的成交落在多个周期里 |
| `CYCLE_MULTI_PLAN` | 一个周期含多个计划的成交，或者为空 |
| `PLAN_FILL_UNMATCHED` | 周期里的某笔成交在订单报告中找不到订单 |
| `PLAN_OVERLAP` | 同一合约上，前一计划尚未持仓归零且全部订单终止，就开始了新计划 |

</Cap>

### C.5.2　不合规与原生平仓单 [#C-5-2]

<Cap id="C.5.2.1" kind="code" tier="rehearsal" tierLabel="演练证据" title="计划契约违例只置空计划读数并写原因，不判回放无效">

- 计划契约是读数的前提，不是账户事实。
- 原生事实超出支持范围或对账失败时，读数函数抛出具名原因 <Ref id="ledger.unreconciled" />，内容是原因码加可定位的细节。
- <Ref id="ledger.readings" /> 捕获原因后，只把该原因所属的读数置空（计划读数、利润来源拆分或回撤之一），其余读数照常读出。
- 「code: detail」写入运行的读数局限列。
- 完整性审计和资格判定不会因为计划不合规而判运行无效或不可用。
- 账户年化、标记价回撤和利润来源拆分照常可用。
- 空值不得当作零，也不得手工填补。

**输入**　读数函数抛出的 <Ref id="ledger.unreconciled" /> 原因（原因码和细节）。

**输出**　对应读数列为空，原因写入运行的读数局限列，经 <Ref id="ledger.ingest_run" /> 随运行行入账。

**强制**　由代码强制：<Ref id="ledger.readings" /> 捕获具名原因，只置空所属读数并写入局限列。

</Cap>

<Cap id="C.5.2.2" kind="code" tier="rehearsal" tierLabel="演练证据" title="下架结算的无标签平仓单只在唯一对应时只读归属到计划">

- 合约下架结算时，引擎（engine）按原生 InstrumentClose 事件自行生成一张只减仓市价平仓单，这张单没有计划标签。
- 计划读数之前先做归属判定，下列条件必须全部满足才归属。
- 条件一：订单带引擎下架结算标识，是只减仓单、市价单，且已成交。
- 条件二：恰有一笔成交，事件序列恰为初始化→接受→成交，账户和合约身份一致。
- 条件三：事件时刻等于该合约唯一一个 InstrumentClose 的时刻，成交价等于结算价。
- 条件四：这笔成交恰属一个已关闭周期，且该周期的平仓订单就是这张单。
- 条件五：此前持仓净量非零、方向与平仓相反，此前事件都早于结算时刻。
- 条件六：周期此前的全部成交属于同一计划。
- 条件七：每个此前事件在订单事件流和成交报告中各恰好出现一次，且逐字段相等。
- 有任何歧义时不归属也不抛错，这张订单回到 <Ref id="ledger.plan_reading" />，按 PLAN_TAG_MISSING 处理。
- 归属不改任何原生行。
- 归属不认证订单由谁生成；排除策略仿造此类订单，由独立源码审查负责。
- 除下架结算平仓单以外，其余无标签订单仍按违例处理。

**输入**　订单报告、订单事件流（table:run_order_event）、成交报告、合约的 InstrumentClose 事件及结算价，以及 <Ref id="ledger.cycles" /> 的周期。

**输出**　client_order_id → 计划标签的映射。

**强制**　由代码强制：<Ref id="ledger.expiry_plan_owners" /> 逐项核对后输出只读映射；策略不得仿造此类订单，这一点由独立源码审查核对。

| 拒绝码 | 条件 |
|---|---|
| `PLAN_TAG_MISSING` | 无标签平仓单不满足全部归属条件或有歧义；该码由 <Ref id="ledger.plan_reading" /> 给出，归属函数本身不抛错 |

</Cap>

### C.6.1　原生预检 [#C-6-1]

代码强制用途事前声明、运行环境按摘要钉死且与候选运行契约一致、原件完整封存和源码暴露豁免判定；预检核对什么、结论怎样解读由 skill 指导。

<Cap id="C.6.1.1" kind="code" tier="rehearsal" tierLabel="演练证据" title="登记前须用同一 CI 运行环境做事前声明用途的最小预检并完整封存">

1. 依次核对候选、输出目录、运行器参数、运行环境与运行契约；任一不符即拒绝，账本与容器都不动。
2. 用与登记相同的导出器和市场提交新鲜导出输入，算出输入身份与有效配置身份。
3. 在一个写事务里写 purpose=precheck 的试验行与开始回执，回执记源码哈希、运行环境、输入身份与配置身份。
4. 事务成功后才启动容器，引擎在钉死运行环境内回放，审计器随后运行。
5. 结束时（包括中断与宿主失败）把原生 stdout/stderr、各阶段退出码、审计与报告原样封存。

- <Ref id="cli.replay_precheck" /> 调用 <Ref id="replay.precheck" />，对一个已发布候选 strategy_id@revision 做原生预检。
- 运行环境引用须是 CI 构建的镜像，并与随后登记用同一摘要。
- 运行器参数只给覆盖改动及其必要依赖的最短窗口与最少合约。
- 输出目录须在临时根之下且尚不存在。
- status 为 passed 表示原生与审计退出为零且无审计问题，否则为 failed。
- 预检不绑定登记，不消耗网格点。
- 登记时对曾执行过该源码的每个试验调用 <Ref id="registration.exposure_exempt" />。
- 豁免只给同时满足以下条件的试验：
- 用途在执行前声明为 precheck。
- 源码、运行环境、市场提交、范围规则版本与经济配置都与登记一致。
- 原件完整。
- 未绑定任何登记。
- 其余执行过该源码的试验一律按 <Ref id="H.4.2.2" /> 拒绝登记。
- 用途写在只追加的试验行上，探索回放不能事后改名为预检。

**输入**　候选引用、运行环境引用、市场提交、运行器参数与输出目录。

**输出**　试验编号、执行封存包名、status、问题清单与只供工程诊断的读数。

**强制**　代码（启动前核对、事务先于容器、封存原件、豁免判定）与账本（只追加的试验行与开始回执）。

| 拒绝码 | 条件 |
|---|---|
| `UNKNOWN_STRATEGY` | 候选不存在 |
| `NOT_TEMPORARY_PATH` | 输出目录不在临时根之下 |
| `PATH_EXISTS` | 输出目录已存在 |
| `RUNNER_OPTION_RESERVED` | 运行器参数含入口保留选项 |
| `RUNTIME_NOT_CI_BUILT` | 运行环境不能解析为唯一摘要，或不带构建源码版本标签 |
| `RUNTIME_CONTRACT_MISMATCH` | 候选运行契约不等于镜像运行契约 |
| `SOURCE_ALREADY_EXPOSED` | 登记时该源码曾在不满足豁免条件的试验中执行过 |

</Cap>

<Cap id="C.6.1.2" kind="skill" tier="rehearsal" tierLabel="演练证据" title="预检须读封存原件逐项核对五项">

- 预检结论是工程证据，不是经济反馈；静态编译或干净退出不算通过。
- Agent 读封存原件核对：构造参数被引擎接受。
- Agent 读封存原件核对：订单接口与参数类型正确，包括到期时间、只减仓 reduce-only 与括号单 bracket order。
- Agent 读封存原件核对：信号只用引擎时钟上已收盘的 K 线，成交晚于决策。
- Agent 读封存原件核对：指标就绪时点。
- Agent 读封存原件核对：规则触发后确有下单、成交或撤单回调。
- 确无交易机会与实现故障分别说明，查不明的保持待诊断。
- 零成交且无机会的预检只支持诊断性尝试，不给经济改善，与 <Ref id="G.4.1.2" /> 一致。
- 预检失败时修复源码，作为新候选重新预检、审查，再以 retry_of 登记。
- 失败的预检不记亏损，也不改研究优先级。
- 预检是主要工程成本，只覆盖改动及其必要依赖。

**强制**　skill：research-round 指导并以 eval 验证；代码不解读预检内容。

</Cap>

### C.6.2　独立源码审查 [#C-6-2]

审查是与账户审计分开的具名 Agent 证据：账本只追加保存结论，代码只核对结构、绑定身份与登记前的通过条件，不解读说明文字。

<Cap id="C.6.2.1" kind="database" tier="verified" tierLabel="已验证" title="独立 Agent 按四项审查预检原件，结论绑定源码与运行环境只追加入账">

- 审查者须是未参与编写的独立 Agent，读一个 purpose=precheck 试验的封存原件。
- 接口 api、因果 causal、活动 activity、就绪 readiness 四项各给 status（passed、failed、unresolved 或 no_opportunity）与非空观察说明。
- 审查经 <Ref id="cli.source_review" /> 与 <Ref id="registration.record_review" /> 写成 Agent 命名的 source-review-* 证据包，记在 <Ref id="table:evidence_bundle" />。
- 包内 source-review.json 存在 <Ref id="table:evidence" />，格式 source-review-v1。
- 字段为 trial_id、source_sha256、image_ref、execution_bundle、四项结论与具名审查者 authority。
- 身份字段由账本从试验行和执行封存中取，不接受调用方填写。
- 同名同内容重试幂等。
- 内容哈希是库内生成列；dolt_diff_evidence 出现任何 modified 或 removed 即为篡改发现。
- 登记与回放绑定时 <Ref id="registration.require_precheck" /> 核对审查：
- 审查存在且完好。
- 源码哈希与运行环境摘要和本次一致。
- 预检原件原生与审计退出为零。
- 四项均为 passed 或 no_opportunity。
- 已入账的失败审查由 <Ref id="qualification.source_reviews" /> 读取，使同源码同运行环境的运行不作经济证据，见 <Ref id="G.4.2.2" />。
- 这是源码审查，不是账户审计，也不升级为代码裁决；报告中两者分别呈现，见 <Ref id="A.5.1.2" />。

**输入**　一个 purpose=precheck 试验的执行封存包与独立 Agent 的四项结论。

**输出**　source-review.json 证据，以及登记或绑定时的通过或拒绝。

**强制**　账本（只追加、库内生成哈希、提交历史）与代码（结构与身份核对）。

| 拒绝码 | 条件 |
|---|---|
| `PRECHECK_CAPTURE_MISSING` | 绑定的预检原件不存在 |
| `RESERVED_BUNDLE` | 证据包名占用产品保留命名空间 |
| `BUNDLE_EXISTS` | 同名证据包内容不同 |
| `LEDGER_CORRUPT` | 读回重算内容哈希不符 |
| `SOURCE_PRECHECK_REQUIRED` | 登记或绑定时缺审查，或审查的源码哈希、运行环境摘要与本次不符 |
| `SOURCE_PRECHECK_FAILED` | 预检原件原生或审计退出非零，或任一项为 failed 或 unresolved |

</Cap>
