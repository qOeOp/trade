# 4　策略文件：一份策略源码从写出来到能拿去登记，必须守住的几条规矩。

第 3 章讲了候选是什么：账本里一份策略源码的精确字节。本章讲这份源码本身，也就是策略文件，该怎么写。它排在提假设（第 5 章）之前：每个假设最后都落成一份新的策略文件，先过本章这些规矩，才能登记和回放。

本章管六件事。策略写成一个单文件，规则和参数全在源码里；成交、费用、资金费这些交易事实只认引擎（发布版 NautilusTrader）；决策只用已经发生的信息；每个持仓按声明挂止损；订单按计划打标签，好数计划胜率；登记前先短跑一次原生预检，再请一个没参与编写的 Agent 做独立源码审查。

举个例子：全池 RSI 路线的 H05 把 RSI 长度从 14 改成 24。这不是给回放传一个新参数，而是改源码、发布成一个新候选。它先在登记要用的同一个运行环境里预检，审查通过后才登记，然后才正式回放。

## 4.1　写成一份可登记的单文件 [#C-1]

策略写成一个文件、一个入口类，规则和参数都在里面；回放只认发布时记下的那份字节。

<Steps>

<Step>

Agent 照 skill 写单文件源码：一个入口类，开头是写明职责立场的文件头。

</Step>

<Step>

发布时只检查文件形态，不运行源码，按内容哈希记成一个候选。

</Step>

<Step>

回放时按哈希取出源码，核对字节没变才加载。

</Step>

<Step>

回放只收策略引用、数据和窗口，带任何策略参数都会被拒绝。

</Step>

<Step>

回放结束时，策略自检报出的任何问题都让这次运行无效。

</Step>

</Steps>

### 单文件、入口与身份一致 [#C-1-1]

发布时记下内容哈希，执行时按同一哈希核对，两头都由代码把关。

#### 一个策略就是一个文件，里面只有一个入口类 [#C-1-1-1]

一个策略是一份完整的 UTF-8 单文件，全部交易规则和参数都在里面。文件里恰好有一个顶层入口类，名字和声明的一致，并且继承引擎的策略基类；回放只实例化这个类。根、策略库模板和派生候选都过同一道检查，没有第二种写法。

候选的身份就是这份文件的字节。规则散在几个文件里，或者入口不唯一，就说不清这次回放到底跑的是什么。

<div className="rd-example">

比如文件里有两个继承引擎策略基类的顶层类，或者入口类的名字和声明的对不上，发布或加载时就会被拒绝。全池 RSI 路线的根和 H01 到 H10，每一版都各自保存成这样一份完整源码。

</div>

#### 实际执行的字节必须和发布时记下的哈希一致 [#C-1-1-2]

发布时只检查文件形态，不运行源码，所以发布成功不证明规则写对了。之后每次从账本读出、每次加载执行，都重算一遍哈希，和发布时的记录比。加载时对不上就拒绝执行；读出时对不上，记为账本损坏。

比较两次回放，前提是确切知道各自跑的是哪份代码。字节悄悄变了还照跑，结果就挂错了候选。

<div className="rd-example">

比如 Agent 在工作目录里改了一行，却没有重新发布，回放读的仍是账本里原来那份字节，改动不会混进旧候选。要是账本里存的字节被动过，读出时哈希对不上，就记为账本损坏。

</div>

### 规则与参数的归属 [#C-1-2]

规则和参数只能写在源码里，回放不收策略参数。

<a id="C-1-2-1" />

**规则和参数只写在源码里，回放不收策略参数**

回放只接受四样东西：策略引用、输入数据、窗口和输出位置。周期、预热、仓位、风险上限、杠杆怎么用，包括单笔名义额占一根 K 线成交额的上限，都写在源码里。构造策略时只传合约、交易起点、预热数据这类回放输入。换一组参数就是改源码，也就是一个新候选。

参数能从外面传进来，同一份源码就能跑出很多不同的策略，候选的身份和试验次数都会对不上。

<div className="rd-example">

全池 RSI 路线里，H05 把 RSI 长度从 14 改成 24，H06 把单笔预算从 100 提到 500，H10 把分钟成交量占比上限从 1% 提到 5%。每一处都是改源码、发布成新候选，没有一次是给回放传参数。

</div>

### 加载时检查：依赖边界与自带钩子 [#C-1-3]

源码在隔离容器里加载，入口类必须带齐两个钩子。

#### 源码只能用锁定的库，在断网、只读的容器里加载 [#C-1-3-1]

源码只能导入标准库、引擎和运行环境里锁定的依赖。回放容器没有网络，文件系统只读，只有报告目录能写；除了引擎喂进来的数据，源码没有别的输入。加载时只核对身份和形态，执行时的安全边界由容器提供。

源码能联网或读别的文件，结果就依赖回放之外的东西，下次重跑不一定一样，也可能偷看到未来的数据。

<div className="rd-example">

比如 H07 要按历史资金费方向过滤新入场，用的资金费只能从引擎喂进来的数据里读，不能在源码里联网去交易所查，也不能读宿主机上的某个文件。

</div>

#### 入口类必须带诊断和自检两个钩子 [#C-1-3-2]

诊断钩子交出策略自报的计数，只写进摘要，不进审计，也不进绩效指标；自报的计数不能借用原生报告里交易事实的名字。自检钩子报出的问题和被拒的订单，都让这次运行无效。策略构造或回调出错时，运行以非零退出，记为无效。

策略自己数的东西可能数错，不能和引擎给出的交易事实混在一起；而策略自己发现的问题，不能被一个看起来正常的结果盖过去。

<div className="rd-example">

比如策略自报「RSI 跌破 30 的信号出现了 500 次」，可以写进摘要供诊断；但不能把这个数叫成「成交数」冒充原生报告。自检要是报出「有一张单没挂上止损」，这次运行直接无效。

</div>

### 文件头的立场与硬契约 [#C-1-4]

文件头由 skill 指导作者逐项对照源码。当前独立审查仅覆盖接口、因果、活动和就绪，不认证全部 27 项立场。

#### 文件头逐行写 27 项职责的立场，硬契约行不能写不适用 [#C-1-4-1]

文件头按模板写，先写出处，再逐行写 27 项策略职责（如止损、仓位），分九组。每行写立场、一句理由和来源：立场是采用、缺省或不适用之一，来源是出处、实现者或研究者（把出处的规则搬到别的市场、周期或品种）。单笔风险与数量、多个机会之间的资金分配、成员变化时的存量处置、保证金缓冲这几行是硬契约，不能写不适用。这条由 skill 指导，评测用例检查。

文件头让审查者和后来的 Agent 一眼看到这个策略在每项职责上的选择，缺了哪项也一目了然，下一个假设可以从缺口里挑。硬契约行写不适用，等于没说仓位和资金怎么管。

<div className="rd-example">

比如 RSI 策略不做对冲，「对冲与非线性暴露」这行可以写不适用并给理由；但「单机会的风险与数量」这行必须写清每笔用多少预算，比如 H06 的每笔 500 USDT，来源标为实现者。

</div>

#### 改源码前先读父版本文件头，只改涉及的职责行，登记时列出 [#C-1-4-2]

改源码之前，Agent 先读研发父版本（新候选所基于的那一版）的文件头。改源码时，文件头只改这次改动涉及的职责行，其余行和父版本逐字相同。登记时列出改了哪几项职责。这条由 skill 指导，评测用例检查。

这样文件头的变化和源码的改动对得上，审查和归因时能直接看出这一版动了哪项职责，不会出现源码改了、文件头还写着旧立场的情况。

<div className="rd-example">

比如某一版只把单笔预算从 100 提到 500，就像 H06 那样。文件头里只该改「单机会的风险与数量」这一行，登记时列出这一项；其余 26 行和父版本一字不差。

</div>

#### 多个合约共用一个账户时，资金怎么分、分不到的怎么办，写在源码里 [#C-1-4-4]

同一账户里多个合约实例共用固定本金时，源码写清资金预算和本金分配：同一批信号怎么一起分资金，分不到资金的机会怎么处理（缩量、延后或放弃），退出单只减仓。不能拿回调执行的先后顺序或引擎拒单代替分配规则：拒单是保证金事实（<Ref id="G.3.2.4" />），不是分配规则。把另一版本的规则合并进来后，分配仍在同一个账户里做，按一处改动登记（<Ref id="H.1.1.3" />）。这条由 skill 指导，评测用例检查。

不写分配规则，谁先拿到钱就取决于引擎碰巧先回调哪个合约，结果换个顺序就变，也说不清是策略的功劳还是顺序的运气。

<div className="rd-example">

比如同一个小时里 30 个合约同时出现 RSI 信号，账户剩下的预算只够开 10 笔。源码要写明按什么排序给这 10 笔分钱，另外 20 笔是缩小数量、等下一根 K 线，还是直接放弃，而不是让先回调的合约先抢到。

</div>

### 工作副本与脚手架 [#C-1-5]

源码从账本拿到工作目录时，改它要守的规则跟着文件一起带过去。

#### 导出工作副本时，改这个文件要守的规则随文件一起写出 [#C-1-5-1]

把候选导出到临时工作目录时，代码同时写出一份工作目录说明和文件头模板。说明只写改这个文件要守的几条规则和下一步该做什么。这些规则不在 skill 里重复。

Agent 改文件时，规则就在手边，不用另去翻 skill；两处各写一遍，迟早会写得不一样。

<div className="rd-example">

说明里会写：这里的源码不是记录，改完要发布才成为新候选；只改涉及的职责行；交易事实只取引擎状态；下一步依次是发布、预检、登记、回放；命令拒绝时按提示补齐再继续，不绕过。

</div>

#### 新策略从脚手架起步，生成时不写账本 [#C-1-5-2]

新策略可以用脚手架生成：源码里带文件头模板、唯一的入口类、两个仓位辅助方法和两个空钩子，同时生成工作目录说明。equity() 给出该合约报价货币的账户权益；order_quantity(quantity, price=None) 把下单数量向下取整到最小变动单位，低于最小变动单位、最小数量或（给了价格时）最小名义额时返回 None。生成时不写账本，发布之后才成为候选。

从同一个骨架起步，单文件、入口类、钩子这些要求一开始就满足，少走加载被拒的弯路；数量经 order_quantity 取整，也不会因低于交易所下限被拒单。生成的只是草稿，还不是研究记录。

## 4.2　把交易事实交给引擎 [#C-2]

成交、费用、资金费、持仓和账户都由引擎产生，策略和 Agent 只读不算。

<Steps>

</Step>

</Step>

<Step>

</Step>

<a id="C-2-1" />

交易事实只有引擎一个来源，回放只负责配置和原样写出。

<a id="C-2-1-1" />

**交易事实只由引擎产生，回放把报告原样写出**

成交、费用、资金费、持仓、余额和订单状态只由引擎产生。所有候选共用同一套固定的账户和撮合条款，源码改不了。回放只负责配置和写出，不计算、不修改、不补造任何交易事实；写出时缺了必需的引擎事实，运行以非零退出，记为无效。保证金不够由引擎拒单，产品不另设保证金审计。

交易事实要是策略或 Agent 自己算，就等于自己给自己打分。全部从引擎来，各个候选才在同一套规则下比较。

## 4.3　只用已发生的信息决策 [#C-3]

每次决策只能用已经收盘的 K 线和已经到达的事件，成交必须落在决策之后。

<Steps>

<Step>

Agent 只按已收盘的 K 线和已发生的事件写决策逻辑。

</Step>

<Step>

原生预检在真实引擎和运行环境里把候选短跑一次，留下决策、下单、成交三种时间戳。

</Step>

<Step>

独立源码审查的因果一项，按这些时间戳核对源码和预检原件。

</Step>

<Step>

因果一项通过，候选才能登记。

</Step>

<Step>

正式回放之后，再逐个计划核对成交都晚于决策 K 线收盘。

</Step>

</Steps>

<a id="C-3-1" />

决策能读到哪些信息，以及成交必须落在决策之后。

<a id="C-3-1-2" />

**成交时刻必须严格晚于决策 K 线的收盘时刻**

源码在决策 K 线的收盘事件里只定下交易意图，订单放到之后的引擎事件里再提交，成交时刻必须严格晚于那根 K 线的收盘。每个计划留下决策、下单、成交三种时间戳，原生预检（<Ref id="replay.precheck" />）和完整回放之后都逐个计划核对。成交和决策落在同一时刻就是实现缺陷，账户审计通过也一样，因为审计不查信号时钟（<Ref id="G.4.1.1" />）；Agent 要撤回基于这次运行的经济解释，修好源码后重新发布、预检、审查，再另行登记。

用收盘价决策又在同一刻成交，等于用还不知道的信息交易，回测会比实盘好看。这种错账户核对查不出来，所以要单独核时钟，并用审查把它挡在登记之前。

<div className="rd-example">

比如 RSI 在 10:00 收盘的那根小时 K 线上跌破 30。源码在这个收盘事件里只记下「要做多」，订单在之后的事件里提交，成交时刻要晚于 10:00。如果成交也记在 10:00，就算账户对账全对，这次结果也要撤回、修源码重来。

</div>

1. skill 指导 Agent 这样写源码。
2. 登记前，独立 Agent 按因果一项审这条时间戳链，结论绑定源码哈希和运行环境，只追加写进账本（<Ref id="registration.record_review" />）。
3. 没有同源码、同运行环境且已通过的预检和审查，登记会被拒绝（<Ref id="registration.require_precheck" />）。

## 4.4　给每个持仓挂保护单 [#C-4]

源码声明设不设止损；设了，每个持仓都要有止损单护着，出现裸仓运行就无效。

<Steps>

<Step>

源码在入口类上声明设不设止损，不写就当作设。

</Step>

<Step>

入场单连同止损、止盈一次提交给引擎。

</Step>

<Step>

入场单结束时，引擎撤掉挂在它下面的保护单；已成交的部分由源码按缺口补挂保护，持仓归零时撤掉剩余订单。

</Step>

<Step>

声明写进执行身份，随运行入账，回放之后改不了。

</Step>

<Step>

完整性审计重建每个时刻的止损覆盖：声明设止损的运行出现裸仓，就判无效。

</Step>

</Steps>

<a id="C-4-1" />

止损声明由代码检查并记下，出现裸仓怎么算由完整性审计按声明判。

<a id="C-4-1-1" />

**止损默认要设；声明不设时，裸仓只报告，不判无效**

源码在入口类上声明设不设止损，不写就当作设。声明只能是「是」或「否」，否则不加载，也不产生运行。声明写进执行身份，随运行入账，要改只能发布新候选；不设止损的理由写在文件头的立场里。完整性审计沿引擎的订单事件重建每个时刻的只减仓止损覆盖：声明设止损的运行出现裸仓就无效，声明不设的只报告。

设不设止损是策略的选择，但选了就要做到。声明先于回放记下，才不会等看了结果再说「这个策略本来就不设止损」。

<div className="rd-example">

全池 RSI 路线的根在原生摘要里记为不设止损，所以它的持仓没有止损单时只报告、不判运行无效。要是后来某一版改成设止损，就得发布新候选；从那以后它的任何一段裸仓都会让运行无效。

</div>

## 4.5　把交易切成可计数的计划 [#C-5]

一个信号下的全部订单打同一个计划标签，计划数和计划胜率只按标签来数。

<Steps>

<Step>

从持仓报告重建持仓周期，核对每笔成交恰好计入一次。

</Step>

<Step>

读出每张订单上的计划标签；下架结算时引擎自动生成的平仓单按规则归属。

</Step>

<Step>

核对计划和持仓周期一一对应，同一合约上计划不重叠。

</Step>

<Step>

算出计划数和计划胜率。

</Step>

<Step>

任何一处不合规，只把计划统计置空并写明原因，随运行入账。

</Step>

</Steps>

### 计划的定义与标签 [#C-5-1]

策略下单时写计划标签，代码按标签把订单归成计划。

#### 每张订单带一个计划标签，胜率按计划数 [#C-5-1-1]

一个计划是一个信号下的全部订单：入场、止损止盈、改仓和平仓。每张订单恰好带一个在本次回放里唯一的标签，后来补挂的保护单也要带。赢是指计划已平，而且算上手续费和资金费的实现盈亏大于零。计划胜率 = 赢的计划数 ÷（已平计划数 + 期末未平计划数）。

按单笔成交数胜率，一笔交易分几次成交就会被重复计数。按计划数，一个信号就是一笔交易，期末没平的也计入分母，胜率不会被偷偷抬高。

<div className="rd-example">

比如一次回放有 100 个计划：90 个已平，其中 50 个算上费用和资金费后赚钱；10 个到期末还没平。计划胜率是 50 ÷ 100 = 50%，持平的和没平的都不算赢。

</div>

<div className="rd-foot"><span className="rd-guard">代码</span> <span className="rd-impl">实现 <Ref id="ledger.plan_metrics">plan_metrics</Ref></span> <span className="rd-tier rd-tier-verified">已验证</span></div>

#### 计划和持仓周期一一对应，同一合约同时只有一个计划 [#C-5-1-2]

持仓周期是一个合约从开仓到持仓归零的那一段。每笔成交恰好属于一个周期，一个周期只装一个计划的成交。前一个计划的持仓没归零、订单没全部结束之前，同一合约不开新计划。持仓归零时策略撤掉剩下的订单；分批加仓仍算同一个计划。

计划和周期一一对上，才能确定每个计划赚了还是亏了。两个计划在同一合约上交叠，盈亏就分不开。

<div className="rd-example">

比如某合约上一个计划已经止损平仓，但止盈单还挂着没撤，这时不能开新计划，要先撤掉那张止盈单。全池 RSI 路线的根一共有 3225 个持仓周期，每个周期都要对上一个计划。

</div>

### 不合规与原生平仓单 [#C-5-2]

计划不合规不影响运行有效；引擎自动生成的平仓单，只有对得上号时才归进计划。

#### 计划不合规只置空计划统计，不判运行无效 [#C-5-2-1]

计划规则是计算计划统计的前提，不是账户事实。违反时只把相关的绩效指标置空，并写明原因和能定位到具体订单的细节。完整性审计和经济证据资格不受影响，其他指标照常给出。空着的值不当作零，也不能手工补上。

标签打错只说明计划数不准，不说明账户的钱算错了。为这个判整个运行无效，代价太大；但把空值当零或者手填，又会造出假数字。

<div className="rd-example">

比如有一张补挂的止损单忘了打标签，这次运行的计划数和计划胜率就空着，旁边写明是哪张订单缺标签。年化、最大回撤这些账户指标照常给出，运行仍然有效。

</div>

#### 下架结算时引擎生成的无标签平仓单，对得上号才归进计划 [#C-5-2-2]

合约下架时，引擎会自动生成一张不带标签的只减仓平仓单。只有当它和结算事件、所在的持仓周期、对应的计划逐项唯一对上时，才归进那个计划。有任何歧义就不归，按缺标签算作违例。归属只读报告、不改报告；策略自己仿造这种单的情况，由独立源码审查排查。

这张单不是策略下的，没有标签；直接算违例会冤枉策略，随便归又可能归错计划。只在对得上号时归属，两头都不出错。

<div className="rd-example">

</div>

## 4.6　登记前的原生预检与独立审查 [#C-6]

登记前先用同一运行环境短跑一次预检，再由另一个 Agent 审源码，两样都过才能登记。

<Steps>

<Step>

候选发布后，用登记将要用的运行环境和市场提交，跑一次最短的预检。

</Step>

<Step>

Agent 读封存的预检原件，分清是没有交易机会还是实现出了故障；有故障就修好，发布成新候选。

</Step>

<Step>

一个没参与编写的 Agent 按接口、因果、活动、就绪四项写审查结论，存进账本。

</Step>

<Step>

登记和回放时，代码核对审查和预检原件跟这一次的源码、运行环境一致，而且都通过。

</Step>

<Step>

通过只说明工程上能跑；能不能当经济证据，还要看完整性审计和有没有实际交易。

</Step>

</Steps>

### 原生预检 [#C-6-1]

预检的用途事先写明、运行环境和登记一致、原件完整封存，都由代码强制。

<a id="C-6-1-1" />

**预检用和登记相同的运行环境，用途事先写明，原件完整封存**

预检用的运行环境必须是自动构建、和随后登记同一摘要的镜像。用途在回放开始前就写进试验，之后不能改；别的用途跑过的回放不能改口叫预检。预检只跑覆盖这次改动所需的最短窗口和最少合约，不消耗网格点。结束时（包括中途中断）把原生输出、退出码和审计结果原样封存。

环境不一样，预检通过说明不了正式回放能跑。用途事先写明，才能把预检和看过结果的研究回放分开，不算作提前看过这份源码的表现。

<div className="rd-example">

全池 RSI 十轮演练里，审查都先于登记，登记都先于正式研究回放。路线一共有 67 次试验，只有 11 次绑定了正式研究运行，另外 56 次没有绑定正式运行，两类分开计数。

</div>

### 独立源码审查 [#C-6-2]

审查是独立 Agent 留下的具名证据，账本只追加不改，代码只核对绑定和是否通过。

<a id="C-6-2-1" />

**另一个 Agent 按四项审查预检原件，都过了才能登记**

审查者必须是没参与编写的 Agent，读的是预检的封存原件。接口、因果、活动、就绪四项各写结论和观察；当前审查不逐项认证全部 27 项职责的立场与源码一致。结论作为证据包只追加进账本，绑定源码和运行环境。登记和回放时，四项必须都是通过或无交易机会，否则拒绝。

写代码的人最容易放过自己的错。换一个没参与的 Agent 照着原件逐项查，才能挡住前视、挂单写错这类审计查不出的问题。
