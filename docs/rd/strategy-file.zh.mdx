# 4　策略文件：一份策略源码从写出来到能拿去登记，必须守住的几条规矩。

第 3 章讲了候选是什么：账本里一份策略源码的精确字节。本章讲这份源码本身，也就是策略文件，该怎么写。它排在提假设（第 5 章）之前：每个假设最后都落成一份新的策略文件，先过本章这些规矩，才能登记和回放。

本章管六件事。策略写成一个单文件，规则和参数全在源码里；成交、费用、资金费这些交易事实只认引擎（发布版 NautilusTrader）；决策只用已经发生的信息；每个持仓按声明挂止损；订单按计划打标签，好数计划胜率；登记前先短跑一次原生预检，再请一个没参与编写的 Agent 做独立源码审查。

举个例子：一个假设把 RSI 长度从 14 改成 24。这不是给回放传一个新参数，而是改源码、发布成一个新候选。它先在登记要用的同一个运行环境里预检，审查通过后才登记，然后才正式回放。

## 4.1　写成一份可登记的单文件 [#C-1]

策略写成一个文件、一个入口类，规则和参数都在里面；回放只认发布时记下的那份字节。

### 单文件、入口与身份一致 [#C-1-1]

发布时记下内容哈希，执行时按同一哈希核对，两头都由代码把关。

#### 一个策略就是一个文件，里面只有一个入口类 [#C-1-1-1]

一个策略是一份完整的 UTF-8 单文件，全部交易规则和参数都在里面。文件里恰好有一个顶层入口类，名字和声明的一致，并且继承引擎的策略基类；回放只实例化这个类。根、策略库模板和派生候选都过同一道检查，没有第二种写法。

候选的身份就是这份文件的字节。规则散在几个文件里，或者入口不唯一，就说不清这次回放到底跑的是什么。

#### 实际执行的字节必须和发布时记下的哈希一致 [#C-1-1-2]

发布时只检查文件形态，不运行源码，所以发布成功不证明规则写对了。之后每次从账本读出、每次加载执行，都重算一遍哈希，和发布时的记录比。加载时对不上就拒绝执行；读出时对不上，记为账本损坏。

比较两次回放，前提是确切知道各自跑的是哪份代码。字节悄悄变了还照跑，结果就挂错了候选。

### 规则与参数的归属 [#C-1-2]

规则和参数只能写在源码里，回放不收策略参数。

<a id="C-1-2-1" />

**规则和参数只写在源码里，回放不收策略参数**

回放只接受四样东西：策略引用、输入数据、窗口和输出位置。周期、预热、仓位、风险上限、杠杆怎么用，包括单笔名义额占一根 K 线成交额的上限，都写在源码里。构造策略时只传合约、交易起点、预热数据这类回放输入。换一组参数就是改源码，也就是一个新候选。

参数能从外面传进来，同一份源码就能跑出很多不同的策略，候选的身份和试验次数都会对不上。

### 加载时检查：依赖边界与自带钩子 [#C-1-3]

源码在隔离容器里加载，入口类必须带齐两个钩子。

#### 源码只能用计算类标准库和引擎的策略接口，在断网、只读的容器里加载 [#C-1-3-1]

源码只能导入计算类标准库和引擎的策略接口（`nautilus_trader` 的 `common`、`config`、`core`、`indicators`、`model`、`trading`）。加载前先静态检查源码：导入别的模块（运行器、行情目录、文件、进程），经允许的模块取到别的模块，按名字执行代码或取属性，读双下划线属性或栈帧，改共享的十进制上下文，读别的对象的私有属性，经导入的对象或调用结果赋值，改绑运行器包在源码外面的回调、时钟或缓存，都拒绝加载。缓存对源码只读：原生报告在回放结束后从缓存读出，源码一调清除或重置就让这次运行失败。回放容器没有网络，文件系统只读，只有报告目录能写；除了引擎喂进来的数据，源码没有别的输入。持仓量和多空比在回放入口带 `--metrics` 时由引擎按归档 `create_time` 之后 10 分钟交付，Paper 和 Live 从币安公开 REST 读同一行并在同一延迟后交付。静态检查不是沙箱，绕开它的写法本身留在源码里，由源码审查来看。

源码和运行器在同一个进程里执行。源码能联网或读别的文件，结果就依赖回放之外的东西，下次重跑不一定一样，也可能偷看到未来的数据；源码能改运行器的对象，就能换掉手续费、撮合或报告，而审计只核对报告之间是否一致，看不出来。

#### 入口类必须带诊断和自检两个钩子 [#C-1-3-2]

诊断钩子交出策略自报的计数，只写进摘要，不进审计，也不进绩效指标；自报的计数不能借用原生报告里交易事实的名字。自检钩子报出的问题和被拒的订单，都让这次运行无效。策略构造或回调出错时，运行以非零退出，记为无效。

策略自己数的东西可能数错，不能和引擎给出的交易事实混在一起；而策略自己发现的问题，不能被一个看起来正常的结果盖过去。

### 文件头的立场与硬契约 [#C-1-4]

文件头写明 27 项策略职责立场，发布与登记时由代码做格式与父子差异硬校验。

#### 文件头逐行写 27 项职责的立场，硬契约行必须写采用 [#C-1-4-1]

文件头按模板写，先写出处，再逐行写 27 项策略职责（`A1..I1`），分九组。每行写立场、一句理由和来源：立场是采用（`adopted`，策略里有对应规则）、缺省（`default`，问题存在而策略没有规则）或不适用（`not applicable`，这条线的合约上任何规则都管不到）之一，来源是出处（`source`）、实现者（`implementer`）或研究者（`researcher`，把出处的规则搬到别的市场、周期或品种）。其中 `E1`（单机会风险与数量）、`E4`（多机会资本分配）、`F5`（成员变化时存量处置）、`H2`（保证金与清算缓冲）四项是运行硬契约，立场必须写 `adopted`；`E3`（回撤与盈亏后风险调整）仅在连续亏损、盈利或账户回撤后改变风险预算比例时才标 `adopted`，常规的按当前权益百分比下单属于 `E1`（`E3` 标 `default`）。发布候选时代码硬校验格式：27 行齐全、立场合法、四项硬契约均为 `adopted`，否则直接拒绝为 `DUTY_HEADER_INVALID`。

文件头让审查者和后来的 Agent 一眼看到这个策略在每项职责上的选择，缺了哪项也一目了然，下一个假设可以从缺口里挑。

#### 改源码前先读父版本文件头，只改涉及的职责行，登记时硬核对差异 [#C-1-4-2]

改源码之前，Agent 先读研发父版本（新候选所基于的那一版）的文件头。改源码时，文件头只改这次改动涉及的职责行，其余行和父版本逐字相同。登记（`registration add`）时列出本次声明改动的职责（`changed_duties`），代码自动比对父版本与每个网格候选的 27 行职责头：凡是父子文件头实际发生变化的行集合与 `changed_duties` 不一致，立即拒绝登记（`DUTY_HEADER_MISMATCH`）。

这样文件头的变化和登记声明严格锁定，审查和归因时能直接看出这一版动了哪项职责，不会出现源码改了、文件头却漏改或偷改其他职责的情况。

#### 多个合约共用一个账户时，资金怎么分、分不到的怎么办，写在源码里 [#C-1-4-4]

同一账户里多个合约实例共用本金时，源码写清资金预算和本金分配：同一批信号怎么一起分资金，分不到资金的机会怎么处理（缩量、延后或放弃），退出单只减仓。不能拿回调执行的先后顺序或引擎拒单代替分配规则：拒单是保证金事实（<Ref id="G.3.2.4" />），不是分配规则。把另一版本的规则合并进来后，分配仍在同一个账户里做，按一处改动登记（<Ref id="H.1.1.3" />）。

不写分配规则，谁先拿到钱就取决于引擎碰巧先回调哪个合约，结果换个顺序就变，也说不清是策略的功劳还是顺序的运气。

### 工作副本与脚手架 [#C-1-5]

源码从账本拿到工作目录时，改它要守的规则跟着文件一起带过去。

#### 导出工作副本时，改这个文件要守的规则随文件一起写出 [#C-1-5-1]

把候选导出到临时工作目录时，代码同时写出一份工作目录说明和文件头模板。说明只写改这个文件要守的几条规则和下一步该做什么。这些规则不在 skill 里重复。Agent 改文件时，规则就在手边，不用另去翻 skill；两处各写一遍，迟早会写得不一样。

#### 新策略从脚手架起步，生成时不写账本 [#C-1-5-2]

新策略可以用脚手架生成：源码里带文件头模板、唯一的入口类、两个仓位辅助方法和两个空钩子，同时生成工作目录说明。`equity()` 给出该合约报价货币的账户权益；`order_quantity(quantity, price=None)` 把下单数量向下取整到最小变动单位，低于最小变动单位、最小数量或（给了价格时）最小名义额时返回 `None`。生成时不写账本，发布之后才成为候选。

## 4.2　把交易事实交给引擎 [#C-2]

成交、费用、资金费、持仓和账户都由引擎产生，策略和 Agent 只读不算。

<a id="C-2-1" />

交易事实只有引擎一个来源，回放只负责配置和原样写出。

<a id="C-2-1-1" />

**交易事实只由引擎产生，回放把报告原样写出**

成交、费用、资金费、持仓、余额和订单状态只由引擎产生。所有候选共用同一套固定的账户和撮合条款（含 `--leverage`，默认 3），源码改不了。回放只负责配置和写出，不计算、不修改、不补造任何交易事实；写出时缺了必需的引擎事实，运行以非零退出，记为无效。保证金不够由引擎拒单，产品不另设保证金审计。

交易事实要是策略或 Agent 自己算，就等于自己给自己打分。全部从引擎来，各个候选才在同一套规则下比较。

## 4.3　只用已发生的信息决策 [#C-3]

每次决策只能用已经收盘的 K 线和已经到达的事件，成交必须落在决策之后。

<a id="C-3-1" />

决策能读到哪些信息，以及成交必须落在决策之后。

<a id="C-3-1-2" />

**成交时刻必须严格晚于决策 K 线的收盘时刻**

源码在决策 K 线的收盘事件里只定下交易意图，订单放到之后的引擎事件里再提交，成交时刻必须严格晚于那根 K 线的收盘。每个计划留下决策、下单、成交三种时间戳，原生预检（`replay.precheck`）和完整回放之后都逐个计划核对。成交和决策落在同一时刻就是实现缺陷，账户审计通过也一样，因为审计不查信号时钟（<Ref id="G.4.1.1" />）；Agent 要撤回基于这次运行的经济解释，修好源码后重新发布、预检、审查，再另行登记。

用收盘价决策又在同一刻成交，等于用还不知道的信息交易，回测会比实盘好看。原生订单事件能证明提交和成交时刻，却不能独立证明任意策略形成决策的时刻；决策时钟由源码契约、原生预检证据和独立源码审查核对：

1. skill 指导 Agent 在收盘回调中只记录意图、不在同一时刻自撮合成交。
2. 登记前，独立 Agent 按因果一项审这条时间戳链，结论绑定源码哈希和运行环境，只追加写进账本（`registration.record_review`）。
3. 没有同源码、同运行环境、同配置且已通过的预检和审查，登记会被拒绝（`registration.require_precheck`）。
4. 当经济证据时只认身份匹配的审查记录（`registration.source_reviews`）；因果审查没过的运行不当经济证据，审查结论和账户审计分开列出（<Ref id="G.4.2.2" />）。

## 4.4　给每个持仓挂保护单 [#C-4]

每个源码都设止损，按原生持仓补齐保护。完整性审计拒绝止损覆盖缺口持续超过一分钟的运行。

<a id="C-4-1" />

止损声明由代码检查并记下，出现裸仓怎么算由完整性审计按声明判。

一个持仓的有效止损合计不超过它的数量，所以不按每笔成交各挂一张。不改单：要移动止损，或者同一时刻连续收到多笔分批成交使实际持仓超过了已挂止损单的数量时，先撤旧单，在撤单回报上再按最新持仓数量提交新止损单；撤单可能被拒，旧单照常工作，源码须处理拒绝事件。审计检查覆盖结果，回调与策略特有的竞态由独立源码审查核对。下单规则（`ORDER_RULE`）全文见 [engine/README.md](https://github.com/qOeOp/trade/blob/main/engine/README.md#subscriptions-orders-and-stop-coverage)。

<a id="C-4-1-1" />

**每个策略都设止损**

源码在入口类上声明设止损，不写就当作设；声明不是「是」的源码不加载，也不产生运行。完整性审计沿原生订单事件核对实际持仓与有效只减仓止损的覆盖缺口；缺口持续严格超过一根执行 K 线（当前一分钟）就列入裸仓区间，使运行无效。短于或恰好一分钟的缺口不拒绝，也不列入区间；审计通过不证明每一刻都有保护。

不设止损的策略在产品里没有位置：真钱运行时，一笔没有保护的持仓就是无上限的亏损。在载入时拒绝，而不是在结果里报告，就不会有人看了结果再说「这个策略本来就不设止损」。

## 4.5　把交易切成可计数的计划 [#C-5]

一个信号下的全部订单打同一个计划标签，计划数和计划胜率只按标签来数。

### 计划的定义与标签 [#C-5-1]

策略下单时写计划标签，代码按标签把订单归成计划。

#### 每张订单带一个计划标签，胜率按计划数 [#C-5-1-1]

一个计划是一个信号下的全部订单：入场、它所开持仓的止损止盈，以及之后减仓或平仓的订单。每张订单恰好带一个在本次回放里唯一的标签，后来补挂的保护单也要带。赢是指计划已平，而且算上手续费和资金费的实现盈亏大于零。计划胜率 = 赢的计划数 ÷（已平计划数 + 期末未平计划数）。

按单笔成交数胜率，一笔交易分几次成交就会被重复计数。按计划数，一个信号就是一笔交易，期末没平的也计入分母，胜率不会被偷偷抬高。

<div className="rd-example">

比如一次回放有 100 个计划：90 个已平，其中 50 个算上费用和资金费后赚钱；10 个到期末还没平。计划胜率是 50 ÷ 100 = 50%，持平的和没平的都不算赢。

</div>

#### 计划和持仓周期一一对应 [#C-5-1-2]

持仓是 HEDGING 的：每张入场单开自己的持仓，持仓周期是这个持仓从开仓到归零的那一段。每笔成交恰好属于一个周期，一个周期只装一个计划的成交，一个计划的成交只在一个周期里。同一合约上的计划可以同时开着；持仓归零时策略撤掉这个计划剩下的订单，免得入场单剩余部分再开出一个持仓。计划和周期一一对上，才能确定每个计划赚了还是亏了。

### 不合规与原生平仓单 [#C-5-2]

计划不合规不影响运行有效；引擎自动生成的平仓单，只有对得上号时才归进计划。

#### 计划不合规只置空计划统计，不判运行无效 [#C-5-2-1]

计划规则是计算计划统计的前提，不是账户事实。违反时只把相关的绩效指标置空，并写明原因和能定位到具体订单的细节。完整性审计和经济证据资格不受影响，其他指标照常给出。空着的值不当作零，也不能手工补上。

#### 下架结算时引擎生成的无标签平仓单，对得上号才归进计划 [#C-5-2-2]

合约下架时，引擎会自动生成一张不带标签的只减仓平仓单。只有当它和结算事件、所在的持仓周期、对应的计划逐项唯一对上时，才归进那个计划。有任何歧义就不归，按缺标签算作违例。归属只读报告、不改报告；策略自己仿造这种单的情况，由独立源码审查排查。

## 4.6　登记前的原生预检与独立审查 [#C-6]

登记前先用同一运行环境短跑一次预检，再由另一个未参与编写的 Agent 对照父子 unified diff 审源码，两道门都过才能登记。

### 原生预检 [#C-6-1]

预检的用途事先写明、运行环境和登记一致、原件完整封存，都由代码强制。

<a id="C-6-1-1" />

**预检用和登记相同的运行环境，用途事先写明，原件完整封存**

预检用的运行环境必须是自动构建、和随后登记同一摘要的镜像。用途在回放开始前就写进试验，之后不能改；别的用途跑过的回放不能改口叫预检。预检只跑覆盖这次改动所需的最短窗口和最少合约，不消耗网格点；交易窗口超过 7 天的预检在开跑前就被拒绝。结束时（包括中途中断）把原生输出、退出码和审计结果原样封存。若一次预检因选窗内无信号导致活动项未决（`unresolved`），同一候选在同一运行环境上补跑触发了交易并审计通过的预检后，未决项即被后续通过的预检消解。

环境不一样，预检通过说明不了正式回放能跑。用途事先写明，才能把预检和看过结果的研究回放分开，不算作提前看过这份源码的表现。

### 独立源码审查 [#C-6-2]

审查是独立 Agent 留下的具名证据，账本只追加不改，代码只核对绑定和是否通过。

<a id="C-6-2-1" />

**另一个 Agent 对照父子 diff 与预检原件按四项盲审，都过了才能登记**

审查者必须是没参与编写的子 Agent，输入只给被审源码、它与父版本的 unified diff（`diff -u`）以及预检的封存原件；仅常数不同的同批次网格候选可放在同一次子 Agent 审查中一并核对。接口、因果、活动、就绪四项各写结论和观察，作为证据包只追加进账本，绑定源码和运行环境。登记和回放时，四项必须都是通过（或活动项为经核实的无交易机会），否则拒绝。因果项要追溯每个价格输入何时已知，审查者用 `market bars` 读同一市场日的已存 K 线与资金费及其交付时刻，不开试验、不算暴露，不写脚本导入 market 内部模块。就绪项看指标是否已收敛，不看原生 `initialized`：递归平均满一个周期就标记 initialized，此时初值仍占约 14%（EMA）或 37%（Wilder 平均，如 ATR）的权重；源码要从实例的第一个输入数起，等初值权重降到 1% 以下（EMA 约 2.5 个周期，Wilder 约 5 个周期）才做决策，预热段过短或模拟盘冷启动时同样成立。

写代码的人最容易放过自己的错。换一个没参与的 Agent 照着父子 diff 与预检原件逐项盲审，才能挡住前视、同刻分批成交止损漏改、冷启动未收敛这类账户审计查不出的问题。
