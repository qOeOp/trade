## C.1　写成一份可登记的单文件 [#C-1]

发布入口只解析源码、记内容哈希并写入账本，得到候选 strategy_id@revision；运行器装载时按同一哈希读字节，核对唯一入口类、依赖边界、两个必带钩子与两项声明，任一不符即拒绝运行。运行器只接受策略引用、输入、窗口与输出，全部规则与参数只能在源码，参数变体就是新候选。文件头用九组立场与三条硬契约写明设计选择，由 skill 指导、供登记前的独立源码审查查漏。四个组件按身份、归属、加载检查、文件头排列，前三者由代码强制，第四个由 skill 指导。

<Step>

</Step>

<Step>

<Ref id="cli.candidate_publish" /> 经 <Ref id="ledger.check_source" /> 只解析不执行，<Ref id="ledger.publish_candidate" /> 以内容哈希写一行候选并提交，返回 strategy_id@revision。

</Step>

<Step>

</Step>

<Step>

### C.1.1　单文件、入口与身份一致 [#C-1-1]

两条能力都由代码强制：发布侧只解析不执行，确认单文件与唯一入口并以内容哈希写入账本；装载侧按同一哈希读字节、执行并核对入口类。输入是源码字节、入口类名与内容哈希，输出是账本里的候选或拒绝码。

<Cap id="C.1.1.1" kind="code" tier="verified" tierLabel="已验证" title="一个完整的单文件，唯一顶层入口是引擎认的策略类">

一个独立策略是一份完整的 UTF-8 单文件源码，含全部交易规则与参数。它恰有一个与声明的入口类名同名的顶层类，该类在本文件内声明且是引擎策略基类的真子类；运行器只实例化这个类。形态分两处核对：发布时 <Ref id="ledger.check_source" /> 只解析不执行，确认源码非空、在长度上限内、可解析、顶层同名类恰为一个（拒绝码 SOURCE_SIZE、SOURCE_SYNTAX、ENTRY_CLASS_INVALID、ENTRY_CLASS_NOT_UNIQUE）；装载时 <Ref id="engine.load_strategy" /> 执行源码后确认入口类在本模块声明并继承引擎策略基类（ENTRY_CLASS_INVALID）。策略库模板、用户自建的根节点 root 与派生候选走同一检查，没有第二种入口形态。由代码强制。

发布 <Ref id="cli.candidate_publish" /> 只解析源码、不执行，证明的是形态而非规则正确。<Ref id="ledger.publish_candidate" /> 以源码字节的 SHA-256 为内容哈希 content hash，在一笔事务里写一行 <Ref id="table:candidate" /> 并提交，返回引用名 strategy_id@revision；相同字节不能再次发布（SOURCE_EXISTS，附该字节对应的引用），任何改动都产生新候选；研发父版本 parent 与改动说明同有同无（LINEAGE_INCOMPLETE），父须存在（UNKNOWN_CANDIDATE）。执行时 <Ref id="engine.load_strategy" /> 读到的字节哈希必须等于发布哈希（CONTENT_HASH_MISMATCH）；封存回放还须与上层写出的源码绑定一致（BINDING_MISMATCH）。任何读取经 <Ref id="ledger.read_candidate" /> 重算存储字节哈希，不符即 LEDGER_CORRUPT。由代码与账本的内容哈希唯一约束共同强制。

### C.1.2　规则与参数的归属 [#C-1-2]

C.1.2.1 由代码强制：运行器的参数面固定为引用、输入、窗口与输出，规则与参数因此只能在源码。C.1.2.2 由 skill 指导：选币规则同样归源码，以环境产出的成员区间为输入。

<Cap id="C.1.2.1" kind="code" tier="rehearsal" tierLabel="演练证据" title="全部规则与参数只在源码；运行器不接受策略参数；参数变体就是新候选">

运行器的命令行由 <Ref id="engine.build_parser" /> 固定为策略引用、输入、窗口、输出目录与探针开关；<Ref id="engine.parse_configuration" /> 对任何未定义选项拒绝（UNKNOWN_OPTION），所以没有策略参数入口，也没有通用键值透传。信号周期与预热声明、仓位、单笔风险、名义上限、杠杆用法等全部规则与参数写在源码，随内容哈希固定。<Ref id="engine.configure_strategy" /> 构造入口类时只传运行器输入（合约、交易起点、策略标识、成员区间、按声明取的预热日线），账户与撮合条款取所有候选共用的 <Ref id="engine.account_contract" />，并进入有效配置与执行身份。参数变体就是新源码、新候选。这些是 Agent 的设计变量，改动不需用户授权，也不记为用户约束（<Ref id="A.2.2.1" />）。由代码强制。

### C.1.3　加载时检查：依赖边界与自带钩子 [#C-1-3]

两条能力由代码强制：装载器把源码作为独立模块执行并核对两个钩子与两项声明，容器与运行环境给出无网络、只读与锁定依赖的边界。钩子输出在回放结束时进入摘要与完整性发现，构造与回调异常由运行器包裹后非零退出。

<Cap id="C.1.3.1" kind="code" tier="rehearsal" tierLabel="演练证据" title="只导入标准库、引擎与锁定依赖，作为独立模块加载；除引擎喂给的数据外无输入，不能联网">

源码只能导入标准库、引擎与运行环境 runtime image 锁定的依赖。<Ref id="engine.load_strategy" /> 以内容哈希命名的独立模块执行源码，无包名、不能相对导入，执行抛错即 SOURCE_EXECUTION_FAILED。运行环境只由 CI 构建（<Ref id="runtime.build_image" />），镜像里只有引擎、运行器与锁定依赖，没有研究或策略模块；回放容器由 <Ref id="runtime.container_command" /> 启动：无网络、根文件系统只读、只读挂载声明的输入、唯一可写的是报告目录。因此除引擎喂给的数据外源码没有其他输入，缺依赖在原生预检的构造阶段暴露。装载只证明身份与形态，不担保任意 Python 安全，执行边界由容器提供。由代码与运行环境强制。

### C.1.4　文件头的立场与硬契约 [#C-1-4]

四条能力都由 skill 指导，代码不裁决：文件头先用九组立场各一行写明采用、缺省或不适用，再写三条硬契约（仓位与资金预算、成员变化处置、共享资本分配）。输出是独立源码审查可逐项核对的声明；资金使用率与生命周期审计由代码产出读数，反馈声明是否兑现。

<Cap id="C.1.4.1" kind="skill" tier="unverified" tierLabel="待验证" tierNote="缺的证据：尚无按九组文件头写出并经独立源码审查查漏的实际候选。" title="文件头按九组各写一行立场：采用／缺省／不适用加一句理由">

文件头按九组（对象与适用性、预测与学习、首次行动与记忆、经济构型、风险与分配、持仓路径、实施、资本、生命周期与可行性）各写一行立场，取值为采用、缺省或不适用，附一句理由，并标明出自出处原话、实现者缺省还是研究者推广（<Ref id="L.1.3.3" />）。27 项职责目录只作 skill 参考文件，供登记前的独立源码审查（<Ref id="C.6.2.1" />）查漏，不进正文。发布不核对文件头，形态检查只看单文件与唯一入口。由 skill 指导，eval 校验，独立源码审查结论作为具名证据。

## C.2　把交易事实交给引擎 [#C-2]

撮合、成交、手续费、资金费（funding）、持仓、账户与风控全部由引擎（engine）产生，以引擎事件与报告为准。数据流只有一个方向：运行器把固定账户与撮合常量配置给引擎并回放，策略从引擎缓存与组合读状态、响应事件、提交订单，引擎审单并撮合，运行器把引擎报告原样写出，审计按报告对账，读数与 Agent 统计只从产品报告读。代码强制配置、原样写出与后果核对；策略与 Agent 不自算交易事实这一条由 skill 指导并经独立源码审查核对。保证金不足由引擎拒单，产品不另设保证金审计。

<Steps>

<Step>

运行器按 engine.account_contract 把净额保证金账户与 K 线撮合常量配置给引擎，经 engine.replay 回放

</Step>

<Step>

策略从引擎缓存（cache）与组合（portfolio）读订单、持仓与账户，响应订单与持仓事件并提交订单

</Step>

<Step>

</Step>

<Step>

engine.write_native_reports 把引擎报告、订单事件史与敞口表原样写出，被否被拒订单与自检发现记为完整性发现

</Step>

<Step>

## C.3　只用已发生的信息决策 [#C-3]

策略源码在每次决策时只能读到引擎时钟上已经收盘的 K 线和已经到达的事件，下的单成交时刻必须严格晚于决策 K 线的收盘。前视偏差（look-ahead bias）和同钟成交都算实现缺陷，不是经济结果。这两条规则由 skill 写给 Agent，Agent 按它们写源码。原生预检（native precheck）留下决策、下单、成交三类时间戳，独立源码审查的因果一项按这些时间戳核对。审查失败时，代码拒绝登记（registration），也不让对应的运行作经济证据。账户审计不查信号时钟，所以因果结论和审计结论分开呈现。

<Steps>

<Step>

### C.3.1　决策能用的信息与成交时钟 [#C-3-1]

两条能力都由 skill 指导。C.3.1.1 限定决策能读什么信息，C.3.1.2 限定成交的时钟。输入是候选源码，输出是预检与回放留存的三类时间戳。两条能力在独立源码审查的因果项上核对，由登记门禁和经济证据资格两处代码执行后果。

<Cap id="C.3.1.1" kind="skill" tier="verified" tierLabel="已验证" title="只按引擎时钟上已收盘的 K 线决策">

做什么：候选源码在每个决策点只读引擎时钟上已经收盘的 K 线和已经到达的事件（成交回报、标记价、资金费、合约生命周期事件）。

源码不得做的事：
- 不用全样本统计。均值、分位、标准化参数都只能按已发生数据滚动计算。
- 不把未来值移到当前行。
- 不在源码里假设 K 线内的价格路径。引擎按 1 分钟 K 线撮合，K 线内顺序未知，见 <Ref id="W.5.1.1" />。

结构事件（摆动点、突破确认等）按它成立的时刻打戳，不在形成它的那根 K 线上行动。

时刻约定：K 线的可用时刻只有收盘时刻一个定义（<Ref id="W.2.1.3" />），导出时事件时间就等于收盘时刻（<Ref id="market.write_bars" />）。高周期 K 线按固定规则从 1 分钟派生（<Ref id="market.derive_bars" />），也在收盘时刻才可用。

输入与输出：输入是 Agent 写的候选源码，输出是满足上述约束的决策逻辑。

谁强制：skill 写成源码规则，没有代码拒绝码。违反时由独立源码审查的因果一项判失败；审查失败的源码由 <Ref id="registration.require_precheck" /> 拒绝登记，对应运行由 <Ref id="qualification.source_reviews" /> 排除出经济证据。

## C.4　给每个持仓挂保护单 [#C-4]

保护单分两层落实。第一层是声明与覆盖：源码用类属性声明是否设止损，加载器检查后把声明写入运行身份，随运行封存；完整性审计沿引擎订单事件史重建每个时刻的只减仓（reduce-only）止损覆盖，按这份声明决定裸仓使运行无效，还是只报告。第二层是挂法与收束：入场连同止损止盈以引擎括号单（bracket order）一次提交，母单终止时由引擎撤其子单；母单终止后留下的已成交数量由源码在回调里按缺口补挂，持仓归零时撤剩余单。两层在审计的覆盖重建里汇合：代码负责声明、引擎配置和审计，skill 指导源码怎么挂、怎么补、怎么收束。

<Steps>

<Step>

源码以类属性 USES_STOP_LOSS 声明是否设止损（缺省 True）；加载器检查为布尔值，并把声明写入运行身份与原生摘要

</Step>

<Step>

入场以引擎括号单提交：OTO 母单入场，只减仓、互为 OUO 的止损与止盈子单在母单成交后激活

</Step>

<Step>

母单到期、撤单或改量终止时，引擎撤其子单；源码在到期与撤单回调里按缺口补挂独立的只减仓止损与止盈

</Step>

<Step>

持仓归零时，源码撤该计划的全部剩余单，计划结束时订单组无残留

</Step>

<Step>

完整性审计沿订单事件史重建持仓与止损覆盖；声明设止损的运行出现裸仓即无效，声明不设的只报告裸仓区间

</Step>

</Steps>

### C.4.1　止损声明与覆盖 [#C-4-1]

加载器检查声明并把它写入运行身份，属代码强制。覆盖要求（任一持仓时刻止损量不少于持仓量）由 skill 写给源码作者；裸仓的判定和一根执行 K 线的容忍长度由审计定义。输入是源码声明和引擎订单事件史，输出是运行身份里的声明字段和审计给出的裸仓区间。

<Cap id="C.4.1.1" kind="code" tier="rehearsal" tierLabel="演练证据" title="是否设止损在源码声明，缺省为设；声明不设的裸仓只报告不拒绝">

源码在入口类上用类属性 USES_STOP_LOSS 声明是否设止损，不写即为 True。加载时，<Ref id="engine.load_strategy" /> 检查它的类型必须恰为 bool，否则拒绝加载，运行器非零退出，不产生运行。通过后，<Ref id="engine.strategy_metadata" /> 把声明写成运行身份字段 strategy_uses_stop_loss，并入原生摘要与执行身份，随研究封存（seal）进入账本；回放之后声明不能再改，要改只能发布新候选。审计读摘要里的这个字段，不读源码：值为 True 时，任何裸仓都使运行无效（invalid）；值为 False 时，裸仓区间只写进审计结果，运行仍可有效（判定见 <Ref id="G.3.3.2" />）。由代码强制：加载器负责类型检查，元数据函数负责写入身份，审计负责按声明分流。声明不设止损的理由由文件头立场写明，不靠运行器推断。

### C.4.2　保护单的挂法与收束 [#C-4-2]

括号单和“母单终止即撤子单”是引擎的原生行为，由运行器通过账户契约开启，属代码。部分成交后的补挂和归零时的收束是源码规则，由 skill 指导。两者都由审计的覆盖重建检查；引擎版本变更后，用运行环境配对重放复核激活与撤单顺序。

<Cap id="C.4.2.1" kind="code" tier="verified" tierLabel="已验证" title="入场连同止损止盈用引擎括号单一次提交；母单终止时引擎撤其子单">

入场与保护用引擎的括号单一次提交，构成一个订单组：入场为 OTO 母单；止损与止盈为子单，均为只减仓、互为 OUO，母单成交后才激活。入场单的有效期用 GTD 加到期时刻 expire_time 表达，不由源码自行计时撤单。母单到期、撤单或改量终止时，由引擎撤销或调整其子单。运行器在 <Ref id="engine.account_contract" /> 里设定 support_contingent_orders=True 与 support_gtd_orders=True，交给场所配置，以开启这两项原生行为；没有另建的订单组管理，也没有自写的撤单逻辑。括号单的每张订单都带同一个计划标签（见 <Ref id="C.5.1.1" />）。由代码强制的只有引擎配置；源码选不选括号单不由加载器检查，没有保护的持仓由 <Ref id="C.4.1.2" /> 的覆盖审计发现。引擎版本变更后，括号单激活与撤子单的顺序须经 <Ref id="research-round/references/changes.md#runtime-parity-replay">运行环境配对重放</Ref> 复核，才算行为未变。

## C.5　把交易切成可计数的计划 [#C-5]

一个信号下的全部订单带同一个计划标签，构成一个计划（plan）；计划与持仓周期一一对应，同一合约同时至多一个活跃计划。计划读数由代码在封存入账时从订单、成交、持仓报告与订单事件史读出，是计划数与计划胜率的唯一来源：先重建持仓周期，再归属下架结算平仓单，最后按标签对应计划与周期。不合规只使计划读数为空并写原因，回放有效性与账户读数不受影响；契约的遵守由策略源码负责，独立源码审查核对。

### C.5.1　计划的定义与标签 [#C-5-1]

两条能力均由代码强制：输入是订单、成交与持仓报告原生行，先由持仓报告重建周期，再按标签把订单归为计划并与周期一一对应，输出计划数、赢数与计划胜率。标签由策略源码在提交订单时写入。

<Cap id="C.5.1.1" kind="code" tier="verified" tierLabel="已验证" title="一个计划＝一个信号在一个计划标签下提交的全部订单；每张订单恰带一个全回放唯一的计划标签">

计划（plan）是一个信号提交的全部订单：分批进场、共用的止损止盈、之后的改仓与平仓。策略源码给每张订单（含括号单 bracket order 的入场单与两张子单、母单终止后补挂的只减仓 reduce-only 单）恰好一个计划标签，标签值在整次回放内唯一；一个计划只涉及一个合约。代码强制：读数函数 <Ref id="ledger.plan_reading" /> 从订单报告的标签读出计划，输入为订单、成交、持仓报告原生行与 <Ref id="ledger.cycles" /> 的周期，输出已平计划数、赢数、期末未平计划数与计划胜率；赢＝周期已平且实现盈亏（含手续费与资金费 funding）大于零，持平与期末未平都不算赢，分母为已平加未平计划数。缺标签、多标签、计划跨合约或标签不可解析时抛出具名原因（PLAN_TAG_MISSING、PLAN_TAG_MULTIPLE、PLAN_MULTI_INSTRUMENT、NATIVE_VALUE_UNREADABLE），按 <Ref id="C.5.2.1" /> 处理。计划读数是描述统计，不改任何原生行。

## C.6　登记前的原生预检与独立审查 [#C-6]

### C.6.1　原生预检 [#C-6-1]

代码强制四件事：预检用途事前声明、运行环境按摘要钉死且与候选运行契约一致、原件完整封存、源码暴露豁免判定。预检要核对什么、结论怎样解读由 skill 指导。输入是已发布候选、CI 构建的运行环境引用、市场提交、最小窗口的运行器参数；输出是 purpose=precheck 的试验行、开始回执、执行封存包与工程问题清单。

<Cap id="C.6.1.1" kind="code" tier="rehearsal" tierLabel="演练证据" title="发布后、登记前，用锁定引擎与实际 CI 运行环境做针对改动的最小预检并封存">

<Ref id="cli.replay_precheck" /> 调用 <Ref id="replay.precheck" />，对一个已发布候选 strategy_id@revision 做事前声明用途的原生预检。
输入：候选引用、运行环境引用、市场提交、运行器参数与输出目录。运行环境引用须是 CI 构建的镜像，并与随后登记用同一摘要；运行器参数只给覆盖改动及其必要依赖的最短窗口与最少合约；输出目录须是尚不存在的临时目录。
启动任何进程前依次核对，任一不符即拒绝，账本与容器都不动：
- 候选存在（UNKNOWN_STRATEGY）；
- 输出目录在临时根之下且尚不存在（NOT_TEMPORARY_PATH、PATH_EXISTS）；
- 运行器参数不含入口保留选项（RUNNER_OPTION_RESERVED）；
- 运行环境能解析为唯一摘要，且带构建源码版本标签（RUNTIME_NOT_CI_BUILT）；
- 候选运行契约等于镜像运行契约（RUNTIME_CONTRACT_MISMATCH）。
核对通过后，用与登记相同的导出器和市场提交新鲜导出输入，并算出输入身份与有效配置身份。随后在一个写事务里写 purpose=precheck 的试验行与开始回执，回执记源码哈希、运行环境、输入身份与配置身份；事务成功后才启动容器。结束时，包括中断与宿主失败，原生 stdout/stderr、各阶段退出码、审计与报告原样封存。
输出：试验编号、执行封存包名、status（passed 表示原生与审计退出为零且无审计问题，否则 failed）、问题清单与只供工程诊断的读数。
预检不绑定登记，不消耗网格点。
暴露豁免：登记时，对曾执行过该源码的每个试验调用 <Ref id="registration.exposure_exempt" />。豁免只给同时满足以下条件的试验：用途在执行前声明为 precheck；源码、运行环境、市场提交、范围规则版本与经济配置都与登记一致；原件完整；未绑定任何登记。其余试验一律按 <Ref id="H.4.2.2" /> 拒绝 SOURCE_ALREADY_EXPOSED。用途写在只追加的试验行上，探索回放不能事后改名为预检。
强制层：代码与账本。

### C.6.2　独立源码审查 [#C-6-2]

审查是具名 Agent 证据，与账户审计分开。账本以只追加证据包保存结论，内容哈希由库内生成；代码只核对结构、绑定身份与登记前的通过条件，不解读说明文字。输入是预检执行封存包，输出是 source-review.json，以及登记或绑定时的通过或拒绝。

<Cap id="C.6.2.1" kind="database" tier="verified" tierLabel="已验证" title="独立 Agent 对预检原件按四项给出结论并绑定源码与运行环境身份，只追加为证据">

审查者须是未参与编写的独立 Agent。它读一个 purpose=precheck 的试验的封存原件，对接口 api、因果 causal、活动 activity、就绪 readiness 四项各给 status（passed、failed、unresolved 或 no_opportunity）与非空观察说明。
审查经 <Ref id="cli.source_review" /> 与 <Ref id="registration.record_review" /> 写成一个 Agent 命名的 source-review-* 证据包，记在 <Ref id="table:evidence_bundle" />；包内文件 source-review.json 存在 <Ref id="table:evidence" />，格式为 source-review-v1，字段为 trial_id、source_sha256、image_ref、execution_bundle、四项结论与具名审查者 authority。身份字段由账本从试验行和执行封存中取，不接受调用方填写。只能绑定真实存在的预检原件，否则拒绝 PRECHECK_CAPTURE_MISSING；占用产品保留命名空间拒绝 RESERVED_BUNDLE。
证据只追加：同名同内容重试幂等，同名不同内容拒绝 BUNDLE_EXISTS。内容哈希是库内生成列，读回重算不符即 LEDGER_CORRUPT；dolt_diff_evidence 出现任何 modified 或 removed 即为篡改发现。
登记与回放绑定时，<Ref id="registration.require_precheck" /> 核对以下各项：审查存在且完好；源码哈希与运行环境摘要和本次一致；预检原件的原生与审计退出为零；四项均为 passed 或 no_opportunity。缺审查或身份不符拒绝 SOURCE_PRECHECK_REQUIRED，原件失败或任一项为 failed 或 unresolved 拒绝 SOURCE_PRECHECK_FAILED。
已入账的失败审查由 <Ref id="qualification.source_reviews" /> 读取，使同源码同运行环境的运行不作经济证据，见 <Ref id="G.4.2.2" />。
边界：这是源码审查，不是账户审计，也不升级为代码裁决；报告中两者分别呈现，见 <Ref id="A.5.1.2" />。
强制层：账本（只追加、生成哈希、提交历史）与代码（结构与身份核对）。
