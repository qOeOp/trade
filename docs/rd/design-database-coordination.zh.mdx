### `ledger_head` [#def-table-ledger_head]

写入头指针单行：每次写入 +1 并记本次操作 ID，是并发写冲突的碰撞点与幂等重放的索引

<TypeTable type={{ "singleton": { type: "TINYINT", description: "恒 1", required: true }, "seq": { type: "BIGINT", description: "每次成功写入 +1", required: true }, "op_id": { type: "VARCHAR(160)", description: "本次写入的操作 ID；两事务写相同值会被 Dolt 合并，所以每次写入必须唯一", required: true } }} />

**键与约束**

- 主键　`singleton`
- CHECK　`singleton = 1`
- CHECK　`seq >= 0`

**Dolt 能力**

- **J.3.2.2**　两事务把同格改为不同值，提交时三方合并冲突，后到者回滚（Dolt 错误 1213）并报 CONCURRENT_WRITE
- **J.3.3.1**　写账号对本表有 UPDATE，对其余业务表只有 INSERT
- **J.3.1.1**　差异表里本表的 modified 行是正常写入，复核排除

**写入方**　`ledger.write`

### `dolt_diff_\<table> / dolt_history_\<table>` [#def-table-dolt_system_tables]

Dolt 系统表，每张业务表各一对，由 Dolt 维护：逐提交差异与行级全史，是只追加留痕与篡改发现的读取面

<TypeTable type={{ "dolt_diff_<t>.diff_type": { type: "ENUM('added','modified','removed')", description: "正常路径只应出现 added；其余值即非追加改动", required: true }, "dolt_diff_<t>.from_<col> / to_<col>": { type: "业务表各列", description: "改动前后的值，定位被改单元格；插入行 from_ 为空，删除行 to_ 为空", required: false }, "dolt_diff_<t>.from_commit / to_commit / to_commit_date": { type: "VARCHAR 提交哈希 / DATETIME", description: "to_commit 把一行绑到写入它的提交", required: true }, "dolt_history_<t>.commit_hash / committer / commit_date": { type: "VARCHAR / VARCHAR / DATETIME", description: "每行在每个提交的取值，单元格级历史", required: true } }} />

**Dolt 能力**

- **J.3.1.1**　整体复核逐表查 diff_type ≠ added 即报篡改发现；dolt_history 证明源码、登记、绩效指标从未被改
- **J.3.1.3**　与 AS OF 配合，按精确版本读并给出每行的写入提交
- **J.3.1.4**　绕过提交校验的写入与改删仍在此留痕
- **J.3.5.2**　复核的只追加检查与登记顺序检查（登记提交早于试验插入提交）读此表

**写入方**　`Dolt（系统表，由每次 dolt_commit 自动维护）`

### `dolt_tests` [#def-table-dolt_tests]

Dolt 原生提交校验表（验证组 commit，由服务级变量 dolt_commit_verification_groups 指定）：每次提交前跑跨表测试，失败拒提交；可被跳过参数绕过，是留痕保证，整体复核再跑一次

<TypeTable type={{ "test_name": { type: "VARCHAR(255)", description: "Dolt 原生列", required: true }, "test_group": { type: "VARCHAR(255)", description: "恒为 commit", required: true }, "test_query": { type: "TEXT", description: "返回违规行数的 SELECT", required: true }, "assertion_type": { type: "VARCHAR(32)", description: "恒为 expected_single_value", required: true }, "assertion_comparator": { type: "VARCHAR(8)", description: "恒为 ==", required: true }, "assertion_value": { type: "VARCHAR(32)", description: "恒为 0", required: true } }} />

**键与约束**

- 主键　`test_name`
- CHECK　`必备行 research_and_validation_trials_have_published_sources：purpose ∈ \{research, validation\} 的试验其源码哈希都在 candidate 表`
- CHECK　`必备行 research_trials_follow_their_registration：每个 purpose = research 的试验恰有一行网格点消耗，且登记包入账早于试验`
- CHECK　`必备行 validation_trials_are_bound：每个 purpose = validation 的试验在 validation_binding 有行`
- CHECK　`必备行 validation_windows_start_after_registration：首次样本外登记的窗口起点晚于登记插入时间；重试沿用原登记的窗口`
- CHECK　`必备行 validation_runs_match_their_registration：样本外试验的候选与窗口等于其登记；共同可交易范围记在开始回执里，由整体复核核对`
- CHECK　`必备行 validation_retries_keep_candidate_and_window：样本外重试保持被验候选、共同可交易范围与窗口不变`
- CHECK　`必备行 witnesses_stamp_validation_registrations：每条凭证所盖提交是一条样本外登记的插入提交`

**Dolt 能力**

- **J.3.1.4**　每次 dolt_commit 前按验证组运行，失败整笔回滚；--skip-verification 可绕过，不是信任边界
- **A.5.2.2**　只约束经认证的 SQL 会话；持有服务目录者可绕过，篡改由 report.review_all 事后发现

**写入方**　`ledger.init`
