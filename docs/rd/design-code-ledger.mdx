### `export_history` [#def-ledger-export_history]

以读账号按精确版本导出账本全史备份与复现清单：候选源码、运行行、单运行报告、逐日序列、持仓周期、登记与判断，以及每个运行的重放身份

```python
def export_history(
    profile: str,
    destination: Path,
    at: str | None,
    trial_ids: list[str] | None,
    with_backup: bool,
) -> dict
```

<TypeTable type={{ "profile": { type: "str", description: "账本档案名；读源码与清单用读账号，全史同步用管理账号（dolt_backup 拒绝读账号）" }, "destination": { type: "Path", description: "导出根，须在账本服务目录与 Git 工作树之外；下设 backup/ 与 reproduce/" }, "at": { type: "str | None", description: "精确版本（标签或提交）；缺省取头提交，导出后以解析出的提交写入清单" }, "trial_ids": { type: "list[str] | None", description: "只导出这些运行及其候选与试验；缺省全部已封存运行" }, "with_backup": { type: "bool", description: "是否增量同步全史备份；False 时只写复现清单" } }} />

**返回**　dict：\{at, commit, ledger_name, backup_path, candidates, runs, images, market_commits, manifest_path, content_hash\}；images 为按摘要列出的运行环境引用，market_commits 为需重新导出的市场提交，content_hash 为清单文件内容哈希

**期望行为**

1. with_backup 时用 dolt_backup 同步全部提交与标签；失败即整笔拒绝。同步后把备份还原到新的临时目录，读出研究 branch 的头提交（用完即删），不等于账本头即拒绝 DOLT_BACKUP。同步前若目标已有备份，其头提交须在研究 branch 的历史里，否则拒绝 BACKUP_DIVERGED 且不同步：dolt_backup 会无声覆盖改写前的备份，而整体复核靠它发现改写（Dolt 2.4.2 实测；用户 10-20 授权）。
2. 按该版本读候选源码并核哈希，每个候选写成一个源码文件。
3. 写复现清单：每个运行列镜像摘要、源码哈希、登记的执行身份、市场提交与窗口，以及报告指纹；按清单重放即可经 engine.compare_reports 复核。
4. 替换已有导出时先把旧导出改名移开、新导出改名到位，再删旧的，过程中不出现缺导出的时刻。

| 拒绝码 | 条件 |
|---|---|
| `LEDGER_PERMISSION` | 连接账号持有 INSERT/UPDATE 权限，不是读账号 |
| `UNKNOWN_REF` | at 不能解析为账本里的标签或提交 |
| `EXPORT_PATH_INVALID` | destination 位于账本服务目录或 Git 工作树内，或已存在且不是本账本的导出 |
| `DOLT_BACKUP` | 全史同步失败，或同步后备份头与账本头不一致 |
| `UNKNOWN_RUN` | trial_ids 中有运行在该版本不存在或尚未封存 |
| `BACKUP_DIVERGED` | 已有备份的头提交不在账本历史里（提交被改写，或是别的库的备份），同步会覆盖它 |

### `original_coverage` [#def-ledger-original_coverage]

入账时只采信本试验开始回执里的覆盖回执（其哈希须等于执行捕获所记）与原始执行捕获里的原生摘要：要求捕获完整封存、各阶段退出成功、回执输入身份等于存储的输入身份，再用 ledger.verify_coverage 重算生命周期事件；任一不符即拒绝，不降级为无事件。

```python
def original_coverage(
    conn: LedgerConnection,
    trial_id: str,
    input_identity: dict,
) -> tuple[dict
```

<TypeTable type={{ "conn": { type: "LedgerConnection", description: "ledger.connect 打开的账本连接，只读使用。" }, "trial_id": { type: "str", description: "试验 ID，用于定位 trial 行及其原始执行捕获。" }, "input_identity": { type: "dict", description: "拟入账运行行的输入身份（登记时存储的内容身份，不含宿主路径）。" } }} />

**返回**　tuple[dict, ...]：由原始捕获里的回执与原生摘要重算、核对一致的生命周期事件元组；没有事件时为空元组。

**期望行为**

1. 读 table:trial 取该试验的候选内容哈希与运行环境身份，以此调用 ledger.read_capture；它的核验拒绝原样传出。返回缺失、未最终封存，或缺执行前回执、执行阶段、原生报告任一项，拒绝 CAPTURE_INCOMPLETE。
2. 各阶段退出码须全为零，否则拒绝 PHASE_FAILED，并带上首个非零阶段名与退出码。
3. 捕获清单只记覆盖回执的哈希：它须等于开始回执里 input-coverage.json 字节的哈希，此后用开始回执那一份；其 input_identity 须等于开始回执记下的输入身份，否则 COVERAGE_MISMATCH。
4. 取开始回执里的覆盖回执（哈希已与捕获核对），其 input_identity 与参数 input_identity 做字典深比较，须完全相等，否则拒绝 INPUT_IDENTITY_MISMATCH。工作目录或调用方另传的回执一律不采信。
5. 从捕获的原生报告取原生摘要，调用 ledger.verify_coverage(coverage, summary)；它的拒绝原样传出，不捕获、不降级。
6. 返回事件元组，交 ledger.ingest_run 写入运行行；本函数不写任何东西。

| 拒绝码 | 条件 |
|---|---|
| `CAPTURE_INCOMPLETE` | 原始执行捕获不存在或未最终封存，或缺执行前回执、执行阶段、原生报告任一项。 |
| `PHASE_FAILED` | 捕获中任一阶段退出码非零。 |
| `INPUT_IDENTITY_MISMATCH` | 覆盖回执的输入身份不等于存储的输入身份。 |
| `COVERAGE_RECEIPT_INVALID / COVERAGE_MISMATCH / LIFECYCLE_*` | 由 ledger.verify_coverage 原样传出。 |
| `COVERAGE_MISMATCH` | 捕获清单记的覆盖回执哈希与开始回执字节的哈希不同 |

### `verify_coverage` [#def-ledger-verify_coverage]

核对覆盖回执与原生摘要一致（版本形态、输入起止、市场提交、合约集合），再交给 engine.lifecycle_events 构造并核对生命周期事件；覆盖事实只透传，不构成无效。审计和入账共用这一个函数。

```python
def verify_coverage(
    coverage: dict,
    summary: dict,
    window: tuple[str, str] | None,
) -> tuple[dict
```

<TypeTable type={{ "coverage": { type: "dict", description: "随执行封存的覆盖回执：format（execution-input-coverage-v1）、effective_config{start, end}、input_identity{market_commit, instruments, lifecycle_bundle}、export_receipts{symbol: 回执，含计数与生命周期片段 episodes}、facts（market.coverage_facts 的输出）。" }, "summary": { type: "dict", description: "引擎原生摘要：input_start_utc、period_end_utc、market_commit、per_coin[{instrument, counts}]。" }, "window": { type: "tuple[str, str] | None", description: "可选的开发窗口（UTC 起止）。给出时，回执与摘要的起止都须等于它；不给时只要求两者彼此相等。" } }} />

**返回**　tuple[dict, ...]：按时钟排序的引擎原生生命周期事件字典（InstrumentStatus / InstrumentClose），没有事件时为空元组。覆盖事实不在返回值里，留在 coverage['facts'] 由调用方呈现。

**期望行为**

1. 校验回执形态：format 为 execution-input-coverage-v1，input_identity 中市场提交与合约集齐全，每个合约都有导出回执。缺项或版本不符拒绝 COVERAGE_RECEIPT_INVALID。
2. 回执合约集须等于摘要 per_coin 的实例集；给定 window 时，回执与摘要的起止还须等于它。不符拒绝 COVERAGE_MISMATCH。
3. 调用 engine.lifecycle_events(coverage, summary)，由它核对格式、起止、市场提交与逐实例生命周期；它的 LIFECYCLE_* 拒绝原样传出，不捕获、不降级。
4. facts 只透传，不参与判定，也不写任何表。
5. 本函数不读写账本，可以直接在工作目录上运行；入账时由 ledger.original_coverage 调用。

| 拒绝码 | 条件 |
|---|---|
| `COVERAGE_RECEIPT_INVALID` | 回执版本不是 execution-input-coverage-v1，输入身份缺市场提交或合约集，或有合约缺导出回执。 |
| `COVERAGE_MISMATCH` | 回执合约集不等于原生摘要的实例集，或给定开发窗口时回执或摘要的起止与它不等。 |
| `LIFECYCLE_*` | engine.lifecycle_events 原样传出的生命周期拒绝。 |

### `connect` [#def-ledger-connect]

按角色建立账本连接；writer 请求分支须逐字等于档案的固定研究分支，reader 只读；数据库授权与匹配限制见接口正文

```python
def connect(
    profile: LedgerProfile,
    role: Literal['writer','reader'],
    branch: str | None,
) -> LedgerConnection
```

<TypeTable type={{ "profile": { type: "LedgerProfile", description: "账本档案：名称、数据库名、服务目录、研究 branch 名、种类（active / isolated / temporary）、备份目录；由 cli 解析后传入" }, "role": { type: "Literal['writer','reader']", description: "writer 只有 SELECT、INSERT、对 ledger_head 单行的 UPDATE 与 dolt_commit 过程的 EXECUTE；reader 只有 SELECT；管理权限不对外" }, "branch": { type: "str | None", description: "要连接的 branch，缺省为档案记录的固定研究 branch；writer 只接受该 branch" } }} />

**返回**　LedgerConnection：已选中 database/branch 的连接，带只读属性 role、database、branch、schema_version；支持上下文管理器，调用方用完关闭

**期望行为**

1. 核对 role 合法；档案不是研究账本、或服务目录下没有该数据库的账号记录即拒绝。
2. writer 时核对 branch 等于档案的固定研究 branch，不等即拒绝，不尝试连接。
3. 从服务目录私有文件读该角色口令并连接，选中 database/branch；服务不可达或账号被拒分别拒绝；连接本身失败时套接字也关闭，不泄漏（pymysql 1.1.2 这时不关它），拒绝码不变。
4. 读 ledger_schema 单行，version 不等于本代码期望的模式版本即关闭连接并拒绝。
5. 返回带角色属性的连接；ledger.write 据此拒绝只读连接。
6. 已知限制（Dolt 2.4.2 实测）：分支权限表按 LIKE 匹配库名、分支名与账号名，下划线是通配符，反斜杠转义不生效，所以研究分支名里的下划线会顺带匹配同形的其他分支；只有管理账号能建分支，SQL 授权按库名逐字匹配。应用层的分支逐字核对与数据库的模式匹配是两个边界，不能据前者宣称原生分支权限已经逐字隔离。
7. 连接时同样核对提交校验组设置为 commit，不是即拒绝 COMMIT_CHECKS_DISABLED。
8. 已知限制（Dolt 2.4.2 实测）：写账号仍能 DOLT_COMMIT --amend 与 --date、临时关外键检查、插入 dolt_tests 与 dolt_ignore 行，任何账号都能改全局提交校验设置；这些不靠权限挡住，由写入前核对与整体复核发现（见第 13 章待定事项）。

| 拒绝码 | 条件 |
|---|---|
| `INVALID_ROLE` | role 不是 writer 或 reader |
| `LEDGER_UNKNOWN` | 服务目录下没有该数据库的账号记录 |
| `LEDGER_KIND` | 档案不是研究账本（如市场库档案） |
| `BRANCH_FORBIDDEN` | writer 请求的 branch 不是档案记录的固定研究 branch |
| `LEDGER_UNAVAILABLE` | 服务未启动或不接受连接 |
| `LEDGER_PERMISSION` | 账号或口令被服务拒绝 |
| `SCHEMA_MISMATCH` | ledger_schema.version 与本代码期望的模式版本不等 |
| `INVALID_REF` | branch 或版本引用形态不合法 |
| `UNKNOWN_REF` | branch 或版本引用在账本中不存在 |
| `COMMIT_CHECKS_DISABLED` | 服务的提交校验组设置不是 commit |

### `write` [#def-ledger-write]

单事务写入并提交；同载荷重试返回原记录；并发写冲突拒绝

```python
def write(
    conn: LedgerConnection,
    kind: str,
    payload: Mapping,
    table: str,
    insert: Callable[[LedgerConnection, str], Mapping],
    replay: Callable[[LedgerConnection, Mapping], Mapping] | None,
    op_id: str | None,
) -> WriteResult
```

<TypeTable type={{ "conn": { type: "LedgerConnection", description: "ledger.connect(role='writer') 得到的连接；一条命令一条连接，读写共用" }, "kind": { type: "str", description: "操作种类（如 publish_candidate、add_bundle、open_trial、ingest_run），进入操作 ID 与提交信息" }, "payload": { type: "Mapping", description: "规范化载荷（键排序、可 JSON 序列化，大对象以内容哈希代入）；op_id = sha256(kind ‖ canonical_json(payload))" }, "table": { type: "str", description: "持有本操作 op_id 列的记录表名，用于幂等查找" }, "insert": { type: "Callable[[LedgerConnection, str], Mapping]", description: "在同一事务内执行全部 INSERT 的回调，收到连接与 op_id，返回给调用方的记录；只允许插入" }, "replay": { type: "Callable[[LedgerConnection, Mapping], Mapping] | None", description: "命中同 op_id 的记录时把它整理成与首次相同形状的返回值；缺省原样返回该行" }, "op_id": { type: "str | None", description: "调用方自定的操作 ID；缺省由 kind 与规范化载荷派生" } }} />

**返回**　WriteResult：\{record, op_id, commit, replayed, write_status\}；首次写入 write_status='written'；命中同 op_id 时 replayed=True、commit 为原记录所在提交、write_status='replayed'；任何拒绝 write_status='not_written'

**期望行为**

1. 核对 conn.role 为 writer 且 branch 为固定研究 branch，否则拒绝；由 kind 与规范化载荷派生 op_id。
2. 开启单一事务，在 table 中按 op_id 查找；命中即回滚并经 replay 返回原记录，不写任何东西。
3. 查 dolt_status，存在未提交的 SQL 改动即拒绝，避免把他人的半截改动一起提交。
4. 执行 insert；随后 UPDATE ledger_head 单行 seq = seq + 1、op_id = 本操作 ID，使并发写在同一格上必然冲突。
5. 同一事务内 CALL dolt_commit('-a', '-m', '\<kind>:\<op_id>')，提交校验组 dolt_tests(commit) 在此运行，失败整笔回滚并拒绝。
6. 返回提交哈希；提交时合并冲突即回滚并拒绝 CONCURRENT_WRITE，调用方重试会按 op_id 命中胜者或重新写入；其他 SQL 错误回滚后按权限或通用错误拒绝。
7. 提交前读服务级的提交校验组设置（@@GLOBAL，提交实际用的那份；会话副本在连接时取、之后不更新，不能读它）；不等于 commit 即回滚并拒绝 COMMIT_CHECKS_DISABLED：任何账号都能改这个全局设置，不核就会在无痕迹的情况下跳过全部提交校验。读设置与提交之间仍有极短窗口，由整体复核重跑提交校验兜底。
8. conn 已处在另一次 ledger.write 的写事务里时（如 open_trial 调 start_receipt），并入调用方事务：不单独提交，返回的提交为空，由最外层一次提交。

| 拒绝码 | 条件 |
|---|---|
| `READ_ONLY_CONNECTION` | conn 不是 writer 角色，或连接的 branch 不是固定研究 branch |
| `DIRTY_WORKING_SET` | 写前 dolt_status 报告有未提交的 SQL 改动 |
| `COMMIT_CHECK_FAILED` | dolt_commit 时提交校验组 dolt_tests(commit) 任一项不通过 |
| `CONCURRENT_WRITE` | 提交时与另一并发写入在 ledger_head 单行或同一记录格上冲突，本事务已回滚 |
| `LEDGER_PERMISSION` | insert 执行了 writer 账号没有的语句（UPDATE/DELETE、其他表或过程） |
| `DOLT_SQL_ERROR` | 其他 SQL 错误；事务已回滚，不留半截记录；消息带服务器的错误原文（截至 300 字符） |
| `COMMIT_CHECKS_DISABLED` | 服务的提交校验组设置不是 commit |

```python
) -> 异常实例
```

**期望行为**

1. 构造时校验 code 形态与 write_status 取值；不合规直接抛 ValueError（编程错误），不伪装成拒绝。
2. write_status 为 unknown 而 operation_id 为空时同样抛 ValueError：声称「可能已写」却不给重试句柄，等于把幂等性交给猜测。
3. message、missing、expected 只记录缺什么与期望契约；类型不接受「如何绕过」类字段，也不展开底层数据库错误文本，防止泄露服务目录或凭证位置。
4. as_dict() 输出固定键集与顺序，missing 序列化为列表；所有抛出方共用同一形态，命令行层只需一处处理。
5. 本类型不读写账本、不记录日志、不依赖任何别的模块；拒绝不是记录，不进入任何表。
6. 拒绝码的集合与触发条件由各抛出方能力定义并在其函数的 refusals 中列出；本模块不维护码表。
7. 可序列化（pickle）：在工作进程里抛出的拒绝带着全部字段原样到达调用方。

```python
def read_capture(conn: LedgerConnection, trial_id: int) -> dict
```

<TypeTable type={{ "conn": { type: "LedgerConnection", description: "只读连接，可带 AS OF 版本" }, "trial_id": { type: "int", description: "要读的试验" } }} />

**返回**　dict：有封存时 \{status: captured, purpose, stages（各阶段名与退出码）, outcome, argv, files（captured 文件的字节）, statuses, listed（清单逐项：状态、sha256、长度）, runtime_failures（结构化异常回执逐行解析）, start（开始回执）, input_coverage 与 input_coverage_bytes（开始回执里的覆盖回执）\}；无最终封存时 \{status: missing, start, input_coverage, reason\}

**期望行为**

1. 读试验行、开始回执包与执行封存包（ledger.load_bundle）；试验不存在拒绝 TRIAL_NOT_FOUND。
2. 核开始回执：format、trial_id、source_sha256、运行环境身份（runtime.validate_identity）与试验行一致且 purpose 与试验行相同，否则拒绝 EXECUTION_IDENTITY。
3. 执行封存包无清单时返回 status = missing 与 reason「原始最终捕获缺失，后来的探针不能替代」；不读、不合并任何 recovery 包。
4. 核封存清单：format、trial_id、source_sha256、运行环境身份与试验行一致，purpose 与开始回执相同，包内无清单外文件，否则拒绝 EXECUTION_IDENTITY。
5. 逐文件核验：状态只允许 captured、captured_empty、hashed、missing、not_started；captured 的存储字节长度与 sha256 须等于清单，hashed 须有合法的 sha256 与长度且不带字节，其余状态须无内容，否则拒绝 LEDGER_CORRUPT；清单里的 strategy.py 只能是 hashed 且哈希等于 trial.source_sha256，存了字节或哈希不符都拒绝 EXECUTION_IDENTITY。hashed 文件的字节在别处（候选行、开始回执或工作目录），读者按清单哈希核对后才用。
6. 把 runtime_failures.jsonl 解析为 runtime_failures 后原样返回；是否构成不可用由 qualification.assess 判定，本函数不裁决。

|---|---|
| `TRIAL_NOT_FOUND` | trial_id 不存在 |
| `EXECUTION_IDENTITY` | 开始回执或封存清单的试验、源码哈希、运行环境身份或用途与试验行不符；包内有清单外文件；清单记的源码哈希与试验不符；文件状态未知 |
| `LEDGER_CORRUPT` | captured 文件的存储字节长度或 sha256 与清单不符，hashed 文件带字节或缺合法哈希，或其他状态带有内容 |

3. 读工作目录的阶段事实文件确定必需原件：引擎阶段退出码为 0 需全部原生报告，审计已运行需其 stdout、stderr 与审计结果；failure_receipt 拒绝码须为 EXECUTION_CAPTURE_LIMIT；任一不满足拒绝 RECOVERY_INCOMPLETE。
4. 按封存同一规则逐文件生成清单（源码与覆盖回执只记哈希）；清单里 strategy.py 的哈希须等于 trial.source_sha256，否则拒绝 EXECUTION_IDENTITY。
5. 经 ledger.write 以 trial_id 与文件清单派生的 op_id 写 evidence_bundle 与 evidence，清单 \{format: execution_recovery_v1, trial_id, purpose, source_sha256, runtime_identity, workdir, files, host_error, limitation\}；同名不同载荷拒绝 BUNDLE_EXISTS。
6. 永不写 trial-\<trial_id>-execution 包；read_capture 对该试验继续返回 missing。

| 拒绝码 | 条件 |
|---|---|
| `RECOVERY_NOT_APPLICABLE` | 原始最终捕获存在；无开始回执；试验 purpose 不是 precheck；workdir 与开始回执不符；该试验有 run 行或已被登记尝试消耗 |
| `RECOVERY_INCOMPLETE` | 阶段事实文件缺失或不合法；按阶段事实必需的原件缺失；failure_receipt 不是容量拒绝回执 |
| `EXECUTION_IDENTITY` | 恢复清单记的源码哈希与试验行不符 |
| `BUNDLE_EXISTS` | 该试验的恢复证据包存在且载荷不同 |

### `seal_capture` [#def-ledger-seal_capture]

2. 以 reader 读路线列表（按入账时间排序）：没有这条即 LINE_UNKNOWN；它是最新一条即 LINE_OPEN（一条路线在下一条被选定时结束）。
3. 封盘点：下一条路线的包所在提交（dolt_diff_evidence_bundle 中 added 的那一行）的父提交；research branch 是线性的，父提交不是恰好一个即 LEDGER_CORRUPT。
4. 同名 tag 已存在：指向同一提交且消息相同即返回 replayed=true；否则 LINE_CLOSED，tag 永不替换。
5. 以服务管理员连接执行 DOLT_TAG('-m', 总结, tag, 封盘提交)（writer 账号不能打 tag）；tag 不改工作集、不经 ledger_head，与研究写入互不冲突。
6. 总结是检索用的目录，不是证据：tag 可被管理员删除，删后下次 research-start 会把这条路线列为未封并重新封。

| 拒绝码 | 条件 |
|---|---|
| `LINE_SUMMARY_INVALID` | 总结不是 UTF-8、为空或超过 32768 字节 |
| `LINE_UNKNOWN` | 没有这条研究路线 |
| `LINE_OPEN` | 它是当前路线 |
| `LINE_CLOSED` | 已经以另一份总结或另一个提交封过 |

### `cycles` [#def-ledger-cycles]

由持仓报告逐行重建持仓周期并算每周期的价格盈亏、手续费与资金费；每笔成交恰属一个周期，否则抛具名原因；周期与计划的一一对应、同合约不重叠由 plan_metrics 核

```python
def cycles(positions: list[dict], fills: list[dict]) -> list[dict]
```

<TypeTable type={{ "positions": { type: "list[dict]", description: "持仓报告原生行（含快照行）：is_inverse、multiplier、events、adjustments、commissions、realized_pnl、ts_closed、ts_last、position_id" }, "fills": { type: "list[dict]", description: "成交报告原生行（event_id）" } }} />

**返回**　list[dict]，与 positions 逐行对应：closed、realized（已实现盈亏）、price（成交现金流：SELL 为正、BUY 为负，乘合约乘数）、commissions、funding、event_ids、ts_last；金额为 Decimal 的 USDT

**期望行为**

1. 逐持仓行核线性合约且记有乘数，否则 UNSUPPORTED_INSTRUMENT；金额非 USDT 即 NON_USDT_MONEY
2. 调整项只接受不改数量的 FUNDING，累加为周期资金费；其他调整即 UNSUPPORTED_ADJUSTMENT
3. 逐成交事件累加价格盈亏并记录 event_id；手续费为持仓行手续费列表之和；closed 取 ts_closed 是否存在
4. 核所有周期的 event_id 多重集恰等于成交报告的 event_id 集且每个恰出现一次，否则 FILL_COVERAGE_MISMATCH
5. 不读订单标签、不改原生行；返回的周期供 plan_metrics、economics、closed_by_year、mark_drawdown 共用

### `metrics_revision` [#def-ledger-metrics_revision]

指标计算代码的版本（产品 checkout 的 HEAD 提交，按原样记录），随封存结果行 run_sealed 与资格检查身份存出，使每个绩效指标与资格判定都能定位到产生它的代码；重算用该版本的同一函数重跑比对

```python
def metrics_revision() -> str
```

**返回**　str：产品 checkout 的 HEAD 提交哈希

**期望行为**

1. 在产品 checkout（缺省为本仓库）运行 git rev-parse HEAD 取提交哈希。
2. 工作树里未提交或未跟踪的文件既不拒绝，也不改变返回值（用户 10-20 授权）；没有区分干净与否的参数。
3. 产品从它的 Git 检出运行；不在检出中时 git rev-parse 失败，抛普通的进程错误，不另设拒绝码。
4. 由 ledger.ingest_run 在封存时写入 run_sealed.metrics_revision（单运行报告本身不带这个键），由 qualification.check_identity 写入检查身份；写入后只读。

### `plan_metrics` [#def-ledger-plan_metrics]

从订单报告的标签读出计划并与持仓周期一一对应后算计划胜率：每张订单恰一个全回放唯一的计划标签，计划限一个合约；赢＝周期已平且实现盈亏（含手续费与资金费）大于零，期末未平算非赢；任何不合规抛出具名原因

```python
def plan_metrics(
    orders: list[dict],
    fills: list[dict],
    positions: list[dict],
    cycles: list[dict],
    order_events: list[dict] | None,
    lifecycle_events: tuple[dict, ...],
) -> dict
```

<TypeTable type={{ "orders": { type: "list[dict]", description: "订单报告原生行（client_order_id、instrument_id、tags、status、ts_init、ts_last）" }, "fills": { type: "list[dict]", description: "成交报告原生行（event_id、client_order_id）" }, "positions": { type: "list[dict]", description: "持仓报告原生行（position_id、ts_last）" }, "cycles": { type: "list[dict]", description: "ledger.cycles 的结果，与 positions 逐行对应" }, "order_events": { type: "list[dict] | None", description: "原生订单事件流，供下架结算平仓单归属" }, "lifecycle_events": { type: "tuple[dict, ...]", description: "窗口内 InstrumentStatus / InstrumentClose 事件" } }} />

**返回**　dict：closed（已平计划数）、wins（赢的计划数）、open（期末未平计划数）、win_rate（wins ÷ (closed+open)，分母为零时 None）

**期望行为**

1. 逐张带标签订单读计划标签组成 plan_of：多于一个即 PLAN_TAG_MULTIPLE，不可解析或缺字段即 NATIVE_VALUE_UNREADABLE；同一标签跨合约即 PLAN_MULTI_INSTRUMENT
2. 以 plan_of 调 ledger.expiry_plan_owners 取下架结算平仓单的只读归属并并入；其余无标签订单即 PLAN_TAG_MISSING
3. 定计划区间：自首单创建到末单终态（终态订单的 ts_last）或周期关闭；有在途订单或未平周期的计划延续到运行末
4. 经成交 event_id 把每个周期的成交映射到订单与计划：成交无订单即 PLAN_FILL_UNMATCHED，周期无成交或含多个计划即 CYCLE_MULTI_PLAN，计划落在多个周期即 PLAN_MULTI_CYCLE
5. 同一合约按起点排序：后一计划起点早于前一计划终点即 PLAN_OVERLAP；分批加仓是同一计划的多档
6. 赢＝周期已平且 realized > 0（已含手续费与资金费）；持平与未平不算赢；win_rate = wins ÷ (closed+open)，分母为零时 None；不改任何原生行

| 拒绝码 | 条件 |
|---|---|
| `PLAN_TAG_MISSING` | 订单无计划标签且不是可唯一归属的下架结算平仓单 |
| `PLAN_TAG_MULTIPLE` | 订单带多于一个计划标签 |
| `PLAN_MULTI_INSTRUMENT` | 同一计划标签出现在多个合约的订单上 |
| `PLAN_FILL_UNMATCHED` | 持仓周期内某笔成交在订单报告中没有订单 |
| `CYCLE_MULTI_PLAN` | 一个持仓周期不含成交或含多个计划的成交 |
| `PLAN_MULTI_CYCLE` | 一个计划的成交落在多个持仓周期 |
| `PLAN_OVERLAP` | 同一合约上新计划起点早于前一计划终点 |
| `NATIVE_VALUE_UNREADABLE` | 原生行缺绩效指标所需字段或标签值不可解析 |

### `unreconciled` [#def-ledger-unreconciled]

原生事实超出支持范围或对账失败的具名原因（码＋细节）；metrics 捕获后把对应绩效指标置空并把原因写入绩效指标局限，运行本身不判无效

```python
def unreconciled(code: str, detail: str) -> 具名原因
```

<TypeTable type={{ "code": { type: "str", description: "大写蛇形原因码（见 cycles、plan_metrics、economics、mark_drawdown 的拒绝码）" }, "detail": { type: "str", description: "一句可定位的细节：涉及的订单、计划、周期或字段，最多列前五项并注明余数" } }} />

**返回**　具名原因（异常类型），字符串形式为「code: detail」，供写入 run.metric_limitations

**期望行为**

1. 只由 ledger 包内的指标计算函数抛出；不写账本、不改原生行
2. metrics 捕获后把该原因所属绩效指标置空（计划统计、经济拆分或回撤），其余绩效指标照常
3. 原因进入绩效指标局限清单并随运行行存出；完整性审计与资格视图不因此判运行无效或不可用
4. 本身是原因类型，无拒绝码；拒绝码由抛出它的指标计算函数给出

```python
def publish(profile: LedgerProfile, branch: str, lock: str | None = None) -> dict
```

<TypeTable type={{ "profile": { type: "LedgerProfile", description: "研究账本或市场库的档案；以服务管理员连接" }, "branch": { type: "str", description: "要推送的分支：研究账本的固定研究分支，市场库的 main" }, "lock": { type: "str | None = None", description: "市场库的导入锁 market-import:<库名>；给出时推送期间持锁，没有导入能落地" } }} />

**返回**　dict：\{database, remote, branch, head, previous_head, tags\}；previous_head 是推送前 origin 的跟踪头（第一次发布为 null），tags 是推送的标签数

**期望行为**

1. 读 origin 远端，没有即 REMOTE_UNSET；远端须合乎库的种类，规则同 ledger.set_remote。
2. 给了 lock 时以 GET_LOCK(lock, 0) 取锁，取不到即 CONCURRENT_IMPORT，什么都不推；连接关闭时释放。
3. 普通推送 branch，不强推：远端历史不是本地历史的祖先即 PUBLISH_REJECTED，之后什么都不推；其他推送失败即 PUBLISH_FAILED，运行中的服务早于其密钥装入启动时（见 ledger.set_remote）消息写明先重启服务（`ledger service stop`、`ledger service start`）。
4. DOLT_FETCH 后核对 origin 的跟踪头等于推送前读到的本地头；抓取失败或不等即 PUBLISH_FAILED。
5. 分支核对通过后按名字逐个推送 refs/tags/\<名字>：Dolt 2.4.2 没有 --tags；推送的标签会无提示地替换远端同名而内容不同的标签（实测），产品从不移动标签，所以只在分支核对过之后推。
6. 失败不回滚本地写入，重跑即补推。

|---|---|
| `REMOTE_UNSET` | 库没有 origin 远端 |

### `publish_candidate` [#def-ledger-publish_candidate]

校验后把一份源码作为一个候选写入账本，一行一个提交；相同字节拒绝并返回该字节对应的候选；研发父版本与改动说明同有同无，父须存在。模板、人造根与派生候选走同一入口，无父即根。

```python
    profile: dict,
    source: bytes,
    strategy_id: str,
    entry_class: str,
    description: str,
    parent: str | None,
    difference: str | None,
    op_id: str | None,
) -> dict
```

<TypeTable type={{ "profile": { type: "dict", description: "写账号的账本连接档案（ledger.connect 所需）" }, "source": { type: "bytes", description: "完整单文件源码原字节，原样入库" }, "strategy_id": { type: "str", description: "引用名中的 ID；只是引用名，身份是内容哈希" }, "entry_class": { type: "str", description: "唯一顶层入口类名" }, "description": { type: "str", description: "发布说明：规则、来源声明与非声明；非空且在备注长度上限内" }, "parent": { type: "str | None", description: "研发父版本 strategy_id@revision；根为 None" }, "difference": { type: "str | None", description: "改动说明；与 parent 同有同无" }, "op_id": { type: "str | None", description: "操作 ID；缺省由载荷（strategy_id、内容哈希、入口类、父）派生，同载荷重试返回原记录" } }} />

**期望行为**

1. 核对 strategy_id 符合引用名格式；调用 ledger.check_source 核对源码形态；description 与 difference 按备注规则核对（非空、长度上限）。
2. 核对 parent 与 difference 同有同无；parent 经 ledger.read_candidate 读到才继续（账本外键同样守卫）。
3. 计算源码 SHA-256 为内容哈希；op_id 缺省由载荷派生；运行契约名取自 引擎包声明的运行契约常量，不由调用方填写。
4. 在 ledger.write 的一笔事务里按内容哈希查 candidate，存在即以 SOURCE_EXISTS 拒绝并附该候选的引用；修订号取该 strategy_id 下最大修订号加一；插入一行（源码原字节、内容哈希、入口类、运行契约、说明、父、改动说明、op_id），created_at 由服务器触发器写入，提交一次。
5. 相同 op_id 重放由 ledger.write 返回原记录，不写第二行；并发写入同格不同值以 CONCURRENT_WRITE 拒绝；写前有未提交改动以 DIRTY_WORKING_SET 拒绝。
6. 全程不读父版本或任何运行的收益、显著性与推荐：亏损或不显著的有效候选照样可作父版本。
7. 调用方给的 op_id 已存在而载荷不同即 OP_ID_CONFLICT，不返回别人的记录。

| 拒绝码 | 条件 |
|---|---|
| `INVALID_ID` | strategy_id 不符合引用名格式 |
| `SOURCE_SIZE / ENTRY_CLASS_INVALID / SOURCE_SYNTAX / ENTRY_CLASS_NOT_UNIQUE` | 由 ledger.check_source 抛出，原样透传 |

### `witness` [#def-ledger-witness]

把一次样本外登记诞生提交的哈希摘要送公共时间戳机构取 RFC 3161 凭证，验证后存入；只发送摘要；按提交幂等；取凭证失败返回 status=failed 而不抛出

```python
def witness(
    conn: LedgerConnection,
    commit: str (CHAR(32)),
    tsa_url: str | None,
    tsa_roots: Path | None,
) -> {status
```

<TypeTable type={{ "conn": { type: "LedgerConnection", description: "ledger.connect 返回的写连接；一条命令一条连接" }, "commit": { type: "str (CHAR(32))", description: "样本外登记行诞生的账本提交哈希，即 dolt_diff_validation_registration 中 diff_type='added' 的 to_commit" }, "tsa_url": { type: "str | None", description: "公共时间戳机构端点，只能是 https；缺省读账本配置" }, "tsa_roots": { type: "Path | None", description: "钉死的根证书 PEM 包；缺省用随产品代码发布、按内容哈希钉死的那份，不从网络取" } }} />

**返回**　\{status: 'stamped' | 'already_stamped' | 'failed', commit, tsa, stamped_at: datetime(UTC) | None, witness_commit: str | None, reason: str | None\}

**期望行为**

1. 核 commit 是样本外登记的诞生提交：dolt_diff_validation_registration 中有 diff_type='added' 且 to_commit=commit 的行，否则拒绝 NOT_REGISTRATION_COMMIT
2. witness 表中该提交的行已存在时不联网，经 ledger.token_time 复验后返回 already_stamped
3. 以 SHA-256(commit) 为摘要构造 TimeStampReq（随机 nonce、certReq=true）POST 到 tsa_url；网络失败、超时或状态非 granted 返回 status=failed、reason=WITNESS_UNAVAILABLE，不写行
4. 经 ledger.token_time(token, commit, tsa_roots, nonce) 验证；另核 genTime 不早于该登记行 created_at、不晚于本机时间加容差（未校准示例值 300 秒）；不符拒绝 WITNESS_INVALID
5. 经 ledger.write 一个事务写 witness 行 \{commit_hash, token=TimeStampToken DER, op_id='witness:\<commit>'\} 并提交；op_id 冲突（并发补取）读回原行按幂等成功
6. 返回 status=stamped、stamped_at=genTime 与本次写入的账本提交

| 拒绝码 | 条件 |
|---|---|
| `NOT_REGISTRATION_COMMIT` | commit 不是任何 validation_registration 行诞生的账本提交 |
| `WITNESS_INVALID` | 响应验证不通过，或 genTime 早于登记 created_at、晚于本机时间加容差 |
| `WITNESS_UNAVAILABLE` | 时间戳机构不可达、超时或未授予；作为 status=failed 的原因返回，登记保留 |
| `DIRTY_WORKING_SET` | 写前发现连接上有未提交的改动（由 ledger.write 透传） |
