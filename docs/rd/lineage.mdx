# 3　候选谱系：说清什么算一个候选，以及候选之间怎样靠父版本和改动说明连成一棵棵树。

<p className="rd-translation-note">English translation pending: this page shows the Chinese source text.</p>


研究循环里，入口要从候选里挑推荐和路线，复盘要回看全部候选，下一个实验要选一个候选当起点。所以在讲怎么写策略、怎么回放之前，先要说清「候选」到底指什么。候选就是账本里一份完整策略源码的精确字节，改一个字节就是另一个候选。

本章做两件事。先定候选的身份：账本按源码字节算出内容哈希（可以理解成这份字节的指纹），以它为准，名字只是叫法。再说候选怎样连起来：新候选指向一个研发父版本（它是从哪一版改来的），附一句改动说明；没有父版本的叫根，是一棵树的起点。这样连成的树和森林叫谱系。任何候选都能再派生新枝，运行结果和推荐都不改变它的身份和位置。

举个例子：全池 RSI 路线里，H01 到 H04 账户都是亏的，比较也不显著，但它们照样是合法的候选，后面的版本继续从它们派生；H06 比 H05 退步，下一步 H07 仍从 H06 改出来。H03 的父版本是 H02，而当时被推荐的是 H01。每一版都留着源码、父版本、改动说明、登记和原生证据，谱系只记「从哪改来、改了什么」，不记成绩好坏。

## 3.1　认定候选：什么算一个候选 [#T-1]

一个候选就是一份完整策略源码的精确字节，身份由账本按字节算出；入账时只核对谱系，不看任何成绩。

<Steps>

<Step>

Agent 写完一份完整的单文件策略源码，决定它是根，还是带父版本和改动说明的派生候选。

</Step>

<Step>

通过发布入口交给账本：账本按字节算出内容哈希，字节重复、父版本不存在、或父版本和改动说明不配套就拒绝，核对通过才入账。

</Step>

<Step>

账本返回引用名和内容哈希，之后登记、回放、报告都按内容哈希指向这个候选。

</Step>

<Step>

以后每次读出候选，都重算一遍哈希，和入账时的记录对一下，对不上就当账本损坏。

</Step>

</Steps>

<a id="T-1-1" />

候选的身份怎么定：什么时候是同一个候选，什么时候是另一个。

<a id="T-1-1-1" />

**候选的身份是源码字节算出的内容哈希，相同字节不能再发布**

账本按源码字节算出内容哈希，这就是候选的身份，Agent 不能填，也不能改。名字和版本号只是引用名：改名、复制或只改注释，只要字节变了，就是另一个候选；同样的字节再发布一次会被拒绝，并指回已有的那个候选。候选只增不改，每次读出都重算哈希核对，对不上就视为账本损坏。

报告和比较必须指向确切的那份源码。身份要是靠名字或手填，两份不同的源码可能共用一个名字，同一份源码也可能被当成两个候选，结果就对不上号。

<div className="rd-example">

全池 RSI 演练里，每个假设的网格点都按已发布版本的内容哈希登记、绑定执行，报告和比较都指回确切的源码。比如把 H05 原样再发布一次，会被拒绝并返回 H05；在它的注释里加一句话再发布，字节变了，就是一个新候选，要作为根、或带上父版本和改动说明另行发布。

</div>

## 3.2　连成谱系：父、对照与分枝 [#T-2]

每个新候选指向一个父版本并写一句改动说明，连成树和森林；任何候选都能再派生，成绩不改变它在谱系里的位置。

<Steps>

<Step>

Agent 选一个已有候选当父版本，写一句改动说明，发布新候选；父版本必须已在账本里，父版本和改动说明要么都有、要么都没有。

</Step>

<Step>

不带父版本的就是根。模板、人造根和派生候选走同一个发布入口，根不能带比较对照。

</Step>

<Step>

登记时只核对谱系，不读父版本或它自己任何一次运行的绩效指标。

</Step>

<Step>

试验、运行、推荐和检验结果都在候选之外产生，改不了候选的身份和谱系。

</Step>

<Step>

想从任何一个候选另开一枝，包括旧的、亏损的，就以它为父版本，回到第一步。

</Step>

</Steps>

<a id="T-2-2" />

每个候选指向自己的父版本，直接连成森林；候选清单把它原样读出来。

<a id="T-2-2-3" />

**候选清单列出全部候选和谱系，不带分数、排序或推荐**

候选清单列出每个候选的身份、父版本和改动说明，并附上它已被试验用掉的网格点，以及对应运行是通过、无效还是没跑完。每个网格点再附上读取当时判定的经济证据资格和原因；不能当证据的，不附绩效指标，也不改写已存的结果。清单里没有分数、排序或推荐，综合推荐由 Agent 另写一条判断记录。

清单是看谱系的底稿，只记事实。里面一旦带上分数或排序，就等于代码替 Agent 做了推荐，也容易让人把「排在前面」误当成「接下来就改它」。

<div className="rd-example">

全池 RSI 路线的清单里，ROOT 是参考根，H01 到 H10 都挂在各自的父版本下，比如 H08 的父版本是 H07；十项正式运行都显示通过、有经济证据资格。最终推荐 H09 这件事不在清单里，而是写在 Agent 的推荐判断里。想看某次复盘时的清单，按那时的账本版本读就行。

</div>
