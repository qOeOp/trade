# Database

The research ledger is a Dolt database at schema generation 2. Each generation starts from an empty ledger and migrates no old data: until 1.0 a schema change starts a new ledger (AGENTS.md); within a generation, a changed reading (`run_reading`) is recomputed by resealing with the new code.

This page says, by responsibility, why each thing is stored and which invariants hold. The schema files define the columns; this page does not restate them.

## What is stored, and how

The ledger and the market directory hold only what a replay cannot give back (AGENTS.md): decisions and declarations (registrations, judgments, source reviews, research lines, out-of-sample registrations); observations that cannot recur (failure logs, source originals, timestamp tokens, market data); the minimal identity to reproduce the rest (complete strategy source, one UTF-8 file per independent strategy; runtime image digest; market day; configuration and input identity); and readings computed at sealing (audit and eligibility verdicts, metrics, report measures, cycles, daily returns) with fingerprints of the native reports. Native reports and other replay outputs are cache: regenerate them into `/tmp` and check them against the fingerprints with the semantic report comparison. A value that stored data derives is never stored; it is computed when read.

Tables fall into three tiers:

- **Commitments**: every business table except `run_reading`. Append only: the writer holds SELECT and INSERT, and `ledger review` reports any changed or removed row (ROW_CHANGED).
- **Readings**: `run_reading`. One current reading per passed run, written only by the product's seal commands; a reseal replaces it after the fingerprints match, and earlier values stay in Dolt history and the public copy.
- **Write coordination**: the single `ledger_head` row, which the writer may UPDATE.

Every write is exactly one transaction, one Dolt commit and one `ledger_head` step; a retry with the same operation id (`op_id`) returns the original record. Times that prove order come from server BEFORE INSERT triggers in UTC, never from the caller or a forgeable commit date; content hashes are generated columns, so a caller cannot pair bytes with another hash. Paper runs live in a separate Paper database and market data in Parquet files in the market directory, neither in the research ledger, and no foreign key crosses the three.

### Where constraints live

CHECK, ENUM, primary and unique keys hold for the writer and cannot be bypassed. Foreign keys are different: the writer can switch foreign key checks off in its session, so they catch product-code mistakes, and `ledger review` rechecks every foreign key of new commits afterwards (CONSTRAINT_VIOLATED).

## Candidates and source reviews

### `candidate` [#def-table-candidate]

A candidate is the raw bytes of one single-file strategy source. The source is stored rather than replay outputs because source, image, market day and configuration replay everything else; its identity is the source's SHA-256, and `strategy_id@revision` is only its name.

- Content addressed: publishing the same bytes again returns the original record by `op_id`; the name (`strategy_id`, `revision`) is unique.
- A parent is named by hash; a candidate with a parent must state the difference and cannot be its own parent.
- Non-exploration trials, registration grid points, judgment subjects and out-of-sample registrations all point to a candidate by source hash.

### `source_review` [#def-table-source_review]

An independent source review: the four findings and the verdict for one native precheck trial. It is another Agent's judgment, which a replay cannot give back, so it is stored.

- The verdict passes exactly when all four findings pass or have no opportunity.
- A review lands only on a precheck trial with a raw precheck capture (`PRECHECK_CAPTURE_MISSING`); reviews are append only, and a re-review is another row.
- Every grid point of a research registration must cite a passed review of the same source.

## Registrations and trials

### `research_registration` [#def-table-research_registration]

A research registration: the prediction, grid, control and execution identity committed on an open research line before any replay. Written before the results, it proves the prediction was not set after seeing them.

- The registration row, its grid points, its comparison design and its `source-<sha256>` source bundle are written in one commit.
- A research replay's trading window must equal the line's development period; a closed line refuses.
- The execution identity (image, market day, universe rule, export hash, configuration hash) with the registration and line forms a unique key that research trials reference by composite foreign key: a trial cannot differ from its registration's execution identity.

### `registration_grid_point` [#def-table-registration_grid_point]

A registration grid point: a candidate the registration commits to run. It fixes what will run before any replay; trial counts and the multiple-testing denominator come from here.

- Written in the registration's commit and read only afterwards.
- Each point cites a passed source review of the same source.
- A point is consumed by at most one research trial (a unique key on trials); invalid and interrupted trials consume it too.

### `comparison_design` [#def-table-comparison_design]

A comparison design: the paired test's parameters (block length, resamples, seed, significance level, minimum effect and reason) that a research or out-of-sample registration commits to. Fixed in advance, so a test cannot pick its parameters afterwards.

- Written in the commit of the registration that cites it; CHECKs bound the parameters and the reason cannot be empty.

### `trial` [#def-table-trial]

A trial: one row per replay, written before the container starts with its purpose, source, line, registration and execution identity; invalid and interrupted replays have rows too. The trial count must include failed attempts, so the row is written before any result exists.

- The writer derives the execution identity from the image inspection and the coverage receipt, never from the caller.
- The trial row, its instruments and its start bundle are committed before the container starts.
- A research trial matches its registration's execution identity and one grid point by composite foreign key; an out-of-sample trial matches its registration's source, universe rule and window, and an out-of-sample registration binds one trial only.
- Exploration and precheck windows must fall in the line's development period (`WINDOW_OUTSIDE_DEVELOPMENT`); the holdout, the history before the development period and the time after the holdout are replayed only at line closing as history trials.
- The working directory enters only the `op_id` hash and is not stored: rerunning from another directory is another trial.

### `trial_instrument` [#def-table-trial_instrument]

A trial's instruments, one row each, written in the trial's commit.

### `trial_capture` [#def-table-trial_capture]

A trial capture's outcome: the state and exit code of each of the native, audit and fingerprint stages, and the outcome class. The cause of a failure often lives only here and does not recur.

- Written once when a capture seals or is refused; CHECKs keep exit codes consistent with states.
- Native logs, audit output and other files go into the `trial-<id>-capture` bundle in the same commit; a recovery can only write a separate `trial-<id>-recovery` bundle.

### `trial_file` [#def-table-trial_file]

Where each captured file went: bytes in the capture bundle (captured), hash only (hashed), or neither. Written in the capture's commit; a hashed file always has a hash and a length.

## Runs and readings

Research, out-of-sample and line-history replays each seal one run. Run rows, daily returns and position cycles are commitments and append only; the report reading has its own table and can be replaced by a reseal after the fingerprints match.

### `run` [#def-table-run]

A run: one sealed verdict. A passed run stores the fingerprints of its native reports, an invalid run lists its reasons; exactly one of the two. The fingerprints make native reports cache: replay again into `/tmp` and compare them semantically against the fingerprints.

- The run row, its first reading, daily returns and position cycles are written in one commit.
- A run whose capture is refused for exceeding a limit still writes an invalid run, which consumes the trial.
- Sealing records the current `ledger_head.seq`, so runs order without reading Dolt history.

### `run_reading` [#def-table-run_reading]

A reading: the current report reading of one passed run, holding the values that cannot be computed once the native reports are gone, with the product commit that computed them. When a measure changes, `replay reseal` replays, and once every fingerprint matches it overwrites the reading with the current code; earlier values stay in Dolt history and the public copy.

- The writer may also UPDATE this table; a trigger refuses moving a reading to another run.
- `ledger review` reports a reading changed outside a reseal commit, and a reseal commit that also wrote commitment rows (READING_REPLACED_OUTSIDE_RESEAL).
- `ledger review` also recomputes derivable values such as the profit bridge from daily returns and cycles and reports any mismatch with the reading (READING_MISMATCH).

### `run_return` [#def-table-run_return]

Daily returns: a passed run's native daily return series with the day's mean gross notional. Paired tests, drawdown and capital-use readings are computed from it, so it is stored by day, not as a summary.

### `run_cycle` [#def-table-run_cycle]

Position cycles: one row per engine position from open to close, with realized P&L, commissions, funding and the plan tag. Trade structure and profit sources are computed from it when read; price P&L reads as realized_pnl + commissions − funding and is not stored.

## Evidence

A bundle is a set of named files, each pointing by content hash to an original stored once. The bundle's kind says what it holds; product kinds are written only by product code, and an Agent writes only its own bundles.

### `evidence_bundle` [#def-table-evidence_bundle]

An evidence bundle: its name is its identity and it is never replaced; it is written in the commit of its business row. A trial's start, capture and recovery bundles begin with `trial-<id>-` and record the trial, at most one of each kind per trial.

### `evidence` [#def-table-evidence]

The bundle's file list: bundle × path → content hash. Reading back recomputes the hash against the original.

### `evidence_content` [#def-table-evidence_content]

Originals: stored once by content; the hash is generated in the database, so a writer cannot pair changed bytes with an old hash. Existing content is only referenced, never inserted again.

## Research lines, targets and judgments

### `research_line` [#def-table-research_line]

A research line: a research route the user selected, storing its name, starting candidate, pinned market day and universe rule, and the development period computed by rule at opening and not chosen. The period is fixed at opening so research cannot move its window afterwards.

- Changing the start or the market day is another line; old rows are never changed.
- The period rule: Q is the last calendar quarter end before today that the market covers; the holdout is the 8 quarters up to Q and the development period the 12 quarters before it (when the starting precheck's instruments cover C quarters before Q and C is under 24, it takes C − 12 quarters, at least 4, leaving 4 quarters for veto segments; under 12 quarters a line cannot open, `LINE_HISTORY_SHORT`).
- Lines opened in the same quarter share the development period; while a line is open, exploration, precheck and research replays trade only inside it.

### `line_close` [#def-table-line_close]

A line closing: ends a research line and stores its summary. Closed lines are neither deleted nor compacted: they are the multiple-testing denominator.

- Before closing, every segment of the closing history test needs a run (`line history`), otherwise `HISTORY_INCOMPLETE`.
- Closing again with the same summary is a replay; after closing the backup syncs, a failed sync does not undo the closing, and `ledger review` reports a lagging backup (BACKUP_BEHIND).

### `line_target` [#def-table-line_target]

Research targets: the maximum drawdown and minimum annual return the user set for a line (or as the ledger default). Targets are the user's and are recorded only as the user states them; they guide reading reports and do not decide candidate eligibility.

- A change appends a row superseding the current one; each scope has one supersession chain.
- A value equal to the current target is not written.

### `judgment` [#def-table-judgment]

An Agent judgment: a recommendation, priority, interpretation or search exposure on a line, based on one exact ledger commit. A judgment is a decision a replay cannot give back, so it is stored, append only; a correction supersedes the earlier judgment of the same line and kind.

- A recommendation must name every candidate of the comparison table it rests on.
- A finished research trial without an interpretation refuses the next registration (`INTERPRETATION_REQUIRED`).

### `judgment_subject` [#def-table-judgment_subject]

Judgment subjects: the candidate, trial or research registration a judgment is about, exactly one per row, written in the judgment's commit.

## Out-of-sample registrations and timestamp witnesses

### `validation_registration` [#def-table-validation_registration]

An out-of-sample registration: the one-off test declaration the user starts, storing a candidate, universe rule, window and comparison design. The window starts after the registration time, and the execution binds only once.

- A retry keeps the original registration's candidate, universe rule and window and is exempt from the start-after-registration rule.
- An out-of-sample trial matches this row's candidate, universe rule and window by composite foreign key; one registration binds one trial.

### `witness` [#def-table-witness]

A timestamp witness: the RFC 3161 token for the commit that inserted an out-of-sample registration, proving the registration existed before its window started. Its time is the token's genTime, verified offline against pinned roots; the token cannot recur, so it is stored.

- At most one witness per registration.
- `ledger review` reports a witness whose commit is not the one that inserted its registration, or is not in this branch's history (WITNESS_UNBOUND).

## Schema version, write coordination and review

### `ledger_schema` [#def-table-ledger_schema]

The single schema-generation row, written when the database is created and writable only by the admin account. Reads and writes check the generation and refuse a mismatch.

### `ledger_head` [#def-table-ledger_head]

The single write-head row: every write steps it and records its operation id, so it is where concurrent writes collide and the index for idempotent replays. Two transactions changing it to different values conflict at commit; the later one rolls back with CONCURRENT_WRITE.

### `dolt_diff_<table>` / `dolt_history_<table>` [#def-table-dolt_system_tables]

System tables Dolt keeps for every table: `dolt_diff_<table>` gives each row's additions, changes and removals between two commits, and `dolt_history_<table>` gives each row's value, commit hash and time at every commit. The ledger keeps no separate audit log; changes and removals leave their trace here.

`ledger review` pins one version with the reader account and checks every table for commits since its last check; findings are reported, never written:

- a commitment row that is not an addition: ROW_CHANGED
- a `run_reading` change outside a reseal commit, or a reseal commit that also wrote commitment rows: READING_REPLACED_OUTSIDE_RESEAL
- an added or changed row whose foreign key does not match: CONSTRAINT_VIOLATED
- a witness token stamping a commit other than its registration's insert: WITNESS_UNBOUND
- the last checked commit or the latest backup head missing from current history: HISTORY_REWRITTEN; a lagging backup: BACKUP_BEHIND

## Read entry points and research history [#read-entry-points]

The research ledger has no SQL views. Reads go through the command line's read commands, which pin one version with the reader account (`--at`, the head commit by default), read the base tables, and compute eligibility, masking and readings in code; read commands never write or publish.

- **Read commands see open lines by default.** Closed lines appear only through their closings and closing history tests, queried by line when needed.
- **Across lines, read only aggregates.** Cross-line numbers such as multiple-testing counts and the closing heat map are SQL aggregates, not run-by-run loads. "Disqualified" is a state derived from readings, never a stored flag.
- **Read-only SQL.** `ledger sql` accepts one read-only statement and refuses writes (`WRITE_VIA_SQL`). Report masking is not data-access isolation: the ledger is public.
- A historical result is reproduced by reading the ledger at its commit (`--at`), replaying the native reports with that code and checking the run's fingerprints.

### Research history and the closing history test [#research-history-views]

While a line is open its trading windows stay inside the development period (<Ref id="table:research_line" />). Opening fixes three spans by rule: the development period (12 quarters as standard), the holdout right after it (8 quarters up to Q), and the history before the development period. An open line uses only the development period; the holdout, the earlier history and the forward span after Q are replayed once, at closing.

`line history` replays every candidate on the line that has a passed research run whose latest such run still has economic evidence, with that run's source, image and configuration, over other windows:

| Segment | Window | Purpose |
|---|---|---|
| veto | each calendar year before the development period, once each | whether the candidate held in earlier years |
| control | the development period once more | must reproduce the original research run, or the row is not judged |
| holdout | the two years after the development period, once | data the open line never used |
| forward | after the holdout to the market's latest complete day | display only |

Each segment writes one trial with purpose `history` and its run; segments with a passed run are skipped, so rerunning resumes. A segment whose latest run is invalid is replayed once more on each `line history` call after the segments without runs: the new trial supersedes the invalid one, the old trial stays in the ledger, and `research history` reads each segment's latest trial with a run, listing superseded ones in the cell's `superseded`. Replays are deterministic and a strategy's own failure fails again, so each call reruns a segment at most once. An invalid segment still counts as having a run and does not block `line close`. A rerun sees data the first run already saw, so trial counts treat it as a reproduction, not a new trial. The participating sources are fixed at the first history trial.

Economic evidence uses the same read-time verdict as `research status` (<Ref id="G.4">7.4</Ref>): a source whose review failed, or whose run has no real fill, is not a candidate, is not replayed, takes no row and does not count in `participants`; both `line history` and `research history` list it with its reason under `without_economic_evidence`, without readings.

`research history` reads each candidate's measures per segment (annual return, mark-price maximum drawdown, Sharpe, cycle count, plan win rate) and judges them against the user's two targets:

- **Veto passes**: every complete veto year's drawdown is within the target and those years' median annual return meets it;
- **Holdout passes**: drawdown within the target and annual return at least the target;
- **Meets targets** (`meets_targets`): both pass; with no complete veto year only the holdout is judged (`judged_on` says what was read).
- **Undecided**: when a needed reading is missing the combined verdict is null and `missing` names the segment. The holdout's own verdict is still given but does not count as meeting targets.

This is a falsification test, not out-of-sample validation: picking candidates by it is a selection among `participants`, and the selection effect has to be counted. The holdout is only unused by this line: lines opened in the same quarter share it, and `holdout_prior_trials` reads the counted trials in this ledger that searched it before; searches outside the ledger cannot be read and the closing summary states them. Out-of-sample validation is the separate one-off test the user starts (<Ref id="table:validation_registration" />).

## Paper database [#paper-db]

Paper runs are execution records, not research: they live in a separate Paper database, never reach the research ledger, are never published, never count as trials and are no exposure to the out-of-sample window. Native report fingerprints do not apply either, since live data cannot be replayed, so the sealed files themselves are kept. The local machine and the remote host each use their own Paper database. It also has the single-row `ledger_schema` and `ledger_head` tables with the same meaning as the research ledger; its writer may also DELETE (`paper delete` removes a sealed run).

### `paper_source` [#def-table-paper_source]

Copied source: `paper start` reads a published candidate from the research ledger and copies its bytes and entry class into the Paper database, so the Paper database reproduces a run's source without the research ledger.

### `paper_run` [#def-table-paper_run]

A Paper run declaration: written before the container starts with the source, runtime, instruments, market day and effective configuration; the run starts at its declaration time.

### `paper_seal` [#def-table-paper_seal]

The seal: written once when the run ends, in the same commit as its files; every run seals with its reasons, however it ended.

### `paper_file` [#def-table-paper_file]

Sealed files: event logs by UTC day, the summary at stop, logs and `seal.json` (readings computed once at sealing). These are live observations that do not recur, so the originals are stored.

## Market directory

### Market directory [#def-table-market_directory]

Financial data lives in plain Parquet files whose paths say what they hold; there is no manifest, and what the files hold is what the market holds. The same code and exchange archives export the same data, so the code in Git is the files' provenance; a lost directory is recomputed from the exchange's public archives and replays read the same content. Only financial data is stored; nothing recomputable is.

```
<market directory>/
  <table>/<YYYY-MM>.parquet            bar, funding, universe_month: one month, every contract
  <table>/<YYYY-MM>/<contract>.parquet agg_trade, quote, metrics: one month, one contract
  instrument.parquet                   contract terms, appended
  lock                                 import lock file
```

- Files are sorted by the table's primary key, strictly increasing, with fixed write parameters, so the same rows write the same bytes; each table's row rules are checked per batch on write (CHECK_FAILED).
- Price and volume scales and derivation rules are code constants; a rule change deletes the affected derived files and reimports, never mixing two rules in one table.
- Files are written to a temporary file, synced, and renamed into place in a fixed order, with the files that set the latest market day placed last: a crash can only advance less, never point the market day at incomplete data.
- Finished months of agg_trade and quote are never rewritten. Rewriting the current month, bars and funding for days already stored must equal the source reread row by row (MONTH_EXISTS), the universe must equal the stored rows (UNIVERSE_CHANGED), and stored metrics rows stay as they are.
- One import at a time: an import holds the file lock throughout and a second one is refused with CONCURRENT_IMPORT; a writer the lock cannot reach is caught when placing checks the target file (same code).
- Contract names join terms and universe rows when read; files have no foreign keys.

**Market day**　The last day D it contains, written `YYYY-MM-DD` (otherwise MARKET_DAY_UNRESOLVED). Trials, registrations, research lines and Paper runs in the research ledger all store it. Reading at a market day returns:

| Table | Rows read |
|---|---|
| bar, funding, quote, agg_trade, metrics | time column on or before D |
| universe_month | months up to the one containing the day after D: a month's list depends only on earlier days, so the last day of a month reads the next month's list |
| instrument | observed_at before the end of the day after D: a day's data is imported the next day and terms are observed then |

An omitted market day means the latest one: the earlier of the last complete day of bars and of metrics; a later date is MARKET_DAY_UNRESOLVED. When that day is a month end and the next month's list is missing, it falls back one day, so the members read never change. When a backfill or late archive changes a market day's content, the rerun export's fingerprint no longer matches and REPRODUCTION_MISMATCH reports it.

### `instrument` [#def-table-instrument]

Contract terms appended by observation time: tick and size steps and limits come from the exchange's published terms, and a delisted contract's steps are inferred from its trades. Terms change and the exchange stops giving old ones, so they are appended by observation.

- Append only: existing observations plus new ones, nothing written when terms did not change; inferred rows carry no limits or classification.
- An export takes the latest row at its market day, and the receipt records CURRENT_SNAPSHOT_APPROXIMATION.

### `bar` [#def-table-bar]

One-minute bars: last price (LAST) and mark price (MARK, no volume); one series per perpetual, several sources joined into one without tracing the source; a gap is a missing row, never made up.

- Prices positive, high and low bracket open and close; only LAST carries volume.
- Two sources disagreeing on the same minute refuse the whole import; neither overwrites the other.

### `quote` [#def-table-quote]

Complete bid/ask state changes inferred from aggTrades by a declared rule; an approximation, not an order book or real executable depth. The rule and its evidence boundary are in <Ref id="W.1.2.1" />.

- Bid positive and ask above bid; same-millisecond states are not merged.
- One file per contract and month, derived from stored <Ref id="table:agg_trade" /> after the month ends and never rewritten; an existing file for the contract and month refuses.
- No book sizes are stored: exports fill both sides with the contract's maximum quantity, which is not real depth.

### `agg_trade` [#def-table-agg_trade]

Binance USD-M complete source aggTrades: the seven official fields plus the contract, including trades that did not change the inferred quote. It is the source original quotes are derived from; when a replay entry asks for trades it is a strategy signal input only and never drives matching.

- A price or quantity that does not fit the encoding refuses the month with SCALE_LOSS, never rounded or re-encoded.
- A missing, duplicated or cross-day discontinuous id is SEQUENCE_GAP, with no substitute source and no patching; the one exception is Binance reusing an id for a later trade, which gives two rows with different keys, both imported.
- Only finished months are imported; an existing file for the contract and month is MONTH_EXISTS.

### `metrics` [#def-table-metrics]

Open interest and three long/short ratios from Binance USD-M's daily metrics archives, one row per contract every 5 minutes, columns named as in the archive. A row describes the moment create_time + 5 minutes; the table keeps archive values, and exports apply the rule giving REST's displayed values and visibility time, so Paper and Live read the same row from REST.

- create_time is on the 5-minute grid and values are non-negative; a value that does not fit the decimal encoding refuses the day with SCALE_LOSS.
- Stored rows stay as they are and each import only adds new days; missing days are reported by coverage reads, not stored.
- The archive's taker buy/sell ratio and open-interest value are computable from stored data or are an exchange price snapshot, and neither is stored.

### `funding` [#def-table-funding]

Funding recorded at the exchange's actual settlement times, jitter kept, exported as engine funding updates. Rates are below 1 in absolute value; rewriting the current month, days already stored must equal the source reread row by row.

### `universe_month` [#def-table-universe_month]

The common tradable universe: the member list produced by a prior rule at the start of each UTC month, without ranking or top-N; contracts delisted later stay in their month's list. Storing the list reproduces any market day's membership path exactly, which enters the input identity.

- Written with the bar import; when a month already has a list, the computed one must equal the stored rows, otherwise UNIVERSE_CHANGED.
- Before placing, the latest month is checked: each member has a LAST bar with volume on the month's previous UTC day, each member has terms, and the universe rule is the current one; any failure is DATA_TESTS_FAILED.
- An out-of-sample binding compares, row by row, the lists of the months before registration at the registered market day and at the current one.
