# H　提假设：一次回放之前，Agent 要界定、查证、写下并锁定什么，其中哪些由代码强制。

<p className="rd-translation-note">English translation pending: this page shows the Chinese source text.</p>


本章定义回放前的四步。第一步界定一个假设（hypothesis）：从候选谱系（lineage）里分别选研发父版本（parent）和比较对照（control），把改动收束为一处规则。第二步先查来源，并把原件留存为证据包（evidence bundle）。第三步写下五样，并声明检验条件。第四步是登记（registration），它先于回放并锁定内容。前三步由 skill 指导，代码只校验形态、范围与引用。登记以及回放时的绑定是代码强制的信任边界，在账本（ledger）事务里执行。候选身份与父子关系归 T 章，可比性与检验读数归 V 章，研究优先级归 F 章，运行环境与执行身份的底层归 J 章。

## H.1　界定一个假设 [#H-1]

界定假设（hypothesis）是回放前的第一步：Agent 在 research-round 指导下，先从 <Ref id="F.2.1.1">研究优先级</Ref> 与候选清单出发，对研发父版本（parent）源码按九组职责查漏并选出下一小批待登记的假设；再对每个假设分别选定父版本与比较对照（control），并把改动收束为一处实际规则改动。数据流是单向的：输入只有候选谱系（lineage）、经济证据可用性视图与研究优先级，输出是一份可登记的假设草案——parent、control_run、change 与候选网格点，交给 <Ref id="H.2.1.1">查来源</Ref> 与 <Ref id="H.3.1.1">写五样</Ref>。本功能里唯一由代码强制的是对照资格与父子关系：<Ref id="registration.validate" /> 在登记与绑定时核对；其余由 skill 指导，代码不返回优先级或分数。

<Steps>

<Step>

读候选清单（<Ref id="E.1.1.2" />）与研究状态清单里的研究优先级（<Ref id="F.2.1.1" />），确定研究路线内下一步要改进的方向

</Step>

<Step>

按九组职责对研发父版本源码查漏，列出缺省与未覆盖的职责作为候选改动方向（<Ref id="H.1.2.1" />）

</Step>

<Step>

把缺失组合与单规则改进放在一起比较信息价值与完整原生运行成本，选出下一小批假设（<Ref id="H.1.2.2" />）

</Step>

<Step>

对每个假设选父版本并写理由（<Ref id="H.1.1.1" />），分别选一个经济证据可用且可比的运行作对照（<Ref id="H.1.1.2" />）

</Step>

<Step>

把改动收束为一处实际规则改动，写明机制与比较维度的雏形（<Ref id="H.1.1.3" />）

</Step>

<Step>

假设草案进入 <Ref id="H.2.1.1">来源检索</Ref> 与 <Ref id="H.3.1.1">五样写作</Ref>；父子关系与对照资格最终由 <Ref id="registration.register" /> 调用 <Ref id="registration.validate" /> 核对

</Step>

</Steps>

### H.1.1　研发父版本、比较对照与改动粒度 [#H-1-1]

三条能力中父版本选择与改动粒度由 skill 指导（research-round「父与对照」「一处改动」两节），对照资格与父子关系由代码强制（<Ref id="registration.validate" /> 调用 <Ref id="qualification.require" /> 与 <Ref id="registration.check_comparable" />）。输入是候选清单与经济证据可用性视图，输出是登记体的 parent、control_run 与 change 三个字段。

<Cap id="H.1.1.1" kind="skill" tier="rehearsal" tierLabel="演练证据" title="研发父版本可以是候选谱系中任一完整候选">

研发父版本（parent）可以是候选谱系（lineage）中任何一个完整候选（candidate，引用名 strategy_id@revision），不限于当前推荐、最近版本或读数最好的版本；亏损、不显著或仅作诊断的有效候选照样可作父版本派生，推荐与检验读数都不授予或剥夺派生资格（<Ref id="T.1.1.2" />）。推荐候选不必是下一实验的父（<Ref id="research-round/SKILL.md#recommendation-vs-next-parent" />）。选父的理由写入登记体 rationale，与对照理由分开写。由 skill 指导（<Ref id="research-round/SKILL.md#parent-and-control" />），eval <Ref id="eval:research-round/losing-candidate-still-derives" /> 检查选亏损候选作父时不请许可、不质疑资格；代码只在登记时核对父是账本里已发布的候选（<Ref id="registration.validate" />，拒绝码 REGISTRATION_INVALID），不评价父的成绩。

<Cap id="H.1.1.2" kind="code" tier="rehearsal" tierLabel="演练证据" title="比较对照与研发父版本分别声明，对照须经济证据可用">

登记体分别声明研发父版本 parent（strategy_id@revision 或空）与比较对照 control_run（run_id 或空）。对照是一个运行（run），须同时满足三项：状态为通过且已封存的研究回放；按当前检查身份具有经济证据资格（有真实原生成交及匹配记录，<Ref id="G.4.1.1" />）；与本次执行身份可比（运行环境摘要、有效配置身份、输入身份三类逐项一致）。对照不必是父版本的运行。根登记（parent 为空）不得带对照与改动；非根登记在父版本故障或零活动时可暂无对照，但 rationale.local 须引用父运行的故障或零活动诊断，此时比较读数置空，直到后续登记选到可用对照。核对由 <Ref id="registration.validate" /> 在登记时执行，并在绑定前（<Ref id="registration.bind" />）按当前读数版本重算一次；拒绝码：RUN_NOT_PASSED（对照非通过或未封存）、COMPARABILITY_MISMATCH（三类身份有冲突，消息指明冲突项）、ECONOMIC_EVIDENCE_UNAVAILABLE（对照无经济证据资格，附原因）、REGISTRATION_INVALID（根带对照或改动、非根缺父、无对照而无故障诊断）。由代码强制，不写账本，只读。

<Cap id="H.1.2.1" kind="skill" tier="unverified" tierLabel="待验证" title="提假设前按九组职责索引查漏">

## H.2　先查来源并留存 [#H-2]

来源工作排在写经济理由之前、登记之前，顺序是检索、阅读与分类、留存、被登记引用。检索与阅读由 research-sources 指导，理由分类由 research-round 指导，二者的产物是检索记录、来源清单与登记体里的分类文字；原件、摘录与检索记录经 evidence add 入账本成证据包（evidence bundle）。代码对来源只强制一点：登记体 sources 列出的证据包必须已在账本，否则登记被拒。来源只影响研究优先级（research priority），不进入审计、资格或比较读数；工程修复不走这条路，只用技术文档与原生预检（native precheck）。

<Steps>

<Step>

读账本中已留存的来源证据包，判断其机制与条件对本次改动是否仍适用，列出机制缺口。

</Step>

<Step>

按 research-sources 针对缺口检索：至少三种表述、至少两个索引，每次检索写一行检索记录。

</Step>

<Step>

逐份阅读来源，记状态、市场、窗口、频率、样本外与成本条件；剔除撤稿，同一工作的多个版本合并。

</Step>

<Step>

把经济理由逐条标为外部依据、本地诊断或自身推测，写进登记体的 rationale 与 sources 说明。

</Step>

<Step>

经 evidence add 把原件副本、摘录与检索记录入账为证据包，登记时以包名引用；不在账本即拒绝。

</Step>

<Step>

回放后找到的材料另开带日期的证据包追加，原登记与原分类不改。

</Step>

</Steps>

### H.2.1　检索 [#H-2-1]

检索全部由 skill 指导：research-round 规定提假设前先查来源，research-sources 规定查哪类来源、怎么检索、怎么记录。输入是拟改动的机制与账本里已留存的来源证据包，输出是检索记录与候选来源清单，交给 H.2.2 分类、H.2.3 留存。代码不检查检索是否做过。

<Cap id="H.2.1.1" kind="skill" tier="rehearsal" tierLabel="演练证据" title="提经济假设前按 research-sources 查论文与可信实践">

提出经济假设（hypothesis）之前，Agent 先查来源，规则见 <Ref id="research-round/SKILL.md#sources-first" />。输入：拟改动的机制，以及账本中已留存的来源证据包。步骤：先读这些证据包，机制与适用条件仍相符的直接引用；只针对机制缺口补检。查哪类来源按 <Ref id="research-sources/SKILL.md#which-source" />，检索方法按 <Ref id="research-sources/SKILL.md#search" />（同一问题至少三种表述、至少两个索引，只引能解析的 DOI 或 arXiv），各索引的查询写法见 <Ref id="research-sources/references/endpoints.md#queries" />。可信实践（credible practice）优先可识别的原作者、官方研究材料或可检视的代码，并记位置、日期与实际检视的内容。输出：检索记录与候选来源清单。工程修复（构造、订单接口、因果时钟）不需要盈利论文，依据是引擎技术文档与原生预检。强制层：skill；由 <Ref id="eval:research-round/sources-before-hypothesis" /> 检验顺序，代码不拒绝。

### H.2.2　理由三分类与来源的作用 [#H-2-2]

## H.3　写下五样 [#H-3]

五样是登记体 research-plan.json 的内容：经济理由与预测（rationale、prediction）、来源证据包（sources，由 H.2 备好）、一个比较维度（metric）连同检验条件（comparison）、完整网格（grid）、本次试验的适用条件（conditions）。理由、预测与适用条件的写法由 skill 指导，代码只核对它们是非空的有限长度文本；维度、检验条件与网格由代码校验形态、范围以及与候选谱系（lineage）是否一致。这些核对都在登记写事务里经 registration.validate 执行，任何一项不合，整份登记都不写入。写完的五样交给 H.4 锁进不可变登记证据包，之后不改；要改就另行登记。

### H.3.1　经济理由与预测 [#H-3-1]

两条能力都由 research-round 的参考文件 hypothesis.md 指导，内容写进登记体的 rationale 与 prediction 字段。结果到行动的映射写在 prediction 里，与预测一并锁定。代码只校验这两个字段是非空的有限长度文本，不评价内容。

<Cap id="H.3.1.1" kind="skill" tier="verified" tierLabel="已验证" title="写明机制、谁付钱、可反驳的预测与代理">

Agent 在登记体 rationale 字段里写经济理由（economic rationale），说清三件事：什么市场机制产生这笔收益；谁在付钱，即对手方是谁或转移的是谁的成本；为什么这个机制在本研究路线的共同可交易范围（universe）与开发窗口内仍应存在。如果机制依赖回放输入里没有的量，就写明用什么代理（proxy）以及这个代理的局限。prediction 字段写一个能被回放结果否定的预测：写明在登记维度上的变化方向，以及这一变化预计体现在哪些成交或持仓特征上。「会赚钱」「表现更好」这类结果无法否定的陈述不算预测。一个假设只含一处实际规则改动，方向模糊时先收束再写（<Ref id="research-round/SKILL.md#one-change" />）。写法由 skill 规定（<Ref id="research-round/references/hypothesis.md#five-items" />）。代码只在 <Ref id="registration.validate" /> 里核对两个字段为非空的有限长度文本，不合即拒绝，拒绝码 REGISTRATION_INVALID；代码不评价理由的好坏。登记后两个字段随登记证据包一起锁定（<Ref id="H.4.1.1" />）。

### H.3.2　比较维度与检验条件 [#H-3-2]

这一组由代码校验：registration.validate 只接受定义了配对推断的维度，并调用 registration.validate_design 校验 comparison 的八个字段的形态与范围。检验条件的数值由 Agent 声明并写明设计理由，随登记锁定；这些数值是方法示例值，不是产品常数。

<Cap id="H.3.2.1" kind="code" tier="rehearsal" tierLabel="演练证据" title="登记只押一个比较维度">

登记体的 metric 字段只取一个比较维度。唯一定义了配对推断的维度是年化收益 annual_return；取其他值时，<Ref id="registration.validate" /> 拒绝，拒绝码 METRIC_UNSUPPORTED。比较维度是检验的对象，不是胜出声明：登记里不写「父版本胜出」之类的结论。比较只在这个维度上给出效应、区间与 p（<Ref id="V.3.1.1" />）。回撤、夏普、胜率、成本、资金使用率等其余读数只作描述，进入推荐时的多维取舍。要扩展可登记的维度，需要修改代码里的推断定义及与之对应的检验条件，不能在登记里临时声明。

### H.3.3　网格与适用条件 [#H-3-3]

网格由代码核对：每个点必须是账本里发布过的候选，父版本与改动说明须与登记一致，源码不重复，运行契约须与运行环境一致，点数为一到五。适用条件的写法由 skill 规定，代码只核对它非空。两者连同运行时探测到的执行身份，一起进入登记证据包。

<Cap id="H.3.3.1" kind="code" tier="verified" tierLabel="已验证" title="网格一到五点一次写定，每点是已发布的精确源码版本">

grid 字段一次写定一到五个网格点，上限五是未校准示例值。每个点写成 \{strategy, parameters\}：strategy 是经 <Ref id="ledger.publish_candidate" /> 发布进 <Ref id="table:candidate" /> 的精确源码版本 strategy_id@revision；parameters 是这个点全部规则参数的完整文字说明，必须是非空的有限长度文本。<Ref id="registration.validate" /> 逐点核对以下几项。第一，候选存在，且候选的研发父版本（parent）等于登记的 parent、改动说明等于登记的 change；根登记时每个点都没有父版本。不合即拒绝，拒绝码 LINEAGE_MISMATCH。第二，候选声明的运行契约等于登记时探测到的运行环境契约，不合即拒绝，拒绝码 CONFIG_MISMATCH。第三，同一源码内容哈希（content hash）不得在网格里出现两次；点数不在一到五之间、或点的格式不符时，同样拒绝，拒绝码 REGISTRATION_INVALID。网格随登记锁定：登记后要加点、改意图或改源码，都必须另行登记，原登记不改。每个点只被一次试验消耗（<Ref id="H.4.2.1" />）。网格点数会进入比较时的多重检验校正（<Ref id="V.3.2.3" />），所以每个试过的配置都必须写进网格、计入点数。

## H.4　登记先于回放并锁定 [#H-4]

登记（registration）是代码强制的信任边界，分两段。登记段：Agent 经 <Ref id="cli.registration_add" /> 调 <Ref id="registration.register" />，先探测钉死的运行环境（runtime image）、按研究路线（research line）钉住的市场提交导出不可变市场输入、在运行环境内读出生效配置，合成执行身份（execution identity），再在一个账本事务里校验并把五样、检验条件、引用与执行身份封成带内容哈希（content hash）的不可变证据包 research-plan.json。回放段：<Ref id="cli.replay_run" /> 经 <Ref id="ledger.open_trial" /> 在写试验（trial）行的同一事务里调 <Ref id="registration.bind" />，把这次回放绑定到一个已登记网格点并写一行消耗记录，任一不符整笔回滚、不启动引擎（engine）子进程。网格点一次性消耗，源码一旦被回放暴露就不能再当新登记。输出是带登记引用的试验与消耗记录，交 V 章比较时核对；服务器时间来源见 <Ref id="J.4.1.1" />，绑定的完整核对清单见 <Ref id="J.4.2.1" />。

<Steps>

<Step>

Agent 发布网格内每个候选（candidate），对每个源码完成原生预检（native precheck）与独立源码审查并入账，然后才登记（<Ref id="eval:research-round/precheck-before-register" />）。

</Step>

<Step>

<Ref id="cli.registration_add" /> 调 <Ref id="registration.register" />：读当前研究路线，解析并探测运行环境、导出市场输入、读生效配置，合成执行身份。

</Step>

<Step>

同一账本事务内 <Ref id="registration.validate" /> 校验登记体与执行身份，通过后写登记证据包 research-plan.json；任一拒绝整笔回滚。

</Step>

<Step>

<Ref id="cli.replay_run" /> 开试验：<Ref id="ledger.open_trial" /> 插入试验行后调 <Ref id="registration.bind" /> 重验登记、比对执行身份与先后时间、写 <Ref id="table:registration_attempt" /> 一行，再写执行开始回执并提交。

</Step>

<Step>

提交成功才启动引擎子进程；绑定任一拒绝则事务回滚，不留试验行，不启动子进程。

</Step>

<Step>

再试同一源码须另登记并填 retry_of；V 章按 <Ref id="table:registration_attempt" /> 与登记包读出比较所需的网格点与试验。

</Step>

</Steps>

### H.4.1　登记身份与先后顺序 [#H-4-1]

三条全部由代码强制：H.4.1.1 锁定登记内容，H.4.1.2 在登记时写定执行身份，H.4.1.3 在回放前按同一事务绑定并核对先后。输入是登记体 JSON、运行环境引用与运行器参数；输出是登记证据包、其中的执行身份，以及绑定后的消耗行。

<Cap id="H.4.1.1" kind="code" tier="verified" tierLabel="已验证" title="五样、检验条件、来源与审查引用锁进不可变登记证据包">

登记把一次假设（hypothesis）回放前要写下的全部内容锁进一份不可变登记证据包（evidence bundle），包内唯一文件为 research-plan.json。输入：登记体（五样——经济理由与预测、来源证据包引用、一个比较维度、完整网格、本次试验的适用条件；检验条件；比较对照 control 的运行引用；网格每点的候选引用 strategy_id@revision 与配置；每点的源码审查引用；可选 retry_of）、运行环境引用、运行器参数。输出：包名、research-plan.json 的内容哈希、执行身份与账本提交。内容哈希由文件字节派生并存入 <Ref id="table:evidence" />，任何读回都经 <Ref id="ledger.load_bundle" /> 重算比对，不符即 LEDGER_CORRUPT；登记包写入后不可改，更正只能是新包。拒绝：字段缺一或多余、来源证据包或审查引用不在账本（REGISTRATION_INVALID）；网格源码在该运行环境下没有通过的预检与审查（SOURCE_PRECHECK_REQUIRED）；包名落在产品保留命名空间（RESERVED_BUNDLE_NAME）；同名包内容不同（DUPLICATE_BUNDLE）。同内容重试幂等返回原记录。全部由代码在登记写事务内强制，Agent 只能经命令行接口写入。

### H.4.2　网格点消耗与源码暴露 [#H-4-2]

两条都由代码强制。消耗由 <Ref id="table:registration_attempt" /> 的主键唯一性与 <Ref id="registration.bind" /> 的核对实现；暴露由 <Ref id="registration.validate" /> 在登记时按同源码的试验记录推断，只有 <Ref id="registration.exposure_exempt" /> 认定的事前声明预检除外。输入是登记体里的网格与 retry_of，输出是允许或拒绝登记、允许或拒绝绑定。

<Cap id="H.4.2.1" kind="code" tier="rehearsal" tierLabel="演练证据" title="每个网格点只消耗一次，再试另登记并写 retry_of">

每个网格点（登记包 × 网格源码）只被消耗一次。绑定成功即在 <Ref id="table:registration_attempt" /> 写入（登记包，源码哈希）→ 试验的映射；主键是（登记包，源码哈希），再次绑定同一点主键冲突即拒绝（GRID_ALREADY_ATTEMPTED），并发同时绑定在提交时冲突，后到者回滚（CONCURRENT_WRITE），不会出现双消耗。消耗行与试验行同生同灭，之后无效或中断的尝试照样保留消耗行并算作消耗。同一源码再试须另登记，并在登记体 retry_of 写明在 registration_attempt 中实际消耗过该源码的先前登记包；缺 retry_of 或指向未消耗该源码的登记即由登记校验拒绝。相同条件的重复不算独立证据：retry_of 把它们连成同一网格点的重复尝试，读数侧据此识别。由代码与账本主键共同强制。
