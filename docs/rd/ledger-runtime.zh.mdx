## J.1　唯一来源：持久研究记录只存账本 [#J-1]

本功能划定持久研究记录的边界：不可重建的证据只进账本 ledger 及其 dolt_backup 备份，其余要么是临时目录里的工作副本，要么是产品源码与运行环境 runtime image 的构建定义。先定入账范围（J.1.1），再定账本之外的去向（J.1.2）。入账判据只有一条：能由账本记录、钉死运行环境与同一市场提交重建的产物不入账。写入一律经 <Ref id="J.3.3.2">声明的命令行接口</Ref>，Agent 不直连写库；入账后的只追加、内容哈希 content hash 与按版本读回由 <Ref id="J.3.1.1" />、<Ref id="J.3.4.1" />、<Ref id="J.3.1.3" /> 保证。代码只守住入账形态与临时路径，「该不该入账」由 Agent 按 research-round skill 判断。

### J.1.2　账本之外的去向 [#J-1-2]

代码强制三件事：探索、预检与封存回放的工作目录必须是临时根之下的新目录（<Ref id="ledger.temporary_path" />）；测试与演练只写临时根下起的隔离账本（<Ref id="cli.ledger_temp" />）；运行环境只由产品源码的自动构建产出。未发布策略的编写位置与「策略正文不进产品源码」由 research-round skill 指导，eval 检查。

<Cap id="J.1.2.1" kind="code" tier="rehearsal" tierLabel="演练证据" title="未发布的策略文件、探索脚本、回放输出、派生报告放工作副本目录">

未发布的策略文件、探索脚本、回放输出与派生报告是工作副本，只放平台临时根之下。代码强制：非登记探索（purpose=explore）与原生预检（purpose=precheck）的输出目录、研究封存回放的工作目录、测试账本的服务目录，都在起容器或起服务之前经 <Ref id="ledger.temporary_path" /> 核对——解析后不在任何临时根之下或恰为临时根本身，拒绝 NOT_TEMPORARY_PATH；已存在（含文件与悬空链接），拒绝 PATH_EXISTS；该函数不创建目录。研究封存回放的工作目录在原生报告入账后删除，失败时保留供诊断并在标准错误打印位置。活动账本反向使用同一判定：服务目录或备份目录落在临时根之下即拒绝（<Ref id="ledger.init" />）。测试、演练与工程试验只写 <Ref id="cli.ledger_temp" /> 起的隔离账本，与活动账本不共享任何路径。

## J.2　记录：账本装什么、谁能写什么 [#J-2]

本功能定义账本 ledger 里每类研究记录的内容与写入者。数据流：发布写候选行 → 登记写不可变登记证据包 → 每次回放在启动容器前写试验行与开始回执 → 回放结束封存原生日志 → research 与 validation 回放一次写入运行行与原生报告行；失败、无效与中断同样入账。结构化事实（读数、计数、身份、时间）全由代码写，Agent 只追加自由文本证据包；账本不存裁决，资格与计数读时算。

### J.2.1　研究对象的记录 [#J-2-1]

候选行由代码在发布时写入 <Ref id="table:candidate" />；登记由代码校验后锁成证据包，存于 <Ref id="table:evidence_bundle" /> 与 <Ref id="table:evidence" />。输入是 Agent 给的源码文件与登记 JSON，输出是带库内内容哈希的只追加行；形态与锁定由代码强制，改什么、为什么改由 skill 指导。

<Cap id="J.2.1.1" kind="database" tier="rehearsal" tierLabel="演练证据" title="候选记录：源码原字节与内容哈希、入口类、运行契约、研发父版本、改动说明">

候选 candidate 的账本记录是一份完整单文件策略源码的原字节，加库内派生的内容哈希 content hash、顶层入口类名、运行契约、说明、研发父版本 parent 与改动说明，引用名为 strategy_id@revision；存于 <Ref id="table:candidate" />，一行一个提交。输入是源码文件与上述字段，输出是一行候选。代码强制，全部在 <Ref id="ledger.publish_candidate" /> 内：先由 <Ref id="ledger.check_source" /> 只解析不执行，核源码非空、在容量上限内（未校准示例值）、可解析为 UTF-8 Python、恰有一个与声明同名的顶层类；相同字节已是候选则拒绝并返回原候选；派生候选须同时给父版本与改动说明且父已在账本中，根两者皆空，只给其一即拒绝；写入经 <Ref id="ledger.write" /> 单事务完成。账本只证明单文件形态与谱系，不证明规则正确；亏损或不显著的候选照样可作父版本继续派生（<Ref id="T.1.1.2" />）。

### J.2.2　回放的记录 [#J-2-2]

## J.3　写入保护：怎么证明没被改 [#J-3]

本节回答「怎么证明账本没被改」，五个组件沿写入路径排列：写入只经命令行接口以写账号进入（J.3.3），每次写入是一个原子幂等的事务（J.3.2），只产生插入行与一个 Dolt 提交（J.3.1）；封存内容的内容哈希由库内派生、读时核验（J.3.4）；全史同步到备份，整体复核由读账号按精确版本事后核对全部不变量（J.3.5）。强制分三处：账号权限与提交校验在账本层，写协议与哈希核验在代码层，复核只报发现、不写记录。保证是留痕而非不可改：同一系统用户能读到服务配置、以管理账号连接或直接改数据目录，这类篡改不能阻止，只能由差异系统表与整体复核事后发现（<Ref id="A.5.2.2" />）。

### J.3.1　只追加 [#J-3-1]

由账本层保证正常路径只有插入：写账号对业务表只有 INSERT，每次写入是一个 Dolt 提交，差异与历史系统表为每行留痕。写错用新的更正证据包改口；读历史按精确版本；正常路径之外的改与删不在写时阻止，由整体复核从差异表报出。

### J.3.2　写入事务 [#J-3-2]

由代码层 <Ref id="ledger.write" /> 把每次写入做成一条连接上的一个事务：核对写角色、按操作 ID 查重放、拒脏工作集、只插入、头指针加一、提交。幂等靠操作 ID，并发靠头指针单行的同格不同值冲突；本组件定义这两张单行表。

<Cap id="J.3.2.1" kind="database" tier="verified" tierLabel="已验证" title="一次写入整笔成或整笔不成">

## J.4　登记先于回放：先后顺序怎么证明 [#J-4]

先后由三样东西证明：登记与试验的时间都由账本触发器写服务器 UTC，Agent 不报时间（J.4.1.1）；回放入口在启动容器前用一个事务写下试验行、绑定行与执行开始回执（J.4.1.2）；绑定器在这个事务里核对登记早于试验、源码与身份一致、预检通过（J.4.2.1）。样本外登记另取公共时间戳凭证，作为不依赖本机时钟的外部先后证明（J.4.2.2）。强制在代码与账本：函数拒绝、提交校验拒提交，整体复核事后重核。网格点一次性消耗与源码暴露规则在 <Ref id="H.4.2.1" />。

## J.5　运行环境钉死：回放在什么里跑 [#J-5]

运行环境由源码托管平台的自动构建产出并推送到镜像注册表（registry）（J.5.1.1），回放侧只按清单摘要引用，身份从镜像本身读出（J.5.1.2）。镜像内容与布局由同一份契约布局声明（J.5.2.1），容器命令由一个函数生成且固定无网络、只读、去特权（J.5.2.2）。所有用途的回放只经命令行入口，入口按固定顺序解析身份、探针检视、导出输入、先写试验记录再起容器、结束后封存（J.5.2.3）。全部规则由代码强制，构建侧不写账本，回放侧不构建镜像。

<Steps>

<Step>

源码托管平台的自动构建按契约布局产出单平台镜像并推送到镜像注册表，带构建源码版本与运行契约标签（runtime.build_image）。

</Step>

<Step>

入口把运行环境引用解析为唯一清单摘要，从镜像读出并核对身份（runtime.resolve、runtime.validate_identity）。

</Step>

<Step>

入口在隔离容器内跑身份探针核对布局与有效配置，并按钉住的市场提交导出输入、算输入身份。

</Step>

<Step>

子进程启动前，同一事务写试验行、登记绑定与开始回执；任一失败不起容器。

</Step>

<Step>

在无网络、只读、去特权且只有报告目录可写的容器内，先运行器后独立审计器。

</Step>

<Step>

结束后（含中断与宿主失败）封存执行捕获；研究与样本外运行一次入账，探索报告只留在临时目录。

</Step>

</Steps>

## J.6　回放身份与复现：每次回放留下什么、怎么重跑 [#J-6]

每次研究与样本外回放绑定三类身份：源码（J.6.1.1）、运行环境（J.6.1.2）、输入（J.6.1.3），覆盖回执（J.6.1.4）随执行一起封存。身份在登记时锁定，回放入口在启动前重算并与登记逐字核对，容器内运行器再核一次，入账时与原生摘要比对；任一不符即拒绝或判无效。三类身份与封存的原生报告构成复现合同（J.6.2.1），读取即核验与「缺失即不可用」（J.6.2.3）保证坏了的封存不冒充可复核，恢复演练（J.6.2.2）证明备份可读回。核验与写入都由代码强制，恢复演练由 skill 指导。

<Steps>

<Step>

登记时 registration.market_inputs 按市场提交导出输入并组装输入身份，runtime.inspect_runtime 核对运行环境身份，二者锁进登记

</Step>

<Step>

回放入口 replay.seal 重新导出并核对导出指纹与运行契约，在工作目录写源码、binding.json、execution.json 与 input-coverage.json

</Step>

<Step>

同一事务写试验行、登记绑定与开始回执，任一拒绝不启动容器；容器内运行器核对源码哈希、入口类与执行绑定

</Step>

<Step>

执行后再算原始导出指纹，汇总无效原因，ledger.ingest_run 入账，执行捕获随之封存

</Step>

<Step>

读取时 ledger.load_run 核验身份与哈希，不符即拒绝，资格视图标该运行不可用

</Step>

<Step>

复现时 ledger.export_history 导出备份与复现清单，按摘要拉回运行环境、同提交重导出、重放并与原生行逐条比较

</Step>

</Steps>

### J.6.1　一次回放绑定的身份 [#J-6-1]

源码身份由回放入口写绑定文件、容器内运行器装载时核哈希；运行环境身份由镜像内探针报告并与宿主读出的清单身份核对；输入身份由导出内容与导出器哈希构成，登记与回放各算一次、执行前后再比原始指纹；覆盖回执启动前写下并随执行封存。全部由代码写入试验、运行与执行封存，Agent 不能手填。

<Cap id="J.6.1.1" kind="code" tier="rehearsal" tierLabel="演练证据" title="源码身份：被执行源码的内容哈希，绑定到账本里的候选版本">
