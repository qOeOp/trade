# H　提假设：一次回放之前，Agent 要界定、查证、写下并锁定什么，其中哪些由代码强制。

本章定义回放前的四步。第一步界定一个假设（hypothesis）：从候选谱系（lineage）里分别选研发父版本（parent）和比较对照（control），把改动收束为一处规则。第二步先查来源，并把原件留存为证据包（evidence bundle）。第三步写下五样，并声明检验条件。第四步是登记（registration），它先于回放并锁定内容。前三步由 skill 指导，代码只校验形态、范围与引用。登记以及回放时的绑定是代码强制的信任边界，在账本（ledger）事务里执行。候选身份与父子关系归 T 章，可比性与检验读数归 V 章，研究优先级归 F 章，运行环境与执行身份的底层归 J 章。

## H.1　界定一个假设 [#H-1]

<Steps>

<Step>

读候选清单（<Ref id="E.1.1.2" />）与研究状态清单里的研究优先级（<Ref id="F.2.1.1" />），定下研究路线内下一步要改进的方向。

</Step>

<Step>

按九组职责对研发父版本源码查漏，列出缺省与未覆盖的职责作为候选改动方向。

</Step>

<Step>

比较缺失组合与单规则改进的信息价值与完整原生运行成本，选出下一小批假设。

</Step>

<Step>

对每个假设选父版本并写理由，另选一个经济证据可用且可比的运行作对照。

</Step>

<Step>

把改动收束为一处实际规则改动，写明机制与比较维度的雏形。

</Step>

<Step>

假设草案（parent、control_run、change 与候选网格点）交给 <Ref id="H.2.1.1">来源检索</Ref> 与 <Ref id="H.3.1.1">五样写作</Ref>，登记时由 <Ref id="registration.register" /> 核对。

</Step>

</Steps>

### H.1.1　研发父版本、比较对照与改动粒度 [#H-1-1]

从候选谱系定下一个假设的父、对照与改动范围。

<Cap id="H.1.1.1" kind="skill" tier="rehearsal" tierLabel="演练证据" title="研发父版本可取候选谱系中任一完整候选，不看推荐与读数">

- 研发父版本（parent）可以是候选谱系（lineage）中任何一个完整候选（candidate，引用名 strategy_id@revision）。
- 不限于当前推荐、最近版本或读数最好的版本。
- 亏损、不显著或仅作诊断的有效候选照样可作父版本派生。
- 推荐与检验读数都不授予或剥夺派生资格（<Ref id="T.1.1.2" />）。
- 推荐候选不必是下一实验的父（<Ref id="research-round/SKILL.md#recommendation-vs-next-parent" />）。
- 选父的理由写入登记体 rationale，与对照理由分开写。
- 代码不评价父的成绩。

**输入**　候选谱系中已发布的完整候选。

**输出**　登记体的 parent 字段与 rationale 中的选父理由。

**强制**　skill 指导（<Ref id="research-round/SKILL.md#parent-and-control" />），eval <Ref id="eval:research-round/losing-candidate-still-derives" /> 检查选亏损候选作父时不请许可、不质疑资格；代码只由 <Ref id="registration.validate" /> 在登记时核对父是已发布候选。

| 拒绝码 | 条件 |
|---|---|
| `REGISTRATION_INVALID` | 登记时父版本不是账本里已发布的候选。 |

</Cap>

<Cap id="H.1.1.2" kind="code" tier="rehearsal" tierLabel="演练证据" title="对照与父版本分别声明，对照须已通过封存、有经济证据且可比">

- 登记体分别声明 parent（strategy_id@revision 或空）与 control_run（run_id 或空）。
- 对照是一个运行（run），不必是父版本的运行。
- 对照须是状态为通过且已封存的研究回放。
- 对照须按当前检查身份具有经济证据资格，即有真实原生成交及匹配记录（<Ref id="G.4.1.1" />）。
- 对照须与本次执行身份可比：运行环境摘要、有效配置身份、输入身份三类逐项一致。
- 根登记（parent 为空）不得带对照与改动。
- 非根登记在父版本故障或零活动时可暂无对照。
- 此时 rationale.local 须引用父运行的故障或零活动诊断。
- 比较读数置空，直到后续登记选到可用对照。

**输入**　登记体的 parent、control_run 与 rationale，以及账本中对照运行的状态、经济证据资格与三类身份。

**输出**　通过，或带拒绝码的拒绝；只读，不写账本。

**强制**　代码强制：<Ref id="registration.validate" /> 调用 <Ref id="qualification.require" /> 与 <Ref id="registration.check_comparable" />，登记时执行，并在 <Ref id="registration.bind" /> 前按当前读数版本重算一次。

| 拒绝码 | 条件 |
|---|---|
| `RUN_NOT_PASSED` | 对照非通过或未封存。 |
| `COMPARABILITY_MISMATCH` | 三类身份有冲突，消息指明冲突项。 |
| `ECONOMIC_EVIDENCE_UNAVAILABLE` | 对照无经济证据资格，附原因。 |
| `REGISTRATION_INVALID` | 根登记带对照或改动、非根登记缺父，或无对照而无故障诊断。 |

</Cap>

<Cap id="H.1.1.3" kind="skill" tier="rehearsal" tierLabel="演练证据" title="一个假设只含一处实际规则改动，与候选改动说明逐字一致">

- 一个假设只含一处实际规则改动，写入登记体 change。
- change 与每个网格点候选的改动说明（difference）逐字一致（<Ref id="T.2.1.1" />）。
- 选币规则（universe_rule 之内的排名、前 N、信号筛选、调整频率）、仓位与资金预算规则的改动也是规则改动（<Ref id="C.1.2.2" />）。
- 入场与出场联动的规则改动算一个联动动作，按一个动作登记与描述，不拆成部件各自归因（<Ref id="research-round/references/feedback.md#coupled-action" />）。
- 由既有规则推导出的量和未启用方法的参数不算改动维度。
- 模糊的研究方向先收束为机制、一处改动、比较维度、网格（grid）与适用条件，再登记。
- 不先回放父版本看结果再调。

**输入**　研究方向与研发父版本源码。

**输出**　登记体 change，以及与之逐字一致的各网格点候选 difference。

**强制**　skill 指导（<Ref id="research-round/SKILL.md#one-change" />），eval <Ref id="eval:research-round/vague-direction" />、<Ref id="eval:research-round/universe-selection-is-a-hypothesis" />、<Ref id="eval:research-round/coupled-change-one-action" /> 分别检查模糊方向先收束、选币改动按假设登记、联动改动按一个动作登记；逐字一致由 <Ref id="registration.validate" /> 核对。

| 拒绝码 | 条件 |
|---|---|
| `LINEAGE_MISMATCH` | change 与网格点候选的改动说明 difference 不逐字一致。 |

</Cap>

### H.1.2　提假设前的查漏与批次选择 [#H-1-2]

提假设前先找缺口，再选出下一小批。

<Cap id="H.1.2.1" kind="skill" tier="unverified" tierLabel="待验证" title="提假设前按九组职责对父版本源码查漏，缺口作候选改动方向">

1. 对照研发父版本源码文件头的九组立场（<Ref id="C.1.4.1" />，每组一行写采用／缺省／不适用加一句理由）。
2. 找出缺省、不适用与未覆盖的职责。
3. 把它们作为候选改动方向写入假设草案。

- 九组职责：对象与适用性、预测与学习、首次行动与记忆、经济构型、风险与分配、持仓路径、实施、资本、生命周期与可行性。
- 职责目录全文只放 skill 参考文件（<Ref id="research-round/references/duty-directory.md#nine-groups" />），不写进正文或登记体。
- 待验证：查漏比不查更快找到有效改动，尚无同条件对照演练。

**输入**　研发父版本源码及其文件头九组立场。

**输出**　假设草案中的候选改动方向。

**强制**　skill 指导（<Ref id="research-round/SKILL.md#duty-gap-check" />），eval <Ref id="eval:research-round/duty-index-gap-check" /> 检查查漏时引用参考文件而不复述目录；代码不参与。

</Cap>

<Cap id="H.1.2.2" kind="skill" tier="unverified" tierLabel="待验证" title="缺失组合与单规则改进共同比较后选下一小批，一批跑完再登下一批">

1. 列出两类候选动作：机制支持的缺失组合（由已发布候选中的部件组成、尚未试过的组合）与单规则改进。
2. 按信息价值与完整原生运行成本比较两类动作。
3. 选出并登记下一小批假设。
4. 按网格全部回放完并读数（<Ref id="research-round/SKILL.md#run-the-grid" />）。
5. 再登记下一批。

- 排序依据见 <Ref id="research-round/references/feedback.md#priority-ranking" />（预期效应、不确定性、机制佐证、覆盖、信息价值与成本）。
- 只消费研究状态清单里的研究优先级（<Ref id="F.2.1.1" />），代码不给优先级或分数。
- 不边看结果边加题，也不预设批次数量。
- 待验证：批次选择对研发效率的前瞻验证尚未进行。

**输入**　研究状态清单里的研究优先级与候选清单。

**输出**　下一小批待登记的假设。

**强制**　skill 指导（<Ref id="research-round/SKILL.md#batch-selection" />），eval <Ref id="eval:research-round/batch-completes-before-next" /> 检查一批跑完才登下一批；代码不参与。

</Cap>

## H.2　先查来源并留存 [#H-2]

<Steps>

<Step>

读账本中已留存的来源证据包，判断机制与条件是否仍适用，列出机制缺口。

</Step>

<Step>

按 research-sources 针对缺口检索（至少三种表述、两个索引），每次检索写一行检索记录。

</Step>

<Step>

逐份阅读来源，记状态与条件，剔除撤稿，合并同一工作的多个版本。

</Step>

<Step>

按 research-round 把经济理由逐条标为外部依据、本地诊断或自身推测，写进登记体 rationale 与 sources 说明。

</Step>

<Step>

经 evidence add 把原件副本、摘录与检索记录入账为证据包；登记以包名引用，包不在账本即被代码拒绝。

</Step>

<Step>

回放后补到的来源另开新包追加（见 <Ref id="H.2.2.3" />）。

</Step>

</Steps>

### H.2.1　检索 [#H-2-1]

由 research-round 与 research-sources 指导，把拟改动的机制变成检索记录与候选来源清单，交给 H.2.2 分类、H.2.3 留存；代码不检查。

<Cap id="H.2.1.1" kind="skill" tier="rehearsal" tierLabel="演练证据" title="提经济假设前先读已留存来源，再按 research-sources 补检缺口">

1. 读账本中已留存的来源证据包，机制与适用条件仍相符的直接引用。
2. 只针对机制缺口补检，来源类别按 <Ref id="research-sources/SKILL.md#which-source" />。
3. 按 <Ref id="research-sources/SKILL.md#search" /> 检索：同一问题至少三种表述、至少两个索引，查询写法见 <Ref id="research-sources/references/endpoints.md#queries" />。
4. 只引能解析的 DOI 或 arXiv，产出检索记录与候选来源清单。

- 规则出处：<Ref id="research-round/SKILL.md#sources-first" />。
- 可信实践（credible practice）优先可识别的原作者、官方研究材料或可检视的代码，并记位置、日期与实际检视的内容。
- 工程修复（构造、订单接口、因果时钟）不需要盈利论文，依据是引擎技术文档与原生预检（native precheck）。

**输入**　拟改动的机制，以及账本中已留存的来源证据包。

**输出**　检索记录与候选来源清单。

**强制**　skill 强制；由 <Ref id="eval:research-round/sources-before-hypothesis" /> 检验先查来源的顺序，代码不拒绝。

</Cap>

<Cap id="H.2.1.2" kind="skill" tier="verified" tierLabel="已验证" title="每次检索记一行范围、读取程度与访问限制，否定断言只写按这些查询没找到">

- 检索记录（search log）规则见 <Ref id="research-sources/SKILL.md#search-log" />，每次检索一行：索引名、查询原文、过滤条件、命中数、查询日期。
- 每行记读取程度（题录、摘要、全文）与访问限制（无密钥、401/403、配额用尽）。
- 同一工作在多个索引命中时按工作合并，保留各索引的标识。
- 否定断言只写「按这些查询没找到」，并附查询与日期。
- 访问失败或全文不可读记为检索限制，不等于不存在先前研究。
- 检索记录作为文件随来源证据包入账（<Ref id="H.2.3.1" />）。

**输入**　每次检索的查询与结果。

**输出**　检索记录文件。

**强制**　skill 强制；由 <Ref id="eval:research-sources/negative-claim-scoped-to-queries" /> 检验，代码不拒绝。

</Cap>

### H.2.2　理由三分类与来源的作用 [#H-2-2]

分类只是登记体 rationale 与 sources 说明里的文字，不设字段、不打分，代码不解析，来源的作用只到研究优先级。

<Cap id="H.2.2.1" kind="skill" tier="rehearsal" tierLabel="演练证据" title="经济理由逐条标为外部依据、本地诊断或自身推测">

- 写法见 <Ref id="research-round/references/source-evidence.md#three-classes" />：外部依据（external support）、本地诊断（local diagnosis）、自身推测（conjecture）。
- 外部依据写出处位置、市场、窗口、频率、成本与验证条件。
- 外部依据说明支持的是机制、具体规则参数，还是只有方法。
- 模板出处、社区实践与方法论文不为具体参数背书。
- 未读到的条件写「未知」。

**输入**　H.2.1 的来源清单与读取记录。

**输出**　登记体 rationale 与 sources 说明中的分类文字。

**强制**　skill 强制；由 <Ref id="eval:research-round/source-three-classes" /> 检验；代码不解析分类，也没有分类字段。

</Cap>

<Cap id="H.2.2.2" kind="skill" tier="rehearsal" tierLabel="演练证据" title="本地诊断引用固定记录，自身推测写成可反驳预测并列未证迁移">

- 写法见 <Ref id="research-round/references/source-evidence.md#local-and-conjecture" />。
- 本地诊断引用固定身份：运行（run）、账本提交与证据包名。
- 本地诊断写明观察到的活动、经济数或源码故障及其范围。
- 内部诊断不写成论文，也不补写没有读到的数值。
- 自身推测写成可反驳的预测。
- 自身推测列出从来源条件迁移到当前市场、窗口、信号与执行频率、成本模型时未证的部分。

**输出**　登记体 rationale 中的本地诊断与自身推测文字。

**强制**　skill 强制；代码只核对被引用的证据包存在（<Ref id="H.2.3.1" />）。

</Cap>

<Cap id="H.2.2.3" kind="skill" tier="verified" tierLabel="已验证" title="来源只影响研究优先级，不证明本市场有效，回放后材料只追加不倒填">

- 规则见 <Ref id="research-sources/SKILL.md#support-and-practice" />。
- 来源证明作者在其市场与窗口研究了什么，不证明在本市场有效。
- 来源只进入研究优先级排序中的机制佐证一项（<Ref id="research-round/references/feedback.md#priority-ranking" />），不进入审计、资格或比较读数。
- 没有论文的方向仍可低优先级探索。
- 不按引用数排名、不设引用门槛、不以缺来源关闭方向（<Ref id="research-round/references/feedback.md#no-exclusion" />）。
- 出处记版本或日期，只有登记前首次可见的版本算事前依据。
- 回放后找到的材料经 <Ref id="ledger.add_bundle" /> 另开带日期的后续证据包追加，原登记与原分类不改。

**强制**　skill 强制；登记证据包不可变（<Ref id="H.4.1.1" />）使倒填在账本里无从发生；由 <Ref id="eval:research-round/later-source-appended-not-backfilled" /> 检验。

</Cap>

### H.2.3　留存来源原件 [#H-2-3]

证据包的存在性由代码在入账与登记时强制，包里放什么由 skill 规定。

<Cap id="H.2.3.1" kind="database" tier="rehearsal" tierLabel="演练证据" title="登记前原件、摘录与检索记录须入账成证据包，登记引用的包缺失即拒绝">

- 登记之前，来源原件副本（不只记链接）、摘录与检索记录经 <Ref id="cli.evidence_add" /> 调 <Ref id="ledger.add_bundle" /> 入账为一个证据包。
- 包头写入 <Ref id="table:evidence_bundle" />，每个文件写入 <Ref id="table:evidence" />，内容哈希（content hash）由字节派生。
- 证据包只追加不改。
- 同内容重试幂等。
- 后来的材料另开新包。
- 视频经 video-evidence skill 处理，只入账地址、媒体 SHA-256 与派生证据（完整转写、带真实时间戳的帧、身份回执）；媒体文件与空文件不入账。
- 登记时 <Ref id="registration.validate" /> 核对登记体 sources 列出的每个包名都在账本。
- Dolt 每次入账是一次提交，提交历史给出来源包与登记的先后，可据此核对事前依据。
- 只追加使原件不能被事后替换。

**输入**　原件副本、摘录、检索记录及包名。

**输出**　账本中的来源证据包（包头与逐文件内容哈希）。

**强制**　代码与账本强制：ledger.add_bundle 只追加并校验包名与内容，registration.validate 在登记时核对 sources 引用。

| 拒绝码 | 条件 |
|---|---|
| `BUNDLE_EXISTS` | 同名证据包已存在且内容不同。 |
| `EMPTY_BUNDLE` | 证据包既没有文件也没有文本。 |
| `RESERVED_BUNDLE` | 包名占用产品保留命名空间。 |
| `REGISTRATION_INVALID` | 登记体 sources 列出的任一证据包不在账本。 |

</Cap>

<Cap id="H.2.3.2" kind="skill" tier="verified" tierLabel="已验证" title="每份来源记状态与条件，撤稿不算来源，复述不算独立来源">

- 按 <Ref id="research-sources/SKILL.md#read" /> 记状态（期刊、工作论文、预印本、学位论文）。
- 记市场、窗口、频率、是否样本外（out-of-sample）、是否扣成本、出处位置（页、节、表或图）。
- 只读到摘要的标「仅摘要」。
- 已撤稿的不算来源。
- 同一工作的预印本、工作论文与期刊版合并为一条，引用发表版。
- 对同一工作的复述不算独立来源。
- 这些记录随原件写进同一来源证据包（<Ref id="H.2.3.1" />），供外部依据写支持范围。

**输入**　候选来源清单中的每份来源。

**输出**　随原件入包的来源状态与条件记录。

**强制**　skill 强制；由 <Ref id="eval:research-sources/source-status-and-conditions" /> 检验，代码不拒绝。

</Cap>

## H.3　写下五样 [#H-3]

<Steps>

<Step>

Agent 在 rationale 与 prediction 里写经济理由、可反驳的预测，以及五类结果各自对应的后续动作。

</Step>

<Step>

在 sources 中引用 H.2 已入账本的来源证据包。

</Step>

<Step>

选定唯一的比较维度 metric，声明检验条件 comparison 并写设计理由。

</Step>

<Step>

把每个网格点的源码作为候选发布进账本，再在 grid 中写定一到五个 strategy_id@revision 及其完整参数说明。

</Step>

<Step>

在 conditions 里写本次试验的适用条件；重试时写明先前的尝试及其局限。

</Step>

<Step>

五样组成登记体 research-plan.json 交 H.4 登记：registration.validate 在登记写事务内完成全部核对，任一项不合整份登记都不写入；登记后锁定不改，要改就另行登记。

</Step>

</Steps>

### H.3.1　经济理由与预测 [#H-3-1]

两样都写进 rationale 与 prediction，结果到行动的映射写在 prediction 里一并锁定。

<Cap id="H.3.1.1" kind="skill" tier="verified" tierLabel="已验证" title="理由写明机制、付钱方与代理，预测必须能被回放结果否定">

- rationale 写什么市场机制产生这笔收益。
- rationale 写谁在付钱：对手方是谁，或转移的是谁的成本。
- rationale 写为什么这个机制在本研究路线的共同可交易范围（universe）与开发窗口内仍应存在。
- 机制依赖回放输入里没有的量时，写明用什么代理（proxy）以及这个代理的局限。
- prediction 写一个能被回放结果否定的预测：在登记维度上的变化方向，以及这一变化预计体现在哪些成交或持仓特征上。
- 「会赚钱」「表现更好」这类结果无法否定的陈述不算预测。
- 一个假设只含一处实际规则改动，方向模糊时先收束再写（<Ref id="research-round/SKILL.md#one-change" />）。
- 登记后两个字段随登记证据包一起锁定（<Ref id="H.4.1.1" />）。

**输入**　已收束为一处规则改动的假设方向。

**输出**　登记体的 rationale 与 prediction 两个文本字段。

**强制**　写法由 skill 规定（<Ref id="research-round/references/hypothesis.md#five-items" />）；代码只在 <Ref id="registration.validate" /> 里核对两个字段为非空的有限长度文本，不评价理由好坏。

| 拒绝码 | 条件 |
|---|---|
| `REGISTRATION_INVALID` | rationale 或 prediction 为空或超出长度上限。 |

</Cap>

<Cap id="H.3.1.2" kind="skill" tier="rehearsal" tierLabel="演练证据" title="回放前在预测里写定五类结果各自的后续动作，事后不改写">

- 结果到行动的映射（outcome map）写在 prediction 字段里，与预测一并锁定。
- 结果分五类：改善；不显著；亏损；零活动（没有实质活动，只留诊断）；无效（完整性审计不通过）。
- 每类写一句：出现这个结果时，后续研究动作及其研究优先级（research priority）怎么变。
- 可选的动作包括沿该方向细化、换比较对照、修复后重试、降低优先级并写明重评条件。
- 映射在回放前随登记锁定。
- 回放后，Agent 按 <Ref id="research-round/references/feedback.md#priority-ranking" /> 依照映射更新优先级。
- 不得根据结果改写映射，也不得把不利结果改写成对方向的排除。
- 映射有遗漏时，补充内容只追加到反馈记录里并注明写于结果之后，不回填登记。

**输入**　预测与登记的比较维度。

**输出**　写在 prediction 字段里的五类结果到行动的映射。

**强制**　由 skill 指导（<Ref id="research-round/references/hypothesis.md#outcome-map" />），并由 eval <Ref id="eval:research-round/outcome-map-not-rewritten" /> 检验；代码不解析映射内容，只在 prediction 字段的非空核对中覆盖到它。

</Cap>

### H.3.2　比较维度与检验条件 [#H-3-2]

检验条件的数值由 Agent 声明并写明设计理由，随登记锁定。

<Cap id="H.3.2.1" kind="code" tier="rehearsal" tierLabel="演练证据" title="登记只押一个比较维度，且必须是定义了配对推断的 annual_return">

- metric 字段只取一个比较维度。
- 唯一定义了配对推断的维度是年化收益 annual_return。
- 比较维度是检验的对象，不是胜出声明：登记里不写「父版本胜出」之类的结论。
- 比较只在这个维度上给出效应、区间与 p（<Ref id="V.3.1.1" />）。
- 回撤、夏普、胜率、成本、资金使用率等其余读数只作描述，进入推荐时的多维取舍。
- 要扩展可登记的维度，需修改代码里的推断定义及与之对应的检验条件，不能在登记里临时声明。

**输入**　登记体的 metric 字段。

**强制**　代码：<Ref id="registration.validate" /> 在登记写事务内核对 metric 是否为定义了配对推断的维度。

| 拒绝码 | 条件 |
|---|---|
| `METRIC_UNSUPPORTED` | metric 取 annual_return 以外的值。 |

</Cap>

<Cap id="H.3.2.2" kind="code" tier="verified" tierLabel="已验证" title="检验条件八项在登记时声明并锁定，数值是未校准的方法示例值">

- comparison 恰含八项：method、alpha、minimum_effect、block_days、resamples、inner_resamples、seed、design_reason。
- method 是检验方法名，必须是 <Ref id="report.paired" /> 所用的配对循环块自助检验（paired block bootstrap）paired-circular-log-mean-v1。
- alpha 是显著性水平；网格有多个点时按点数做 Bonferroni 校正（<Ref id="V.3.2.3" />）。
- minimum_effect 是最小关心改进，用年化收益差的小数表示。
- minimum_effect 只作描述性对照，因为 p 检验的是差值为零。
- block_days 是块长，单位为日。
- resamples 与 inner_resamples 分别是外层和嵌套学生化的重抽次数。
- seed 是随机种子。
- design_reason 写误判与漏检怎么权衡、样本有多少天、收益的时间依赖与块长怎么选、预计效应与可分辨效应相比如何。
- 数值由 Agent 按研究情境选择，是方法示例值、未校准，不是产品常数；数值随登记锁定，事后不改。
- 报告把这些数值与效应、区间、p 并列呈现，并标「方法示例值，未校准」（<Ref id="research-round/references/feedback.md#p-and-threshold" />）。
- 样本外登记也用 registration.validate_design 校验检验条件（<Ref id="registration.validation_register" />）。

**输入**　登记体的 comparison 字段。

**输出**　随登记锁定的检验条件，供比较与报告读取。

**强制**　代码：<Ref id="registration.validate" /> 调用 registration.validate_design，只校验字段集合以及各字段的类型与范围，不评价数值是否合理。

| 拒绝码 | 条件 |
|---|---|
| `REGISTRATION_INVALID` | comparison 的字段不恰为这八项，或某字段的类型、范围不符。 |

</Cap>

### H.3.3　网格与适用条件 [#H-3-3]

网格定试什么，适用条件定结果在什么范围成立。

<Cap id="H.3.3.1" kind="code" tier="verified" tierLabel="已验证" title="网格一次写定一到五点，每点是已发布、谱系与运行契约一致的源码版本">

- grid 字段一次写定一到五个网格点，上限五是未校准示例值。
- 每个点写成 \{strategy, parameters\}。
- strategy 是经 <Ref id="ledger.publish_candidate" /> 发布进 <Ref id="table:candidate" /> 的精确源码版本 strategy_id@revision。
- parameters 是这个点全部规则参数的完整文字说明，必须是非空的有限长度文本。
- 候选必须存在，其研发父版本（parent）等于登记的 parent、改动说明等于登记的 change。
- 根登记时每个点都没有父版本。
- 候选声明的运行契约必须等于登记时探测到的运行环境契约。
- 同一源码内容哈希（content hash）不得在网格里出现两次。
- 网格随登记锁定：登记后要加点、改意图或改源码，都必须另行登记，原登记不改。
- 每个点只被一次试验消耗（<Ref id="H.4.2.1" />）。
- 网格点数进入比较时的多重检验校正（<Ref id="V.3.2.3" />），所以每个试过的配置都必须写进网格、计入点数。

**输入**　已发布进账本的各网格点候选，以及登记时探测到的运行环境契约。

**输出**　登记体的 grid 字段。

**强制**　代码：<Ref id="registration.validate" /> 在登记写事务内逐点对照账本候选与探测到的运行环境核对。

| 拒绝码 | 条件 |
|---|---|
| `LINEAGE_MISMATCH` | 候选不存在，或候选的 parent、改动说明与登记的 parent、change 不一致（根登记时点带有父版本）。 |
| `CONFIG_MISMATCH` | 候选声明的运行契约不等于登记时探测到的运行环境契约。 |
| `REGISTRATION_INVALID` | 同一源码内容哈希在网格里出现两次，点数不在一到五之间，或点的格式不符。 |

</Cap>

<Cap id="H.3.3.2" kind="skill" tier="rehearsal" tierLabel="演练证据" title="适用条件界定结果成立的范围，不是排除范围，事后不收窄">

- conditions 写本次试验的适用条件：被执行的源码、实际规则改动、参数、输入（市场提交与共同可交易范围规则 universe_rule）、开发窗口、运行环境（runtime image）。
- 它界定结果作为条件证据成立的范围（<Ref id="research-round/references/feedback.md#comparison-conditions" />），不是排除范围。
- 结果不利时，只能读成「在这些条件下」不显著或亏损。
- 不得事后收窄条件来挽救结果，也不得把结果扩大成对机制或方向的排除。
- 历史上的负面结果连同其适用条件进入研究状态（<Ref id="research-round/references/state-list.md#history-feedback" />）。
- 重试登记（带 retry_of，见 <Ref id="H.4.2.1" />）在条件里写明先前的尝试及其局限。
- 条件文字与执行身份（运行环境摘要、有效配置、输入身份）一起锁进登记证据包；执行身份由代码在登记时探测并写入（<Ref id="H.4.1.2" />）。

**输入**　本次试验的源码、改动、参数、输入、开发窗口与运行环境。

**输出**　登记体的 conditions 文本字段。

**强制**　写法由 skill 规定（<Ref id="research-round/references/hypothesis.md#conditions" />），并由 eval <Ref id="eval:research-round/conditions-not-exclusion" /> 检验；代码只在 <Ref id="registration.validate" /> 里核对 conditions 为非空的有限长度文本。

| 拒绝码 | 条件 |
|---|---|
| `REGISTRATION_INVALID` | conditions 为空或超出长度上限。 |

</Cap>

## H.4　登记先于回放并锁定 [#H-4]

<Steps>

<Step>

Agent 发布网格内每个候选（candidate），对每个源码完成原生预检（native precheck）与独立源码审查并入账，然后才登记（<Ref id="eval:research-round/precheck-before-register" />）。

</Step>

<Step>

<Ref id="cli.registration_add" /> 调 <Ref id="registration.register" />：读当前研究路线，探测运行环境，导出市场输入，读生效配置，合成执行身份。

</Step>

<Step>

同一账本事务内 <Ref id="registration.validate" /> 校验登记体与执行身份，通过后写登记证据包 research-plan.json；任一拒绝整笔回滚。

</Step>

<Step>

<Ref id="cli.replay_run" /> 开试验：<Ref id="ledger.open_trial" /> 插入试验行后调 <Ref id="registration.bind" /> 重验登记、比对执行身份与先后时间、写 <Ref id="table:registration_attempt" /> 一行，再写执行开始回执并提交。

</Step>

<Step>

提交成功才启动引擎（engine）子进程；绑定任一拒绝则事务回滚，不留试验行，不启动子进程。

</Step>

<Step>

V 章按 <Ref id="table:registration_attempt" /> 与登记包读出比较所需的网格点与试验。

</Step>

</Steps>

### H.4.1　登记身份与先后顺序 [#H-4-1]

输入登记体、运行环境引用与运行器参数；输出登记证据包、其中的执行身份，以及绑定后的消耗行。

<Cap id="H.4.1.1" kind="code" tier="verified" tierLabel="已验证" title="登记把五样、检验条件与引用锁进不可变证据包 research-plan.json">

- 登记把一次假设（hypothesis）回放前要写下的全部内容锁进一份不可变登记证据包（evidence bundle），包内唯一文件为 research-plan.json。
- 内容哈希（content hash）由文件字节派生，存入 <Ref id="table:evidence" />。
- 任何读回都经 <Ref id="ledger.load_bundle" /> 重算内容哈希比对。
- 登记包写入后不可改，更正只能是新包。
- 同内容重试幂等返回原记录。

**输入**　登记体（五样：经济理由与预测、来源证据包引用、一个比较维度、完整网格、本次试验的适用条件；检验条件；比较对照 control 的运行引用；网格每点的候选引用 strategy_id@revision 与配置；每点的源码审查引用；可选 retry_of）、运行环境引用、运行器参数。

**输出**　包名、research-plan.json 的内容哈希、执行身份与账本提交。

**强制**　代码在登记写事务内强制；Agent 只能经 <Ref id="cli.registration_add" /> 写入。

| 拒绝码 | 条件 |
|---|---|
| `REGISTRATION_INVALID` | 字段缺一或多余，或来源证据包、审查引用不在账本。 |
| `SOURCE_PRECHECK_REQUIRED` | 网格源码在该运行环境下没有通过的预检与审查。 |
| `RESERVED_BUNDLE_NAME` | 包名落在产品保留命名空间。 |
| `DUPLICATE_BUNDLE` | 同名包内容不同。 |
| `LEDGER_CORRUPT` | 读回时重算的内容哈希与存储值不符。 |

</Cap>

<Cap id="H.4.1.2" kind="code" tier="rehearsal" tierLabel="演练证据" title="执行身份在登记时由探测运行环境与导出不可变输入合成写定">

1. 经 <Ref id="ledger.current_line" /> 读最新研究路线（research line）：开发窗口（development window）、钉住的市场提交、范围规则。
2. 经 <Ref id="runtime.resolve" /> 把运行环境引用解析为唯一清单摘要，缺省为镜像注册表（registry）的 main 标签。
3. 经 <Ref id="runtime.inspect_runtime" /> 在隔离容器内运行身份探针，读出运行契约、依赖锁哈希与生效配置。
4. 经 <Ref id="registration.market_inputs" /> 按研究路线的市场提交新鲜导出不可变市场输入，并算导出内容身份。
5. 合成执行身份 \{image_digest, runtime_contract, effective_config, input_identity\}，随登记体一起写入 research-plan.json。

- 执行身份在登记时写定，使回放前的绑定有可核对的对象。
- 执行身份不能手写；宿主路径不进身份。
- 登记的交易窗口必须等于研究路线的开发窗口。
- 运行环境与导出的拒绝码由其定义处给出，并原样透传。
- 导出与探测的工作副本只留在临时目录，账本不存导出数据与镜像。

**输入**　运行环境引用与当前研究路线。

**输出**　写入 research-plan.json 的执行身份。

**强制**　代码在登记入口 <Ref id="registration.register" /> 内强制。

| 拒绝码 | 条件 |
|---|---|
| `NO_RESEARCH_LINE` | 没有研究路线。 |
| `WINDOW_MISMATCH` | 登记的交易窗口不等于研究路线的开发窗口。 |

</Cap>

<Cap id="H.4.1.3" kind="code" tier="verified" tierLabel="已验证" title="研究回放启动引擎前，须在开试验同一事务里绑定已登记网格点">

1. <Ref id="ledger.open_trial" /> 插入试验行后，在同一数据库事务里调 <Ref id="registration.bind" />。
2. 读回登记包并重验内容哈希，重跑登记校验。
3. 核对被执行源码在锁定网格内。
4. 核对运行环境摘要、生效配置、输入身份与登记逐项一致。
5. 核对预检与审查仍有效。
6. 核对登记的服务器时间严格早于试验的服务器时间。
7. 核对该网格点未被消耗（见 H.4.2.1）。
8. 全部通过才写消耗行，与试验行、执行开始回执在同一账本提交落账；提交成功后才启动引擎子进程。

- 适用于每次研究封存（seal）回放，即试验 purpose = research。
- 任一不符即抛拒绝、事务整笔回滚、不留试验行、不启动子进程。
- 登记晚于回放的试验不成为候选证据。
- 时间由服务器触发器写（<Ref id="J.4.1.1" />），完整核对清单见 <Ref id="J.4.2.1" />；本能力只规定顺序与原子性。

**输入**　登记包名、本次试验实际的执行身份、被执行源码的内容哈希、刚插入的试验主键。

**输出**　与试验行同事务提交的消耗行，或整笔回滚的拒绝。

**强制**　代码在 <Ref id="ledger.open_trial" /> 的试验写事务内调 <Ref id="registration.bind" /> 强制。

| 拒绝码 | 条件 |
|---|---|
| `LEDGER_CORRUPT` | 读回的登记包内容哈希不符。 |
| `REGISTRATION_INVALID` | 重跑登记校验不通过。 |
| `LINEAGE_MISMATCH` | 重跑登记校验发现谱系不符。 |
| `SOURCE_MISMATCH` | 被执行源码不在锁定网格内。 |
| `EXECUTION_MISMATCH` | 运行环境摘要、生效配置或输入身份与登记不一致，并指明冲突项。 |
| `SOURCE_PRECHECK_REQUIRED` | 预检或审查已不再有效。 |
| `SOURCE_PRECHECK_FAILED` | 预检失败。 |
| `REGISTRATION_TOO_LATE` | 登记的服务器时间不早于试验的服务器时间。 |
| `GRID_ALREADY_ATTEMPTED` | 该网格点已被消耗。 |

</Cap>

### H.4.2　网格点消耗与源码暴露 [#H-4-2]

输入登记体里的网格与 retry_of 以及绑定请求；输出允许或拒绝登记、允许或拒绝绑定。

<Cap id="H.4.2.1" kind="code" tier="rehearsal" tierLabel="演练证据" title="每个网格点只消耗一次，同源码再试须另登记并写 retry_of">

- 网格点是（登记包 × 网格源码），只被消耗一次。
- 绑定成功即在 <Ref id="table:registration_attempt" /> 写入（登记包，源码哈希）→ 试验的映射，主键为（登记包，源码哈希）。
- 消耗行与试验行同生同灭；之后无效或中断的尝试照样保留消耗行并算作消耗。
- 同一源码再试须另登记，并在登记体 retry_of 写明在 registration_attempt 中实际消耗过该源码的先前登记包。
- 缺 retry_of 或 retry_of 指向未消耗该源码的登记，由登记校验拒绝。
- 相同条件的重复不算独立证据：retry_of 把它们连成同一网格点的重复尝试，读数侧据此识别。

**输入**　登记体里的网格与 retry_of，以及绑定请求。

**输出**　允许或拒绝登记、允许或拒绝绑定；绑定成功时写一行消耗记录。

**强制**　代码（<Ref id="registration.bind" /> 与 <Ref id="registration.validate" />）与账本主键共同强制。

| 拒绝码 | 条件 |
|---|---|
| `GRID_ALREADY_ATTEMPTED` | 再次绑定同一网格点，主键冲突。 |
| `CONCURRENT_WRITE` | 并发同时绑定同一点，提交时冲突，后到者回滚，不会出现双消耗。 |

</Cap>

<Cap id="H.4.2.2" kind="code" tier="rehearsal" tierLabel="演练证据" title="已暴露的源码不能当新登记，仅事前声明的原生预检豁免">

- 登记时，网格中每个源码按内容哈希查 <Ref id="table:trial" />，只要已被任一 explore 或 research 试验执行过即视为已暴露。
- 已暴露的源码不能作为新登记，未登记的探索也不能事后补登为登记结果。
- 唯一豁免由 <Ref id="registration.exposure_exempt" /> 判定，对象是原生预检。
- 豁免条件：purpose = precheck、事前声明用途、同源码同运行环境、未绑定任何登记、原件完整。
- 失败或重复的预检不成为登记尝试。
- 已暴露的源码只能以 retry_of 另登记（规则见 H.4.2.1）。

**输入**　登记体里的网格源码内容哈希与 retry_of。

**输出**　允许或拒绝登记。

**强制**　代码在登记校验 <Ref id="registration.validate" /> 中按试验记录强制，不依赖 Agent 自述。

| 拒绝码 | 条件 |
|---|---|
| `SOURCE_ALREADY_EXPOSED` | 源码已暴露、不在豁免内且未以 retry_of 另登记。 |

</Cap>
