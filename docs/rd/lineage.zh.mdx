# T　候选谱系：回答什么算一个候选，以及候选之间怎样经研发父版本与改动说明连成树和森林。

本章定义候选（candidate）的身份与候选谱系（lineage）。候选是账本（ledger）里一份完整源码的精确字节，以内容哈希（content hash）唯一，由登记（registration）后的一处改动产生；非根候选带研发父版本（parent）与改动说明，根节点（root）无父无比较对照（control）；树合成森林，任一候选可再派生。账本表结构与发布、登记核对强制这些约束，不读运行读数；推荐与读数不改身份。推荐见 <Ref id="F.3.2.1">F 章</Ref>，入口见 <Ref id="E.3.1.1">E 章</Ref>。

## T.1　认定候选：什么算一个候选 [#T-1]

认定候选（candidate）把「什么算一个候选」收口为三件事：身份（精确源码字节与内容哈希 content hash）、产生方式（登记 registration 后的一处实际改动加一次发布）、起点（无父无对照的根 root）。数据流只有一条：Agent 把完整单文件源码经发布入口交给账本（ledger）→ 账本从字节派生内容哈希，重复字节拒绝并返回已存在的版本，父不存在或父与改动说明不配套拒绝 → 登记核对只看谱系（父与改动说明等于登记锁定的内容，根不得带比较对照 control），不读任何运行读数 → 候选进入谱系，可被任何后续登记声明为研发父版本（parent）。身份与根的约束由账本表结构强制（生成列哈希加唯一约束、父与改动说明同空同非空的检查约束）；派生不设门槛由登记核对的输入集合保证——代码里没有收益、显著性、资格或推荐状态这类输入。试验（trial）、运行（run）、推荐（recommendation）与检验读数（reading）都在候选之外产生，对候选身份没有写权。

<Step>

Agent 在工作副本写完一份完整单文件源码，决定它是根（不带父）还是派生候选（带研发父版本 strategy_id@revision 与一句改动说明）。

</Step>

<Step>

经 <Ref id="ledger.publish_candidate" /> 发布：账本从字节派生 SHA-256 内容哈希；相同字节以 SOURCE_EXISTS 拒绝并返回已存在的 strategy_id@revision；父不存在以 PARENT_NOT_FOUND 拒绝，父与改动说明不配套以 LINEAGE_INCOMPLETE 拒绝；成功则写入 <Ref id="table:candidate" /> 一行并做一个账本提交，返回 strategy_id@revision 与内容哈希。

</Step>

<Step>

登记时 <Ref id="registration.validate" /> 只核谱系：网格每点的父与改动说明等于登记锁定的内容，父为空（根）而声明了比较对照以 ROOT_WITH_CONTROL 拒绝；不读父版本或自身运行的任何读数。

</Step>

<Step>

候选进入谱系；<Ref id="report.candidates" /> 并列读出全部候选的源码身份、父与改动说明，不带分数、资格标记或排序。

</Step>

<Step>

任何后续读取（登记、封存回放、谱系读取）经 <Ref id="ledger.read_candidate" /> 取候选，读回时重算存储字节的哈希，与记录的内容哈希不符以 LEDGER_CORRUPT 拒绝。

</Step>

</Steps>

### T.1.1　候选的身份与根 [#T-1-1]

身份与根由 <Ref id="table:candidate" /> 的约束（内容哈希生成列加唯一约束；父版本与改动说明同空同非空）与两道代码核对（发布 <Ref id="ledger.publish_candidate" />、登记 <Ref id="registration.validate" />）共同强制；skill 节 <Ref id="research-round/SKILL.md#parent-and-control" /> 只负责提醒 Agent：亏损或不显著的有效候选照样可作研发父版本。输入是源码字节、可选的父版本引用与改动说明；输出是 strategy_id@revision 与内容哈希。

<Cap id="T.1.1.1" kind="database" tier="verified" tierLabel="已验证" tierNote="演练中，每个假设的网格点都以已发布版本的内容哈希登记并绑定执行，报告与比较都指向精确源码。" title="候选保存精确源码字节，以内容哈希唯一标识；相同源码不能成为两个候选">

一个候选（candidate）是账本（ledger）里一份完整单文件策略源码的精确字节。身份是账本从该字节派生的 SHA-256 内容哈希（content hash）：由 <Ref id="table:candidate" /> 的生成列 source_sha256 计算并设唯一约束，Agent 不填写也不能改写。输入：源码字节、入口类名、运行契约、发布说明，可选研发父版本引用（strategy_id@revision）与改动说明；输出：引用名 strategy_id@revision 与内容哈希。相同字节再次经 <Ref id="ledger.publish_candidate" /> 发布，以 SOURCE_EXISTS 拒绝并返回已存在的 strategy_id@revision；改名、复制到另一个 strategy_id 或只改注释——字节变了就是另一个候选，字节不变就被拒绝。「是否同一候选」只看内容哈希，strategy_id@revision 只是引用名。读回时 <Ref id="ledger.read_candidate" /> 重算存储字节的哈希，与记录的内容哈希不符以 LEDGER_CORRUPT 拒绝。登记、试验与报告绑定的都是这份内容哈希，不是名字或版本号；候选行只增不改，每次发布恰一个账本提交，行级全史由 Dolt 系统表 <Ref id="table:dolt_system_tables" /> 读出，任一历史时刻的谱系经 <Ref id="ledger.read_as_of" /> 读取。强制层：账本（生成列、唯一约束、只增提交）加代码（发布与读取函数）。

### T.2.1　父关系与比较对照怎么记 [#T-2-1]

父边由 <Ref id="table:candidate" /> 的自引用外键与 <Ref id="ledger.publish_candidate" /> 强制存在与方向；边的语义（改动说明）由 <Ref id="registration.validate" /> 与登记锁定的「一处改动」逐字核对；比较对照由登记检查、<Ref id="registration.check_comparable" /> 的可比性核对与 <Ref id="qualification.require" /> 的经济证据资格三重核对。输入是登记里的 parent、control、change 与网格点，输出是接受的登记或具名拒绝码；三条能力都由代码或账本强制，没有 skill 裁量。

<Cap id="T.2.1.1" kind="code" tier="rehearsal" tierLabel="演练证据" title="非根候选必带一个研发父版本和改动说明；改动说明必须与登记锁定的那一处规则改动一致，不一致拒绝登记">

输入：发布时的源码字节、可选的 parent（strategy_id@revision）与 difference（一句改动说明）；登记时的 parent、change 与一到五个网格点（每点是已发布候选的引用名）。规则一（发布层，代码）：<Ref id="ledger.publish_candidate" /> 要求 parent 与 difference 同有同无——只给了其中一个以 LINEAGE_INCOMPLETE 拒绝，不写任何行；parent 不是 strategy_id@revision 格式以 BAD_REF 拒绝；账本里没有该父候选以 UNKNOWN_STRATEGY 拒绝（账本外键同样守卫）。这三个码由该函数的 refusals 定义。无父无改动说明即发布为根。规则二（登记层，代码）：<Ref id="registration.validate" /> 对登记里每个网格点经 <Ref id="ledger.read_candidate" /> 读出该候选的 parent 与 difference，要求 parent 等于登记锁定的 parent、difference 逐字等于登记锁定的 change；任一点不等以 LINEAGE_MISMATCH 拒绝整份登记，账本不留半截记录。规则三（账本层）：<Ref id="table:candidate" /> 对父列与改动说明列施加同有同无的检查约束，父列是指向本表主键的外键。效果：改动说明是谱系边上唯一的语义，与登记的「一处改动」互为约束，边不能事后补写，任何比较结论都能回到「改了哪一处」。演练中，全部研究候选以父加改动说明发布，父或改动说明与锁定改动不一致的网格点被登记检查拒绝。

父关系只有一种来源：发布时由 Agent 显式给出的 parent，写入 <Ref id="table:candidate" /> 的 (parent_strategy_id, parent_revision) 列，该列是指向同表主键 (strategy_id, revision) 的外键，因此只能指向写入当时已存在的候选。写入经 <Ref id="ledger.write" /> 在一个事务里完成并形成一个账本提交；账本对候选表只允许 INSERT，没有改父列的路径，created_at 由服务器触发器打。父早于子由两件事证明：外键要求父行先存在；父行所在提交早于子行所在提交，可从 <Ref id="table:dolt_system_tables" /> 读出父行的提交早于子行、且父列在全史里只出现过一个值。由「父指向已存在版本且只追加」推出谱系无环、是一片森林。产品不从文件名、revision 序号、代码相似度、提交历史或试验记录推断父子，也不自动合并、重排或修补谱系；<Ref id="table:trial" /> 只引用被执行候选的身份，不另记父子关系。审计据此按提交顺序逐边复核，不依赖 Agent 的叙述。

登记体里 parent 与 control 是两个独立字段：parent 是改动所基于的候选（strategy_id@revision），control 是一次已封存运行（run）的身份，二者不必对应同一候选——以上一版为父、以更早的有效运行为对照是合法登记。<Ref id="registration.validate" /> 分别核对：parent 须经 <Ref id="ledger.read_candidate" /> 读到；根候选不得带 control，带了拒绝；control 若给出，须满足三条，任一不满足以具名码拒绝整份登记：运行通过完整性审计且已封存（否则 <Ref id="registration.check_comparable" /> 以 RUN_NOT_PASSED 拒绝）；运行环境摘要、有效配置身份与输入身份同本次执行身份逐项一致（否则 COMPARABILITY_MISMATCH 并指明冲突项）；运行有经济证据资格（否则 <Ref id="qualification.require" /> 以 ECONOMIC_EVIDENCE_UNAVAILABLE 拒绝并给原因）。control 可为空：故障、无效或零活动的父可被修复派生并以无对照登记，回放照常进行并计入试验，只是不产生改善、区间与 p。对照的可比性与可用性核两次——登记时与回放绑定前（<Ref id="H.4.1.3" />、<Ref id="V.2.3.1" />），两次之间对照的资格若因读时视图变化而丢失，绑定拒绝。强制层：代码（登记检查、可比性核对、资格硬门）。演练中，父与对照不同的登记实际发生，故障父的修复以无对照登记后回放，比较读数置空。

<p className="rd-resolves">父与对照分离让故障或零活动的版本不打断谱系，也不让无经济证据的运行成为比较基准。</p>

</Cap>

### T.2.2　树、森林与候选清单 [#T-2-2]

森林由 <Ref id="table:candidate" /> 的可空自引用外键自然给出，不另建树表；候选清单由 <Ref id="report.candidates" /> 读出并经 <Ref id="cli.candidate_list" /> 暴露；跨枝借用不扩表，由 skill 指导登记为一个父加来源证据。输入是账本版本（当前提交或 AS OF 的提交、标签），输出是全部候选及其登记尝试、运行状态与经济证据可用性的 JSON；清单里没有推荐分数、资格标记或排序。前两条由账本与代码强制，第三条由 skill 指导并以 eval 校验。

<Cap id="T.2.2.1" kind="database" tier="verified" tierLabel="已验证" title="每棵树从一个根节点开始，所有树合起来是一片森林；可从任何历史候选另开一枝，不以它是否被推荐为前提">

候选谱系（lineage）是一片森林：<Ref id="table:candidate" /> 的父列可空，父为空的行是根（根只能是策略库模板或人造根，见 <Ref id="T.1.1.3" />），每个根连同所有经父列可达的后代是一棵树，全部树共存于同一账本。候选表没有「活跃」「推荐」「有效」之类状态列，因此任一已存在的行都能被新发布的候选引用为 parent：被推荐与否、是否最新、运行是否有效都不是前提（<Ref id="E.4.2.1" /> 由用户选起点，<Ref id="F.3.2.2" /> 推荐与下一父分开）。换路线或回到历史候选只是以它为父再发布，谱系不改写、不重排、不删枝。谱系按版本读取：<Ref id="report.candidates" /> 以 AS OF 读某一提交或标签时的全部树，用于复读入口当时看到的森林。强制层：账本结构（可空自引用外键、只追加）。演练中，从非最新候选另开一枝、推荐候选与下一实验父版本不同，谱系未被改写。

**使用**　<Ref id="table:candidate" />、<Ref id="report.candidates" />

**依据**　[\[33\]](/zh/docs/appendix-references/#ref-33 "Git — git-branch 手册") [\[2\]](/zh/docs/appendix-references/#ref-2 "Yamada et al. 2025, arXiv:2504.08066") [\[1\]](/zh/docs/appendix-references/#ref-1 "Microsoft RD-Agent") [\[19\]](/zh/docs/appendix-references/#ref-19 "Dolt — Querying history")

</div>

<p className="rd-resolves">换研究路线或回到历史候选都不改写谱系；入口从森林选路线，而不是从「最好的一批」里选。</p>

</Cap>

<Cap id="T.2.2.2" kind="skill" tier="unverified" tierLabel="待验证" title="合并另一版本的规则算一处改动：一个研发父版本，另一版本记为来源证据；不继承任一方成绩，完整回放并计入试验">

把另一候选的某条规则并入当前候选时，Agent 按 <Ref id="research-round/SKILL.md#merge-rule" /> 操作：选定唯一的 parent（通常是接收规则的一方），把合并写成对它的一处改动（<Ref id="research-round/SKILL.md#one-change" />：联动的几行算一个改动）；被借用的候选以其 strategy_id@revision 与内容哈希写进一个来源证据包（<Ref id="table:evidence_bundle" />，登记前经 <Ref id="H.2.3.1" /> 入账），在登记体的 sources 里引用，作为「本地诊断」类依据而非第二个父。<Ref id="registration.register" /> 内的 <Ref id="registration.validate" /> 核对 sources 引用的证据包在账本里存在，不存在拒绝；登记体只有一个 parent 字段，双父在结构上不可写。合并后的候选不继承任一方的读数：必须完整回放，计入试验，比较只对登记声明的 control 做；源码仍守单文件契约与三条硬契约（<Ref id="C.1.4.2" />、<Ref id="C.1.4.3" />、<Ref id="research-round/references/strategy-authoring.md#hard-contract-allocation" />），合并带来的资本分配变化须在源码里写明。强制层：skill 指导 Agent 的记法，代码只强制「来源证据包存在」与「单父」。待验证：缺演练中实际发生的合并登记，也缺「一父加来源证据」与双父记法在审计可读性上的比较。

<p className="rd-resolves">不扩表、不建组合服务就能记录跨枝借用，借用的出处可追溯到精确版本。</p>

<Cap id="T.2.2.3" kind="code" tier="rehearsal" tierLabel="演练证据" title="候选清单读出全部候选的源码身份、父与改动、登记尝试及其运行状态与经济可用性，不带推荐分数或资格标记">

候选清单是 Agent 读谱系的唯一命令行入口 <Ref id="cli.candidate_list" />，内部调用 <Ref id="report.candidates" />。输入：账本档案，可选 at（提交哈希或标签；缺省读当前）。输出：\{ledger_commit, checker, candidates[]\}，每个候选带 strategy_id、revision、source_sha256、父（parent_strategy_id, parent_revision）、difference、description、created_at，以及 attempts[]——每个登记尝试（<Ref id="table:registration_attempt" />：一个被试验消耗的网格点）带登记证据包、消耗它的 trial_id、run_id、run_status（passed | invalid | unfinished）与 availability（按 <Ref id="qualification.check_identity" /> 给出的检查身份、经 <Ref id="qualification.assess" /> 当下算出的经济证据可用性与原因）；valid_evidence 为任一尝试经济证据可用。无 run 的尝试（中断、未完成）仍列出并标 unfinished，因为网格点已被消耗；零成交或无效的尝试只显示为不可用，不附读数。可用性是读时视图，不改写存储的 run.status 与审计结论（<Ref id="G.4.2.3" />）。清单不含任何分数、资格标记、排序或占位推荐，候选只按 (strategy_id, revision) 自然顺序稳定输出；推荐与理由由 Agent 另写证据包（<Ref id="F.3.2.1" />）。按版本读历史：只读连接由 report.candidates 经 <Ref id="ledger.read_as_of" /> 按 at 以 AS OF 打开并钉住提交，命令层不自开连接；输出附实际读到的 ledger_commit 供复读。拒绝：at 解析不到提交或标签 LEDGER_REF_NOT_FOUND；所读版本的模式版本与代码不一致 LEDGER_SCHEMA_MISMATCH；尝试引用的源码哈希在同版本候选表中缺失或 run 指向不存在的 trial，LEDGER_CORRUPT 并指明首个不一致行，不静默丢行。强制层：代码（只读，不写账本）。演练中，入口恢复与复盘推荐从候选清单读出谱系、尝试与可用性，零成交与无效尝试在清单里只显示为不可用。
