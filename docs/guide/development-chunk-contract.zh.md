# 开发切片

## 选择范围

从用户故事选择一个能够交付并读回的结果，明确负责的 Owner、输入生产者、实际消费者与权限边界。
可以是服务内功能，也可以是跨服务交接；不以首页是否已画出节点决定能否开发。
缺失的设计在实现前补齐，并与实际测量一起更新。

## 最小检查

| 问题         | 需要明确的内容                                 |
| ------------ | ---------------------------------------------- |
| 用户得到什么 | 可观察结果及完成条件                           |
| 谁负责       | 一个事实写入者、必要的输入与消费者             |
| 复用什么     | 当前 Nautilus API 或既有服务操作，以及具体缺口 |
| 失败怎么办   | 拒绝、未知、重复请求与恢复的行为               |
| 怎么验证     | 真实消费者、必要的边界检查及当前仓库门禁       |

Agent 自行组织计划和证据。普通文字、文件引用与执行结果即可，不要求固定规划 JSON、
全套默认测试、图节点注册或通用任务状态机。规模较大的变更可以分步交付，
但每一步必须保留唯一权威、权限和已经规定的拒绝行为。

## 证据与权限

证据绑定实际候选、输入与执行结果；过时参考不能代替当前源码验证。
[Agent 实现指南](./agent-implementation/)说明如何查证原生接口。
架构与业务边界变化同步修改所属章节；用户目的、交易授权、保护封口等变化遵守 `AGENTS.md`。

现有 `validate:development-chunk` 是可选的结构化记录工具。
使用它时，其严格字段、不可变 Git 解析与校验仍适用；它不授予开发或生产权限，
也不是提交普通开发任务、研究实验或原生策略的必经入口。
