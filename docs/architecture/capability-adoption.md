# Capability Adoption

This page connects the existing engine to the target product architecture. It does not add an Owner, claim that a target contract is already implemented, or make a crate authoritative. The global Flow defines business authority; packages remain replaceable implementation units behind that authority.

## Adoption rules

- A crate may support more than one Owner only through separate typed ports. Shared code never implies shared write authority.
- Direct reuse means preserving useful computation or protocol code behind the destination Owner contract, not preserving every current mutation path.
- Foundation code owns no trading truth. It may store, transport, serialize, observe, or expose facts only on behalf of the Owner that committed them.
- A target product surface is not considered implemented merely because the Flow names it or a low-level API is reachable.

## Strategy Factory capability disposition

Strategy Factory is not one all-or-nothing migration. `PRESENT` means the named source facet is directly verified;
`PARTIAL` means only the listed facet exists and the missing target semantics remain unimplemented;
`ABSENT_TARGET_ONLY` is a target seam or prohibition, not an existing reusable capability. Adoption disposition is
separate from source availability and never preserves a legacy writer by implication.

## Shared-state migration

The existing shared Cache is a migration surface, not a future Owner. Market Data alone writes instrument and market facts; Execution alone writes raw order, fill, fee, venue, and Recovery Case facts; Portfolio alone writes account and exposure projections; Runtime alone writes generation checkpoints and readiness state. Other consumers receive read-only views.

The generic MessageBus may carry commands and uncommitted internal traffic. Event Rail is a narrower projection that publishes only committed Owner events. Delivery, retry, and replay never replace the source Owner fact or its terminal state.

## Observability capability disposition

The existing MessageBus and Event Store are reusable mechanisms, not an Observability authority. Adopt MessageBus only behind typed Owner ports and Event Rail; adopt Event Store only behind Owner-scoped append/read APIs and transactional outbox boundaries. Existing logging, tracing, metrics, collector, broker durability, Dashboard, or OpenTelemetry capability is not inferred from crate names.

The target Telemetry Gateway admits OTLP-compatible receivers, processors, and exporters behind one replaceable port. The target Status Projection consumes committed Event Wakes and policy-admitted telemetry idempotently, stores checkpoints, and can rebuild. Alert Routing wraps Telegram and future adapters without making delivery a business result. Dashboard API serves only the Global Status View. Kafka, NATS, Redpanda, OpenTelemetry Collector, ClickHouse, PostgreSQL, and vendor backends remain implementation candidates, not preselected product dependencies.

## Authority migration gates

1. **Single order writer** — Strategy, Execution Algorithm, Risk, and adapters cannot write denial or order lifecycle state outside Execution Order Engine.
2. **Permit-bound effects** — for add-risk, Runtime receives a terminal Risk Decision and one-use Reservation before creating an Authorized Order Command.
   Decrease-only instead requires exact `PERMIT_DECREASE_ONLY` and explicit-none
   Reservation/claim lineage. Both paths require Execution `PREPARED`, Risk adapter admission, and matching
   `ADMITTED_ONCE` before invocation.
3. **Owner-scoped durability** — Event Store and persistence calls append through the native Owner boundary. Unknown capture or replay state stays unknown and activates the relevant recovery fence.
4. **Artifact identity reuse** — indicator, feature, strategy, configuration, and dependency identities are frozen in Strategy Artifact and remain identical across replay, paper, and live Runtime.
5. **No shell or telemetry by implication** — LobeHub, the configured Agent Shell (OpenClaw or Codex), Telegram, OTLP collection, a broker, and Dashboard remain target capabilities until a canonical consumer and adapter satisfy their contracts. OpenClaw and Codex share one principal and permission surface, are mutually exclusive for a deployment, and cannot become competing writers. Every mutating request admission binds the authoritative shell-history head whose unique `ACTIVE` binding is selected; already admitted work remains bound to its original immutable origin. Their presence in Flow is not implementation evidence.

## Owner Migration Envelope

Migration happens one fact surface and one Owner at a time. Each slice binds a migration identity, migrated fact
surface, predecessor and successor revisions, existing writer and readers, target Owner, dependencies, common
evidence cut, admission stage, rollback disposition, incident Owner, and observations for writer identity, fence,
parity, unresolved effects, reconciliation, and source freshness. This envelope records required evidence, not
implementation progress.

The conceptual stages are `UNSTARTED → SHADOW_READ_ONLY → PREDECESSOR_FENCED → RECONCILED →
SUCCESSOR_ACTIVE → VERIFIED`. At most one writer exists. Zero, unknown, or multiple writers admit no mutation;
a fenced downtime window is acceptable. Successor activation requires the predecessor fence, complete
dependencies, and exact common-cut reconciliation.

After the successor has written a fact, rollback is allowed only when reverse compatibility and exact
reconciliation are proved. Otherwise the surface remains fenced and recovers forward. Old in-flight request
identities join their original Owner receipts after cutover and never create a second effect. Shadow telemetry
cannot override stale, mismatched, or unavailable authoritative Owner facts.

| Migration slice                                | Target authority or custodian       | Successor activation proof                                                                                                                | Rollback boundary and incident authority                                                                                                                                             |
| ---------------------------------------------- | ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Market and instrument facts                    | Market Data                         | Source lineage, freshness, correction frontier, license scope, and common PIT cut reconcile                                               | No successor fact may be lost or rewritten; Market Data owns migration admission and parity incidents.                                                                               |
| Orders and external effects                    | Execution                           | Predecessor fenced; exact permit-bound effect set, venue readback, and reconciliation cut close                                           | After a successor effect, rollback needs reverse-read proof and exact venue reconciliation; otherwise recover forward under Execution.                                               |
| Account, exposure, and performance projections | Portfolio                           | Execution and Market Data source cuts reconcile to one account projection                                                                 | A projection never becomes venue or market truth; Portfolio owns projection migration incidents.                                                                                     |
| Strategy generation checkpoint and readiness   | Runtime                             | Predecessor generation fenced and checkpoint replay reconciled                                                                            | No successor may resume through predecessor state; Runtime owns migration incidents but not Recovery closure.                                                                        |
| Recovery Case and closure                      | Execution Reconciler                | Runtime readiness, active Risk fence, Effect Journal, readback, Risk closure, and Portfolio closure share one cut                         | No incomplete or unknown case can become `KNOWN_CLOSED`; closure never resumes trading.                                                                                              |
| Agent Shell request origin                     | Product Edge non-business custodian | Predecessor Shell fenced; successor binding active; every already admitted in-flight request identity resolves under its original binding | Reversal cannot rewrite request identity, authorization, or Owner receipt; Product Edge owns only binding and Shell cutover incidents, never Owner receipts or business transitions. |

The migrating business Owner, or the declared non-business custodian for a boundary surface, owns stage admission
and parity. A boundary custodian never gains business-fact or receipt authority. Unknown trading effect stops
migration and enters the existing Runtime/Risk/Execution Recovery Case path; rollout cannot resume before
`KNOWN_CLOSED`. A failed slice does not promote or roll back an unrelated slice and never creates a global
authority transfer.

Migration stops on a dual or unknown writer, stale or missing evidence, parity drift, unresolved effect,
incompatible state, failed consumer read, or unavailable incident authority.

## Development use

Before changing a current crate, identify its row, destination Owner, allowed writers, and migration gate, then
fill one [Development Chunk Contract](../../guide/development-chunk-contract/). A change that preserves those
contracts may choose its own internal data structures, process topology, protocols, and performance strategy.
A change that moves a business fact, creates another writer, or bypasses a gate requires an architecture change
before implementation.
